## 1. The defect (measured — do not re-derive, verify and extend)

`tortoise/pack_registry.py::_build_kind_expansions` builds a pre-computed kind expansion table. It is wrong
in TWO independent ways. `#11000` names one; the second was measured while scoping `#11656` and posted to
`#11000` (comment 6753211884).

### Leg A — the headline: pack child → parent is dropped

`pack_registry.py:2847`:

```python
for child, parent in p.kind_subclasses.items():  # noqa: B007
    full_child = f"{ns}:{child}"
    if full_child not in expansions:
        expansions[full_child] = [full_child]
```

`parent` is bound and **never read** — the `# noqa: B007` is the proof. The comment directly above says
*"Apply subclassOf: children also expand to parent"*, which is false. Measured at `main`:

```
dev:issue     -> ['dev:issue', 'pm:issue']   # 'pt ': parent 'WorkItem' ABSENT
dev:epic      -> ['dev:epic']                # parent 'Project' ABSENT
WorkItem      -> ['WorkItem', 'dev:issue', 'dev:pullRequest', 'marketing:content',
                  'product-strategy:feature', 'product-strategy:requirement',
                  'pm:issue', 'pm:card', 'venture:actionItem']   # parent→children WORKS
```

So only the child→parent direction is missing. (`dev:issue → pm:issue` comes from `equivalentTo`, not
from subclassing — do not "fix" it there.)

### Leg B — the core hierarchy is NOT in the table at all

`get_subclasses` (`pack_registry.py:2786`) reads ONLY pack-declared `kind_subclasses`, so **ONTOLOGY §6's
core-subclass table is never registered**. Measured:

```
expand_kind('Object')   = ['Object']    # §6 lists Project, WorkItem, Problem, tag, user, skill, tool, …
expand_kind('Subject')  = ['Subject']   # §6 lists organization, team, role, legalPerson, naturalPerson
expand_kind('Point')    = ['Point']
expand_kind('Event')    = ['Event']
expand_kind('Document') = ['Document', 'product-strategy:architecture']
                          # ^ the ONLY child, and only because a PACK declared subclassOf: Document
get_subclasses('Subject') = []
get_subclasses('Object')  = []
```

**Leg B is a hard dependency of `#11656`**, which must accept a declared `toKind: Subject` as "a Subject or
any subtype". Do NOT fix Leg B by special-casing `Subject`: register the §6 core parentage as expansion
input, the same way pack `subclassOf` is. If you conclude Leg B is a different root and must not land here,
**say so explicitly in your report and in a comment on #11000** and stop — do not silently skip it.
