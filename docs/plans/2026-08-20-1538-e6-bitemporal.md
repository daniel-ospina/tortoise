## Design Decisions

### D1 — Property naming: ontology-canonical camelCase, not the epic's snake_case

The epic/issue wording says `valid_at`/`invalid_at` + `created_at`/`expired_at`. The **ontology and the codebase already disagree with that spelling**:

- `docs/ONTOLOGY.md §4.1 Point` **already registers `validFrom` / `validTo`** (ISO8601, "Temporal validity window", Impl = ✅).
- `createdAt` exists on every point (written by `create_point`).
- `mining.py` (`_temporal_wire`, W-4 #786) **already writes `validFrom`** = session frontmatter date (valid time, not ingest time).
- The graph convention is camelCase throughout (`createdAt`, `updatedAt`, `startedAt`, `endedAt`, `capturedAt`, `eventId`).

**Decision:** write `validFrom` / `validTo` / `expiredAt` (camelCase). `expiredAt` is the **single genuinely new additive property** (transaction time of supersession/expiry). Mapping vs the epic wording: `valid_at`→`validFrom`, `invalid_at`→`validTo` (the valid-window end — Graphiti's `invalid_at` is our `validTo`), `created_at`→`createdAt` (exists), `expired_at`→`expiredAt` (new). No backfill/migration in V3 — legacy undated points read as an open window (see D6).

Semantic split (already in the ontology's Event model, §4.5 `startedAt`/`endedAt` = valid time vs `capturedAt` = transaction time):
- **Valid time (world):** `validFrom` = the fact became true (session date / `when` slot); `validTo` = the fact ceased being true (successor's `validFrom`, or withdrawal time).
- **Transaction time (graph):** `createdAt` = when the record was written; `expiredAt` = when the record was superseded/expired.

### D2 — One writer for windows: `supersede_point` (and `invalidate_point`) stamp the window

E5's contract says **call the existing canonical `supersede()` — no new SDK tool**. The window stamp belongs INSIDE `supersede_point` (sdk.py:2228) so all three write sites (hosted reconcile supersede, `promote_point` temporal-replacement, eval ingest) get windows for free, and the SDK stays the single writer:

- On supersession, `supersede_point` additionally sets on **old**: `validTo` = successor's `validFrom` (contiguous Graphiti windows: the old fact stops being true exactly when the new fact became true), `expiredAt` = transaction `now`.
- `validFrom` of the successor is taken from a new **optional kwarg `valid_from: str | None = None`**; when absent, read the successor's `validFrom` property (it may have been set at create), fall back to the successor's `createdAt`, fall back to `now` (monotone, never gap).
- `invalidate_point` (sdk.py:2158, CORRECTS-only, no edge transfer — the retraction/DELETE-soft path E7 uses) sets `validTo = now`, `expiredAt = now` (a withdrawal terminates the window at withdrawal time).
- Backward compatible: kwargs optional, stamps additive; existing supersede tests assert the new props only additively.

This keeps the E2E-9 restore sound: every CORRECTS chain edge now carries window endpoints derivable from the two points, so the V3 chain walk needs no extra machinery.

### D3 — `validFrom` is written at creation for the extractor path

`validFrom` = the fact's valid-time start = E1's `when` slot (session date). Write path: `extract_session_v2(..., session_date=)` (E1) → point dicts carry `when` → `execute_embed` passes it through to the Layer-1 payload → the consumer (`create_point(validFrom=…)`) writes it. `create_point` already accepts arbitrary props (`SET n += $props`). mining.py's W-4 already established this exact convention for the temporal-wiring path — the extractor path now follows it. **Undated points are legal**: no `validFrom` → open window, `[valid]` marker omitted (byte-identical rendering today).

### D4 — No new status, no new edge, no new kind

"expired" is a **property, not a status**. Terminal state stays `superseded`/`outdated` (existing machinery, ONTOLOGY §4.1 + `_exclude_status_clause`). The `expiredAt` property is transaction metadata complementing the status. No changes to `POINT_STATUS_VALUES`, no new edge types (CORRECTS remains the only supersession edge), no `valid*` operators. Ontology impact is exactly one registered additive property (`expiredAt`) — the approved additive-properties category.

### D5 — Default retrieval prefers live = the existing terminal-status exclusion, formalized

"Prefers live" is **already the default**: `TERMINAL_EXCLUDED_STATUSES` (retracted, superseded, outdated, archived, deprecated) is applied uniformly in `run_fts_query`/`run_vector_query`/`run_structural_query` (search_engine.py:15-38, #1391), and `tortoise_fts_query` excludes terminal points unless `include_terminal=True`. E6 does **not** change the ranking or the exclusion — it (a) asserts it (regression-lock), and (b) extends the **promoted-state decoration** (`fetch_point_epistemic_state`, #1353 D8) with the window fields so decorated hits carry `valid_from`/`valid_to`/`expired_at`. Co-retrieval of the superseded point (E2E-6) remains E5's `include_terminal` opt-in; E6 only adds the marker rendering on whatever hits carry window state.

### D6 — Point-in-time restore = supersession-chain walk (V3); window queries are V4-conditional

V3 mechanism (E2E-9, per 05-detailed-e2e.md): **walk the CORRECTS chain from the current live point to the point whose `[validFrom, validTo]` interval covers the target date**. Legacy undated points → open interval (a superseded point without `validTo` covers everything before its successor's `validFrom` — equivalent coverage, no special case beyond `IS NULL` handling). New SDK surface:

- `TortoiseSDK.restore_point_at(point_id, at_date) -> dict` — returns the point valid at `at_date` (chain walk), plus `chain: [...]` and the current value for context. **Explicit ambiguity signal** when two candidates plausibly cover the date (E2E-9 owned negative) — never a silent wrong answer.
- Optional MCP tool `tortoise_restore_point_at` (additive surface, #1353 `expand_relationships` pattern — see ⛔ G5).

V4 (post-baseline follow-up run): window-indexed restore (Cypher interval filter `validFrom <= $t AND (validTo IS NULL OR validTo >= $t)`) replaces/backs the chain walk under the same call signature, so the harness/reader call site does not change. The V4 assertions (`[valid …]` correctness on window queries, restore recall measured against the V3 baseline) are **V4-conditional** — this issue implements the V3 mechanism and ships the window properties; it does NOT gate on the follow-up run.

### D7 — Marker shape: `[valid …]` renders alongside the existing supersession markers

`retrieve.py` already renders `[SUPERSEDED BY: …]` / `[SUPERSES: …]` via `_supersede_marker` (#1367). E6 extends the same decoration point (`render_context` / `_annotate_hits`) with:

- live hit with `validFrom` → `[valid since <from>]`
- superseded hit (via `include_terminal` co-retrieval) → `[valid <from> → <to>]`; with `expiredAt` → `[valid <from> → <to>; expired <tx-date>]`
- undated hits → no marker (byte-identical rendering)

ISO date strings (`YYYY-MM-DD`, the dataset/`when` normalization) — no full timestamps in the reader context. `SearchResult` promoted fields gain `valid_from`/`valid_to`/`expired_at` (additive keys, emitted only when present — same #1353 D8 rule).

## ⛔ CONDITIONAL GATE NOTES

- **G1 — Property naming vs the issue wording.** The issue says `valid_at`/`invalid_at`/`created_at`/`expired_at`. This plan writes **`validFrom`/`validTo`/`expiredAt`** because `validFrom`/`validTo` are ALREADY registered in ONTOLOGY §4.1 (Impl ✅, written by mining.py W-4) and the codebase is camelCase. **`expiredAt` is the only new property** — an approved additive property, but it needs: (a) owner confirmation of the naming reconciliation (snake_case would require registering FOUR new properties and diverge from mining.py), and (b) a one-line ONTOLOGY.md §4.1 registration for `expiredAt` (ISO8601, transaction time, written by supersede/invalidate). No migration; no backfill.
- **G2 — E5 eval-ingest ownership.** The V3 restore is untestable unless the eval graph gets real CORRECTS chains. That application (`ingest_v2.py`) is nominally E5's ("no drops at write/ingest/read"); if E5 merges without it, Task 0 absorbs it into E6 (explicit scope note in the issue comment).
- **G3 — V4-conditional assertions.** Window-query retrieval (`validFrom`/`validTo` interval filter) and restore-recall measurement are asserted ONLY in the post-baseline follow-up run. This issue implements the chain-walk restore + first-class properties + markers (the V3 E2E-9 mechanism). Do NOT gate on the follow-up run.
- **G4 — Ontology invariant.** No new status ('expired' is NOT a status), no new edge types (CORRECTS only), no new kinds, no new operators. Verify at code review: diff touches no `POINT_STATUS_VALUES`, no `valid_predicates`, no master-list entries.
- **G5 — MCP tool surface.** E5's contract says "no new SDK tool" (canonical `supersede()` only). `restore_point_at` is a READ surface (like `expand_relationships` #1353), not a lifecycle writer — but if the reviewer reads the constraint strictly, ship the SDK method and defer the MCP tool to V4.
- **G6 — `when`/`validFrom` payload acceptance.** Adding `when` to the Layer-1 payload requires `commit_schema.validate_payload_dict` to accept it (additive field) or hosted commits will 422. If the epic's payload schema is treated as frozen this moves to V4 — but then E2E-9's fixture can only exercise the eval ingest path (which bypasses the endpoint), still valid for the V3 gate.

## Open Questions

1. **Window end for an undated successor:** successor `validFrom` → successor `createdAt` → `now`. Confirm the `createdAt` middle step is desired (it makes windows contiguous for undated facts without inventing dates); alternative is `now` only.
2. **`[valid …]` on live hits:** show `[valid since <from>]` on live hits (informative — helps the reader date facts) or restrict markers to superseded/expired hits only (diff-noise minimization)? Recommended: show it when present; it's cheap and the reader already gets "session date" annotations.
3. **Restore ambiguity policy:** exact-window coverage only, or nearest-covering when the target falls in a gap? Recommended: coverage only + explicit ambiguity signal; gap → `found:false` + nearest window (never guess).
4. **Window index for V4:** at 500-Q scale, is a Cypher range scan (`validFrom <= $t AND (validTo IS NULL OR validTo >= $t)`) acceptable, or do we need an FTS/interval index? Recommend range scan (the graph is small per question); revisit if the follow-up run shows latency regression.
5. **`restore_by_query` wrapper:** needed for the harness (retrieve live hit → restore), or does E2E-9 fixture call `restore_point_at` directly with the live id? Recommend the fixture calls the id-based surface (deterministic, no retrieval confound); the wrapper is V4 if the run protocol wants end-to-end restore answers.
6. **Marker ISO format:** full ISO8601 timestamps vs `YYYY-MM-DD` in reader context. Recommend `YYYY-MM-DD` (matches the dataset's `haystack_dates` and the `Current Date` header); timestamps stay on the graph properties.

## Failure Modes

- **Windows written at only one write site** (e.g., eval ingest path calls `supersede_point` but hosted reconcile doesn't thread `valid_from`) → stamped-from-read fallback (D2) covers it; T1 asserts the fallback chain.
