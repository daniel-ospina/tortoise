## 1. Decision

**Chosen: Approach A (App-Self-Contained) as the core, with C's isolated-scratch restore drill absorbed as the drill mode of the restore endpoint.**

| Approach | Verdict | Rationale |
|---|---|---|
| **A — App-Self-Contained** | **Chosen (core)** | Daemon is detector **and** reporter (files issues itself via repo-scoped PAT on Fly) → satisfies non-negotiable (b) driver-disabled leg. Zero infra cost. One restore code path (no divergence). |
| **B — Passive App + External Watchers** | Rejected | $4–8/mo in machines, credential sprawl (R2 on 3 surfaces, PATs on 2 machines), standalone restore module drifts from `restore_backup`. No failure-coverage win over A: a Fly Machine cron can die as silently as a workflow. |
| **C — Isolated-DB Restore + Detector/Reporter Split** | Rejected as architecture; **drill absorbed** | Fails non-negotiable (b) by construction: with the driver disabled, the R2 stall-markers are never read → staleness unreported. Split-brain on `REGISTRY_DB_URI` cutover; operator env-change inside the RTO path. Its genuinely good idea — zero-production-risk restore rehearsal — is adopted as the **drill** mode of the restore endpoint. |

### Why A on outcome quality (not convenience)

1. **Failure-mode coverage is total within one invariant — "at least one watcher alive", and BOTH watchers can compute freshness independently.** The driver computes R2 freshness **directly** in its pre-flight (it has R2 creds) — so an OOM crash-loop (#545, the documented class) where `/status` answers between restarts but the in-process daemon is repeatedly killed is still caught: the driver sees the R2 objects aging and files STALE itself. The daemon (driver-disabled leg) files directly via its own PAT. Mutual heartbeats provide the cross-check (driver→daemon WATCHER_DOWN via /status; daemon→driver DRIVER_DOWN via R2). The only blind spot is the double-failure (app down **and** driver disabled) — an accepted residual, documented in §10.
2. **The driver-disabled leg is covered by construction.** The daemon files GitHub issues itself. It does not depend on any R2 marker being *read* by anyone — it *is* the reporter. This is the exact leg the envelope says "decides the alerting sink".
3. **In-process registry dump is safe** because it is a *bounded carve-out*: cheap COUNT size-guard before dump (>100k nodes → abort + alert), registry-scope lock, never concurrent. The #545 OOM history is respected by the guard, not ignored. Team dumps (#655) never run in-process — that path stays external-worker.

### Registry wiring correction (CONTROLLER DECISION — v2, empirically verified)

**The control-plane data lives in `registry_control_plane`, NOT `registry_tortoise`.** Verified by code + empirical run (this worktree): `TortoiseSDK(namespace='registry')` exposes TWO graphs —
- `_get_proj()` (sdk.py:238) → **`registry_tortoise`** — the registry namespace's *projection* graph (near-empty in production; the SDK's data-plane handle).
- `_get_registry()` (sdk.py:296–320) → **`registry_control_plane`** — the *canonical control-plane graph*: every Team / Membership / APIKey / Invitation node lives here, indexed (`Team.name`, `Membership.team_id/user_id`, `APIKey.team_id/key_hash`), and every registry read/write (`get_current_team` auth, provision, register, create_api_key, revoke, invites, session/key, reconcile, onboarding) goes through `_get_registry()` → `{ns}_control_plane`. The repo's own test `test_registry_stamp_lands_in_canonical_registry` (tests/test_hosted_backup.py:1226) asserts this wiring. Empirical check: `CREATE (:Team)` → `registry_control_plane: 1 node`, `registry_tortoise: 0 nodes`.

**The plan backs up `registry_control_plane`** — the graph where the data is. `registry_tortoise` is NOT a backup target (it is the SDK projection shell). The Phase-7 P0 (a DR pipeline backing up the empty projection graph while passing every check = the #101 class) is fixed by this correction.

**Dump-handle wiring (implementation-critical):** `create_backup(proj, registry, storage, …)` dumps `proj.g` — for the registry we must pass a `proj` bound to **`registry_control_plane`** (via `_registry_sdk()._get_registry()` / `db.select_graph("registry_control_plane")`), NOT the SDK's `_get_proj().g` (registry_tortoise). The `registry` param (stamps) is the same handle. `graph_name="registry_control_plane"` flows into manifest + restore isolation checks.

## 2. Problem Statement

The hosted control plane (Fly app `tortoise-y4mjjq`, FalkorDB Cloud `registry_control_plane` graph — teams, memberships, API keys, invitations, the graph auth itself reads) has **no DR story**: no scheduled backups, no restore path (a registry restore through the tenant mechanism would be circular — auth reads the very graph being replaced), no freshness observability, and day-granular-only retention that cannot serve an hourly cadence. A registry loss means manual reconstruction or full data loss — and nothing would alert if backups silently stopped (#101 class). Issue #596 mandates: scheduled backup of the knowledge graphs, dual-watcher staleness detection that survives any single watcher failing (including the external driver being disabled), **dual-channel alerting — Telegram push (human) + GitHub issue (agent) — implemented under #673**, and sub-daily retention.

**Wiring gaps to close (verified):**
- **Fly secrets:** deploy-hosted.yml (lines 47–52, #643/#644) already conditionally syncs `TORTOISE_BACKUP_KEY` + `R2_*`×4 to Fly when set — the next deploy carries them. **Genuinely new Fly secrets:** `GITHUB_ISSUES_PAT`, `BACKUP_ALERT_ASSIGNEE`, `REGISTRY_DRILL_DB_URI`, `REGISTRY_SIMULATE_ENABLED` (synced via deploy-hosted.yml) + **`REGISTRY_RESTORE_KEY` (set out-of-band by the operator, never synced — see §3.5/§8)**.
- **GH repo secrets** already contain `FASTAPI_INTERNAL_KEY`, `R2_*`, `TORTOISE_BACKUP_KEY` (set 2026-08-08) — the GH Actions driver can call internal endpoints and read/write R2 with existing secrets. **Runtime-verify** (deploy gate is warn-only).
- **Repo remote is `daniel-ospina/tortoise`** (not `premise-labs/tortoise`) — `GH_REPO` must default to the actual remote and be required-when-enabled (Phase-7 P1-3: a default pointing at a nonexistent repo silently kills the alert channel).
- No repo workflow has a `schedule:` trigger today.
- `Team{id:'registry'}` does not exist → `create_backup`'s stamp `MATCH (t:Team {id:$team_id})` silently no-ops for the registry → BackupMarker node + pure-R2 freshness required.

In-graph stamps (Team `backup_latest_at`, BackupMarker) roll back with the restored snapshot → display-only, never alert inputs. `state.json` records restore events for the POST_RESTORE grace window (§3.6.2).

### 3.3 Backup run — `POST /v1/internal/backups/registry`

Internal-key protected (`_check_internal`). Flow:

1. **Lock:** registry-scope asyncio lock, non-blocking. Held (backup/restore/drill in progress) ⇒ `202 {"status":"already_running"}` (no queueing — next hourly run retries).
2. **Skip window:** newest primary object < `REGISTRY_SKIP_FRESH_MIN` old ⇒ `200 {"status":"skipped_recently_done"}` (absorbs GH jitter/double-dispatch).
3. **Size guard:** cheap `MATCH (n) RETURN count(n)` on `registry_control_plane`. `> REGISTRY_SIZE_GUARD_MAX_NODES` ⇒ **abort before dump**, write `ops/registry/events/size-guard-abort-{ts}.json`, file SIZE_GUARD_ABORT alert (deduped), `409 {"status":"aborted_size_guard","count":N,"max":M}`. **No dump object, no state.json write.**
4. **Dump (bounded carve-out):** `create_backup(proj, registry, storage, team_id="registry", graph_name="registry_control_plane")` — **`proj` bound to `registry_control_plane` via `FalkorProjection.from_uri(db_uri, graph_name="registry_control_plane")` on the same DB (or an explicit duck-typed wrapper exposing `.g` = the `_get_registry()` handle — cycle-2 P2-1: `create_backup` reads only `proj.g`; the raw handle alone raises AttributeError, so the construction is a deliberate wiring decision, pinned here)**; `registry` (stamps) = the `_get_registry()` handle. **No signature change needed** — `backup_id = f"registry/{ts}Z_{rand}"` is a valid key shape, prune's key parser handles it, `_validate_team_id("registry")` passes. Serialized under the registry lock — never concurrent with anything. **P0-guard regression test (cycle-2 P2-1):** seed a Team node via `_get_registry()`, run the registry routine, assert `manifest.graph_name == "registry_control_plane"` AND `node_count >= 1` — a backup of the empty projection can never pass.
5. **Stamp:** `MERGE (m:BackupMarker {id:'registry'}) SET m.backup_latest_at=$ts, m.latest_object_key=$key` in `registry_control_plane` (solves the `Team{id:'registry'}`-doesn't-exist caveat). Display-only — never an alert input.
6. **Empty-content guard (cycle-2 P2-1; cycle-3 P1-1; cycle-4 re-baseline — TRANSITION-gated, no false positives at 0-tenant steady state):** evaluated from the dump BEFORE the state.json write (guard = step 6, state.json = step 7 — numeric order matches execution order). **Steady-0 is OK** (the registry is legitimately ~0 nodes at 0 tenants — the chronic state; surfaced as a distinct low-severity `EMPTY_REGISTRY` signal in `/status`, never an incident). **DATA_LOSS_CANDIDATE fires only on a transition:** the `node_count` persisted in the PRIOR state.json (read before the upsert — cycle-6 P4 wording) `> 0` → now `0`, or a >50% drop vs prior counts. On fire: abort + file DATA_LOSS_CANDIDATE (**per-event incident id, manual close only**), no state.json write. **Re-baseline action (cycle-4 P2):** an explicit operator **`re-baseline`** endpoint (unified name — cycle-6 P4) updates `state.json` counts to current + closes the incident — distinct from suppression (which remains the blind-spot mechanism); consider label-level thresholds (teams/api_keys/invitations) instead of a flat >50% node drop (follow-up #661). A wiped-but-present graph must never look "fresh" at 0 nodes.
7. **state.json:** upsert `{source:"backup", latest_backup_at, latest_object_key, updated_at, node_count, counts:{nodes, teams, api_keys, invitations}}` — **counts persisted for the transition guard** (cycle-3 P1-1). Runs only if the empty-content guard passes.
8. **Prune:** `prune_backups(storage, "registry", keep_hourly=24, keep_daily=7, keep_weekly=4)` (§3.4).
9. **Close** any open SIZE_GUARD_ABORT **and BACKUP_SET_MISSING** incidents (a successful dump created primary objects, clearing both conditions — cycle-6 P1); DATA_LOSS_CANDIDATE closes **only via manual operator close** after verification (never auto-close).
10. Response: `200 {"status":"backed_up","object_keys":[...],"counts":{"registry_control_plane": {nodes,edges}},"pruned":N}`.

**3.3.1 Serialization & safety contract:** one lock family (`_REGISTRY_BACKUP_LOCKS`) shared by run / restore / drill, plus registration in the existing `_BACKUP_RESTORE_LOCKS` map under `"registry"`. Registry dump is the **only** in-process dump on the platform. Team dumps (#655) never run in the API process. **Single-instance assumption pinned:** fly.toml runs one VM; the in-memory lock + maintenance flag are process-scoped — documented in the runbook (Phase-7 P3-3 / P2-6).

**3.3.2 Registry stamp caveat — resolved:** `BackupMarker {id:'registry'}` node (display) + `ops/registry/state.json` (restore-surviving) + R2 object listing (authoritative freshness). No reliance on a `Team{id:'registry'}` node.

### 3.4 Retention — `keep_hourly` extension of `prune_backups`

`prune_backups(storage, team_id, keep_daily=7, keep_weekly=4, *, keep_hourly=0)`. When `keep_hourly=0` → existing behavior byte-for-byte (backward compatible; team call sites unchanged — **"call-sites unchanged", not "signatures unchanged"**: `target_graph` is keyword-only default-None; Phase-7 P4-1).

When `keep_hourly>0` (registry stream), applied newest→oldest over `backups/registry/{ts}_{rand}/` key dirs (single registry graph — no bucketing needed):
1. Keep the newest key per UTC hour for the last `keep_hourly` hours.
2. Keep the newest key per UTC day for the last `keep_daily` days, skipping buckets already kept.
3. Keep the newest key per ISO week for the last `keep_weekly` weeks, skipping kept.
4. Delete everything else. **Never delete the newest key.** Idempotent; storage-interface agnostic; `ops/` prefixes untouched; whole key dirs pruned together.

Bounded result: ~24 hourly + 7 daily + 4 weekly (≈35 objects — bounded and cheap). **Key-shape contract pinned by test:** `run_registry_backup` object keys round-trip through `prune_backups`' 4-part key-splitter + `backup_id` equality (Phase-7 P4-13).

### 3.5 Restore-and-rotate — `POST /v1/internal/backups/registry/restore`

**Auth: `_check_internal` AND a dedicated `REGISTRY_RESTORE_KEY` — applied to `drill: false` ONLY (Phase-7 P2-3 + cycle-2 P1/P2-3 + cycle-3 P0-1 + cycle-5 P0 threat-model scope).** Drill mode (`drill: true`) authenticates with the internal key alone: it is scratch-only by construction (`target_graph` regex `^_drill_`/`^registry_drill_`, cross-team/canonical targets rejected by the isolation checks), so the workflow-run drill can authenticate without exposing the restore key to GH Actions. **Distribution:** the operator sets `REGISTRY_RESTORE_KEY` on Fly **out-of-band** (`fly secrets set`, documented in the runbook incident path); deploy-hosted.yml **explicitly EXCLUDES it** (comment + active negative check). **Threat-model scope (cycle-5 P0 — honest, no overclaim):** the repo's main branch is unprotected and `FLY_API_TOKEN` (a GH secret) already gives any main-push collaborator full app takeover (deploy code, set any Fly secret). The restore key therefore defends against **credential-compromise scenarios** (leaked internal key, exfiltrated workflow token/R2 creds, malicious PR reviewer with read) — NOT against a trusted main-push collaborator. Documented in §10 + runbook; hardening follow-ups (deploy-scoped Fly token, branch protection) filed separately. Transport: dedicated header `X-Registry-Restore-Key`, never body/query, never logged, `hmac.compare_digest` (mirroring `_check_internal`), ≥32 bytes enforced at config validation. Operator-invoked, never scheduled. Request `{"backup_key": "...", "confirm": true, "rotate_all": false, "drill": false}` (`backup_key` optional — default rule in step 6). **`confirm` enforcement (cycle-3 P2-4): `drill: false` requires `confirm == true` exactly (400 otherwise), enforced before the pre-restore capture or any graph write; `drill: true` may skip it.** **Missing-key semantics (cycle-6 P4): `REGISTRY_RESTORE_KEY` absent ⇒ `drill: false` requests 503 + `/status` `restore_key: missing`; `drill: true` remains available with the internal key alone (scratch-only by construction).** Serialized on the registry lock; backup/prune in progress ⇒ `202`.

1. **`target_graph` validation (Phase-7 P2-2):** real restore ⇒ must equal `registry_control_plane`; drill ⇒ must match `^_drill_` / `^registry_drill_`; anything else ⇒ `400` before any destructive step. Unit test for the collision case (an operator typo must never target a tenant graph).
2. **Maintenance window (Phase-7 P1-1 — gate at the write, not hand-curated; cycle-2 P3-5 — mechanism pinned):** module-level maintenance flag consulted where the registry handle is obtained (hosted_api.py builds a fresh SDK per request; in-flight requests that cached the handle before the window are bounded by request duration and covered by the accepted app-wide-503 policy), plus a top-of-handler check in internal writers. `get_current_team` returns `503 + Retry-After: 60` while set (documented as an app-wide tenant 503 for the duration of the restore op — accepted, Phase-7 P2-1; it prevents mid-swap `500 Auth error`) **AND all registry-graph writes are blocked** — covering: tenant-key routes (`POST /v1/backups`, `POST /v1/team/keys`), session-auth writers (`POST /v1/graphs`, `/v1/invites`, `/v1/invites/accept`, `DELETE/PATCH /v1/teams/{id}/members/{user_id}`, `POST /v1/session/key`, `POST /v1/onboarding/team`), and internal writers (`/v1/internal/provision`, `/v1/internal/reconcile` top-check, `/internal/demo`, GitHub-connect callback). **The restore handler itself writes through an explicit bypass (holds lock + marker + keys — cycle-2 P3-5); all other writers stay gated; tested.**
3. **Restore-in-progress marker (Phase-7 P2-6; cycle-2 P3-4 — FAIL-CLOSED; cycle-4 marker semantics reconciled with §3.1):** write `ops/registry/restore-in-progress-{ts}.json` (`target_graph`, `stage`) **BEFORE the swap**; a marker write failure **aborts the restore before any destructive step** (mirrors the fail-closed live-graph checks). **Boot check: ANY `restore-in-progress-*` without a matching `restore-result-*` ⇒ the app refuses registry writes until the operator explicitly clears the marker — regardless of age, NO timed window (cycle-4 P2).** Mid-restore crash ⇒ runbook: restore from `pre-restore-safety-{ts}/dump.enc`.
4. **Safety export:** dump the live `registry_control_plane` → `ops/registry/restores/pre-restore-safety-{ts}/dump.enc` (belt-and-suspenders on top of `restore_backup`'s internal pre-restore copy). `if not drill`.
5. **Capture (restore-and-rotate, surgical primary):** `MATCH (k:APIKey) WHERE k.revoked_at IS NOT NULL RETURN k.id, k.revoked_at` + active-key inventory + **Invitation status (`accepted_at`, `status`) + Membership snapshot** → `ops/registry/restores/pre-restore-{ts}.json.enc` (**encrypted with `TORTOISE_BACKUP_KEY`** — Phase-7 P3-5; cycle-3 P2-3: a daemon sweep step deletes captures >30 days past restore verification, plus bounded retention for safety exports/restore-results) **before touching the live graph**. Prevents resurrection: the snapshot predates post-snapshot revocations; a naive restore would re-validate every revoked key.
6. **Restore:** `restore_backup(db, registry, storage, backup_key, team_id="registry", graph_name="registry_control_plane")` with a new `target_graph: str | None = None` param. **Live-phase binding (cycle-3 P1-2; cycle-4 P2 staging-names):** when `target_graph` is set, ALL live-phase operations (empty-guard read, pre-restore safety copy, live delete, swap copy) bind to `target_graph`; the fail-closed graph-ISOLATION checks bind to `graph_name`. **Staging/pre-restore graph names derive from `target_graph` when set** (drill → `_drill_{ts}_restore_{rnd}` — a mid-drill crash must never leave a full registry copy under a provenance-derived name the boot GC misses); the boot GC sweeps `_drill_*`, `registry_drill_*`, AND `_restore_*`/`_pre_restore_*` patterns. A db-handle-spy unit test asserts **exact-name** destructive calls (delete/copy targets) never reference `registry_control_plane` during `drill: true`. **Empty-archive guard (cycle-2 P2-1):** a `node_count == 0` archive targeting the canonical registry is REFUSED without an explicit `allow_empty: true` operator flag; the `backup_key` default is one rule: **the newest non-empty archive**, falling back to `state.json.latest_object_key` only if no non-empty archive exists. Any verification failure leaves the live graph untouched (existing guarantee) ⇒ maintenance cleared, `409` with `RestoreVerificationError` detail, state.json untouched.
7. **Post-restore index rebuild (Phase-7 P3-2):** run the registry index-ensure on the restored graph (mirroring the tenant restore path's `_ensure_indexes()`); the drill asserts index presence. **Restore-writer self-exclusion (cycle-2 P3-5):** the restore handler (holding lock + marker + keys) writes through an explicit bypass of the maintenance gate — all OTHER registry writers stay gated; tested. `restore_backup`'s end-stamp (`Team{id:'registry'}` `backup_restored_at`) is skipped when `drill: true` (a drill must never write the live graph even if a registry Team node exists).
8. **Re-apply revocations:** for each captured APIKey id present in the restored graph: `MATCH (k:APIKey {id:$id}) SET k.revoked_at=$captured, k.revoked_reason='restore-reapply'`. **Skip ids NOT found in the restored graph** — a key created AFTER the snapshot and revoked before restore has no resurrection risk. Verify `reapplied >= |keys_existing_in_restored ∩ captured_revoked|`; any **existing** key that fails re-apply ⇒ **rotate-all fallback**: `SET k.revoked_at=now(), k.revoked_reason='restore-rotate-all'` on all APIKey nodes, respond `"rotated_all": true` (operator re-issues; internal key is env-based, unaffected). Invitations present in the restored graph with `status='revoked'`/`accepted_at` re-applied similarly; post-snapshot memberships/teams listed in the diff as **accepted RPO-bounded residuals** (Phase-7 P3-8).
9. **Verify content:** label counts from the decrypted payload vs re-queried restored graph; sampled spot-check (N=20 nodes seeded-random across labels, M=30 sampled edges — props/degree vs payload).
10. **Diff report:** active-key ids captured at step 5 vs snapshot-active ids ⇒ `lost_keys_since_snapshot`; membership/invitation deltas ⇒ `lost_memberships_since_snapshot` (RPO-bounded loss made explicit; operator re-issues if needed).
11. **state.json:** `{source:"restore", restored_at, latest_backup_at:<snapshot ts>, latest_object_key, node_count, counts:{nodes, teams, api_keys, invitations}}` — **counts included per the §3.1 schema so the transition guard has a baseline immediately post-restore (cycle-5 P4).** `if not drill`.
11b. **restore-result write (cycle-6 P3 — the boot check's matching artifact):** persist `ops/registry/restores/restore-result-{ts}.json` (`{key, counts, revocations{reapplied, fallback}, duration, verified_at}` — the step-13 response payload) with the SAME `{ts}` as the restore-in-progress marker; **ordering pinned: result written BEFORE the marker is deleted; marker deleted only after the result is durable** — a crash after swap-complete but before marker-delete must not wedge writes (the boot check finds the matching result and permits). `if not drill`.
12. **Close** open STALE / NEVER / METADATA_LOST / LIVENESS_NO_WORK / R2_DOWN / ALERTER_DOWN incidents (canonical kind names; daemon also resolves within one poll). **`BACKUP_SET_MISSING` resolves via §3.3 step 9 (a successful dump created primary objects), NOT here — restores never write backup objects (cycle-6 P1).** **Maintenance flag cleared before response on BOTH success and failure paths (cycle-6 P4).** `if not drill`.
13. Response: `200 {"status":"restored","restored_at","snapshot_at","counts","revocations":{"captured":N,"reapplied":M,"fallback":bool},"lost_keys_since_snapshot":[...],"spot_check":{"nodes":20,"edges":30,"mismatches":0}}`.

### 3.6 Staleness daemon — `tortoise/backup_watcher.py` (envelope (b): detector **and** reporter)

Spawned in `_lifespan` (precedent: #545 pre-warm thread): `threading.Thread(daemon=True)`, initial delay 60 s, then poll every `REGISTRY_WATCHER_POLL_SECONDS`. **Spawn gating (Phase-7 P3-1):** spawned only when `backup_config` validates (enabled + required secrets) **and** not in a test environment (env-gated like `RATE_LIMIT_DISABLED`). **Read-only w.r.t. the graphs** (never touches FalkorDB — asserted by test); writes only R2 heartbeat/alert objects and files GitHub issues. Per-poll try/except + consecutive-failure counter (surfaced in `/status`) — a crashed poll never kills the app. **Watchdog + timeouts (cycle-2 P3-3):** a small watchdog thread restarts the daemon thread if it exits (`is_alive()` check — a hung or crashed poll loop cannot silently die); explicit socket timeouts on EVERY urllib/GitHub/R2 call so no poll can hang; "daemon not running" is a first-class `/status` signal that the driver's WATCHER_DOWN check keys on in addition to heartbeat age. **Memory guard:** process-level `resource.getrusage(RUSAGE_SELF).ru_maxrss` trend sampled per poll; restart the daemon thread above a threshold (per-thread RSS is not measurable in CPython — Phase-7 P2-4; the daemon holds no graph objects, streams urllib responses, caps response sizes).

**3.6.1 Poll** — pure `compute_status(now, objects, state_json, driver_heartbeat, thresholds, last_known_good)`:

**R2-reachability semantics (Phase-7 P1-2; cycle-2 P2-2; cycle-3 P2-2 — R2 outage must NEITHER fabricate NOR silence):** when R2 is unreachable, `compute_status` evaluates from **last-known-good state** (cached from the previous successful poll). **On fresh boot with an empty cache and R2 down, the daemon evaluates UNKNOWN → NO daemon alert** (silence is honest when nothing was read; NEVER_BACKED_UP requires a confirmed-empty listing or a prior successful poll). **Driver-side escalation closes the fresh-boot window (cycle-3 P2-2):** when `/status` reports `r2_ok: false`, the driver files an **R2_DOWN / CHANNEL_IMPAIRED** issue via `GITHUB_TOKEN` (GH-search dedup — needs no R2). When degraded-from-known-good, the daemon files via the **GH-search fallback + in-memory last-filed guard** (no R2 dedup object needed). R2 outage is a first-order expected failure (credential rotation, Cloudflare billing, bucket policy) — it must escalate, not go silent.

| state.json | primary objects | Age vs threshold | Status (→ incident kind) |
|---|---|---|---|
| — | none | — | `never` (after boot grace) → **NEVER_BACKED_UP** |
| absent/unparseable | ≥1 | — | **METADATA_LOST** (freshness still computable from objects) |
| present, `source=restore`, `now−restored_at < threshold` | — | — | **POST_RESTORE** (no alert; re-arms once threshold elapses without a new backup) |
| present | present | `now − newest_primary_ts > threshold` | **STALE** (authoritative signal = newest object ts, scan universe = `backups/registry/*/dump.enc` + non-expired `ops/registry/simulate/*` objects — cycle-2 P3-6 unification; state.json cross-checked, never overrides) |
| present | **none** | — | **BACKUP_SET_MISSING** (cycle-3 P2-1: state.json present but zero primary objects — a bulk delete or erroneous prune; fires on a **confirmed-empty listing**, never on a failed listing — unreachable R2 evaluates from last-known-good, cycle-4 P4) |
| present | present | ≤ threshold | OK |

Plus: `now − driver_heartbeat.ran_at > REGISTRY_DRIVER_DOWN_THRESHOLD_MIN` ⇒ **DRIVER_DOWN** (workflow deleted / GH 60-day auto-disable / GH outage), gated on last-known-good R2 state and suppressed while `REGISTRY_BACKUP_ENABLED=false` (kill-switch = operator pause, not a dead driver).

**3.6.2 Tri-state (envelope):** `never` (no objects, no marker) / `stamp-missing` (objects exist, marker/state.json absent — METADATA_LOST incident) / `stale` (freshness breach). All three alertable. Reconciling stamp vs R2: **R2 object listing is authoritative** (restore-surviving); a rolled-back in-graph stamp can never trigger an alert.

**3.6.3 Mutual supervision (heartbeats):** daemon writes `ops/registry/watcher-heartbeat.json` every poll; driver's pre-flight reads its age from `/status` and files **WATCHER_DOWN** if stale > 30 min — **only when `/status` reports `r2_ok: true`** (an R2 outage must not fabricate a dead watcher). Driver's heartbeat is written **through the app** (`POST /v1/internal/driver/heartbeat`). When the app is down, DRIVER_DOWN is moot (the driver's own direct-freshness check files STALE; if both are down, that's the documented residual).

**3.6.4 Alert lifecycle (per kind, per incident):**
- **Create-once FIRST, file SECOND (R2 object is the linearization point):** on alert-worthy status, `create_if_not_exists(ops/registry/alerts/{KIND}-{incident_id}.json, placeholder)` is attempted FIRST (`incident_id := {YYYYMMDDTHHMMSSZ}` at first detection — ISO timestamp for periodic kinds, per-event UUID for DATA_LOSS_CANDIDATE; single id scheme pinned here, cycle-6 P4). **Winner** proceeds to file the GitHub issue via the **urllib GitHub client** (stdlib — no `gh` binary on Fly), then backfills `issue_number`. **Loser (412) adopts — WITH the state-machine branch (cycle-6 P3): if the adopted object carries `issue_number`, skip filing; if it is a placeholder (issue_number absent — winner died between create and backfill), the adopter BECOMES the filer via the GH-search fallback path (dedup by open-issue search prevents duplicates). A create-then-die window must never leave an incident permanently silent.**
- **R2-outage / filing-failure fallback:** GH-search fallback (search open `label:dr:backup` + kind in title) + per-kind in-memory last-filed guard. The daemon NEVER deletes dedup objects on filing failure (Phase-7 P3-9).
- While open: overwrite `last_seen_at` only. **No new issue.**
- On recovery: close issue with resolution comment + **delete the dedup object** (delete-to-resolve ⇒ a later recurrence is a *new* incident).
- Suppression: `ops/registry/suppression.json` `{kind: {until: ISO}}` — checked before create/reopen.
- **Driver-side filings** (APP_DOWN, WATCHER_DOWN, LIVENESS_NO_WORK, STALE, R2_DOWN/CHANNEL_IMPAIRED, ALERTER_DOWN — cycle-4 P4: all routed through the create-once/GH-search-fallback lifecycle) use the same R2 create-once objects with GH-search fallback.

**3.6.5 Simulated-stale hooks (env-gated, fail closed):** `POST /v1/internal/backups/registry/simulate-stale` writes `ops/registry/simulate/stale-{ts}.json` with an embedded `expires_at` (Phase-7 P3-10). **The newest-primary scan reads key timestamps** — the simulate object carries an old age-ts and wins newest-primary selection while real backups stay fresh in the listing scan ordering (spec: scan sorts by object key; the simulate key's ts makes it the newest key while its `age_ts` field is old — unit test: fresh real backup + simulate object ⇒ STALE). `simulate-recover` deletes the simulate object; expired simulate objects are ignored by `compute_status`. Double-gated: internal key + `REGISTRY_SIMULATE_ENABLED=true`.

2. **Kill-switch branch:** `status.enabled == false` ⇒ skip run, heartbeat, filings; `exit 0`.
3. **Direct R2 freshness check (Phase-7 P1-1 — the OOM crash-loop leg; cycle-3 P2-2 driver semantics):** the driver lists `backups/registry/*/dump.enc` itself (aws CLI; R2 creds already in GH) and computes newest ts. If age > threshold, file **STALE independently of `/status`**. **Listing failure (non-zero aws exit / timeout / AccessDenied) ⇒ skip freshness evaluation this run — log only, no STALE/NEVER filing** (a failed listing is never "confirmed empty"); only a successful listing with zero objects is NEVER-eligible. Cross-check the daemon's `r2_ok` from `/status` (filing R2_DOWN when false). This is the mandated app-down/crash-loop coverage: an OOM crash-loop where `/status` answers between restarts but the daemon is repeatedly killed is still caught.
4. `POST /v1/internal/backups/registry` run (202/skip handled as normal states).
5. `POST /v1/internal/reconcile` ride-along (#654); **skipped when the run returned 202 (lock held = restore/drill in progress — reconcile writes the registry and must not race a restore)**.
6. `POST /v1/internal/driver/heartbeat {"run_id", "results"}`.
7. Recovery: status succeeded this run ⇒ close any open APP_DOWN / WATCHER_DOWN / STALE issues (self-heal) — **EXCLUDING simulate-triggered STALE incidents** (cycle-2 P3-6). **PAT-death leg (cycle-3 P3-3):** when `/status` reports `gh_ok: false` (daemon's PAT dead), the driver files **ALERTER_DOWN** via `GITHUB_TOKEN` (GH-search dedup) — the channel's death must not be invisible.

**Direct-R2 leg tooling (cycle-2 P3-7):** the driver uses the **`aws` CLI** (preinstalled on ubuntu runners) with `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` + `--endpoint-url https://{R2_ACCOUNT_ID}.r2.cloudflarestorage.com` for the freshness listing. **3.8.1 Liveness semantics (rescoped — Phase-7 P2-8):** no-work = the run **did not back up** (`skipped_recently_done` or error) **AND** reconcile empty. **Reconcile-empty alone never emits a liveness alert at 0 teams** (reconcile is chronically empty at 0 teams — a permanent flapping issue would drown the channel). Reconcile-empty keys on `reprovisioned == 0 AND expired_keys_swept == 0` (reconcile always returns ≥1 `notes` — response shape is not the signal). **DRIVER_DOWN** (daemon-side) covers a dead driver.

### 3.9 Verification-restore drill (acceptance's "≥1 executed verification restore")

`POST /v1/internal/backups/registry/restore {"drill": true, "backup_key": null}` — same restore pipeline with `target_graph="_drill_{ts}"` (isolated scratch namespace on the same instance by default; `REGISTRY_DRILL_DB_URI` overrides to a separate scratch instance when provided). Zero production writes — asserted by test (state.json + alerts/* unchanged; **maintenance flag NOT set** — drill never 503s tenants, Phase-7 P3-4). Checks (named in the response):
1. **Restore integrity:** scratch node/edge counts match the archive payload.
2. **Content spot-check:** per label, sample up to 20 nodes (deterministic ordering) + sampled edge set — full prop maps and relationship-type counts vs the archive.
3. **Swap rehearsal (Phase-7 P2-5; cycle-2 P3-6 — copy-then-delete so the source survives):** the drill rehearses the swap mechanics on scratch graphs (restore into scratch A → **`GRAPH.COPY` A→B first, then delete A** — the source survives the delete), exercising the riskiest middle (live delete + copy) mechanically, plus endpoint-side RTO measured (not wall-clock incl. GH scheduling).
4. **Rotation check:** keys revoked in the live registry are revoked in the restored scratch graph (exercises capture/re-apply semantics).
5. **Index check:** registry indexes present post-restore.
Cleanup: scratch graphs deleted in `finally`.

**Boot-time drill-graph GC (cycle-3 P3-4; cycle-5 — full pattern set):** on boot, sweep `_drill_*`, `registry_drill_*`, `_restore_*`, and `_pre_restore_*` graphs older than N hours (a crash mid-drill/restore leaves a full registry snapshot on the production instance — the N-hours age qualifier applies to ALL four patterns); namespace-reservation note in the runbook (never name a real graph with those prefixes).

Cadence: **rollout drill (mandatory, operator-invoked — Phase-7 P2-7: the operator runs it manually with documented commands, exercising the incident credential path) + `workflow_dispatch` on demand.** **The monthly cron is DEFERRED to a follow-up decision** (Phase-7 P3-11 / Qwen P2 resolved: default to the confirmed problem's "no recurring drills" boundary). **Drill rate-limit (cycle-3 P4-2; cycle-5 P3 — ENFORCED):** drills share the registry lock AND accepts are cooldown-limited **≥1h between `drill:true` requests, enforced at the endpoint** (§4 step 9) — a collaborator holding the internal key cannot DoS backups with continuous drills (the cooldown + STALE-at-90-min escalation bound it). Result artifact uploaded to the workflow run.

## 9. Rejected Alternatives (with "when it would have been better")

- **B — Fly Machine cron + probe Machine:** rejected — credential sprawl (R2 on 3 surfaces, PATs on 2 machines), $4–8/mo infra, restore-module drift, and no better coverage (a Fly Machine cron can die as silently as a workflow). *Would have been better if* scheduler determinism independent of GitHub were a hard requirement, or the app must host zero background work (the #545 OOM history is the cautionary precedent — escape hatch documented).
- **C — Isolated-DB restore + detector/reporter split:** rejected as the staleness architecture — violates non-negotiable (b) by construction (driver disabled ⇒ R2 markers unread ⇒ staleness invisible), plus split-brain risk on `REGISTRY_DB_URI` cutover, operator env-change inside the RTO path. *Would have been better if* a hard security boundary forbade any token on Fly — then the envelope itself would need renegotiation. Its isolated-scratch restore is **absorbed** as the drill mode (§3.9).
- **Parts of A rejected:** (i) *driver-as-sole-alerter* — driver death silently kills all alerting; the daemon must file directly. (ii) *in-graph stamp as freshness authority* — restore rolls stamps back; R2 objects are the authority. (iii) *wide-scope PAT* — single-repo fine-grained. (iv) *per-graph prefix R2 layout* — key-scheme surgery for zero gain (ONE registry graph). (v) *monthly drill cron by default* — deferred to follow-up (Phase-7 P3-11); rollout + dispatch satisfies acceptance.

## 10. Risks & Decisions to Confirm

- **R2 conditional-write support (`IfNoneMatch='*'`):** supported by Cloudflare R2 (GA 2024); fallback documented: HEAD-check + list-based adoption.
- **GH Actions 60-day auto-disable:** covered by daemon DRIVER_DOWN.
- **GH single-provider axis (Phase-7 P3-9; v3 update):** scheduling terminates in GitHub; alerting is now **dual-provider** — the GitHub issue (agent) + **Telegram push (human, #673)** — so a GH incident degrades the agent leg but the human still gets paged via Telegram; the reverse holds via the GH-search fallback. Named failure axis in the runbook.
- **R2 outage:** neither fabricates (r2_ok gates) nor silences (last-known-good + GH-search fallback) incidents.
- **Restore window:** tenants get **503s for the duration of the restore op** (not just the swap — Phase-7 P2-1/P2-10 accepted: a clean 503 beats a mid-swap 500 Auth error; bounded seconds-to-minutes at ≤ 100k nodes). Confirm acceptable with product.
- **`REGISTRY_RESTORE_KEY` on Fly:** dedicated operator secret; rotation runbook; `FASTAPI_INTERNAL_KEY` still rotated when collaborators leave.
- **Threshold tuning:** STALE = 90 min, DRIVER_DOWN = 4 h, poll = 10 min, grace = 2 h. Confirm.
- **GH jitter false-positives:** a > 90-min gap may transiently file STALE; auto-close on next backup self-heals; dedup keeps it to one issue.
- **`TORTOISE_BACKUP_KEY` rotation:** old archives become unreadable; runbook documents rotate-between-backups only.
- **Registry backup-content confidentiality (cycle-5 P2 — accepted inherited boundary, consistent with the threat model):** registry dumps/captures/safety exports are encrypted with `TORTOISE_BACKUP_KEY`, which exists as a GH secret — so GH-capable collaborators can decrypt them. Under the cycle-5 P0 trust model (main-push collaborators are trusted; FLY_API_TOKEN = full takeover) this is an **accepted inherited boundary**, documented in the runbook; a Fly-only registry encryption key (never in GH) is a hardening follow-up. **Forged-archive selection (cycle-5 P3):** under the same trust model, a trusted collaborator could plant a self-consistent forged archive; the restore runbook mandates an operator-side provenance cross-check of the chosen archive against Fly app logs before `confirm`.
- **Partial-wipe residual (cycle-5 P3 — decision, not hedge):** a <50% node-count wipe of a low-count label (e.g., invitations) can evade DATA_LOSS_CANDIDATE; **accepted residual**, bounded by RPO freshness detection + the restore-time diff report; label-level thresholds are a follow-up.
- **Mid-restore crash:** restore-in-progress marker + pre-restore-safety export + boot check + runbook recovery procedure (Phase-7 P2-6).
- **Single-instance assumption:** in-memory lock + maintenance flag are process-scoped; fly.toml = one VM; documented; scale-out re-opens quiescence bounds (accepted write-loss ≤ RPO).
- **Residual corner (accepted):** app down **and** driver disabled simultaneously ⇒ no alert from the daemon; the residual is bounded by the driver's direct-freshness leg + Telegram push (#673) closing the app-down leg (reopen condition: first unattended app-down).
- **Decisions to confirm:** alert assignee handle; label names (`dr:backup`); maintenance-503 policy; driver `exit 0` after filing APP_DOWN (recommended).
