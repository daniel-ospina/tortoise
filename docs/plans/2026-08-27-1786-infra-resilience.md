**Goal:** Make the LongMemEval pipeline structurally unable to permanently lose a question to **write-path** infrastructure contention, and remove the dominant stall trigger from the shared FalkorDB container — so the test measures extraction/retrieval quality, not infra. (Scope note — P2-1: the guarantee covers the WRITE-path loss surface; `reader:`/`judge:`-site LLM-provider transients that exhaust `_call_with_backoff` remain permanently skipped by design — a named, separate residual with its own follow-up, recorded in Task 2 Step 2 / §8.)

**Architecture:** Two-layer defense, mechanism-matched to the verified loss chain. **Layer 1 (make loss impossible):** bounded jittered retry on the ingest write stages + a bounded whole-question retry with a narrowed transient predicate, plus resume re-attempts of transient-failed questions (`--retry-failed`) with failure-entry lifecycle (remove-on-success). **Layer 2 (remove the stall trigger):** disable automatic RDB BGSAVE in the falkordb compose (`--save ""`, AOF already provides durability) with an INFO-persistence preflight gate, and give the eval its own elevated retrieval deadline through the existing `_elevated_timeout_ms` seam (SDK default untouched). Load hygiene (worker guidance + host-load warning) is advisory; breaker latency-tripping is deferred behind a trigger condition.

## 1. Confirmed Problem (scoping Phase 2, problem-verify clean)

The eval pipeline loses questions when the shared FalkorDB container stalls under the eval's own ingest load + parallel sessions. The **verified loss mechanism is the UN-TIMED WRITE PATH**, not the retrieval path:

1. `proj.g.query()` passes `timeout=None` (`tortoise/projection/__init__.py:89` — `_GuardedGraph.query`); the only client-side bound is the connection `socket_timeout=10` (`:797`).
2. During a server-side stall (suspect: periodic RDB BGSAVE forking a 4.8 GB heap on a `cpus:"2"`-capped container under host load ~50; `#1733` already proved BGSAVE fork OOM at the 2 g cap), in-flight un-timed write commands blow through the 10 s socket bound → `redis.exceptions.TimeoutError` (reprs as `network:TimeoutError` in redis-py 8.1.0).
3. The question dies mid-Phase-A ingest writes. The ingest stage has **no retry wrapper** (only reader/judge get `_call_with_backoff`, `tools/longmem_eval/run.py:517`), and the checkpoint **permanently skips** failed questions on resume (`run.py:1657-1662`).

**Evidence (reval run 2026-08-27, 46 Q, 5 workers):**
- 4 failures, all `single-session-user`, error repr `network:TimeoutError` (redis TimeoutError identity confirmed from `redis-py 8.1.0` source — not an LLM-provider error). Three failed within 4 ms of each other (02:10:34.088/.092/.092) — a shared server-stall event, not independent slowness; the 4th (66f24dbb) at 02:19:54.
- All 4 died **mid-Phase-A writes** (session indices s22/48, s30/45, s38/53, s21/50 — ingest not complete), immediately after `create_point` traffic and `Strategies timed out (500ms) — collected 0/3` lines from concurrent workers.
- Survivors' retrieval was **healthy**: mean 43.7 ms, p95 82 ms, max 128 ms; all **42** survivors have non-empty leg traces (vector ok 42, structural ok 42, fts ok 27 + empty 15 — 46 Q − 4 failures = 42; the 4 failed qids died mid-Phase-A with no leg traces, so the counts are survivor-only; P2-2). The issue's retrieval-timeout framing is falsified **for the loss mechanism** — retrieval is a secondary gap, not the killer.
- Ingest averages **1,533,924 ms (~25.6 min) per question** × 5 workers — the eval run is itself the dominant load generator (self-DoS), and the 4 lost questions ≈ 1.7 h of paid LLM extraction discarded.

**Secondary gaps (still in scope, lower priority):**
- **G1 — soft retrieval budget:** the 500 ms collective deadline is a client-side `as_completed` timeout; the server-side `GRAPH.QUERY TIMEOUT 500` is best-effort (24 slow legs ran 1.9–9.5 s and returned; post-hoc "exceeded timeout" warn-and-keep, `search_engine.py:360-366`). A cancelled worker thread keeps running (Python threads can't be killed), holding a connection.
- **G2 — breaker blind to slowness:** the per-strategy breaker (`tortoise/search_engine.py:51-146`) trips only on exceptions; slow-but-successful queries record success → it can never fail over on slow degradation (24 slow events, 0 opens in the log).
- **G3 — nominal recovery:** `#1776` grades ingest-site transients `ingest:retries_exhausted` (recoverable-class), but the runtime never retries and the checkpoint permanently skips them — "recoverable" is a label, not a behavior.

**Falsification note (weakest assumption):** the BGSAVE-fork causality at the *current* config (8 g / cpus:"2") is **inferred, not measured**: `#1733` proved fork OOM at 2 g; Redis docs validate fork pauses (ms→~1 s, CPU-intensive); but the specific ≥9.5 s legs at 8 g/2 cpu are not fork-attributed. The R4 E2E (Task 8) is an explicit falsification gate for this. If stalls occur without fork events, R1/R2/R3/R7 carry the load and R4 is not the cause (see Rejected Alternatives → measurement-isolation).

**Confidence:** High on the write-path loss mechanism (exception identity + log adjacency + timeout=None + retrieval-health evidence); Medium on BGSAVE-as-trigger (mechanism validated externally, n=1 in-log); High on no-ingest-retry and permanent-resume-skip; High on breaker-can't-trip-on-slow.

## 3. Pattern Research

> **Findings date:** 2026-08-27

**Library docs (preflight)** — no new third-party deps introduced; all touched surfaces are in-repo (redis-py 8.1.0, falkordb v4.20.4 driver, docker-compose). Verified in installed sources: redis-py 8.1.0 `execute_command` does **not** thread any `timeout` option into `read_response` (its `timeout` param is `SENTINEL`-gated and never set from command options) — a per-command client-side socket timeout via `execute_command(timeout=…)` **does not exist** as documented; falkordb's `Graph.query(timeout=…)` emits the **server-side** `TIMEOUT` clause. The eval-side elevation seam (`_elevated_timeout_ms`, `search_engine.py:997`) is the real, existing mechanism.

**Library version & API surface** — [2 calls: redis-py pooling + persistence]
- Canonical: redis-py — one long-lived client with a pool sized to expected concurrency; creating a new client per request is an anti-pattern (redis.io docs; redis-py docs "a pool should not be shared across clients"). Our per-question fresh-SDK/connection pattern is the anti-pattern, but pooling **cannot fix a server-side stall** (rejected with rationale below).
- Known pitfall: Redis RDB persistence uses `fork()`, which "can pause Redis for milliseconds to even around one second on very large datasets"; `BGSAVE` is CPU-intensive; `fork()` latency is observable via `INFO persistence → latest_fork_usec` (redis.io persistence + latency docs). AOF provides durability independent of RDB (Redis loads AOF in preference at startup — confirmed in-repo #915 comment). **This validates R4.** `BGREWRITEAOF` also forks (same stall shape) → R4 must bump `--auto-aof-rewrite-min-size`.

**Idiomatic usage patterns** — [1 call: eval-harness resilience]
- Canonical/competitor: long-running benchmark harnesses checkpoint successes and resume (LM Evaluation Harness `--use_cache` skips evaluated samples; LLM Readiness Harness arXiv:2603.27355 documents resume/checkpoint for connection interruptions). Measurement isolation is the dominant practice for "measure the model, not the machine" (SWE-bench runs each instance in an isolated container). Our checkpoint **permanently skipping failed questions** is the gap R3 closes; full measurement isolation (dedicated DB) is flagged as an owner decision.

**Library/framework pitfalls** — [2 calls: circuit breakers + retry discipline]
- Canonical: modern circuit breakers (Resilience4j) support `slowCallRateThreshold` — treating slow calls as failures. Our breaker lacks this (feature gap, G2) — but latency-tripping converts slow-degradation into **empty results**, which is recall-contamination risk: `VECTOR_TIMEOUT_MS=5000` exists precisely because empty-vs-slow is ambiguous on the vector arm (`retrieve.py:150-153`). Hence R6 is deferred/optional, not primary.
- Known pitfall: retries amplify load on overloaded systems (AWS Builders' Library "Timeouts, retries, and backoff with jitter"; AWS REL05-BP03: control/limit retry calls; full jitter prevents aligned retry storms). R1/R2 are bounded (2 + 1 attempts) with jitter; the existing `_call_with_backoff` uses **half-jitter** (`0.5 + random/2`) — accepted as negligible at these retry counts (P3 note from solution-verify).

> **Gate skipped (Micro-style justified-skip note):** no third-party library is introduced or version-pinned in this plan; all buckets above are applied to *behavior verification* of already-pinned deps (redis-py 8.1.0, falkordb driver, docker-compose), not new dependency adoption.

## 6. Implementation Tasks

### Task 1: Ingest write-stage retry + bounded whole-question retry (R1 + R2)

**Intent:** The verified loss mechanism is a single transient `redis.exceptions.TimeoutError` on an un-timed write killing the question with zero retries. Add bounded jittered retries at the two cheapest recovery points so a transient stall cannot lose a question.
**Acceptance:** A question whose ingest write raises `redis.exceptions.TimeoutError` (or `ConnectionError`) once or twice completes with correct evidence; parse/structural/fatal errors are never retried; no duplicate points are created on replay (E7 probes); the new retry constant is fingerprinted (mirror `max_retries` — it is results-relevant, P1-1) and recorded in methodology.
**Files:**
- Modify: `tools/longmem_eval/run.py` (call-site wiring, `INGEST_WRITE_RETRIES`, methodology, whole-question retry)

- Test: `tests/` (new `test_eval_ingest_retry.py` + existing eval test dir)
