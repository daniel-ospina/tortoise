# Implementation Plan — Issue #1348: Measure RRF fusion quality levers (pool floor, k sweep, GraphRanker verdict)

> Draft from solution-converge (Phase 5). Pending solution-verify (Phase 5.5) + parallel review gates (Phase 7).

## Problem statement

Three RRF-fusion levers are unmeasured: (1) production pool depth is hardcoded `str_limit = limit * 2` (sdk.py:8725), below the RRF 50–100 consensus sweet spot at typical limits (pool 20 at limit=10); (2) fusion constant k is hardcoded 60 (search_engine.py:633) with no sweep; (3) GraphRanker (#25) is unwired from the fused path and unscorable on the synthetic oracle corpus (all three signals null: random α/β, random edges, dead recency). P@5=0.924 near ceiling at depth 50 means unpaired deltas at n≈100 are unpowered — the measurement must be paired and in-loop.

## Proposed solution (synthesis: A "Fusion-native harness" + B's discipline + env-var convention)

- **Pool floor (prod):** inline `TORTOISE_POOL_FLOOR` env knob (matches the repo's 23-knob convention) + optional `pool_floor` param on the SDK search methods for programmatic override (the E2E-8 leg and tests need it). New rule: `str_limit = max(limit * 2, pool_floor)` (full-scan exempt). Returned limit unchanged — truncation at sdk.py:8851 precedes EP decoration at 8853+, so decoration is flat (#1353 NOT a dependency).
- **k sweep (eval):** paired in-loop computation. `retrieve_per_strategy` already produces per-strategy ranked lists; compute `rrf_fusion(..., k=20/60/100)` once per query from those identical lists — perfectly paired, tightest CIs, single run. Pure Python over rank positions; no retrieval re-run.
- **GraphRanker leg:** add `"fused_rerank"` to `STRATEGIES` (run.py:75) — real path, in-harness: `GraphRanker.rerank` over the fused pool (scores.rrf drives similarity; graph_boost from confidence + degree). Two arms on the SAME corpus: fused ON vs OFF.
- **Corpus enhancement (default GraphRanker leg):** `generate_oracle_points(..., enhance_signals=True)` — topic-correlated `n.confidence` derived from topic-biased α/β draws (overlapping ranges, noisy not tautological) and topic-correlated operator edges between EXISTING nodes only (no new nodes; no oracle-denominator or FTS/vector input shift). **Byte-identical unenhanced path:** posterior draws are the last per-point draws (synthetic_corpus.py:522–524), so an isolated `random.Random(seed ^ salt)` for enhanced signals preserves content/embeddings exactly; recency stays dead (documented).
- **Two-phase sequencing:** Phase 1 = depth×k sweep on the plain committed corpus (baseline comparability, reproduces baseline-embedded-2026-08-17.json); Phase 2 = enhance, then GraphRanker arms. Retrieval metrics are EP-blind (run_fts/vector/structural score text/embedding/kind; rrf_fusion rank-only; EP annotation post-truncation), so Phase-1 metrics are contamination-free by construction — the report declares this.

## Rejected alternatives

- **B "Layered analysis" (post-processor + 3 separate runs)** — *would have been better* if the harness were frozen (e.g., #1144 CI gate locked run.py), letting the sweep ship with zero harness risk; or if P@5 had headroom, where unpaired 3-run deltas would still be interpretable. Rejected: near-ceiling 0.924 makes unpaired n=100 deltas unpowered; a post-processor rerank drifts from harness semantics (RRF input truncation, annotation shapes) and yields a less honest GraphRanker verdict.
- **C "Explicit orchestration" (subprocess sweep_k.py + rerank_eval.py)** — *would have been better* if cross-leg state bleed were a real risk (full isolation) or if the harness were unsafe to touch at all. Rejected: heaviest tooling, slowest (3× DB re-runs), no statistical gain — in-loop pairing is strictly superior.
- **Config module for pool floor (A's `tortoise/config.py`)** — *would have been better* if ≥5 knobs were imminent (a config module pays off then); for one knob the 23-knob env convention is the repo's native pattern. The SDK param, not a module, covers the eval's programmatic need.
