# #1765 — Scoping: User profile + identity/credential separation (add login methods + recovery banner)

> issue-scoping v5.1 double diamond · Complex tier · Team: organisation-design-team
> Scope doc — feeds writing-plans.
> **User decisions (2026-08-26):** (1) FULL implementation — no probe-gating, no phase-slicing; `teams.email` demotion ships now (pre-launch, migration-safe). (2) Include everything: banner + profile + linking + unlink. (3) Terminology: "login methods" (not "ways in"); API keys are NOT counted as login methods. (4) Username feature DROPPED — users identified by unique ID + email; invites via email/GitHub; no handles. (5) Banner CTA promises working add-methods.

## Confirmed Problem

Identity facts are conflated across three tables:

- **`teams.email`** — globally-unique *team* attribute (`uq_teams_email`, 20260813000004:107); written by signup/claim/onboarding (`claim_membership` Step 6 unconditional overwrite; `PATCH /v1/onboarding/state` → `update_team_email`; **tenant-provision edge function `supabase/functions/tenant-provision/index.ts:413` passes `p_email` on the mainline signup path**). Doubles as signup idempotency key (`team_by_email` :3007). Consumers: abuse owner-notify (`abuse.py` `_team_email`), provision COALESCE (0010:90, keyless:92), `team_by_id` + `/v1/team`, `oauth.py:500`, registry `Team.email` parity.
- **User anchor** — `team_memberships.user_id` (Supabase uuid, NULL for anon) + GoTrue `auth.identities` (the per-user credential store ALREADY exists). Password capability is a third signal (`auth.users.encrypted_password`; GoTrue admin API does NOT expose it — #2085: `updateUser({password})` creates no email identity row).
- **`api_keys.created_by`** — mixed attribution: uuid (session mints), `anon-*`/`reg-*` (provision/register), `st_` (agent signup), client-supplied, raw email (registry), NULL (bootstrap).

**Deliverables (full):** (1) profile page — add GitHub/Google/email+password login methods over time; (2) dashboard recovery banner for single-login-method users → routes to profile page; (3) `teams.email` demoted to a team contact field (identity anchor removed).

## Decision (solution-converge, 2 independent agents agreed; user approved full scope)

**SERVER-AUTHORITY core.** Gates live server-side because that's where the login-method floor can be made atomic, re-auth enforced, and audit kept. No phase-slicing: banner, profile, linking, unlink, and the `teams.email` demotion ship together.

- **`GET /v1/user/identity`** — server-computed inventory → banner + profile method list. Response includes `linking_available` (server-known manual-linking state) — **the banner never renders when manual linking is off** (never promises add-methods that can't work; P7-fix).
- **Linking** (add-OAuth, add-email+password) + **unlink** with atomic floor (permit-reservation).
- **`teams.email` demotion** (in scope): drop `uq_teams_email`; identity flows (claim Step-6, onboarding PATCH) never write `teams.email`; signup idempotency re-anchored on the deterministic `reg-<sha256(email)[:12]>` membership identity; consumers re-pointed; `teams.email` retained as an optional team contact field (column kept).
- **Invariant (always):** identity flows never write `teams.email` (design + pytest static-assertion guard — repo precedent, not a new workflow).
- **Login-method floor semantics:** floor = strict login methods; API keys are a separate "Dashboard credentials" tier, NEVER counted (a key can't recover a forgotten password).
- **No username:** users identified by unique ID + email; invites via email/GitHub. `display_name` machine-sync (#1691) unchanged.

## Architecture & Key Flows

### Inventory, banner, profile

```
auth.identities ──(service-role RPC)──┐
auth.users (encrypted_password, email_confirmed_at) ─┤-> user_identity_inventory RPC ─> GET /v1/user/identity ─> banner.show + linking_available + profile
api_keys.created_by (filtered) ───────┘      (SECURITY DEFINER, service_role-only)
```

- **`user_identity_inventory(p_user_id)`** SECURITY DEFINER RPC (pgTAP-testable; schema-coupled to `auth.users` — NOT GoTrue-version-independent). Returns `(provider, provider_id, email_confirmed_at, has_password, keys_tier, login_methods, banner.show)`.
- **login_methods formula (P7-fix — THE critical predicate, DA-verified):**
  - `has_password := (encrypted_password IS NOT NULL AND encrypted_password <> '')` — **OAuth-created users have `encrypted_password = ''`, so `IS NOT NULL` alone is a phantom-password bug** (overcounts → suppresses banner for at-risk users AND over-grants the unlink floor → lockout).
  - `email_method := (auth.users.email IS NOT NULL AND auth.users.email_confirmed_at IS NOT NULL) OR has_password` — **recovery-capability signal off `auth.users.email` + `email_confirmed_at`, NOT the email identity row (P7-cycle-2 pre-committed fallback):** recovery works off the confirmed user email regardless of whether GoTrue created an `email` identity row; the identity-row conjunct would false-positive the banner for a fully recoverable user if staging check (b) = NO. Confirmation source pinned to `auth.users.email_confirmed_at` (auth.identities has NO such column; OAuth verification lives in `identity_data.email_verified`).
  - `login_methods := count(identity rows WHERE provider NOT IN ('email')) + email_method`.
  - Staging checks (ship blockers): (a) OAuth-only user's raw `encrypted_password` value; (b) whether GoTrue creates an `email` identity row for unverified-OAuth-email signups; (c) hosted `CreateEmailIdentityOnPasswordSetEnabled` state. Tests for all three shapes (OAuth-empty-password, unconfirmed-OAuth-email, password-only #2085).
- **Banner:** renders iff `login_methods <= 1 AND NOT (email confirmed AND has_password)` (P7-fix — safe email+password users don't get false-positive banners) AND ≥1 method AND non-anon team AND inventory fetch succeeded. Never for anon teams (#1148 Protect covers) or keyless anon (#1716). Fail-closed on fetch error. **`linking_available=false` (cycle-2):** banner STILL renders in promise-free form — "Your account is protected by only one login method. Still stuck? Contact hello@premiselabs.co" (TTL-dismissible, no add-methods promise) — never leaves at-risk users with zero surface. `linking_available=true` copy (existing voice): **"Your account is protected by only one login method — add another (Google or email+password) so you can always get back in."** Unconfirmed-email case: "add a login method — or add a confirmed email so you can always recover." **Inventory refetch rule (cycle-2):** every successful mutation (link/unlink/email-confirm) refetches inventory; banner + list refetch on window focus (kills confirm-in-another-tab staleness).
- **RecoveryBanner component** (P7-fix): `.recovery-banner` variant of the `protect-banner` family (NOT the transient inline `.banner` div — :2624 is green/in-memory ✕, wrong family for a persistent security notice). Dismissal (cycle-2): **conditional on actionability** — actionable (confirmed-email single-method, linking on): no-dismiss; NOT actionable (unconfirmed email): TTL-dismissible (`tt_recovery_dismissed` + TTL) + contact-support copy. **Unconfirmed-email affordance (cycle-2):** "Resend confirmation email" button on banner/profile (GoTrue resend; audit + rate-limit) — without it the banner is a permanent unactionable trap; staging check: confirm → banner clears end-to-end. Stacking rule concrete (cycle-2): recovery banner renders ABOVE transient banners; invite/suspension dismiss does NOT dismiss recovery; recovery persists until actioned/dismissed. `role="region"` + `aria-label`, keyboard-reachable CTA, flex-wrap on narrow viewports, no new motion.
- **Profile placement (P7-fix, cycle-2 DECIDED):** **Profile = a 6th nav tab** — resolves the placement-vs-return-contract contradiction; keeps the OAuth-return + banner-CTA deep-link on the existing tab state machine (`setTab('profile')` works as written). Cost accepted: nav-overflow at narrow widths → horizontal-scroll/ellipsis nav + <768px no-horizontal-scroll e2e (375px precedent test_legal_pages.py; note Billing IS in the nav — the #1689 precedent is the Setup button at header-right :2650-2652). Account-blob stays Switch team + Log out only. (writing-plans may revisit blob-placement if overflow proves worse — record decision.)
- **Shared `AddLoginMethodButtons` component (P7-fix):** the add-method UI (3 buttons + collapsible email+password form + busy/error states) is already duplicated verbatim in the claim card (:2153-2202) and Protect screen (:2240-2286); the profile would add a third copy. Extract once, handlers as props (claim: signInWithOAuth+POST /v1/claim; profile: link-intent+linkIdentity; email: /v1/claim/email vs updateUser). Copy family: "Connect GitHub / Connect Google login" (attach semantics — claim/protect family, `.claim-actions`).
- **Profile states** (P7-fix): `membersStatus` convention (status-classified, not booleans); inventory background-hydrated (#1567 — don't block chrome); retry affordance on error; method list shows provider, email, confirmation status (accessible text), #1511 "Last used" pill via shared `getLastAuthMethod`; API-keys tier displays `key_prefix`/labels ONLY — never plaintext (keys table discipline :2948-3000); unlink via `window.confirm()` with consequence-bearing copy; manual-linking-off state reuses "Still stuck? Contact hello@premiselabs.co".

### Linking (add-OAuth, add-email+password)

- **Precondition:** hosted `enable_manual_linking` ON (ops runbook). Local `config.toml:173` stays `false` — local tests cover fail-closed + inventory/banner; the WORKING linked flow is verified staging-manual (already a ship blocker; align wording). **Error-code matching, never status:** `manual_linking_disabled` = **404**; `single_identity_not_deletable` = **422**; `identity_already_exists` = **422**; `email_conflict_identity_not_deletable` = **422**; link/unlink re-auth = **`reauthentication_not_valid` 422**; `reauthentication_needed` 400 = password-update path only. Fail-closed UI when disabled.
- **Re-auth gate (P7-fix — mechanism chosen, DA-verified):** gate = **real sign-in within `REAUTH_WINDOW`** using `auth.users.last_sign_in_at` (updated only by actual `signInWithPassword` / provider sign-in). **`reauthenticate()` is NOT used** — verified: it is `GET /reauthenticate`, emails an OTP nonce, does NOT verify the password, does NOT update `last_sign_in_at`; it does not compose with the freshness gate (vacuous-or-broken). OAuth-only users (no password): re-sign-in via provider to refresh `last_sign_in_at`. Optional OTP-grade proof (if wanted): collect the emailed nonce + verify via GoTrue `/verify` before link-commit — separate step, not the gate. Applied to BOTH link-intent and unlink. `reauthentication_not_valid` → client "Sign in again to continue" → **reusable re-auth dialog (cycle-2):** password field → `signInWithPassword`; provider buttons → OAuth round, **same-provider enforced** (a different provider with private/unverified email auto-links a NEW user + placeholder team → account split); link-commit detects `auth.uid` mismatch → "signed in as a different account — sign out and retry" instead of generic 422; re-auth return uses the same flowId-scoped sessionStorage marker pattern → auto-resumes the pending action or lands back on profile with "Sign in refreshed — try again".
- **Add-OAuth:** client executes vendored `linkIdentity({provider})` — REDIRECT flow (PKCE flowId, NOT popup) — after server `link-intent` (HMAC-signed nonce, TTL 120s, replay-safe `link_intents` table, RLS service_role-only, per-IP rate-limited — claim shape). **The vendored client's storage MUST be wired to the parent-domain cookie adapter** (`sb-tortoise-auth-token`) or the post-redirect return lands on the login wall (#1225 bug class) — extend `tests/test_cross_subdomain_cookie_sync.py`. Post-redirect resume contract (P7-fix): flowId in `redirectTo` search params; **flowId-scoped** sessionStorage marker (two concurrent flows can coexist at SDK level — PKCE verifiers are per-flowId); return handled in the MOUNT EFFECT (mirror claim-flow :875-925: detect marker → `setTab('profile')` → `history.replaceState` strips params → stale markers cleared silently — preserve SEARCH, never hash); expired-intent → silent clear. TTL vs slow mobile round-trip (P7-fix): on link-commit with expired intent, still verify identity ownership + provider + confirmed-email and return a specific **"already linked — refresh your profile"** state (audit it) rather than generic error — or TTL ~10 min + sweep.
- **`link-commit`:** verify intent + identity row NEW since intent + belongs to session user + provider matches + `email_confirmed_at` set + adoption signal (identity email matches another team's `teams.email` → surfaced with enumeration-safe copy "this email may already be in use" + audited, NEVER automated; note the signal degrades post-demotion as teams.email goes stale) → audit `identity_link`.
- **Add-email+password:** NEVER admin-create (handle_new_user placeholder splits accounts). **Branch on `email_confirmed_at`, NOT email presence (cycle-2):** confirmed → `updateUser({password})` alone; unconfirmed or absent (GitHub private) → change-email + confirmation + set-password — branching on presence alone leaves an unconfirmable address with permanently dead email-recovery and a confirm-loop banner. Handle `double_confirm_changes` (config.toml:244 — old unverified email must not block via mail-to-nowhere). Adoption signal ALSO runs on change-email (P7-fix). Staging check (c) extended: unconfirmed-old-email change-email case. Map `email_exists` 422. OTP rejected as PRIMARY (account-confusion); OTP degrade only when target email verified unclaimed. #2085 by design: password adds no identity row — `has_password` is the tracked signal; verify deployed GoTrue at staging. Post-impl verification: signOut → `signInWithPassword` → same `auth.uid`.

### Unlink (permit-reservation — atomic floor)

GoTrue's native floor (`single_identity_not_deletable` 422 when `len(identities) <= 1`, atomic) makes ZERO-login-methods unreachable through GoTrue. The permit-reservation enforces the STRICTER product floor — "never below **2** login methods" (`reserve_unlink`: ONE SECURITY DEFINER transaction, `INSERT INTO user_unlink_permits SELECT … WHERE (login_methods - pending_permits - 1) >= 2 AND identity belongs to user` — **post-unlink state >= 2, P7-cycle-2-fix**: without the `-1`, at login_methods=2 the server grants a floor-violating permit (2→1) and at 3 two tabs BOTH get permits (3→1)). Tab A at 3: 2>=2 granted; Tab B: 1<2 → 409. Client disable rule stays `login_methods - 1 < 2` — now consistent. Server performs GoTrue `DELETE /user/identities/{id}` forwarding THIS request's validated session token (bounded BFF, never stored), post-state verify `login_methods >= 1`, consume permit, audit `identity_unlink`. `single_identity_not_deletable` surfaced explicitly ("add another login method first") — NOT misclassified as reauth. **Stale-permit double-unlink (cycle-2):** second DELETE → GoTrue 404 → benign "already unlinked — refresh your profile" (same family as expired-intent), audited. **Confirm dialog (cycle-2):** `window.confirm()` naming the provider + post-state ("Remove GitHub login from your account? You'll still have Google + email/password to sign in."); Remove gets AddLoginMethodButtons-style busy/error handling (multi-hop permit + DELETE). **Compensate the permit on every GoTrue failure path** (retries don't deadlock on `UNLINK_IN_PROGRESS`); sweep only for crash windows, sweep TTL > GoTrue HTTP timeout (15s). Per-IP rate-limited (link-intent too — stolen-session OTP spam). **429 UX (cycle-2):** "Too many attempts — try again in a few minutes", same error channel. Requires `enable_manual_linking` (route middleware).
