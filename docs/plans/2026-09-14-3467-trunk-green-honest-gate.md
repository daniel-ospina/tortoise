> **For Pi:** Use `executing-plans` to implement this plan task-by-task. **Execution order is the table in §Execution order, not the task numbers.**

**Goal:** Make `main` green and make the required CI gate something an author can act on — **so ordinary (non-`--admin`) merges become possible again**, and CI returns to being boring.

**Architecture:** Three independent defects are stacked, and they must be separated or the fix will not hold:

1. **The ratchet (#3467):** `main` is red *and* `python-ci-gate` (the AND of every shard) is required, so **while the trunk is red the aggregate is red for the large majority of PRs — 32 of 41 on 2026-09-15. It is NOT "no PR can ever be green": 7 of 41 carry `python-ci-gate` SUCCESS, so the earlier wording was too strong.** → merges reach for `--admin` → an `--admin` merge cannot distinguish "already red on main" from "new failure" → red accumulates. Live instance: PR #3420 merged with its own tripwire test failing. *(Corrected 2026-09-15: `test_markers` is **no longer** red on `main` — it appears only in the 2026-09-13 failing set, so this step's earlier claim that it is "red on `main` today" had gone stale. Also corrected: the trunk red count is **falling** (~16 → 5), so the ratchet is a **historically demonstrated** mechanism, not a currently-growing trend. See §Post-scoping corrections.)*
2. **An unsound comparison:** the isolation layer (`ci-failure-set.sh --diff`) compares the PR's failing set against a union of main's. But the PR lane runs a **diff-gated subset** (`"full": false`, surfaces `[api, core]`) while the main baseline runs the **full** set (`"full": true`). **The defect, stated correctly (cycle-13 fix — rewritten, not annotated; the earlier text asserted the backwards mechanism as fact and then contradicted it two sentences later in the same paragraph):** `unique = observation − baseline`, so the failure condition is **a baseline that is not a saturated superset of the same lane's failures**. A baseline that is *smaller* than it should be manufactures false uniques; a baseline that is *larger* is safe. The requirement is therefore the **lane** (already enforced by the filter) and the **union over N runs** (already shipped) — never a population match. This is a design defect, not a symptom of the red trunk

   > **⛔ CYCLE-9 CORRECTION — the remedy named above was WRONG, and every downstream task inherited it.** Because `unique = observation − baseline`, **removing entries from the baseline can only ADD uniques**; it can never remove the false uniques this defect is about. The defect is real but it was **mis-diagnosed as a population problem**: the live false uniques came from a **single-run baseline** (main failing one of two order-dependent siblings per run — **tortoise #3458**, which names both `test_import_wrong_key_422` and `test_import_count_mismatch_422`; *the parser header mis-cites this as "tortoise #3469", which is an unrelated merged docs PR — see §Post-scoping corrections*), and the shipped remedy is the **union over N runs**, a **superset**, plus the **lane filter**. **No population rule was ever required.** The correct statement of the defect is therefore: *a baseline that is not a saturated superset of the same lane's failures*. See Task 11 Step 1 for the set algebra, the two unsound directions, and the deletion of the rule.
3. **Step-gates that fail on main:** `redislite server leak: 7 orphans after suite, threshold 6` on main; `73/120/126/174` (threshold 12) on PRs. Three independent orphan step-gates exist (fast, slow, carve-out) — see below — and any of them can keep the gate red on its own.

## Scoping amendment — 2026-09-15 (`issue-scoping`, Phase 5–5.5)

**Why this section exists.** `plan-review` was stopped by operator instruction at cycle 16 as a human-authorized **escalation exit** (recorded in `operations/logs/cycle-status.yaml`, `clean: false`). **Tier: Standard, not Complex — documented, not assumed.** The Complex extras buy independent exploration the plan already bought sixteen times over; the deciding factor was that the *approach* question, not the *detail* question, was unverified. The verifier's own finding — that the recommended correction survived adversarial reproduction on real pytest 8.4.2 output — is the evidence that Standard depth was sufficient here.

**Phase 5 decision — Approach 1, the monotone node-id ledger.** Chosen over Approach 2 (verifier-recompute only) and Approach 3 (require evidence of *passing the same code*, i.e. a real merge queue). Rationale: the unsound predicate is **negative** (`unique to this PR: 0`, reached by absence), and `admin-merge.sh:103-129` already forbids that polarity — *"BLOCK unless its condition is AFFIRMATIVELY true"*. Approach 2 hardens the negative predicate without changing its polarity; Approach 3 would false-block essentially everything at today's queue state. Approach 1 is a **derivation from the file's own stated doctrine**, and it closes a class the counters structurally cannot: a node-id that *vanishes* from a re-run leaves `extracted == examined`, `truncated=0`, and still merges.

**Phase 5.5 cycle 1 — NOT CLEAN: P0 closed, 2×P1 opened by testing the fix.** Verdict: `2 P1 · 2 P2 · 1 P3`, all applied in one pass.
