# #3963 — capture is session-end-only: durable spool + idempotent replay + incremental cadence

**Goal:** an interrupted, killed, or laptop-closed session is still filed on the
next opportunity, and no loss path is silent.

**Tier:** Standard (bug, capture path). **UX_RATING:** low. **ONTOLOGY_RATING:** low.
**ARCH_RATING:** medium (a new local durability layer on two capture legs).

**Scope boundary:** capture *reliability* only. Extraction quality (Objective 2) is
explicitly out of scope.

## Root cause (confirmed)

Capture was a single `SessionEnd` / `session_shutdown` network call. That construct
is structurally best-effort: Claude Code's `SessionEnd` has no decision control and
a ~1.5 s default timeout after which the hook is **cancelled** (a measured run took
9.26 s — #3754), and stop-hooks **do not fire on user interrupts**. The transcript is
already durable on disk during the session, so an interrupted session loses the
**filing**, not the data. The fix is therefore a **local spool + idempotent replay** —
not "save more often" alone.

## Cadence: cheap capture per turn, costly extraction deferred

- **Cheap capture — every `turn_end`.** Each turn appends only the NEW turn(s) to a
  local write-ahead log. The append is O(new turns), so nothing is re-uploaded
  per turn. (The snapshot handed to the spool is the harness's own O(conversation)
  read — our added tax is the append, not a session-sized rewrite.) No network.
- **Costly filing — deferred to the first opportunity after the session is no longer
  live:** `session_start` (a later session replays an interrupted one), `agent_end`
  for a *different* session, and `session_shutdown` as the **final flush**.

The field converges on per-turn capture with deferred extraction; no product ships a
product-defined "every N turns" constant, so **there is no N here** (research §c.2).

**Why the live session is deliberately never filed mid-conversation:** the server
upserts on `session_id` and replays a succeeded session as a no-op. Filing a growing
conversation would freeze the capture at that snapshot and silently drop every later
turn — trading one silent loss for another. The snapshot is durable after every turn;
only the *filing* waits.

## The spool

- **Location:** `~/.tortoise/capture-spool/` (`TORTOISE_CAPTURE_SPOOL_DIR` overrides).
- **Shape:** per session, `<entry_key>.meta.json` + `<entry_key>.turns.jsonl` — an
  **append-only** turn log, so a growing session rewrites nothing.
- **Bounded by COUNT *and* BYTES** — three ceilings: `max_entries` (1000),
  `max_total_bytes` (256 MiB), `max_entry_bytes` (16 MiB). Eviction is **oldest-first**,
  never the entry just written. The per-entry ceiling must exceed the **server's own**
  legal maximum, or a legal capture is discarded as oversized: 500 turns × 5000 chars ×
  up to 4 UTF-8 bytes/char ≈ 10 MB, plus the envelope. (A 4 MiB ceiling — the first cut —
  silently discarded legal CJK sessions whole; the review caught it.)
- **⛔ NOT a TTL.** #3870 (owner) ruled the local capture spool is type-2 user data
  kept **until the user deletes it**, and that a TTL / max-age / "prune after N days"
  **contradicts** that ruling. A count or byte bound is a *size* bound, not a clock.
- **Every discard is recorded** — a reason + detail line appended to
  `discarded.jsonl` (`entry_too_large`, `spool_count_exceeded`,
  `spool_total_bytes_exceeded`, `corrupt_entry`, `transcript_empty`,
  `permanent_http_<status>`). No silent drops.

## Idempotency key

`session_id` remains the **server's** upsert key. On top of it the client derives a
content-addressed key:

```
capture_key = sha256( session_id \0 sha256(canonical(turns)) )
```

- Stable across replays → an already-filed identical snapshot short-circuits before
  the network (ONE POST, ONE session).
- Distinct when the conversation changed.
- It is the same key that makes #3713's in-flight `409` benign: the 409 is
  **retryable**, so the retry replays rather than losing the write.

## Failure policy

| Condition | Action |
|---|---|
| network / timeout / 5xx / 3xx / 408 / 425 / 429 | defer, exponential backoff (30 s → 6 h cap) |
| `402` — **every** 402 | defer (#4714) — the hosted quota gate refuses a capture whose *estimated* point cost would cross the org cap, and that estimate is computed from the **incoming** capture, so the identical capture succeeds once a node is freed or the tier changes. Classifying it permanent made `_discard_entry` unlink the spool's only copy. Prose is not matched — the client ships independently. |
| `409` — **every** 409 | defer — a retry replays (#3713 in-flight) or succeeds later (recording was briefly disabled); a capture is never destroyed by a policy state the user can reverse. The server's prose is deliberately **not** matched — the client ships independently of the server. |
| any other 4xx | **discard + record the reason**, never retry |
| over count/byte bound | **evict + record**, oldest first |
| filesystem write / mkdir failure | **discard + record** (`spool_write_failed`) — a full disk is a loss, and a loss is never silent |

**The compare-and-swap is against the POSTED content, not the meta.** The
on-disk turn log is re-read after a 2xx and compared (by digest) with the turns
that were actually POSTed. Comparing meta-to-meta was wrong: a writer killed
between its log append and its meta write leaves the meta digest stale, so the
check passed while an unposted turn was marked filed forever. (Review cycle 3,
P2.)

**Write-back is a compare-and-swap, not a blind write.** A `turn_end` (or a resumed
session, or a cross-process drain) can grow an entry while its POST is in flight;
stamping the pre-POST snapshot back would mark the NEWER turns filed under the OLD key
and the next flush would skip them forever. On success the `filed_key` is stamped only
when the on-disk digest still equals the posted digest; on a transient failure the
write-back merges into the **current** on-disk entry. (This was the review's P0.)

**The turn log is append-only, but the append is only taken when the log ends at a
record boundary.** A process killed mid-append (exactly the interruption this spool
exists for) leaves a partial line; appending to it would FUSE the next turn into the
garbage tail, the tail would be skipped on read-back, and the meta digest would still
cover the lost turn — a silent, unrecoverable loss. A torn tail forces a full rewrite
from the snapshot. (Review cycle 2, P1.)

**The live session is never filed at `session_start` either.** On `/reload` Pi emits
`session_shutdown{reload}` (skipped) then `session_start{reload}` for the SAME session
that `turn_end` just spooled; filing it would make the server replay it (extraction
skipped) and stamp `filed_key`, so every post-reload turn is stored but never
extracted. `session_start` drains OTHER sessions only. (Review cycle 2, P1.) The
**Claude leg** has the same hazard, because `session-start.sh` → `tortoise session
drain` and `--resume` / `/clear` / a compaction all reuse the session id: the hook
reads `session_id` from its stdin JSON and passes `--exclude-session-id`, so the
drain holds the LIVE session back (reported as `held back N`, counted separately
from `skipped N`) for its own final flush. (Review cycle 4, P1.)

**A session that arrives without a `--session-id` is addressed by its TRANSCRIPT
PATH, not its content.** A content-addressed id changes on every snapshot of a
growing conversation, so the per-turn `session spool` created one entry per turn —
filed as N sessions and N server-side extractions. `_local_session_id()` = stem
(≤240 chars) + `"-"` + `sha256(resolved path)[:12]` = 253 chars: stable across
snapshots, and still distinct for two transcripts that share a basename. (Review
cycle 4, P2.)

**`session spool` needs no credentials and no config.** It is dispatched before the
config resolver and the `api_key` gate — the cheap capture is local, so a
local-only install (and a corrupt `credentials.json`) must not turn the mechanism of
record into a silent no-op. (Review cycle 4, P2.)

**An unreadable turn log is a recorded discard on BOTH legs.** The Python leg
guarded the read; the Pi leg did not, so `readFileSync`'s `EISDIR`/`EACCES` escaped
`readSpoolTurns` and aborted the whole flush loop — one corrupt entry permanently
wedged every session sorted after it, with no ledger line. Both legs now return `[]`
and record `transcript_empty`. (Review cycle 4, P1.) The ENCODING half is the same class one door over: `UnicodeDecodeError` is a `ValueError`, NOT an `OSError`, so it escaped all three Python read guards (`read_spool_turns`, `read_spool_meta`, `list_spool_metas`). That is not theoretical — a killed partial append writes a torn multi-byte character (turns are stored raw UTF-8 for CJK/emoji), which crashed the per-turn `session spool` with a traceback and wedged the drain with NO record, losing the filing of every session sorted after it. All three clauses now include it, and a corrupt-typed meta FIELD cannot crash the ordering or the backoff read either (`str(...)` coercion in `_age_key`, a guarded `_backoff_ms`). (Review cycle 8, P1/P3.)

**A malformed HTTP response defers; it does not abort the drain.**
`http.client.HTTPException` (`BadStatusLine`, `IncompleteRead`, `LineTooLong`,
`InvalidURL`) derives from `Exception`, NOT `OSError`, so a proxy/LB with a malformed
status line escaped the transport wrapper and killed the drain loop. It is now a
`status=None` deferral. (Review cycle 4, P2.)

**An unlistable spool is RECORDED, never reported as an empty one — at BOTH levels.**
`Path.is_dir()` is `True` for a mode-000 directory and `Path.glob`/`readdirSync`
SWALLOW the EACCES its `scandir` hits, so the listing looked empty: the drain
reported "nothing to file" forever for a spool it could not read, with no ledger
line (and the Pi leg threw out of the whole flush). Both legs now list with an
error-surfacing call (`os.scandir` / a `try`-wrapped `readdirSync`) and record
`spool_unreadable`. (Review cycle 5, P2.) The ROOT is the second level and the
nastier one: `Path.exists()` itself RAISES `PermissionError` when a parent lacks
traverse permission (so the pre-check crashed `session drain` with a traceback on
the Python leg), while `existsSync` returns *false* (so the Pi leg reported an
empty spool with no record). `exists()`/`existsSync` are therefore gone from the
listing path entirely: absent-vs-unreadable is decided by the listing call itself
(`ENOENT`/`FileNotFoundError` = fresh install, any other `OSError` = recorded).
(Review cycle 6, P1.)

**An unreadable / non-UTF-8 transcript is recorded, and `session spool` still
exits 0.** The per-turn mechanism of record must not raise a traceback out of
`UserPromptSubmit` — an EACCES or a non-UTF-8 byte was an uncaught
`PermissionError`/`UnicodeDecodeError` (exit 1, no record). It is now a
`transcript_unreadable` ledger line, on stderr, exit 0. (Review cycle 5, P2.)
There is deliberately no `transcript_path.exists()` pre-check either: `exists()`
RAISES on a non-traversable parent directory, so the pre-check was itself the
exit-1 path. `FileNotFoundError` from the read is "not found" (its own message),
every other failure is the recorded loss. (Review cycle 7, P2.)
`session spool` also no longer returns 1 when an entry is discarded as
over-bound: the documented contract is exit 0, and a caller must not read a
completed capture as a failure.

**`session drain` exits 0 even with no config, or a corrupt one — and whatever else
goes wrong.** It is backgrounded from SessionStart, so it resolves its own config
best-effort (`_cmd_session_drain_best_effort`) and reports "nothing to file"
instead of surfacing exit 1. (Review cycle 5, P3.) The wrapper carries ONE blanket
`except Exception` → exit 0 around EVERYTHING, the config resolver included: a
backgrounded SessionStart hook must never crash, and the resolver can itself raise
something that is not `_ConfigError` (`Path.is_file()` on an unreadable
`~/.tortoise` raises `PermissionError`). (Review cycles 6 and 7, P1/P2.)

**The per-turn hook passes the capture's stderr through.** Its stdout must stay
empty (it is injected into the user's prompt), but swallowing stderr too meant a
silently-failing capture — a wrong interpreter, an unreadable transcript — was
indistinguishable from a healthy one, which is the very failure #3963 removes.
(Review cycle 5, P3.) The hooks ALSO carry a `-f` pre-check and their own conversion, so fixing the CLI was not enough: `-f` is FALSE for an unreadable file or a non-traversable parent, and the conversion swallowed the read error — together they skipped the turn (and every later turn of that session) with no spool write and no ledger line, making the CLI's new `transcript_unreadable` classification UNREACHABLE on the Claude leg. Both `session-turn.sh` and `session-end.sh` now attempt the read, treat `FileNotFoundError` as "nothing yet", and on any other failure append a `transcript_unreadable` line to the same `discarded.jsonl` (schema mirrors `record_discard`) before exiting 0. The conversion's own catch has the same
encoding door as the Python readers — `except OSError` does NOT catch
`UnicodeDecodeError` — so it catches `(OSError, UnicodeDecodeError)` too: a torn
byte in a real transcript is precisely what a kill mid-append leaves, and it was
reproduced escaping the hook as an uncaught traceback with no record. (Review
cycle 8, P2 + the cycle-8 VGATE pass.)

**A discard records its reason BEFORE it removes the entry files.** The ledger line
is the contract ("never a silent drop"); unlinking first left a SIGKILL / ENOSPC
window in which an unfiled capture was deleted with NO record. A leftover entry
behind a record is at worst a duplicate line, which an audit can reconcile; a
missing line cannot be. (Review cycle 4, P2.) This applies to EVERY discard path,
including `entry_too_large` — the one that deletes a *previously spooled* entry:
it now goes through `_discard_entry`/`discardEntry` rather than an inline
unlink-then-record pair, on both legs. (Review cycle 5, P3.)

**`session_start`/`agent_end`/`session_shutdown` are hooks; `tortoise session drain`
is the CLI replay.** `session-start.sh` runs it backgrounded so a large replay never
spends the SessionStart budget.

**Read-back returns exactly what is stored.** The meta's `turns_count`/
`content_digest` describe the store, so a role filter at READ time would POST fewer
turns than the entry marks filed. Non-conversational roles are excluded at CAPTURE
time (the same policy the Pi leg applies), and the exclusion is reported. (Review
cycle 2, P2.)

**Unwrapped transport failures defer, they do not crash.** urllib does not wrap a read
`TimeoutError`, `http.client.RemoteDisconnected` from `getresponse()`, or a non-JSON 2xx
body; all three become `status=None` (retryable) rather than escaping `flush_spool` and
killing the capture path. (Review cycle 2, P2.)

**Durable writes are `fsync`ed — including the per-turn append** (the path that
holds the most recent turns), and abandoned `*.tmp-<pid>` scratch files (which
match neither the meta glob nor the byte count) are swept by age — a temp is ours, not
user data, so this is a housekeeping sweep, not a data TTL. (Review cycle 2, P3.)

## Legs

- **Pi** — `tortoise/pi-hooks/tortoise-capture.ts` (+ `node --test` suite).
- **Claude Code / CLI** — `tortoise/capture_spool.py`, wired through three
  commands: `tortoise session spool` (the CHEAP per-turn capture — the
  `UserPromptSubmit` hook `session-turn.sh`, no network), `tortoise session
  capture` (write-before-upload; the SessionEnd **final flush**), and
  `tortoise session drain` (the replay opportunity, run best-effort and
  backgrounded by `session-start.sh`). SessionEnd is therefore no longer the
  mechanism of record — without `session-turn.sh` an interrupted Claude session
  would still spool nothing, which is exactly the loss #3963 removes.

### Adversarial Threat Surface

In scope: (1) a spool entry silently lost on a filesystem failure — closed by the
`spool_write_failed` discard; (2) a newer turn silently marked filed by a stale
write-back — closed by the compare-and-swap; (3) a capture silently destroyed by a
misclassified HTTP status (3xx, 409) — closed by the retry classification;
(4) a capture silently *unreachable* — an unreadable spool directory **or spool
root**, an unreadable turn log, or an unreadable transcript — closed by the
`spool_unreadable` / `transcript_empty` / `transcript_unreadable` records. This is
the class the cycle-4, cycle-5 and cycle-6 reviews each found a hole in (the log
file, then the `entries/` directory, then the root), which is exactly why it is
declared as a class and not as three point fixes.

Out of scope (declared): the **#3713 concurrent-producer** double POST. The server's
`session_id` upsert converges the result, so no duplicate session and no data loss;
producer-side election is a separate hardening.

Bound: the declared classes above are each closed by a test that REDs on a named
mutation. Findings OUTSIDE this declaration are follow-up issues by default, not
re-chased here; the full-diff `code-review` gate (its own 10-cycle cap) is what
drove cycles 1–4.

## Residual edge (untested by design)

**Concurrent producers on one host.** The in-process `inFlight` set and the
per-session `filed_key` are per-process; two *different* processes capturing the same
`session_id` can both POST. The server's `session_id` upsert converges them to one
session (and the second may see the #3713 in-flight 409, which is retryable), so
duplication is not possible — but the double POST is not prevented client-side. That
is the producer/`#3713` hardening, tracked separately; not re-solved here.

**Residual within this change (cycle 8).** After the cycle-8 fixes, the remaining `exists()`/unguarded-read surface is `read_discards` (Python) and `readDiscards` (TS) — diagnostics only, no capture path — plus `_sweep_stale_temp_files`, whose `glob` swallows EACCES by design (a temp file that cannot be listed is swept later). Every capture/flush/drain path now decides absent-vs-unreadable at the read/listing CALL, and the TS leg was already immune because all of its readers use a bare `catch {}`.

**Residual within this change (cycle 7).** Two diagnostic readers —
`read_discards` (`capture_spool.py`) and `readDiscards` (`tortoise-capture.ts`) —
still use an `exists()`/`existsSync` pre-check plus an unguarded read. Neither is on
the capture, flush or drain path (they are for tests and `discarded.jsonl`
inspection), so no captured turn can be lost through them; they are flagged here
rather than hardened, because wiring them into a capture path would re-open the
class this file just closed three times.

**Residual within this change (cycle 5).** In the Pi leg, the `entry_too_large`
branch's record-before-remove ORDER is verified structurally — it calls
`discardEntry`, whose ordering is asserted by its own test — while the Python leg
observes the order directly (module-level functions make the calls spy-able).
There is no in-process way to observe the TS branch's internal call order, so the
TS guarantee is "it uses the tested helper", not an executed assertion.
Behaviourally, that branch's discard IS asserted on both legs.

**Residual within this change (cycle 4).** The `discarded.jsonl` append itself is
best-effort (`recordDiscard`/`record_discard` swallow an `OSError` — a full disk must
not throw out of a capture path), so a discard whose *ledger write* fails on a full
disk is reported only on stderr. The ordering guarantee proven above is "the reason is
attempted before the data is removed", not "the reason is durable against ENOSPC".
Making the ledger a fsync'd two-phase commit is a follow-up, not a silent claim here.
