### Pattern Research

> **Findings date:** 2026-08-20
> **Library docs preflight (Sub-step B.0):** no context7 in this session's MCP catalog — library-docs lookup done via Perplexity web_search against sbert.net docs + huggingface.co/cross-encoder.

**Library version & API surface** (sentence-transformers `CrossEncoder`, pinned `>=3,<6` — 1 call; well-known pattern, proportional depth):
- Canonical: `CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")`; score pairs via `model.predict([(query, passage), ...])` — **`predict()` is the current API; `score_pairs` is deprecated/legacy** (v3+). Batches internally; `max_length` init param truncates at the **tokenizer level**.
- Competitor variance: MS MARCO cross-encoders return **logits** by default; `activation_fn=torch.nn.Sigmoid()` yields [0,1] scores. **Ranking is unchanged by the sigmoid** — only the MMR λ tradeoff needs the normalized scale (MMR mixes relevance with a [0,1] similarity).
- Known pitfall: model download happens at first use into the HF cache (HF_HOME/HF_HUB_CACHE) — the eval env must be online once, or the model pre-warmed; treat load failure as a **recorded degradation** (rerank off + reason in the report), never a run abort.

**Idiomatic usage patterns** (two-stage retrieval + MMR — 1 call; consensus pattern, proportional depth):
- Canonical: retrieve broadly → rerank precisely (Pinecone two-stage; OpenSearch rerank pipeline; LangChain `CrossEncoderReranker` in `ContextualCompressionRetriever`). Production heuristics: retrieve ~50 candidates, rerank to top-10 (bludiesel.ai).
- Competitor variance: graphiti ships 16 search recipes incl. RRF/MMR/cross-encoder rerankers (epic brief Tech Stack Research, 2026-08-20); the production pattern combines reranker output with diversity — `MMR_score(doc) = (1−λ)·rel − λ·max_sim(doc, selected)` applied **after** cross-encoder reranking (tianpan.co). This is exactly the epic's R6 shape: RRF → cross-encoder → MMR.
- Known pitfall: **reranking cannot fix upstream recall misses** — the rerank pool must be deep enough that the correct evidence is in it (hence the R6 deeper-pool decision, 2× today's 20).

**Library/framework pitfalls** (cross-encoder + MMR in RAG — 1 call; proportional depth):
- Canonical: reranking is a **precision stage, not a recall stage**; track recall@k so the reranker does not silently drop relevant docs (bigdataboutique; duncanleung).
- Competitor variance: reranking helps when recall is already high, hurts when low; query-distribution mismatch and shortlist misses are the failure modes (futureagi; RAG Cookbook 2026); CPU cross-encoder inference is fine for small pools (tens of ms at pool 40), a real constraint only for interactive large-pool systems (unrag.dev).
- Known pitfall: **query-passage ordering matters** (query first, passage second); λ=1 degenerates MMR to pure rerank (no diversity), λ=0 to pure similarity (relevance-blind); long chunks add latency (truncate at a char pre-limit + tokenizer `max_length`).

## Design Decisions

**D1 — The rerank stage lives in the eval retrieval layer, not the production engine.**
`tortoise/search_engine.py` + `sdk.tortoise_fts_query` are **untouched**. Rationale: (a) R6 is a run-calibration-dependent compounding layer, *measured* in the follow-up run (03-scope boundary rationale (c)) — the measured surface is S11 (the eval retrieval stack), which the issue itself names; (b) a cross-encoder in production `tortoise_fts_query` would change every consumer's latency + ordering with no calibration; (c) the `order_by="graph"` GraphRanker path in `sdk.tortoise_fts_query` (search the `GraphRanker` symbol — the graph-informed fusion rerank, #25) is a **different mechanism** — do not confuse or extend it here. If the follow-up run shows a win, promoting rerank into production search recipes is a separate issue (Open Questions).

**D2 — Off-path is byte-identical to the V3 baseline.**
When rerank is off: pool = `max(ks)` (20), **no rerank keys in the returned dict** (today's exact **8-key** shape: `question_id, hits, session_recall@k, turn_recall@k, evidence_recall@k, context_tokens, context_point_count, retrieval_latency_ms`), no extra queries. The only structural refactor is extracting the existing inline recall loop into `_recall_metrics` (identical math; the `evidence_point_count` Cypher already runs once, before the `for k in ks` loop — **no hoisting exists or is needed**). Byte-identity is trivially verified by the existing `test_longmem_runner.py` assertions. The rerank gate short-circuits before any rerank work (no `rerank.py` import side effects at module import time).

**D3 — Scorer resolution precedes pool deepening; degradation is genuinely byte-identical; the reader/context invariant holds on every path.**
`retrieve_for_question` resolves `get_scorer()` **before** choosing the pool depth: pool = `rerank_pool` (40) only when `rerank_on AND scorer is not None`; otherwise pool = `max(ks)` (20) and `rerank_pass.degrade_reason` is set. A degraded (load-failure) question therefore retrieves the same 20-pool as the baseline — no pool-effect contamination masquerading as a rerank result. **The invariant is two-case, stated precisely:** (a) non-applied paths: the pool-only arm and the score-failure/load-failure degrade paths **truncate hits to `top_k`** (`len(ret["hits"]) == context_point_count == min(len(pool), top_k)`), while the plain off-path (no rerank, no pool override) returns the full pool **untruncated** (`len(ret["hits"]) == pool size`, `context_point_count == min(len(hits), top_k)` — today's behavior, byte-identical; the two coincide at the defaults where `pool == top_k`); (b) the applied path → `rerank_hits` returns the **selected-only** reordered list, so `len(ret["hits"]) == context_point_count == selected_count ≤ top_k`. In ALL cases `context_tokens` is estimated over exactly the hits the reader consumes (`context_points`). `--rerank-pool N` is honored **when explicitly passed even with rerank off** (the pool-only isolation arm); the env default `TORTOISE_LME_RERANK_POOL` applies only while rerank is on.

**D4 — The R6 arm deepens the pool (40) and records a pool-coverage diagnostic.**
Cross-encoders reorder, they don't recall (pitfall finding). The R6 arm fetches `limit=40` (`rerank_pool`, default 2× the baseline 20) so the reranker has reorderable headroom. **Pre-registered interpretation:** the follow-up delta vs the V3 baseline is the composite **R6 recipe** (deeper pool + cross-encoder + MMR) — the scope note "MMR-vs-dedup tuning remains V5" keeps sub-knob sweeps out of this issue. `rerank_pass` records `pool_recall@k` (recall over the full 40-pool, pre-MMR) vs the selected recall — the gap is selection-loss, the 40-vs-20 lift is pool-effect. The pool-only isolation arm (`--rerank off --rerank-pool 40`) separates the two when the owner wants it.

**D5 — Cross-encoder only; LLM rerank is a documented future option.**
Scope says "cross-encoder/LLM rerank". Decision: cross-encoder only for R6 — deterministic, reproducible, ~tens of ms at pool 40 on CPU, zero provider cost (benchmark comparability; the LightMem lesson is about retriever *choice*, which must stay fixed across the compared cells). LLM rerank of the top-5 is noted in Open Questions as a V5 candidate (needs provider budget + pinning).

**D6 — `match_source` keeps leg provenance; the rerank pass is recorded additively, and the leg-mix bucket is a partition.**
E2E-1 (V3 gate set) requires `match_source` to record *which leg found the hit*, never null. E2E-10 (V4-conditional) requires *"match_source records the rerank pass"* + the scope's "rerank pass recorded in leg-mix". These reconcile as: **hits keep their provenance `match_source`** and gain additive flags `reranked: true` (cross-encoder moved the hit vs raw RRF order) / `mmr_promoted: true` (diversity raised it above its raw rank); the **leg-mix `rerank` bucket counts selection-loss only — the `mmr_dropped` hits** (which carry no provenance leg in the selected list), so the partition invariant **`sum(provenance legs) + dropped = pool_size`** holds — equivalently, the leg-mix dict including the `rerank` bucket sums to `pool_size` (matching Task 2's `pool_size = len(selected) + dropped`). `reranked`/`mmr_promoted` movement is a separate overlay metric, not a leg bucket — never double-counted. The per-question `rerank_pass` record carries the stage stats. Rejected alternative: rewriting `match_source="rerank"` — it would destroy leg attribution (E2E-1) and break the leg-mix sum.

**D7 — MMR: hard per-session cap + scale-consistent similarity; truncation in one place.**
`MMR(d) = λ·rel(d) − (1−λ)·max_{s∈S} sim(d, s)` (greedy), with a **hard per-session cap** (`per_session_cap=2`, E2E-10 "≤1–2") — a candidate from a session already at cap is skipped. `rel` = sigmoid(cross-encoder logits) ∈ (0,1). `sim` = **`(1 + cos)/2`** over the point `embedding` property (normalized to [0,1] so cosine and Jaccard share a scale — a mixed-availability pool must not distort the λ tradeoff); per-pair fallback to **Jaccard token overlap** when either side lacks an embedding **or the dimensions mismatch** (embedder drift — fallback, never a crash). Embeddings arrive from FalkorDB as round-tripped float lists (follow the existing stored-embedding fetch pattern in `sdk.py` — search the `np.asarray(emb` round-trip; no custom vecf32 decoder; the storage format is fragile per the `vecf32(` write comment). Hits with an **empty `session_id` are exempt from capping** (each treated as its own group). Char pre-truncation (`RERANK_TRUNCATE_CHARS=2048`) lives in `rerank_hits` so BOTH scorers exercise it; `CrossEncoder.max_length=512` is the tokenizer-level backstop. `λ=0.7`, `cap=2` pinned — knob sweeps are V5.

**D8 — Real-model failures degrade to rerank-off with a recorded reason, and transient failures are cached with a short TTL, never pinned.**
(a) Load failure → `degrade_reason` set, 20-pool fallback (D3), report records the degradation (M4 retry-then-fix posture). (b) **Failures are cached with a 60s TTL** (`_fail_cache`): a persistent outage is re-attempted at most ~1/min per question, not 500×/run — the hub is not hammered; successes are cached permanently. (c) **Score failure** after a successful load — including a length-mismatched result — is guarded inside `rerank_hits` (try/except around `score()`) → same degrade contract, never a per-question failure. (d) The follow-up harness **pre-warms** the scorer in `run_main` — **gated on the effective rerank being on** (a baseline run must never load the ~90MB model — D2/Gate 7) — and records `model_load_ms` once in the report config; the cold-cache download never lands inside a question's `rerank_latency_ms`. **A pre-warm failure does NOT disable the run**: per-question `get_scorer` TTL-retries continue (b).

**D9 — Checkpoint/resume never blends arms; stale pre-R6 checkpoints remain resumable under baseline configs only.**
The R6 arm **requires a fresh checkpoint** (run protocol: the follow-up is a new run against the V3 baseline report — not a resume of it). `run.py` records the **full effective config** `{rerank_enabled, rerank_pool_applied, per_session_cap, mmr_lambda, rerank_model}` — **`rerank_pool_applied` is the EFFECTIVE APPLIED pool** (the `max(ks)`-adjusted value, matching the report's `pool_size`; a plain baseline run records 20, never the nominal env default 40). Resume is **three-valued**: (a) no rerank config key in the checkpoint (genuinely pre-R6) → ALLOWED **only when the effective config is baseline** (rerank off, default pool — baseline checkpoint resumes stay a supported protocol path; **note: once M7's checkpoint fingerprint gate (git_sha + config + prompt, E2E-2) lands with the V3 build, pre-R6 checkpoints are refused by M7 regardless — D9(a) applies only while M7 is absent**); a pre-R6 checkpoint resumed with `--rerank` or a non-default pool is **REFUSED** before any question executes (it would silently blend un-reranked baseline outcomes into an R6 report — Gate 8's exact hazard); (b) config present and equal → allowed; (c) config present and different (incl. an applied-pool change) → refused with the same clear pre-loop message. The report's rerank aggregation is `.get()`-safe so a stale pre-R6 checkpoint can't `KeyError` the build.

```python
def test_mmr_select_promotes_relevant_over_near_duplicate():
    # 3 candidates: d0 exact evidence, d1 near-duplicate (high sim to d0), d2 unrelated
    scores = {0: 0.95, 1: 0.90, 2: 0.10}
    sims = {(0, 1): 0.98, (0, 2): 0.2, (1, 2): 0.2}
    sessions = {0: "s1", 1: "s1", 2: "s2"}
    selected, dropped = mmr_select(
        scores, sims, sessions, top_k=2, per_session_cap=1, lambda_=0.7)
    assert selected == [0, 2] and 1 in dropped  # near-duplicate suppressed

def test_mmr_select_enforces_per_session_cap():
    scores = {i: 1.0 - i * 0.01 for i in range(6)}     # 3 chunks × 2 sessions
    sessions = {i: f"s{i // 3}" for i in range(6)}
    selected, _ = mmr_select(scores, {}, sessions, top_k=6,
                             per_session_cap=2, lambda_=0.7)
    from collections import Counter
    counts = Counter(sessions[i] for i in selected)
    assert max(counts.values()) <= 2 and len(selected) == 4  # pool dries at cap

def test_mmr_select_validation():
    with pytest.raises(ValueError):
        mmr_select({}, {}, {}, top_k=5, per_session_cap=0, lambda_=0.7)
    with pytest.raises(ValueError):
        mmr_select({}, {}, {}, top_k=5, per_session_cap=2, lambda_=1.5)

def test_mmr_select_missing_session_key_defined():
    # contract: a candidate absent from `sessions` is treated as its own
    # group (never KeyError, never silently capped with ""-group hits)
    scores = {0: 0.9, 1: 0.8, 2: 0.7}
    sessions = {0: "s1"}                     # 1 and 2 have NO session
    selected, _ = mmr_select(scores, {}, sessions, top_k=3,
                             per_session_cap=1, lambda_=0.7)
    assert len(selected) == 3                # un-capped: all three survive

def test_rerank_enabled_gate(monkeypatch):
    monkeypatch.delenv("TORTOISE_LME_RERANK", raising=False)  # hermetic
    assert rerank_enabled(True) and not rerank_enabled(False)
    assert not rerank_enabled(None)          # env unset → off (fail-safe)

        assert rerank_enabled(None)          # env=1 flips the DEFAULT on

def test_cross_encoder_scorer_degrades_with_ttl(monkeypatch):
    # load failures are cached with a short TTL (no hub hammering on a
    # persistent outage), then retried after expiry; successes are cached
    # permanently (D8b)
    calls = {"n": 0}
    def _flaky(*a, **k):
        calls["n"] += 1
        if calls["n"] < 2:
            raise RuntimeError("transient network error")
        return object()
    monkeypatch.setattr(rerank, "CrossEncoderScorer", _flaky)
    clock = {"t": 0.0}
    _real = rerank._NOW                       # capture before patching
    monkeypatch.setattr(rerank, "_NOW", lambda: clock["t"])
    sc1, reason1 = get_scorer("whatever-model")
    assert sc1 is None and reason1
    # inside the TTL window: NOT re-attempted (constructor count stays 1)
    sc2, reason2 = get_scorer("whatever-model")
    assert sc2 is None and calls["n"] == 1
    # after TTL expiry (clock advanced): re-attempted and cached
    clock["t"] = _real() + 120.0
    sc3, reason3 = get_scorer("whatever-model")
    assert sc3 is not None and not reason3 and calls["n"] == 2
```

```python
"""R6 — cross-encoder rerank + MMR diversity (issue #1545, epic #1509).

Post-fusion rerank stage for the LongMemEval retrieval path. Off by default:
``retrieve_for_question`` calls this ONLY when the R6 gate is on (see
retrieve.py), so the V3 baseline path is byte-identical. Production search
(``search_engine.py`` / ``sdk.tortoise_fts_query``) is intentionally
untouched — this is the eval-layer measured surface (S11).

MMR: MMR(d) = lambda_*rel(d) - (1-lambda_)*max_sim(d, selected), greedy, with a
hard per-session cap (E2E-10: one session can't monopolize the context).
"""
from __future__ import annotations

import logging
import os
import threading
import time
from typing import Callable, Sequence

logger = logging.getLogger(__name__)

RERANK_MODEL_DEFAULT = "cross-encoder/ms-marco-MiniLM-L6-v2"
RERANK_MAX_LENGTH = 512          # tokenizer-level (CrossEncoder max_length)
RERANK_TRUNCATE_CHARS = 2048     # char pre-truncation (≈500 tokens) — the
                                 # two limits are aligned so long raw
                                 # transcripts cannot blow the tokenizer

def rerank_enabled(flag: bool | None) -> bool:

def mmr_select(
    scores: dict[int, float],
    sims: dict[tuple[int, int], float],
    sessions: dict[int, str],
    *,
    top_k: int,
    per_session_cap: int,
    lambda_: float,
) -> tuple[list[int], list[int]]:
    """Greedy MMR with a hard per-session cap.

    Returns (selected_indices, dropped_indices) in selection order. A
    candidate whose session already has ``per_session_cap`` selected hits is
    skipped; candidates ABSENT from ``sessions`` (or with an empty session
    id) are their own group and are never capped by other hits. Selection
    stops when the pool is exhausted or ``top_k`` is reached — the caller
    reports ``len(selected)`` (never implied ``top_k``).
    """
    if per_session_cap < 1:
        raise ValueError(f"per_session_cap must be >= 1, got {per_session_cap}")
    if not (0.0 <= lambda_ <= 1.0):
        raise ValueError(f"lambda_ must be in [0,1], got {lambda_}")
    cands = sorted(scores)          # deterministic tie-break by index
    selected: list[int] = []
    dropped: list[int] = []
    session_counts: dict[str, int] = {}
    for _ in range(min(top_k, len(cands))):
        best, best_val = None, float("-inf")
        for i in cands:
            if i in selected:
                continue
            sid = sessions.get(i)
            if sid and session_counts.get(sid, 0) >= per_session_cap:
                continue            # capped (empty/missing sid → never capped)
            rel = scores[i]
            sim = max((sims.get((i, j), sims.get((j, i), 0.0))
                       for j in selected), default=0.0)
            val = lambda_ * rel - (1.0 - lambda_) * sim
            if val > best_val:
                best, best_val = i, val
        if best is None:
            break
        selected.append(best)
        sid = sessions.get(best)
        if sid:
            session_counts[sid] = session_counts.get(sid, 0) + 1
    dropped = [i for i in cands if i not in selected]
    return selected, dropped

    return os.environ.get("TORTOISE_LME_RERANK_MODEL", RERANK_MODEL_DEFAULT).strip() \

class CrossEncoderScorer:
    """Lazy-loaded cross-encoder. Scores (query, content) pairs → sigmoid
    normalized (0,1). MS MARCO models return logits; the sigmoid is needed
    only to put rel on the same scale as the MMR similarity term (ranking is
    unchanged without it — pinned by the API-surface finding)."""

    def __init__(self, model: str, max_length: int = RERANK_MAX_LENGTH):
        from sentence_transformers import CrossEncoder
        import threading as _t
        self._model = CrossEncoder(model, max_length=max_length)
        self._lock = _t.Lock()   # serializes predict() under workers>1

    def score(self, query: str, contents: Sequence[str]) -> list[float]:
        # Per-instance lock: workers>1 (run.py --workers) share this instance
        # across threads — concurrent predict() is not documented thread-safe
        with self._lock:
            import torch
            pairs = [(query, c) for c in contents]  # char pre-truncation lives in
                                                    # rerank_hits (both scorers
                                                    # exercise it — D7); max_length
                                                    # is the tokenizer backstop
            logits = self._model.predict(pairs)     # v3+ API (score_pairs deprecated)
            return [float(torch.sigmoid(torch.tensor(x))) for x in logits]


class FakeScorer:
    """Deterministic test double: query-token-overlap over content length
    (no model). Normalizing by content length keeps near-duplicates strictly
    below the exact match (pure query-overlap would tie them)."""

    def score(self, query: str, contents: Sequence[str]) -> list[float]:
        qtoks = set(query.lower().split())
        out = []
        for c in contents:
            ctoks = set(c.lower().split())
            out.append(len(qtoks & ctoks) / max(len(ctoks), 1))
        return out


_scorer_lock = threading.Lock()
_scorer_cache: dict[str, CrossEncoderScorer] = {}   # successes — permanent
_fail_cache: dict[str, float] = {}                  # failures — short-TTL only
                                                    # (a persistent outage is
                                                    # retried at most ~1/min,
                                                    # not 500×/run — D8b)
_RETRY_TTL_S = 60.0
_NOW = time.monotonic


def get_scorer(model: str | None = None) -> tuple[CrossEncoderScorer | None, str]:
    """Load (cache) the cross-encoder; returns (scorer, reason). Successes are
    cached forever; failures are cached with a short TTL (``_RETRY_TTL_S``) so a
    persistent outage degrades quickly instead of hammering the HF hub.

    DOUBLE-CHECKED LOCKING: ``_scorer_lock`` is held ACROSS construction — a
    concurrent cache miss (``--workers > 1``) blocks until the first thread's
    constructor finishes, then returns the cached instance. Without this, two
    workers can double-download the ~90MB model and diverge on instances."""
    name = model or _model_name()
    with _scorer_lock:
        if name in _scorer_cache:
            return _scorer_cache[name], ""
        if name in _fail_cache and _NOW() - _fail_cache[name] < _RETRY_TTL_S:
            return None, f"{name}: load failed recently (retry in ~{_RETRY_TTL_S:.0f}s)"
        try:
            sc = CrossEncoderScorer(name)      # constructed INSIDE the lock
        except Exception as e:  # noqa: BLE001 — model download/failure
            logger.warning("cross-encoder %s unavailable — R6 degrades to "
                           "rerank-off for this question: %s", name, e)
            _fail_cache[name] = _NOW()
            return None, f"{name}: {e!r}"
        _scorer_cache[name] = sc
        _fail_cache.pop(name, None)
        return sc, ""
```

```python
    sdk: TortoiseSDK,
    question: dict,
    *,
    ks: tuple[int, ...] = (5, 10, 20),
    top_k: int = 20,

    retrieves the SAME 20-pool as the baseline, never a 40-pool stand-in).
    The reader/context invariant holds on EVERY path:
    ``len(hits) == context_point_count == min(pool_limit, top_k)``.
    ``rerank_pool`` is honored when explicitly passed even with rerank off
    (pool-only arm); env defaults apply only when rerank is on."""
    qid = question["question_id"]
    answer_sessions = set(question.get("answer_session_ids") or [])
    dates: list[str] = question.get("haystack_dates") or []
    evidence_turn_ids = {...}  # unchanged
    rerank_on = rerank_enabled(rerank)
    from .rerank import get_scorer
    scorer, degrade_reason = get_scorer(rerank_model) if rerank_on else (None, "")
    cap = per_session_cap if per_session_cap is not None \

        else _env_float("TORTOISE_LME_RERANK_LAMBDA", 0.7)
    pool_override = rerank_pool if rerank_pool is not None \
        else _env_int("TORTOISE_LME_RERANK_POOL", 40)

    # The explicit pool override applies ONLY on the rerank-off arm (the
    # pool-only isolation arm); with rerank ON, a degraded (scorer-None)
    # question must fall back to the baseline 20-pool — never a 40-pool
    # stand-in (D3/S11 pool contamination).
    use_deep_pool = pool_override > max(ks) and (
        (rerank_pool is not None and not rerank_on)
        or (rerank_on and scorer is not None))

    start = time.monotonic()

    evidence_point_count = ev_rows[0][0] if ev_rows else 0

                evidence_point_count=evidence_point_count)
```

5. **Pool-only isolation arm execution.** Now expressible (`--rerank off --rerank-pool 40` — deeper pool, baseline ordering, hits truncated to `top_k`, no rerank keys) — whether the owner wants it run to decompose the composite delta is a run-protocol decision, not a code change.
6. **Shared-cross-encoder concurrency (handled, not deferred).** run.py ALREADY ships `--workers` (default 1, ThreadPoolExecutor dispatch) — the shared `CrossEncoder` instance is used across worker threads when `workers>1`. Concurrency is handled by: (a) `get_scorer` holding the cache lock **across construction** (concurrent cache misses cannot double-load the ~90MB model), and (b) a per-instance lock inside `CrossEncoderScorer.score()` serializing `predict()` (not documented thread-safe). Cost: `predict()` at pool 40 is ~10–50ms, so serialization under workers=8 is acceptable. Oversubscription (N threads × torch intra-op threads) remains a perf caveat, not a correctness issue.
