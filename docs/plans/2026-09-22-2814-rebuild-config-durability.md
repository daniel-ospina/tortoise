# Rebuild Durability for Authoritative Configuration — Implementation Plan

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

> **Design of record is NOT on main.** Decision **D5** of the WS-A design lives in `docs/plans/2026-09-10-write-contract-five-doors.md` on the **unmerged** branch `design/2820-ws-a-write-contract` (PR **#2888**, still DRAFT). Read it with `git show origin/design/2820-ws-a-write-contract:docs/plans/2026-09-10-write-contract-five-doors.md`. Its line numbers are stale (it cites `:1301`/`:1157`/`:74-90`/`:2045-2075`; the real sites are `:3197`/`:2738`/`:230`/`:4680`), and its blanket guard-filter rationale is overstated — `_is_bulk_wipe` is *form-dependent* (a **property** filter disengages it; a **label** filter does not), so C2 holds but for a narrower reason than D5 states. #2814 implements D5 standalone (D5 is independent of WS-A steps 1–5).

**Goal:** `rebuild_all` must stop destroying graph-resident **authoritative configuration**. Today every node is wiped by the unconditional, load-bearing `MATCH (n) DETACH DELETE n` and only the journal is replayed; `:PackInstall`/`:PackManifest` ride no journal event at all, `Meta{key:'calibration_milestone'}` emits `CalibrationRecorded` but **no projection fold consumes it** (`_NO_PROJECTION_FOLD`, `projection/__init__.py:1339`), and the future `:Pipeline` records are specified as graph-resident — so the documented recovery path silently reverts a configured graph to defaults. Because #2728 makes a missing marker mean "legacy union, no restriction", the silent case is a **permissions change**, not a lost preference.

**Confirmed problem (scoping Phase 2):** `rebuild_all` destroys graph-resident authoritative configuration because the rebuild path's durable-preservation mechanism is an **ad-hoc, per-class enrolment list** (`_SNAPSHOT_SECTIONS` + per-class pre-wipe proofs) with **no declared node-class durability contract** — so these classes were never enrolled, and there is no durable record, no restore, and no operator-visible distinction between "never configured" and "configured then wiped".

**Team:** epistemic-team · **Complexity:** standard · **Tier:** Standard

<!-- research-path: #2814 scoping comment (### Axis Research); adopted/rejected synthesis in §3 and the scope comment -->

**Architecture:** Reuse the durable pre-wipe sidecar that already guards `rebuild_all` (#2943/#3947) instead of inventing a mechanism. Add a **declared** config registry (`_config_classes()`: `:PackInstall`, `:PackManifest`, keyed `:Meta`), capture it into a new flat `config_snapshot` section **before** the unconditional wipe, restore it registry-literally after journal replay, verify the restored `(label, identity)` set, and record an unmatched result as a sticky `:Meta{key:'config_reset'}` marker (the third state — deliberately **not** called a "tombstone", which is a controlled `docs/ONTOLOGY.md` term for retracted Points). The wipe statement stays byte-identical and the wipe guard is untouched.

**Tech Stack:** Python 3.12+, FalkorDB (embedded via `TORTOISE_TEST_CARVE_OUT=1` and docker via `TORTOISE_DB_URI`), pytest, uv. **No third-party dependency is added.**

   **⚠️ Two corrections here, both from plan-review (do not regress them).**
   (i) **No completeness check inside `_write_prewipe_snapshot`** (cycle 2). That function must stay **permissive**: its verbatim round-trip of a *partial* payload is pinned by existing tests, which write 4-key payloads and assert `_load_prewipe_snapshot(path) == good` (`tests/test_projection.py:3489-3510`, `:3515-3517`), pass deliberately malformed payloads where only the **loader** should raise (`:3579`), and assert the **size** refusal's message (`tests/test_rebuild_turn_points_3947.py:703`). A writer-side key check breaks several at once.
   (ii) **Key presence alone is not the guarantee** (cycle 3). `{**{k: [] for k in _SNAPSHOT_SECTIONS}, …}` makes every key present, but the loader treats `[]` and an absent key **identically** (`:447-448` `data.get(key, [])`; `:534` entry-less check), so a section dropped from the **merged literal** (`:3054-3068`) or the **union return literal** (`:771-774`) would still be written as `[]`, load as empty, and be destroyed by the wipe — the harm class unchanged. Deriving the **values** (as above) makes that omission raise at capture time, pre-wipe. **Scope the claim precisely:** the derivation makes a miss in the **union return literal** (`:771-774`) raise. It does **not** structurally cover the **fresh-arg literal** (`:3054-3068`) — the mandated `fresh.get("config_snapshot") or []` yields `[]` for an omitted key without raising, and the union's return literal then supplies the key, so no `KeyError` fires. That leg is covered by `test_rebuild_all_write_payload_covers_every_snapshot_section`'s non-empty round-trip assertion (pre-wipe), **not** structurally — stated here so the guarantee is not over-read.
   (iii) **`snapshot_pending` (`:3106-3109`) must be derived too** (cycle 3) — it is a **fourth** hand-maintained membership list, and an omission there is *worse* than the `[]` case: a config-only graph would take `snapshot_pending = False`, **no sidecar would be written at all**, and the wipe+replay would silently destroy the config. All five locals are assigned from `merged` by `:3062-3075`, so `snapshot_pending = any(merged[k] for k in _SNAPSHOT_SECTIONS)` is exact and folds in `config_snapshot` automatically.

## 2. Architecture

**Chosen approach: A1 `Declared-ConfigSections` (flat-section variant).** Authoritative configuration is enrolled as **one new section (`config_snapshot`)** of the existing durable pre-wipe sidecar, driven by **one declared registry** that *is* the node-class durability contract.

```
capture (registry-driven)
  → validate every entry
  → REFUSE if capture or validation failed        (graph untouched)
  → union with any leftover sidecar
  → write durable sidecar
  → MATCH (n) DETACH DELETE n                     (BYTE-IDENTICAL, guard engaged)
  → journal replay
  → restore config from the section               (registry-literal Cypher, $ params)
  → verify restored identity set → config_reset marker on mismatch
  → retire sidecar (entry-less payload)
```

**Declared registry** (the contract for the classes enrolled **today**; labels/keys come from the domain constants, never re-typed — see §3(b)):

```python
@dataclass(frozen=True)
class _ConfigClass:
    label: str                            # from the domain constant
    identity_prop: str                    # code literal
    keys: frozenset[str] | None = None    # key-scoped (:Meta); None = label-wide

_CONFIG_CLASS_BY_LABEL: dict[str, _ConfigClass] = {}  # lazily filled INSIDE _config_classes()
```

```python
# `_config_classes()` is the ONLY accessor — memoised, imports its three domain
# constants function-locally, runs `_assert_config_registry_safe()` ON FIRST
# CALL (the load/validate + capture paths, both pre-wipe), and populates
# `_CONFIG_CLASS_BY_LABEL` as a side effect (the map starts EMPTY at module
# scope: a bare `{}` literal evaluates nothing).
# There is NO `... = _config_classes()` assignment at module scope and NO
# import-time `_assert_config_registry_safe()` call — either one re-creates the
# projection → pack_state → sdk → projection cycle.
```

**⚠️ The registry MUST NOT be bound *or validated* at module scope (P1, cycle 2; cycle 3 reproduced the half-fix).** The constants live behind modules that import `tortoise.projection`: `sdk.py:36-38` does `from .projection import FalkorProjection` at module level, `pack_state.py:55` does `from tortoise.sdk import TortoiseSDK`, and `pack_manifest_store.py:44` imports `pack_state`. A module-scope binding **or an import-time call** therefore creates the cycle **projection → pack_state → sdk → projection**. Cycle 3 reproduced both halves on the current tree: appending a module-scope `_CONFIG_CLASS_BY_LABEL = {c.label: c for c in _config_classes()}` (or any `= _config_classes()` at module scope) breaks **`import tortoise.sdk`** (`ImportError: cannot import name 'TortoiseSDK'`) and **`import tortoise.pack_manifest_store`**; appending an import-time `_assert_config_registry_safe()` breaks `import tortoise.sdk` identically. `import tortoise.projection` alone *succeeds* in both cases — which is why a naive check misses it, and why §6 step 8 checks all three modules. The mechanism is therefore a **function-local (lazy) import** in a memoised `_config_classes()`, exactly the style `rebuild_all` already uses for `import os` / `from tortoise.log import EventLog`, with `_assert_config_registry_safe()` run on first call — which is the load/validate path and the capture path, both **pre-wipe**.

**What this declaration is, and is NOT.** It is the durability disposition of the classes **enrolled today**, plus the *rule* by which a class is classified authoritative ("graph-resident, non-journaled, not re-derivable ⇒ snapshot + restore"). It is **NOT** a completeness gate: nothing here fails when a new authoritative class is written by a new writer — that is #2296 Indicator 3, which is **dormant and unowned** (§7). Enrolment is therefore **by hand**, and that residual is stated rather than implied. **And the incompleteness is not hypothetical — this lane's Phase 6 wiring check and the plan-review cycle found concrete classes the rule classifies but this registry does not enrol, and filed them: #4641** (`:OnboardingState` + its `:OnboardingStep` nodes and `COMPLETED_STEP` edges — zero hits in `projection/__init__.py`, absent from `_SNAPSHOT_SECTIONS`; plus `:TeamMeta`, a `CREATE`-written marker whose presence gates first-org idempotency) and **#4653** (`:GraphEventMeta.last_seq`, the event-log watermark — also zero hits in `projection/__init__.py`, and re-derivable from the replayed log, so its fix is a post-replay re-derivation mirroring `hosted_backup._restore_event_meta`, **not** a snapshot enrolment). Neither is enrolled here: #4641 needs **edge** capture and this registry's flat entry shape carries nodes only (restoring the node without the step edges would be a *silent partial restore*), and #4653 is re-derivable, so enrolling it in a snapshot would be the wrong mechanism.

**⚠️ A correction the plan-review cycle forced on this plan's own reasoning.** Earlier drafts used membership of `_EXPORT_SKIP_LABELS` / `_EXPORT_SKIP_META_KEYS` as evidence that the platform calls a class *derived* ("not in the export-skip set, so it is content"). **That inference is invalid** — export-skip is an export/backup mechanism, **not a durability authority** — and `:GraphEventMeta` is the proof: it **is** export-skipped, and `hosted_backup` carries it on a separate side-channel precisely because its loss corrupts the event log's `seq` monotonicity (`hosted_backup.py:443-452`). So the export-skip set is cited in this plan only as *corroboration* for `:EpMeta` and the FTS markers, never as a classifier.

What this plan *does* enforce is the bounded case that the classes it names cannot be silently de-enrolled by a rename: the registry is built from the domain constants and a liveness test asserts them (§3(b)). **Note on the identity property:** it differs per class (`PackInstall`/`PackManifest` → `namespace`, keyed `:Meta` → `key`). The existing `_CANONICAL_ENTITY_ID_PROPS` (`:1382`) declares the same *kind* of table for **entity** labels (`Point`/`Subject`/`Object`/`Document`/`Source`/`Event` → `id`, except `Event` → `eventId`) with the same membership gate (`:5596-5599`); the config table is deliberately **separate** (different axis, different identity props — a pack install is not a canonical entity), and §11 records that as a `keep separate` disposition with the shared *pattern* named.

## 3. Design decisions

**(a) One flat `config_snapshot` section, not per-label sections.** Entry shape `{"label": str, "props": dict}`. Ten sites edit per new surface; with one section each edit adds one token, with N sections each adds N. **The reason is maintenance simplicity with a structural backstop, not a correctness argument about the retirement payload** — `_clear_prewipe_snapshot` always builds a *fresh* literal, so a retirement artifact cannot carry live config, and the loader reads sections with `data.get(key)` so an omitted section is empty, not carried. To remove the drift the section count could still cause, **the retirement payload is DERIVED from the section tuple** (`{k: [] for k in _SNAPSHOT_SECTIONS}`, mirroring `version`/`created_at`/`completed`), so no hand-maintained list can go stale at that site. *(A3 `PackConfigValueCarrier` is not affected by this choice; A1's flat shape is simply the smaller surface.)*

**`_config_key(entry)` MUST be `(label, identity_value)`, not `identity_value` alone.** The section is flat, so entries of different labels share one key space; with an identity-only key, `PackInstall{namespace:'x'}` and `Meta{key:'x'}` would collide in `_union`, `_merge_entry` would keep the left entry's `label` and merge the other's `props` — silently dropping the `Meta` entry and writing a foreign property onto the pack node. A cross-label same-identity collision is pinned in §5.

**Why the loss is silent, and the in-file kin this design sits beside.** Fail-closed before the wipe is not invented here: `_assert_episodic_points_recreatable` (`:2671`) already runs immediately before the wipe (`:3193`) and raises **with the graph untouched** when data the wipe is about to destroy cannot be reconstructed. The config capture/refusal is its sibling — same placement, same contract. And the loss is silent for a specific, verified reason: the starter pack set is *deliberately* self-healing. `get_tenant_packs` is a recorded read-through write (`tests/tool_surface_capabilities.py:52`) that `MERGE`s `:PackInstall` for the starter namespaces and sets `status='active'` — so after a wipe the graph does **not** look empty, it looks freshly provisioned. `installed_at` returns as a **fresh** timestamp (`coalesce(p.installed_at, $now)`, `pack_state.py:293`) and *custom* `:PackManifest` content is not self-healed at all, so the operator-facing signal is a graph that appears configured, in the default state — which is why the §8 third-state marker is load-bearing rather than cosmetic. (The starter set's re-activation is **intended** (`pack_state.py` docstring: "the introspection surface self-heals on first read"); it is the *custom* set and the timestamps that are unrecoverable.)

**(b) Label safety — no sidecar-derived string reaches Cypher string assembly.** Labels and identity-property names come from the registry; the identity *value* and the property map reach Cypher only as `$`-bound parameters. Capture Cypher is built from registry literals only (`MATCH (n:<label>)` or `MATCH (n:Meta) WHERE n.key IN $keys` — **never** label-wide over `:Meta`, which is what keeps `point_fts_v2`/`event_fts_v2` derived). An entry naming an undeclared label or an undeclared `Meta` key is refused **before the wipe**. An **first-call** `_assert_config_registry_safe()` rejects identifiers that are not `^[A-Za-z_][A-Za-z0-9_]*$`, empty Meta keys, and any `_SNAPSHOT_SECTIONS`/`_SNAPSHOT_ENTRY_CHECK` mismatch (the latter would otherwise be a `KeyError` inside validation).

**The registry reads the domain constants, and the liveness test is bound to what the writers actually WRITE.** A bare re-typed `"PackInstall"` would de-enrol the class the moment `pack_state.PACK_INSTALL_LABEL` (or `pack_manifest_store.PACK_MANIFEST_LABEL`) were renamed — silently, with every other test green. So `_config_classes()` builds its entries from `PACK_INSTALL_LABEL`, `PACK_MANIFEST_LABEL` and `TortoiseSDK._CALIBRATION_MARKER_KEY`, and `_assert_config_registry_safe()` asserts the declared `:Meta` key set equals `{TortoiseSDK._CALIBRATION_MARKER_KEY, _CONFIG_RESET_KEY}`.

**⚠️ A membership assertion against the constants the registry is itself built from is tautological.** `PACK_INSTALL_LABEL` (`pack_state.py:59`) is currently **dead** — the label is written and read as the literal `:PackInstall` at `pack_state.py:290` (the `ensure_tenant_packs` **writer**) and `:345` (the `_read_installs` **reader**, `:341-348`), and at `pack_manifest_store.py:224` — so renaming either the constant or a literal silently de-enrols the issue's headline class with every named test green. This plan therefore **binds both labels to their declaration** (a minimal two-module touch): `pack_state.py` and `pack_manifest_store.py` interpolate `PACK_INSTALL_LABEL` into the label position of **every** `MERGE`/`MATCH` they use for the class — the four sites are `pack_state.py:290` (writer) and `:345` (reader `MATCH`), and `pack_manifest_store.py:224` (writer `MERGE`) and **`:291`** (`delete_tenant_manifest`'s `MATCH … SET p.status = 'removed'` — the `status='removed'` write §5's survival test exercises). The reader's and the deleter's `MATCH`es are bound too, not just the writers': they are the statements the registry's *capture* query mirrors, and a drift there would make the liveness test's agreement claim hollow. **Two further in-library literals are deliberately NOT bound in this change, and are recorded as such rather than left implied:** `hosted_api.py:16431` (the export/import `MERGE (p:PackInstall {namespace:$ns})` in `_apply_import_pack_config`) and `export.py:80` (the reader behind `collect_pack_config`). Both sit on the **export/import axis whose contract is #1936's** (§11's `keep separate` row), which this change deliberately leaves read-only; binding them is a rename-hygiene follow-up recorded against #1936. The claim above is therefore scoped to the **two modules Step 2 touches** — not "every literal in the repo". `PACK_MANIFEST_LABEL` (`:210`/`:263`/`:278`/`:289`) and `_CALIBRATION_MARKER_KEY` (`sdk.py:20659`/`20675`, plus the literal pinned in `tests/test_gate_b_tooling.py:223`) are already bound. The liveness assertion is **falsifying, not tautological** — and its mechanism is part of the spec, not left to the implementer (the same tautology class solution-verify caught twice: a constant-vs-constant comparison reads the same constant twice and cannot fail). The test must be able to fail if a **literal** replaces the constant: either a **static** assertion that the four Cypher sites interpolate `PACK_INSTALL_LABEL` (no bare `:PackInstall` label literal remains in their string literals), or a **live** one — monkeypatch `pack_state.PACK_INSTALL_LABEL`, clear the `_config_classes()` memo, run the real writer on a scratch graph, and assert the written node's label follows the renamed constant. §14 Task 3 step 1 states this and step 2 requires the pre-binding run to **FAIL** (if it passes, the chosen mechanism is not falsifying). With that, `test_config_registry_covers_domain_writers` is non-tautological, and a real `rebuild_all` run in `tests/test_pack_state.py` / `tests/test_pack_manifest_store.py` demonstrates the writer's label and the registry's label agree under an actual rebuild. **Scope note:** this pins the classes this plan *names*; it is **not** the general "every authoritative writer's label is declared" gate — that is #2296 Indicator 3, unowned (§7).

**(c) `config_reset` — a sticky `:Meta{key:'config_reset'}` marker with two provable triggers.**

- Node: `:Meta {key:'config_reset', at, last_at, count, reason}` — the repo's existing `:Meta{key:…}` idiom, captured by the registry's key-scoped `Meta` class so it rides the same sidecar and the same restore leg as the config it describes.
- **Sticky**: `rebuild_all` never clears it; `count`/`last_at` are monotonic on one node (so accumulation cannot arise). It is cleared only by an explicit operator action — and that action is **wired, not asserted** (plan-review P2): a module-level `clear_config_reset` + the **private** SDK delegate `_clear_config_reset()`, surfaced to the operator by the **CLI** (the two new return keys are printed by `_cmd_rebuild`, `tortoise/__main__.py:44-52`) and documented in the rebuild runbook Task 7 updates. **Naming:** this is called the `config_reset` **marker** or **third state**, deliberately **not** a "tombstone" — "Tombstone" is a controlled term in `docs/ONTOLOGY.md:833` with a precise contract (a retracted `Point` returned by `get_point`), which this keyed `:Meta` node is not.
- **T2 (pre-wipe, primary):** a leftover sidecar whose `version` is `None` or `< 2` (a pre-preservation rescue file) that carries **no `config_reset` marker already**, staged directly into the section (no pre-wipe graph write) with `reason='legacy_sidecar_no_config_record'`. **The gate keys on the rescue file's version ONLY — deliberately NOT on an empty merged `config_snapshot`** (execution-time correction): the wipe can be followed by the self-heal this issue names (`ensure_tenant_packs` repopulating starter `:PackInstall` rows before the retry), so the fresh capture can be **NON-empty** while the real custom configuration the old build destroyed is still unknown. Gating on emptiness reported that as a clean `N of N restored` with no marker — a false "restored" for an unknown state. A false "unknown" is safe and operator-clearable; a false "restored" is not. The staged marker is **excluded from the reported `config_expected`/`config_restored` counts** (it asserts unprovability, it is not captured configuration) but **kept inside the post-restore verification**: if its own restore write failed, the graph would be state-UNKNOWN with no marker and `config_reset` would read False — the same false "restored", re-entering through the marker itself. The returned `config_reset` is therefore fail-**safe** (an unreadable marker also reports True), with a companion `config_reset_read_failed` key so the CLI says "could not be read" rather than asserting a marker it cannot see.
- **T1 (post-restore, secondary):** the post-restore verification finds a captured `(label, identity)` missing → `ERROR` + `reason='restore_incomplete'`. A true positive, never a raise (a post-wipe raise would leave an empty store).
- False-positive direction is the safe one and is stated as such: after #2728, absence ⇒ legacy union ⇒ a permissions change, so a false negative is strictly dangerous. Marking every never-configured graph is rejected — it would make the marker meaningless.

**(d) Version bump 1 → 2 with a readable set `(1, 2)`.** Not bumping is the fail-open choice, and the mechanism is precise: **without the bump the new writer still stamps `version: 1`** — the version is set by the **callers'** payloads, not by `_write_prewipe_snapshot` (`:541-590` just `json.dumps`es the caller's dict verbatim): `rebuild_all`'s write payload (`:3112`) and `_clear_prewipe_snapshot` (`:603`) — so a v1 binary reading it accepts the file and **ignores `config_snapshot` entirely** — the wipe lands with the rescue file sitting right there. Bumping makes the old binary **refuse** (a literal `version: 2` already fails its `version != 1` check at `:441`), i.e. a refused rebuild rather than a silent config loss. C6 is satisfied by the read set: a v1 leftover still loads (and is what T2 keys on). The ~11 tests hardcoding `"version": 1` need **no edits** — they round-trip through the loader, which returns the payload verbatim.

**⚠️ Rollout and ordering — a new refusal that did not exist before, stated rather than discovered (plan-review P2).** Decision (d) reasons only about a **pending** v2 sidecar, where refusal is the intended fail-closed outcome. It does **not** hold for the **retired** payload, whose whole contract is that it is harmless: `_clear_prewipe_snapshot` first rewrites `{version: <current>, completed: True, <all sections empty>}` and only then unlinks, explicitly so a crash or a failed unlink leaves an artifact that "merges nothing" (`:592-600`, pinned by `tests/test_projection.py:3610-3620`). That pin holds only for a loader whose readable set contains the written version: after the bump, an **older** binary raises on `version != 1` at `:441` **before** the entry-less check at `:534`, so a retired v2 sidecar whose unlink failed turns every `rebuild_all` **and** embedded auto-recovery in that directory into a hard refusal. Consequences, all stated in the runbook (Task 7): (i) deploy the new binary everywhere before any `rebuild_all` writes a v2 sidecar; (ii) on rollback the remedy is to **upgrade**, never to delete a **pending** sidecar (deleting it destroys the only copy of the pre-wipe config) — the "delete the rescue file" remedy in §8 applies to the **retired, entry-less** case only; (iii) the retired-payload case is recorded as a **named residual** (§8), not solved here, because retiring under a version the *previous* release accepts would contradict the version bump's purpose (the bump is what makes the fresh-payload case refuse) — and a partial retirement version would be a second addressable state with no test.

**(e) Precedence — MUST be per-section, because `_merge_entry`'s rule does not hold for config.**
1. *Sidecar union (pre-wipe)*: **for `config_snapshot` the merge is PER-KEY on `_config_key(entry)` — a colliding key keeps the LEFTOVER entry verbatim (no field-merge), and a fresh-only key is appended.** Two directions, one rule:
   - *Collision* — the leftover wins **wholesale**. `_merge_entry`'s "absences fill, presence wins" is justified by replay gaps (a partial replay recreates a node with properties ABSENT), and its discriminator is *presence*. That discriminator **fails for config**: no journal fold writes these labels (§(g)), and the one thing that does re-create them is the **self-healing read path** — `ensure_tenant_packs` `MERGE`s starter `:PackInstall` nodes with *present* defaults (`status='active'`, `source='starter'`, catalog `version`, fresh `installed_at`; `pack_state.py:290-293`). So on the crash-mid-replay path — where `recover_from_log` refuses (`db_count > 0`, `consistency.py:106-108`), the sidecar is kept, and an intervening `get_tenant_packs`/`packs_list` read self-heals the starter set — a fresh-wins merge **overwrites the leftover's real values with self-healed defaults**: `PackInstall{dev, version 0.9.0, status 'removed', source 'custom'}` becomes `{version 0.3.0, status 'active', source 'starter', installed_at: now}`. That is #2814's exact harm recurring *after* this fix (reproduced on `main` with a starter-heal probe).
   - *Fresh-only key* — **appended, never dropped.** A section-granular "take the leftover verbatim" rule would be wrong: config provisioned into the graph *after* an interrupted wipe but *before* the retry (`upsert_tenant_manifest` → `:PackManifest` + `:PackInstall{source:'custom'}`) has no leftover counterpart, so dropping it hands it to the **retry's own wipe** (`:3197`) and it is never restored — silent unrecoverable loss, the very harm class this issue removes. A fresh-only key cannot overwrite anything, so appending it costs nothing. (The cycle-1 wording claimed post-wipe writes "survive untouched" — only a write between the retry's wipe and its restore does; the fresh-only leg is what protects the rest.)
   
   `_config_key(entry) = (label, identity_value)` (§(a)) is the key, so the two legs cannot collide across labels. Config **never** routes through `_merge_entry`. Pinned in **both** directions by one test: `test_leftover_config_wins_over_self_healed_defaults` asserts a colliding key keeps the leftover's values **and** a fresh-only key survives the retry; the loss direction is separately pinned by `test_fresh_only_config_key_survives_pending_leftover`. **Named residual from the collision leg (not silently absorbed):** within the interrupted-rebuild window, an operator edit to an *existing* config key is reverted to the leftover (resurrection of a deliberately deleted `:PackManifest`, the pending-sidecar half of §8 class 3). The retired-sidecar half is already safe (`_clear_prewipe_snapshot` writes an entry-less payload → merge is a no-op). The window, its direction, and the remedy (delete the rescue file) are recorded in §8 and pinned by `test_pending_sidecar_restores_leftover_config_over_a_post_wipe_delete`.
2. *Post-replay restore*: **snapshot-wins** by construction (`MERGE … SET n += $props` after replay), which is the store-authoritative rule `docs/durability-posture.md` states and is identical to how `:Batch`/`:Session` already behave. Today's collision count is **zero** (`CalibrationRecorded` is in `_NO_PROJECTION_FOLD`; no fold writes these labels). Named caveat, filed not silent: if #2792 ever makes `:Pipeline` journal-authoritative, rule 2 must be reopened.

**(f) Pre-wipe proof vs post-restore verification.** Proven **pre-wipe**: capture complete; every entry valid; every captured label/Meta key resolves in the registry (restorability); the sidecar write succeeded. Verified **post-restore** (T1): the captured `(label, identity)` set vs the live graph, immediately before sidecar retirement. Never raise post-wipe.

**(g) `recover_from_log` interaction — stated, not discovered.** `consistency.py:102-108` refuses auto-recovery when `MATCH (n) RETURN count(n) > 0`. Config restore stays on the existing post-replay leg, so: a crash between the wipe and the replay writes nothing → `db_count == 0` → auto-recovery routes to `rebuild_all` → config restored; a crash mid-replay → `db_count > 0` → `recover_from_log` refuses, **keeps the sidecar**, and an explicit `tortoise rebuild --dir` restores. **The sticky marker's own consequence, stated plainly:** unlike a `:Batch` marker (released on promote/commit), `config_reset` persists until an operator clears it, so a graph whose data is gone but whose marker remains reports `count(n) > 0` and **suppresses auto-recovery indefinitely** — surfacing as a warning on the healthy open path (`:2325-2336`) and as a **raise** via `_recover_or_raise` (`:2338-2347`) on the probe-failed path. That direction is *safe* (it refuses rather than wipes) but it is a real availability effect, so it is **recorded as a named residual and pinned by a test** (`test_recover_from_log_refuses_nonempty_graph_with_config`), **not** silently absorbed: changing `consistency.py`'s gate to exclude bookkeeping nodes is a separate recovery-semantics decision and out of this unit.

**(h) The audit (issue Fix-direction 5).** One read-only pass over the graphs this lane can reach, plus a read-only scan for pre-preservation rescue files. **No auto-repair.** The result, its exact command, and its three limits (no hosted tenant graph reachable; a completed prior wipe is indistinguishable from never-configured; only the leftover-sidecar direction is positively probed) are recorded on #2814. The operator-facing query lands as a subsection of `docs/durability-posture.md` — no new script.

**(i) Registry vs exporter drift — pin by test, do not unify now.** The export contract is #1936's. The pin is one-directional and correct: `preserved ⊆ exported` — every label-wide config class must **not** be in `_EXPORT_SKIP_LABELS`, every declared Meta key must **not** be in `_EXPORT_SKIP_META_KEYS`, the FTS keys must **not** be declared config keys, and `CalibrationRecorded` must stay in `_NO_PROJECTION_FOLD`. **The reverse direction is NOT a rule** (export-skipped ⇒ derived): `:GraphEventMeta` is export-skipped and load-bearing, so that inference is invalid (§2) — a reverse pin would contradict #4653. The doc declaration and the code registry are pinned to each other instead (decision (j)).

**(j) The declaration's home is the canonical doc, and it is pinned to the code registry.** `docs/durability-posture.md:22-28` states it is "the single source of truth for durability claims" and that other files "must not carry a durability authority claim of their own". So the **complete** node-class map's home is that file — #2296 contributes Indicators 1-3 **into** it, not as a rival artifact (§2's earlier "the complete map stays #2296's" is corrected to this). And because a doc list can silently go stale against `_config_classes()` (the doc gate `tests/test_durability_posture.py` is a text-pattern check over the phrase "source of truth" and never reads node classes), **`test_config_registry_doc_consistency` pins both directions**: `{label-wide preserved} == {c.label for c in _config_classes()}`, `{declared Meta keys} == {TortoiseSDK._CALIBRATION_MARKER_KEY, _CONFIG_RESET_KEY}`, and the declared non-preserved set matches the named set (`:EpMeta`, the FTS keys) — the same bidirectional-liveness shape `tests/tool_surface_capabilities.py:131-215` already uses for `DECLARED_WRITE_SURFACE_MAP`.
