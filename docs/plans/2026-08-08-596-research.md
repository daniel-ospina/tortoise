# Research — #596 (targeted, project depth)

**Date:** 2026-08-08 | **Stage:** research (2 web queries + repo-internal sweep)

## Findings

### Scheduler mechanics (external driver)
- GH Actions `schedule:` is **"quietly unreliable"** — 30–60 min jitter, possible skipped runs under load, no exact-time guarantee (community threads: github/community#156282, #194300; SO 79534419). For a **daily** team backup, jitter/skip is tolerable **iff** the staleness pre-flight + alerting are loud. For the **hourly** registry backup the same applies.
- Fly.io scheduled Machines (`[machine] schedule`) are the alternative; both are external drivers with independent failure domain. **Decision deferred to scope:** workflow (visible run history, zero new infra — chosen default) vs Fly Machine (needs its own deployable unit).
- Mitigation shape: the external driver runs a **staleness pre-flight** (fetch `Team.backup_latest_at`/R2 latest key before backing up; fail loudly if stale) so a down app, a broken workflow, and a missed backup are all *visible*.

### Alerting channel
- Repo has **no Slack/webhook infra** (no SLACK/WEBHOOK/NOTIFY/ALERT in .env.example; no webhook module).
- The repo's established automation output channel is **GitHub issues**: `post-merge-validation.yml` flags issues on failure (#559); test-debt-gate auto-files issues. `scripts/` files issues via gh.
- **Chosen alert channel:** file a GitHub issue (repo-established), plus the failed GH Actions run itself is visible. No new external dependency. (Slack webhook remains a future option — out of scope.)

### Registry / control-plane backup (repo-internal)
- Team nodes live in the registry graph (`namespace='registry'`, `_make_sdk(namespace='registry')`), shape: `id, name, tier ('free' default), backup_enabled (false default), created_at, max_*`.
- `_require_backup_tier(team)` (hosted_api.py:2531) gates backups to Pro — the internal backup-all endpoint must enumerate **Pro teams** (`tier != 'free'` AND `backup_enabled`) from the registry and call the existing `create_backup`/`prune_backups` per team.
- The registry graph itself (`registry_control_plane`) is reachable via `namespace='registry'` — `create_backup` accepts arbitrary `graph_name` + a projection, so the registry is backup-able with the existing machinery (needs its own SDK/projection wiring — see scope).
- `/v1/internal/reconcile` (hosted_api.py:1936, "Called by an external cron; internal-key protected") is the shape template for new `/v1/internal/backup/*` endpoints.

## Design constraints carried into scope
1. External driver primary (independent failure domain — fly.toml documents OOM crash-loops, #545).
2. Staleness pre-flight lives OUTSIDE the app (in the driver) — failure must be loud when the app is down.
3. Alert channel = GitHub issue filing (no new infra).
4. Restore-freshness check = warn-level, never a hard block.
5. Idempotent re-runs (timestamped object keys make duplicate runs harmless; prune keeps retention).
6. Endpoints mirror `/v1/internal/reconcile` (internal-key auth, shape).
