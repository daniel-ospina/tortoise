# A2 — Aggregation + Answer-from-Newer Reader Instructions (#1547)

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

**Goal:** Teach the LongMemEval reader to (a) answer knowledge-update (KU) questions from the newest/superseding point and honor the date-conditional rule (point-in-time → value valid at the asked date via E5's chain-walk, current value as context only), and (b) aggregate multi-session (MSR) questions with counting discipline (distinct events, no double-count, reconcile by date) — expressed purely in ontology terms (subject refs + supersession edges), with **no parallel mechanism, no new fields, no new retrieval path**.

**Team:** epistemic-team
**Role:** (none — plan authored from the epic worktree)

**Architecture:** Prompt-only change in `tools/longmem_eval/reader.py`. The reader's context already carries everything needed — the `[SUPERSEDED BY: …]` / `[SUPERSES: …]` markers (CORRECTS edges rendered, #1367/#1353 landed) and `(session date YYYY-MM-DD)` annotations (E1/`render_context`). A2 adds two type-tailored fragments (`knowledge-update`, `multi-session`) to `_TYPE_FRAGMENTS`, mirroring the existing temporal/preference pattern (#1366). V3 point-in-time restore = walk the supersession chain by session date (E5's co-retrieved CORRECTS state); first-class `valid_at`/`invalid_at` windows are E6's, post-baseline, out of scope here.

## 1. Design Decisions

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Mechanism | **Prompt-only; no retrieval/context/graph changes** | The reader's context already carries the ontology state (supersession markers + session dates). Adding a parallel decoration/query layer violates the owner's "no parallel mechanism" mandate and the epic's ontology-first principle (§2.4 of 00-scope). |
| D2 | Scope of new fragments | Two: `knowledge-update` (answer-from-newer + date-conditional rule) and `multi-session` (aggregation discipline) | The verification checklist names exactly these two failure modes (KU answer-from-newer; MSR aggregation). They are the two categories that consume supersession/cross-session state. `single-session-*` and `temporal-reasoning` are untouched. |
| D3 | Ontology vocabulary in the fragments | Name the reader-visible ontology terms: **subject** (same subject+attribute across entries), **supersession edges** (the `[SUPERSEDED BY]`/`[SUPERSES]` markers = CORRECTS), **session date** (the `(session date YYYY-MM-DD)` annotation = the `when` anchor) | Owner mandate: "expressed via subject refs + supersession edges (ontology terms)". The reader must reason about *versions of the same fact connected by supersession*, not about a parallel flag/layer. |
| D4 | Point-in-time restore (V3) | **Chain-walk on session dates** using the co-retrieved superseding + superseded entries — no `valid_at`/`invalid_at` fields | MECE fix: E6 owns first-class bi-temporal windows post-baseline. V3's E2E-9 mechanism is exactly E5's chain: the superseded point and its superseder are both in context with session-date annotations; the fragment instructs the reader to pick the version whose session date is the latest on/before the asked date. |
| D5 | Date-conditional rule encoding | KU fragment contains **both branches** (current-value → newest/superseding; point-in-time → value valid at asked date, current value as context only) | Review P2 fix on the issue; this is the concrete reader instruction that makes E2E-6 and E2E-9 both pass with the SAME fragment. |
| D6 | Abstention license | Both fragments keep the A1 path open ("state what IS present; say you do not know when the asked value is absent / no version covers the asked date") | Interplay with A1 (#1546, sibling issue): over-committing fragments would burn abstention questions. The existing temporal fragment's "commit-first, abstain-on-absent" pattern is the template. |
| D7 | `MockReader` | **Unchanged** | It answers from `has_answer`-marked evidence turns regardless of type — no aggregation/recency semantics to add; mini-fixture tests (`mini_ku_004`, `mini_msr_002`) already pass via evidence-turn containment and stay green. |
| D8 | Marker rendering | **Unchanged** (`render_context` / `_supersede_marker` untouched) | E5/#1367 owns the marker rendering. A2 consumes it. The only conceivable addition (superseding claim's date inside the marker) is flagged as a conditional gate (G4) + open question O2 — not core scope. |
| D9 | Parity source-string | Update `reader_prompt_source()` in `run.py` in the same PR | `battery/parity/runner.py` hashes that string as the reader-prompt identity for the methodology-unchanged check; if A2 changes the prompt without updating the source string, the persisted hash silently describes a stale prompt (and vice-versa a mismatched unchanged-check). |

**Rejected alternatives:**
- *Parallel restore path / `valid_at` windows in V3* — explicitly forbidden by the MECE serialization fix (E6's job, post-baseline). A2's chain-walk rides E5's machinery.
- *New context decoration (e.g., `[CURRENT VALUE]` tag, subject grouping, per-version dates)* — parallel mechanism + new format; the markers + session dates already suffice for the reasoning the fragments encode. (O2 reopens only if the real run proves the chain is under-visible.)
- *Fold the fragments into `_SYSTEM_PROMPT` unconditionally* — would degrade other categories and break the type-tailored dispatch pattern the reader is pinned around (M5).

**Step 1.1 — Add `_KNOWLEDGE_UPDATE_FRAGMENT`:**

```python
_KNOWLEDGE_UPDATE_FRAGMENT = (
    "\n\nKNOWLEDGE-UPDATE INSTRUCTIONS: this question asks about a fact "
    "that may have changed across sessions. The context can contain several "
    "versions of the same fact (same subject and attribute — e.g. the gym "
    "schedule) linked by supersession edges: the replaced version carries a "
    "'[SUPERSEDED BY: <newer value>]' marker, the newer version carries "
    "'[SUPERSES: <replaced values>]', and every entry is annotated "
    "'(session date YYYY-MM-DD)'.\n"
    "- If the question asks for the CURRENT value (currently / now / these "
    "days), answer from the NEWEST, superseding version — never from a "
    "superseded one. Superseded entries are context only.\n"
    "- If the question asks what the value WAS at a specific date (what "
    "was … at/on/before <date>, back in <month>), answer from the version "
    "whose session date is the latest on or before the asked date — walk "
    "the supersession chain by session date. The current value may be "
    "mentioned only as context, never as the answer.\n"
    "- If no version's session date covers the asked date, or the newest "
    "version is absent, say you do not know rather than guessing."
)
```

**Step 1.2 — Add `_MULTI_SESSION_FRAGMENT`:**

```python
_MULTI_SESSION_FRAGMENT = (
    "\n\nMULTI-SESSION REASONING INSTRUCTIONS: this question spans several "
    "dated sessions in the context. Aggregate across them with counting "
    "discipline:\n"
    "- Count each distinct event or decision ONCE. The same fact restated "
    "in a later session (same subject, same value) is the SAME event — "
    "never double-count it, and do not count mentions as events.\n"
    "- Reconcile by date: when entries conflict, the value from the latest "
    "session date is the current one; earlier entries remain events of "
    "their time (entries may be linked by supersession — '[SUPERSEDED BY: "
    "…]' / '[SUPERSES: …]' markers).\n"
    "- Answer the specific question asked (which/where/when/how many) by "
    "synthesizing from the distinct events — do not dump every entry.\n"
    "- If the asked information is absent from the context, say you do not "
    "know rather than guessing."
)
```

**Step 1.3 — Register both in the dispatch table:**

```python

    "single-session-preference": _PREFERENCE_FRAGMENT,
    "knowledge-update": _KNOWLEDGE_UPDATE_FRAGMENT,
    "multi-session": _MULTI_SESSION_FRAGMENT,
}
```

## 5. ⛔ CONDITIONAL GATE NOTES

> **Bottom line: A2 itself requires ZERO ontology changes, ZERO architecture changes, ZERO new fields.** That is the entire point of the owner's "ontology terms, no parallel mechanism" mandate. Everything below is a *dependency gate* (land before/with A2) or a *deferred-to-E6* boundary, not new A2 scope.

- **G1 (dependency, blocking) — E5 (#1537) must land before A2's value materializes.** A2's fragments consume (a) the `[SUPERSEDED BY]/[SUPERSES]` markers — already rendering today (#1367/#1353), and (b) the eval's co-retrieval of superseded points — `retrieve_for_question` → `hybrid_search` currently calls `tortoise_fts_query` **without `include_terminal`**, so superseded (terminal-status) points are excluded from the base pool. E5's checklist owns the `include_terminal` opt-in for co-retrieval. **A2's integration tests pass `include_terminal=True` directly and do not block on it**; but the real-run E2E-6/9 assertions depend on E5's wiring. If E5's co-retrieval is delayed, A2 ships (harmless — fragments only fire when markers render) but the E2E-6/9 real-run gate stays red until E5 lands.
- **G2 (dependency, non-blocking) — M5 (#1525) reader pinning.** A2 changes the prompt M5 pins. Order is flexible (both land before the run protocol step 3 pilot); M5's methodology must record the final prompt including A2's fragments.
- **G3 (boundary, no action) — E6 owns first-class validity windows.** A2 deliberately implements NO `valid_at`/`invalid_at`/window machinery. Any plan step that adds a window field or a parallel restore layer violates the MECE serialization fix and must be rejected.
- **G4 (conditional scope-creep guard) — superseding-claim date in the marker.** If the real run (protocol step 5) shows E2E-9 chain-walk failures because the superseding point is not co-retrieved and `[SUPERSEDED BY: …]` carries no date, the minimal fix is a decoration enhancement in `_supersede_marker`/retrieve.py (render the superseding claim's `created_at`, which the D8 payload already carries — `search_engine.py:213`), **not** a new mechanism. This is out of A2's core scope and gated on evidence from the run; see O2. Any such change must be coordinated with E5 (#1537, which owns the marker) and R5 (#1544, date ordering).
- **G5 (sync obligation) — parity source string.** Task 4 is mandatory in the same PR: changing `reader.py` without updating `run.py:reader_prompt_source()` leaves the report's persisted `reader_prompt_hash` describing a stale prompt (battery/parity methodology-unchanged check hazard).
