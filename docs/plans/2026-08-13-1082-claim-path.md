## Confirmed Problem
Zero-email teams (anon-/reg- identity rows, NULL user_id) can't complete setup: no verified identifier, no dashboard session access, no recovery — and after #1081's ceiling work, a permanently reduced ceiling with no unlock. #1082 attaches a genuinely verified identifier to the existing owner membership (same key, same team, memories intact) and gates the ceiling raise on that link.

## Merged Solution (controller convergence, 2026-08-13)

**Axis 1 — OAuth transport: GoTrue-native claim (ZERO new server-side OAuth).**
- The platform already ships GoTrue client OAuth (`signInWithProvider`) in signup.html:713-738, signin.html:755-760, and the dashboard (PKCE). No new env vars (GOOGLE_CLIENT_ID etc.), no server OAuth app, no state-token dict, no callback endpoint.
- Claim = ONE endpoint requiring BOTH credentials in one request: pasted `tt_` key (key-possession anchor — structurally the ONLY anchor: anon rows are identity-anchored, teams.email NULL, so no logged-in identity can match an unclaimed team; key gate also blocks the E1 session-rotation ATO ladder) + fresh Supabase session JWT (provider-asserted verified email).
- `POST /v1/claim`: verify_session_jwt (session_auth.py:115-158) → get_current_team with pasted key (hosted_api.py:864) → **assert provider-verified email (invariant): `app_metadata.providers ∩ {github, google} ≠ ∅`** — app_metadata is user-level, always present, survives token refresh (unlike `amr` which is optional and refresh-mutated to `token_refresh`). Secondary confirmatory conjunct: `/auth/v1/user` `email_confirmed_at` (AND, never OR). Fail-closed on null email AND on email+password-only sessions (a confirmed password session must NOT claim + overwrite teams.email — solution-verify P2-3; negative tests: fresh password token, refreshed password token, amr-less token) → derive lookup_hash from the verified key → `claim_membership(p_lookup_hash, p_user_id, p_email)` service-role RPC → audit `team_claim`.
- **Claim rate limit:** reuse #1081's per-IP limiter posture (2/24h) on POST /v1/claim + 429 test (P3-FIX-H restated).
- **Audit shape:** claim migration adds `detail JSONB` to audit_events (0002 has no provider/email columns) — provider, email, user_id in detail; operation='team_claim'.
- GitHub `user:email` scope = Supabase dashboard provider config (not code); fail-closed if email null in JWT.
- Freshness: dashboard claim card calls signInWithProvider on click (fresh assertion by construction); CLI `--claim` prints key + dashboard URL (no device flow — one-time human act, key already printed at mint).

## claim_membership RPC (migration 20260813000003) — BINDING FIXED (solution-verify P1)

**⛔ Authorization binding (P1, refined — solution-verify cycle 2):** the RPC NEVER accepts `team_id`/`identity` from the request body. reg- identities are deterministic (`reg-<sha256(email)[:12]>`) and anon identities surface in api_keys.created_by/audit — client-supplied team_id/identity would let any key + any session JWT claim ANY team. **Resolution path (two steps inside the RPC):**
1. `SELECT team_id FROM api_keys WHERE lookup_hash = $h AND revoked_at IS NULL` — api_keys.lookup_hash is UNIQUE (0007) and revocation-aware (revoked keys never resolve); this is the authoritative key→team binding (NOT team_memberships.lookup_hash which is non-unique and revocation-blind).
2. `UPDATE team_memberships SET user_id=$uid, identity=NULL WHERE team_id=$tid AND role='owner' AND user_id IS NULL AND status='active'` → verify FOUND.
The key's team is the only thing claimable. `api_keys.created_by` carries the anon identity server-side for provenance. Structurally blocks member-key→owner escalation (session keys live only in api_keys with created_via='bootstrap', never owner membership rows).


- SECURITY DEFINER, service_role ONLY, NO auth.uid() inside (P2-FIX-J: session JWT verified server-side in hosted_api; RPC is service-role — mirror tenant-provision pattern).
- **Signature (FINAL): `claim_membership(p_lookup_hash text, p_user_id uuid, p_email text)`** — team_id/identity resolved INSIDE the RPC (never accepted from client); email overwrite INSIDE the atomic transaction (P2-FIX-K).
- Body: (1) resolve team_id from api_keys by lookup_hash + revoked_at IS NULL; (2) UPDATE owner row SET user_id=$uid, identity=NULL, (teams.email=$p_email via teams upsert in same txn) WHERE team_id=$tid AND role='owner' AND user_id IS NULL AND status='active' → verify FOUND (0 rows → 409 already_claimed, concurrent-safe via MVCC row lock); (3) handle uq_member_team conflict (existing ($uid,$tid) row → merge/promote + copy lookup_hash/key_hash + SET status='active' (a 'removed' row promoted to owner must reactivate — P4), drop identity row BEFORE promote — P3-FIX-R); (4) drop leftover placeholder; (5) idempotent re-claim order (P3-FIX-Q): owner by (team_id,user_id=$uid) → noop success; else owner by lookup_hash → link; else 409. Unique-violation catch → 409 email_in_use (P3-FIX-S).
- teams.email overwrite = verified OAuth email (unconditional, P1-FIX-B); partial unique index uq_teams_email + 409 email_in_use on cross-team collision (P3-FIX-S).
- Owner ≤1 invariant: partial unique index **`CREATE UNIQUE INDEX uq_member_owner ON team_memberships(team_id) WHERE role='owner' AND team_id <> ''`** (P3-FIX-P + solution-verify P1: the handle_new_user placeholder rows all share team_id='' + role='owner' — WITHOUT the `team_id <> ''` exclusion, the 2nd+ signup raises a unique violation inside the trigger → platform-wide signup breakage on deploy. Also `AND status='active'` to match the predicate). Migration pre-scan: assert no existing team has 2 owner rows before applying (abort-with-report otherwise). Merge ordering: DROP the identity row BEFORE promoting the member row (promote-first violates the new index mid-transaction).
- Caller-auth at API layer: hosted_api validates claim token/state + session JWT externally before RPC (P2-FIX-J).

## Welcome double-provision guard (P2-FIX-D + solution-verify P2)

**Initial sign-in path:** signup.html:721/signin.html:760 OAuth ALWAYS redirects to WELCOME_URL; welcome.html Phase 2 mints a NEW team when the membership query is empty (RLS hides NULL-user_id rows). An anon owner's FIRST sign-in (needed to reach the dashboard claim card) would mint a stray team before the card exists. Fix: `?claim=1` claim-intent routing from signin/signup → dashboard claim card (never welcome.html) for users with a stored claimable key; welcome's Phase-2 mint additionally checks server-side `GET /v1/claim/status` (key/identity-scoped, service-role) for a claimable identity row before provisioning.

**Dashboard claim card is ALL-NEW client code** (main.jsx has zero signInWithProvider today). The pasted key must survive the OAuth redirect via sessionStorage — NEVER in `redirectTo` (GoTrue puts it in the OAuth state URL → leak).

**Selfhost:** registry-mode anon teams have no claim path (claim requires Supabase JWKS + RPC). Scope decision: the anon-predicate ceiling applies Supabase-mode ONLY in v1; registry mode keeps free tier (selfhost is operator-controlled, not a farm surface) — documented, no claim needed. If registry anon teams later need claiming, that is a separate issue.
- Claim callback/claim card NEVER redirects to welcome.html provisioning before claim RPC commits (welcome.html:724-730 mints a NEW team when no user_id-scoped membership — would orphan). Error/retry page on RPC failure (P3-FIX-U); pre-claim routing uses server-side identity-scoped lookup (RLS hides NULL-user_id rows from authenticated).

## Rejected alternatives (with when-better)
1. Server-side OAuth device flow (github/connect mirror) — new env vars, server OAuth app, state dict, callback endpoint for a ONE-TIME human act. Better when: claim were recurring (it isn't) or GoTrue providers unavailable (they're not).
2. Stored tier column + backfill — drift risk (tier vs predicate), backfill decision for pre-existing teams. Better when: tier-in-DB debuggability is required or a raw teams.tier read exists off the auth path.
3. Edge-function claim service — second prod surface in Deno for a single endpoint. Better when: hosted_api OAuth were already server-side (it isn't — GoTrue-native).
4. Keyless claim (session-only) — structurally impossible: no identity matches an unclaimed team (anon rows identity-anchored, email NULL); would also open E1 session-rotation ATO. Rejected by construction.
5. Email-OTP claim — no unbucketed email infra (GoTrue 30/hr bucket = #801 P1 class; Resend 100/day free); zero OTP plumbing; OAuth = provider-verified with no sends. Follow-on: OTP template + per-recipient Resend send on notify.py path.
