# R5 — Temporal/Recency Implementation Plan (issue #1544)

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

**Goal:** Make the retrieval stack temporally aware — recency-weighted RRF fusion, TR-constraint detection ("between…and…", "ago", "how many days") driving time-window filtering and time-ordered rendering, dated Events in the TR retrieval pool, and a tighter TR top_k cap to cut the transcript flood (9/18 TR losses were reader refusals under ~40k-token floods despite sr@5=1.0).

**Team:** epistemic-team
**Role:** _n/a_

**Epic contract:** `docs/epics/2026-08-20-1509-extractor-v3/03-scope.md` (R5) + `04-plan.md` §5/§7 (architecture component 2 — retrieval; E2E-4 owning test). Test-design surface: #1515 surface 28 (temporal) → E1/R5. Test alignment: E2E-4. Dependencies: E1 (#1533, dates).

**Architecture:** Three cooperating layers, each default-off so the V3 baseline stays byte-identical outside TR:
1. **Engine** (`tortoise/search_engine.py` + `tortoise/sdk.py`): `rrf_fusion` gains an optional recency multiplier (`recency_weights` × `recency_boost`) fed by a batch date fetch (`recency_field`) inside `tortoise_fts_query`. Reuses the existing `_created_sort_key` (ISO + epoch mixed-format safe) — today it is EP-decoration-only; R5 is its first retrieval use. Default off → existing RRF behavior unchanged.
2. **Eval ingestion** (`tools/longmem_eval/ingest.py` + `ingest_v2.py`): session dates land on the graph — `created_at=session_date` on points, one dated `:Event` (kind `lmeHaystackSession`, `startedAt=session_date`) per haystack session with `aboutSession` linkage. E1-adjacent hook: the v2 leg threads `session_date` into `extract_session_v2` (⛔ gated on #1533).
3. **Eval retrieval** (`tools/longmem_eval/retrieve.py` + `run.py`): TR questions (question_type == `temporal-reasoning`) get (a) the events union pool (`point` + `event`), (b) engine recency weighting keyed on the dataset's `haystack_dates` via graph `created_at`/`startedAt`, (c) TR-constraint detection → time-window filter before truncation, (d) time-ascending rendering for the reader context, (e) `tr_top_k=12` cap (20→12). Non-TR questions keep the exact current path (points-only, RRF order, top_k=20) — regression-guarded.

No ontology change: no new kinds, edges, or expansion packs. All node properties used (`created_at`, `startedAt`, `session_id`, `lme_session_index`, `eventId`) already exist. New `eventKind` string `lmeHaystackSession` mirrors the existing eval-instrumentation kind `lmeHaystackCaptured` — not an ontology kind.

## Design Decisions

### D1. Date weight lives in the engine (`rrf_fusion` + `tortoise_fts_query`), default-off
`rrf_fusion` gains `recency_weights: dict[str, float] | None = None` and `recency_boost: float = 0.0`. Final score per doc: `rrf(d) × (1 + recency_boost × weight(d))`. When weights are None or boost is 0, the arithmetic is untouched → **byte-identical output** for all existing callers (including `tests/eval/retrieval/run.py`, `task0_probe.py`, and the 5 existing `TestRRFFusion` cases).

Weight source: `_recency_factors(entries)` — new helper in `search_engine.py` reusing `_created_sort_key` for date parsing. Rank-based percentile among dated candidates: newest → 1.0, oldest → 0.0, undated/unparseable → 0.0 (no boost). Rank-based (not age-based) so it is format-agnostic and immune to out-of-range ages; ties break by id for determinism. `recency_boost` default when enabled: **0.5** (knob — sweep in the run protocol micro-test, protocol step 2).

Why engine-side (not eval-side post-re-rank): the V3 run measures the REAL retrieval stack (E2E-1, "test the real tortoise"); the production memory layer gets "recent facts rank higher" (R5 customer value) for real graphs too, and the eval exercises exactly what production runs. One code path, one test surface.

### D2. `tortoise_fts_query` recency wiring — batch date fetch, fail-open
New kwargs: `recency_field: str | None = None`, `recency_boost: float = 0.0` (clamped 0.0–10.0). Applied **after the RRF fusion + threshold filter (step 4), before the kind filter (step 5)** so it re-ranks the fused candidate set, then `result_ids = list(fused.keys())` truncation picks up the new order. One batch Cypher per call:

```cypher
MATCH (n:{graph_label}) WHERE n.{id_field} IN $ids RETURN n.{id_field}, n.{recency_field}
```

(`id_field` is the existing per-entity field — `id` for Point, `eventId` for Event; `graph_label` likewise.) Any exception → `logger.warning("recency weighting failed — falling back to plain RRF")` + continue with unfused ordering (graceful degrade, matches the engine's circuit-breaker pattern). Callers: the eval passes `recency_field="createdAt"` for points / `"startedAt"` for events.

**Property-name verification (already done, implementer re-confirms):** the canonical Point timestamp property is camelCase `createdAt` — `create_point` (`sdk.py:1408`) creates with `createdAt:$now` and then applies caller props via `SET n += $props` (line ~1434), so an explicit `createdAt` prop **overwrites** the server default; the search engine's existing supersession decoration queries `n.createdAt` directly (`search_engine.py:1038/1059/1081`) and `_created_sort_key` parses the VALUE (key-agnostic). `recency_field` is a Cypher property name and must match the stored key (`createdAt`, not `created_at` — the snake variant appears only as an API alias in the engine's returned dicts).

### D3. Eval ingest writes session dates onto the graph (the recency source)
The eval must give the engine real dates, since turn points are created with `created_at=now` today. `ingest.py` (deterministic leg) and `ingest_v2.py` write, per haystack session:
- Points (turn points, raw transcripts, v2 statement points): `createdAt = session_date` **when the session date is non-empty**, else the explicit sentinel `1970-01-01T00:00:00Z` (deterministic-oldest → recency factor 0). Explicit-write-always avoids the trap where the server default `createdAt=now` silently gives undated sessions maximum recency boost. Mechanism confirmed: `create_point` applies props via `SET n += $props` after the `CREATE`, so an explicit `createdAt` prop overwrites the default (safe in the eval's fresh per-question graphs, where points are created exactly once via the `_point_exists` idempotency guard — the dedup path is not hit). The reader never consumes `createdAt` (it renders the dataset's `haystack_dates` annotation), so the sentinel cannot cause a false date-answer (E2E-4 owned negative stays safe).
- Events: one dated timeline `:Event` per session — `create_event(name=f"lme_{qid}_s{si}", eventKind="lmeHaystackSession", startedAt=session_date, endedAt=session_date, sessionId=sid, lme_question_id=qid, lme_session_index=si, is_episodic=True)` + `(e)-[:aboutSession]->(s:Session)` edge. **Skipped entirely when `session_date` is empty** (undated session → no timeline event; honest absence). `sessionId=sid` (dataset session id) is critical: `session_recall@k` keys on `h["session_id"]`, and events must join the same sessions as points. The existing `lmeHaystackCaptured` provenance event is untouched.

The deterministic leg's per-session events are intentionally minimal (name = `lme_{qid}_s{si}` — they prove the timeline surface, they don't fake extraction). Real event content arrives via the v2 leg's payload events (`eventKind=core:occurrence` etc.), which get `startedAt=session_date` — ⛔ gated on E1 (#1533) threading `session_date` into `extract_session_v2` (see Conditional Gates).

### D4. TR questions get the events union pool; non-TR stays points-only
`hybrid_search(sdk, query, limit, *, entity_types=("point",), recency_fields=None, recency_boost=0.0)`. TR questions pass `entity_types=("point", "event")`; results merge by RRF score desc (each hit carries `scores.rrf` via `SearchResult.to_dict()`, comparable across the two calls — same k constant, same leg structure), deterministic tiebreak on id. Event hits use `eventId` as `id` — the Point/Event namespaces never collide (different label, different id field).

Rationale for TR-only union: changing the pool for all question types would confound the V3 baseline against v2 (M8 statistical discipline — vary one component at a time). E2E-4's "no `entity_type='point'` filter only" is satisfied for the TR category where dated events matter.

### D5. TR-constraint detection → time-window filter
New `detect_time_constraint(question_text) -> TimeConstraint` (dataclass: `kind ∈ {"interval", "recency", "ordering", None}`, `start`, `end`) in `tools/longmem_eval/retrieve.py`, gated on `question_type == "temporal-reasoning"` (authoritative) with regex refinement:

| Kind | Trigger | Behavior |
|---|---|---|
| `interval` | `between <date> and <date>` (ISO or `Month day[, year]`) | hard filter: keep hits whose `session_date ∈ [start, end]` (inclusive) |
| `recency` | `N days/weeks/months ago`, `last N …` | hard filter: `session_date ∈ [question_date − N_days, question_date]`; unit map day=1, week=7, month=30 |
| `ordering` | `how many days`, `how long`, `when did`, bare `ago` with no bound | no filter — the question needs the full dated set to compute a span/ordering |
| `None` | no match | no filter, no reorder (pure date-weight path) |

Window filter applies **before top_k truncation** on the annotated hits (session_recall@k therefore measures the in-window pool — correct TR semantics). **Defensive rule:** when the filter would empty the dated pool (no in-window hits), fall back to the unfiltered pool (never starve the reader into abstention) — recorded as `"tr_window_fallback": true` in the retrieval result.

### D6. Time-ordered rendering (ascending) for TR
For TR questions, after truncation the **context** handed to the reader is stable-sorted ascending by `session_date` (dated first, undated last). `render_context` is unchanged — ordering arrives in the list. Recall metrics keep retrieval (RRF+dateweight) order — they measure retrieval, not rendering. Ascending order makes the reader's timeline computation natural for the dominant "how many days ago / between X and Y" shapes (the `_TEMPORAL_FRAGMENT` already instructs the reader to compute from the per-session date annotations). New optional `render_order: str = "rrf" | "time_asc"` on `retrieve_for_question` (default `"rrf"`).

### D7. TR top_k cap 20→12, knob-exposed
`run.py`: `DEFAULT_TR_TOP_K = 12`; new CLI `--tr-top-k` (default 12), `--tr-date-weight` (default 0.5), `--tr-events/--no-tr-events` (default ON). `retrieve_for_question` computes `effective_top_k = tr_top_k if is_tr else top_k`. The three knobs are recorded in the report methodology (M7 provenance) and available for the run protocol's knob sweeps (protocol steps 2/6). Note: R1's session-dedup (#1540) is the complementary flood control; R5's cap is independent and lands regardless.

### D8. Event annotation on the eval path
New `event_props_for_hits(proj, event_ids)` in `ingest.py` (one batch Cypher on `(n:Event)` by `eventId` returning `sessionId`, `lme_session_index`; `has_answer` hardcoded False — evidence marking is point-level, M6 scope). `_annotate_hits` merges `point_props | event_props` (namespaces disjoint; lookup by `h["id"]` unchanged). `session_date` annotation comes from the existing `lme_session_index → haystack_dates` mapping, identical for both labels.

```python
def _recency_factors(entries: list[tuple[str, Any]]) -> dict[str, float]:
    """Rank-based recency factor per id, newest→1.0, oldest→0.0.

    Reuses ``_created_sort_key`` (ISO + epoch mixed-format safe, #1353).
    Undated/unparseable ids get 0.0 (no boost). Ties on the same date sort
    by id for determinism and share the highest factor in their rank group.
    """
    dated = [(pid, _created_sort_key(d))
             for pid, d in entries if d not in (None, "")]
    factors: dict[str, float] = {pid: 0.0 for pid, _ in entries}
    if len(dated) < 2:
        return factors
    ordered = sorted(dated, key=lambda t: (t[1], t[0]))
    n = len(ordered)
    for i, (pid, _k) in enumerate(ordered):
        factors[pid] = (n - 1 - i) / (n - 1)
    return factors
```

And update `rrf_fusion` (keep existing docstring, add params):

```python
def rrf_fusion(
    ranked_lists: list[list[tuple[str, float]]],
    k: int = 60,
    *,
    recency_weights: dict[str, float] | None = None,
    recency_boost: float = 0.0,
) -> dict[str, float]:
    scores: dict[str, float] = {}
    for ranked in ranked_lists:
        for rank, (pid, _score) in enumerate(ranked):
            rrf_score = 1.0 / (k + rank + 1)
            scores[pid] = scores.get(pid, 0.0) + rrf_score
    if recency_weights and recency_boost > 0:
        for pid in scores:
            w = recency_weights.get(pid, 0.0)
            if w > 0:
                scores[pid] = scores[pid] * (1.0 + recency_boost * w)
    return dict(sorted(scores.items(), key=lambda x: x[1], reverse=True))
```

```python
@dataclass(frozen=True)
class TimeConstraint:
    kind: str | None            # "interval" | "recency" | "ordering" | None
    start: str | None = None    # ISO date (interval) | day count (recency)
    end: str | None = None      # ISO date (interval)

_UNIT_DAYS = {"day": 1, "week": 7, "month": 30}

def detect_time_constraint(text: str, *, default_year: int | None = None) -> TimeConstraint:
    """… see Task 5 acceptance …"""
    t = " ".join(text.lower().split())
    # recency bound: "N days/weeks/months ago" / "last N …"
    m = re.search(r"(?:(\d+)\s+(days?|weeks?|months?)\s+ago|last\s+(\d+)\s+(days?|weeks?|months?))", t)
    if m:
        n = int(m.group(1) or m.group(3)); unit = (m.group(2) or m.group(4)).rstrip("s")
        return TimeConstraint("recency", start=str(n * _UNIT_DAYS[unit]))
    if re.search(r"\bago\b", t) and re.search(r"\bhow\s+(many\s+)?days\b", t):
        return TimeConstraint("ordering")
    # interval: "between <Month day> and <Month day>" (year from default_year)
    m = re.search(r"between\s+([a-z]+)\s+(\d{1,2})\s+and\s+([a-z]+)\s+(\d{1,2})", t)
    if m:
        def _iso(mon, day):
            d = datetime.strptime(f"{mon} {day} {default_year or 2026}", "%B %d %Y")
            return d.date().isoformat()
        return TimeConstraint("interval", start=_iso(m.group(1), m.group(2)),
                              end=_iso(m.group(3), m.group(4)))
    if re.search(r"\bhow\s+(many\s+days|long)\b|\bwhen\s+did\b", t):
        return TimeConstraint("ordering")
    return TimeConstraint(None)
```

(Exact regexes are guidance — tune against the fixture TR questions + the full-S-split TR subset during the run protocol micro-test; the dataclass contract is the stable surface.)
