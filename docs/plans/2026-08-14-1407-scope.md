# Issue #1407 Scope — Scenario corpus v1: sealed, deterministic scenario packs

## Confirmed Problem

The Agent-Reasoning Eval Battery (epic #1402) needs a **single owned, sealed, deterministic scenario corpus** that every downstream consumer (Tier-1 probes #1409, Tier-2 streams #1411, Tier-3 differential #1412, parity #1413) loads. Without it: (a) scenario content would be duplicated/diverged across probe modules, (b) gold answers could leak into the reader path (S5 flag — corrupts every delta), (c) repeated runs would drift (no determinism, S7), and (d) train/waves/held-out splits would be ad-hoc (L2/L3 contamination control unverifiable).

The corpus must be the **single owner of ALL scenario content** — Tier-1 packs (20 decision, 15 contradiction with pinned k=5, 15 calibration-with-known-outcome, 10 retraction), loopy/contested (≥10), D4 adversarial attack_type pack, and Tier-2/Tier-3 stream packs (6 families × 3 reps, 10 interdependent, held-out wave variants, A/¬A cross-session contradictions, decision-drift, D3 feedback-loop) — with gold answers **sealed** (gitignored store, reader-path guard) and **splits** (train/waves/held-out).

### Why This Framing

- **Root cause framing:** the epic's plan §4 defines the scenario.json schema and the S5/S8 verification checklist; the issue's O/I/T defines counts and sealing. The problem is a *content + sealing infrastructure* problem, not a *harness logic* problem (harness is #1406/#1409+).
- **Alternative framings considered and rejected:**
  - *"Corpus is just a big static JSON committed once"* — rejected: no reader-guard, no determinism verification; a committed corpus.json without a builder cannot be re-verified (S5 flag) and content drift is unmanaged. (Strongest static variant — committed corpus.json + committed separate golds file with load-time separation — was also weighed: it wins on zero-machinery but loses on authoring ergonomics, schema validation at authoring time, regeneration determinism, and tamper-evidence hashes; the builder's ergonomics/validation win is decisive for a corpus the team will iterate on across waves.)
  - *"Scenario packs authored directly in each probe module"* — rejected: violates "single owner of ALL scenario content" (epic-decompose §3 decision); causes cross-module drift and makes splits/sealing unmanageable.
  - *"Gold answers stored only in a gitignored authoring file, absent from the repo entirely"* — rejected: breaks determinism for fresh clones/CI (gold store could not be rebuilt → scorer path dead), and the epic's data model puts gold in the scenario record. The seal's job is *reader isolation*, not cryptographic secrecy (internal tooling — plan §4 "no RLS needed").
  - *"Per-pack YAML files (corpus/{r1,r3,contradiction,...}/packs.yaml) + builder glob"* — rejected for atomic cross-pack validation and single-source simplicity; revisit at ~200 scenarios if the single file becomes diff-hostile.
- **Deviations from the issue's literal wording (flagged):** (1) golds authored in committed `corpus.yaml` rather than only in the gitignored store — the store remains gitignored + reader-isolated, but authored golds live in YAML under the reader-isolation threat model (internal tooling; the S5 flag is about *reader-path leakage*, which the guard eliminates — plaintext golds never reach the agent under test, never appear in the committed reader artifact `corpus.json`, and machine-readable scorer golds stay out of PR diffs via the gitignored store). (2) the held-out L2 family is the **6th authored template, not a 7th**: 5 templates × 3 reps in waves + 1 held-out template × 3 reps = 18 total ("6 families × 3 reps" satisfied as 5×3 waves + 1×3 held out).
- **Threat model (file-read vector):** the S5 seal is reader-isolation: the reader-rendered prompt and the committed reader artifact (`corpus.json`) contain no gold. Committed `corpus.yaml` does contain authored golds — residual risk: an agent-under-test with repo read access could read `battery/config/`. Mitigation: arm adapters must not grant the agent repo access to `battery/config` (folded into the S4 arm-isolation contract; residual risk accepted for internal tooling — the agents under test are sandboxed harness arms, not repo-exploring agents).
- **Falsification check (rendered as acceptance criteria):** AC1 — every required pack loads with its authored count (pack loadability); AC2 — no gold of any scenario is reachable via the reader path: load-time (no gold key) AND render-time (no gold substring in rendered prompt, allowlist for enum tokens) AND store (gitignored, sealed, fails closed); AC3 — determinism: two builds are byte-identical, fresh clone rebuilds identically; AC4 — splits: every scenario in exactly one split, held-out non-empty, ≥3 waves; AC5 — k=5 pin enforced at build time; AC6 — controls bijection (15↔15). Maps 1:1 to the issue's O/I/T indicators (corpus.json with packs+splits; gold sealed; k pinned; attack_type field).
- **Confidence:** 90 — residual risk: contract ambiguity at the edges (k-bounds, controls ownership) is now pinned in the pack table below; would drop to ~75 if E2E-1.2 controls were not corpus-owned.

**Packless families (documented, no corpus pack):** L6 (distillation fidelity — re-scores existing corpus scenarios via #1411), D2 (longitudinal spread — reuses L1/L2 streams via #1412), D1 (verdict rule — profile assembly only, #1415).

**Controls (E2E-1.2 FP gate):** exactly **15** of the 20 decision scenarios carry `matched_control_for: <contradiction_id>` forming a **bijective pairing** — every contradiction scenario is referenced by exactly one control (builder invariant + manifest count == 15). Matching criteria: control has the same family shape (R2/R4-style decision with comparable turn count ±1) so the FP measurement is meaningful (matched non-contradictory input).

**wave_variant interpretation (E2E-2.3):** variants are one-shot, held out from all waves, presented only at the wave-3/final checkpoint; each carries `variant_of: <train decision id>` (builder resolution invariant).

**Cross-session k (L4):** `cross_session_contradiction` scenarios also carry the `k` injection field (=5, the session index of the ¬A plant) so k semantics are uniform across both contradiction-bearing packs.

**Tier semantics:** `tier` = scenario shape (probe = single-session; stream = multi-session script; differential = hostile/robustness). Downstream Tier-3 pack selection (#1412) MUST select by `family`/`task_type`, never by `tier` alone — `feedback_loop` (D3) is stream-shaped but Tier-3-scored, and `adversarial` (D4) is differential-shaped.

**Reader-guard semantics (render-time):** `render_reader_prompt` renders the arm-compatible prompt pack ONLY — `attack_type` and other metadata are consumed by the harness/scorer (#1412) and must NOT be rendered into the agent prompt (rendering it would spoil E2E-3.5's adversarial realism). The gold-substring scan uses exact-match on full gold values; the allowlist for enum-shaped golds is **derived from the schema's gold-enum constants** (the same constants the builder validates against — single source, cannot drift) e.g. `undecided`. Adversarial `attack_type` is excluded from the scan because the D4 gold is the expected action/confidence, not the attack label.

**Builder manifest (emitted in corpus.json):** `{corpus_version: "1.0", content_sha256, golds_sha256, pack_counts: {...}, family_coverage: [...], split_counts: {train, wave-1, wave-2, wave-3, held_out}}`. `content_sha256` = canonical digest of the reader-facing scenarios array; `golds_sha256` = canonical digest of `.gold_store/golds.json` — `verify_seal` compares the store digest against `golds_sha256` (per-scenario records additionally carry `gold_sha256` replacing the gold). Downstream run_artifact.json records `corpus_version` + `content_sha256` (pinning contract — S5 "pinned dataset versions"; parity leg refuses on mismatch per plan §6; run_artifact schema owner: #1406).

## External Research (Phase 1.5 artifact)

### Axis Research

> **Findings date:** 2026-08-14 · **Granularity:** task-level (standard); PRIOR_RESEARCH dedup against epic research brief (02-research-brief.md) + battery spec + scope 03-scope.md. Axes fired: Content/S5 (benchmark dataset structure, gold handling, splits) + Architecture (sealing mechanism). In-repo precedent scanned first.

**Axis 1 — Benchmark dataset schema conventions (Content/S5)**
- *Canonical:* Released agentic-memory benchmarks use **JSONL, one record per task**, with task content and gold answers co-located in the record but **consumed only by the evaluator** — the agent-under-test never sees the record's gold fields. MemoryArena (ZexueHe/memoryarena, HF; https://huggingface.co/datasets/ZexueHe/memoryarena + https://memoryarena.github.io/): rows `id`, `questions[]` (subtask queries), `answers[]` (per-subtask golds), `backgrounds`; multi-session interdependent subtasks with strict causal ordering. LongMemEval (in-repo `tools/longmem_eval/dataset.py`): per-instance `question, answer, haystack_sessions[{role,content,has_answer}]` — the `has_answer` stamp marks evidence turns; the reader only ever sees sessions, the judge sees the gold.
- *Competitor variance:* τ-bench/tau2-bench (https://github.com/sierra-research/tau-bench, https://github.com/sierra-research/tau2-bench) separates **evaluation criteria from task instructions**: `instruction` (agent-visible), `evaluation_criteria.actions` (one reference trajectory — replayed on a fresh env to derive a target DB end state compared by hash), `communicate_info` (substring golds), `nl_assertions` (LLM-judge golds); rewards multiply per `reward_basis`. Key pattern: **gold is used to derive an end-state expectation, never fed to the agent**.
- *Pitfall:* "Gold-like answers" bias LLM judges (AI21, https://www.ai21.com/blog/gold-like-answers-benchmarks/); unvalidated judge rubrics on task/tool tasks show low reliability (epic brief arXiv 2606.29920). → Golds should be *deterministic machine-checkable* where possible (expected outcome / direction / enum), not free-text prose.

**Axis 2 — Gold handling + contamination control / splits (S5, S8)**
- *Canonical:* **held-out split at example-creation time** — a portion (10–20%) physically isolated before development begins, used once at final evaluation; for streaming/rotating benchmarks, larger holds (25–30%) with pre-published rotation (https://theneuralbase.com/llm-benchmarks/learn/advanced/holdout-verification/). "Stop Uploading Test Data in Plain Text" (Jacovi et al., EMNLP 2023, https://aclanthology.org/2023.emnlp-main.308.pdf): prevent contamination by **encrypting/restricting test data**, refusing to evaluate without training-exclusion controls; few-shot prompts are contaminated data too.
- *Competitor variance:* NeurIPS 2025 Datasets & Benchmarks "Establishing Best Practices for Building Rigorous Agentic Benchmarks" (https://proceedings.neurips.cc/paper_files/paper/2025/file/f316275b44ee2de533102913828a8107-Paper-Datasets_and_Benchmarks_Track.pdf): R.3 "private, held-out test set at benchmark release", R.4 "consistently update challenges to avoid overfitting", R.10 ground-truth noise quantification.
- *Pitfall:* iterating on a test set leaks information even without training (selection-bias feedback loop); the strongest preventive strategies are dynamic/rolling refresh + private holds (EMNLP 2026 contamination survey, "Are LLM Benchmarks Already Contaminated?", https://aclanthology.org/2026.gem-main.50.pdf). → For an internal battery: **author splits at creation time** (per-scenario `split:`/`wave:` in the YAML — not derived later), **commit the reader-facing corpus.json to pin dataset version** (S5), and **gitignore + hash-seal the gold store** (tamper-evidence; machine-readable scorer golds never in PR diffs). Authored golds in committed YAML are accepted under the reader-isolation threat model (internal tooling — the S5 flag is reader-path leakage, which the reader-guard eliminates; deviation from the issue's literal store-only wording flagged above).

**Axis 3 — In-repo precedent (Architecture)**
- *Canonical:* `tools/longmem_eval/` (issue #1144) establishes the runner pattern: dataset loader (stdlib, never committed, cache outside repo), `reader.py` (LLMReader/MockReader — reader sees context only), `judge.py` (gold comparison), `retrieve.py` (render_context). Our corpus mirrors: loader + reader-safe loading + sealed golds for the judge/scorer. Tests import via `sys.path.insert(0, repo_root)` + `tools.longmem_eval.*` — battery uses the same convention (`battery.*`).
- *Pitfall:* the longmem_eval reader/judge separation can silently regress when corpus content grows — gold answers could creep into prompt material (e.g., a scenario author writing the expected outcome into the scenario text). Guard tests must be **load-time (schema: no gold key in reader dicts) AND render-time (rendered reader prompt contains no gold substring)** — both sides asserted, not just unit-level field checks.

  - `battery/config/build_corpus.py` — `build_corpus(source=None, out_dir=None) -> BuildResult` (writes `corpus.json` + `.gold_store/golds.json`); deterministic (pinned seed, canonical serialization: `json.dumps(sort_keys=True, ensure_ascii=False, indent=2)`, no sets, no timestamps/absolute paths — contributor rule); validates schema + invariants (below); refuses on invalid corpus.

- **Test matrix (each invariant → test):** schema/fields+enums+ids · pack counts (20/15/15/10/12/10/18/10/6/6/6/6) · k=5 pin (contradiction + cross-session) · sealing (no gold plaintext in corpus.json; store gitignored; per-scenario gold_sha256 present + store digest matches manifest golds_sha256; load-time no-gold-key; render-time no-gold-substring with enum-derived allowlist) · splits partition (exactly-one, held-out non-empty, ≥3 waves) · controls bijection · determinism (build twice → byte-identical; fresh-clone rebuild diff) · zero-context render (self-contained prompt packs) · GoldStore fail-closed (SealMissingError/SealMismatchError).
- **Surfaces:** S5 (benchmark data — pinned corpus.json + version/sha recorded in run_artifact by downstream; sealed golds), S8 (config — schema). No DB, no external services, no auth.

## Rejected Alternatives

1. **Static committed corpus.json only (no builder, no yaml):** cannot regenerate the gold store deterministically; content edits bypass validation; sealing unverifiable. Chosen approach's builder re-derives corpus.json + store from YAML → drift impossible, hashes verify the seal. (Strongest static variant — corpus.json + committed golds file with load-time separation — also rejected: see "Why This Framing".)
2. **Gold store as the only gold source (golds NOT in yaml):** fresh clones/CI cannot rebuild the scorer path; determinism across machines breaks. Rejected — YAML remains the source of truth; the gitignored store is the *deployment artifact* the scorer reads, never committed, never in the reader path.
3. **Splits derived by the builder (random assignment):** violates "split at creation time" best practice (teams can re-roll until convenient). Splits are authored per scenario; builder only validates the partition.
4. **Per-pack YAML files (corpus/{r1,r3,contradiction,...}/packs.yaml) + builder glob:** rejected for atomic cross-pack validation and single-source simplicity; revisit at ~200 scenarios.
