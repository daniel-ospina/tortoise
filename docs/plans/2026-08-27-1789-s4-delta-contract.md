# Plan — #1789: S4 re-emit tax — switch to a delta/gaps-only contract

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.
>
> **Base note:** local `main` is STALE (HEAD fdc0e568, `_S2_S4_MAX_TOKENS = 8000`). The #1787 cap raise IS merged on `origin/main` (PR #1811, `_S2_S4_MAX_TOKENS = 16000`, `_scaled_deadline`, `deadline_aborts`). **Task 0 rebases onto origin/main.** Line references in this plan are to the LOCAL tree (pre-#1787) unless marked `[post-#1787]`; the two trees differ by ~+15 lines in the S4 region.

**Goal:** Eliminate the S4 re-emit tax — S4 currently re-emits the COMPLETE embed list (S2 + corrections + gaps) per call, making S4 output ≈ 1.4–2× S2 output (the tax: extra cost, extra latency, and the truncation surface #1787's cap raise reduced but did not eliminate). Switch S4 to a **delta/gaps-only contract**: S4 emits only gap additions + full-item corrections in the SAME contract shape; the existing E4 programmatic union merges them into the S2 base. Outcome targets: S4/S2 output ratio < 0.5 (implied ≥ 50% output reduction on the expected [1.4, 2] baseline — satisfies the issue's ≥ 40% target with margin), no accuracy/recall regression (accuracy ≥ 0.826, chunk_evidence@20 ≥ 0.738 — the HARD floor, hold-or-improve vs the 0.7375 baseline; the #1787-recorded [0.7375, 0.738) sign-off band is NOT inherited by this plan — I-2-4), no new partial-loss modes.

**Team:** epistemic-team
**Tier:** standard (complexity:standard — Architecture domain; bounded prompt+call-site+measurement surface, no contract/schema/merge rewrite)

**Architecture:** Default-on `TORTOISE_S4_DELTA` env gate selects delta variants of the S4 templates (`S4_TMPL_DELTA` / `S4_TMPL_CORE_ONLY_DELTA`) whose instructions teach "emit ONLY gap additions + full-item corrections; unchanged S2 items are preserved by the merge — omit them". The existing E4 `merge_embed_lists` (extractor_v2.py:1506) already implements the delta-apply semantics: S4 wins on `_merge_key` identity collision (correction), S2 items S4 omits are PRESERVED (no silent drops), S4-only items append (gap addition), retractions merge additively. `_OUTPUT_SCHEMA` (D5, #1746 coupling) is UNTOUCHED — same item shapes; the D5 "contract edit → schema edit" coupling never fires. The legacy `S4_TMPL`/`S4_TMPL_CORE_ONLY`/`OUTPUT_CONTRACT` constants stay byte-identical (revert path). Three bounded code changes accompany the prompt rewrite: (1) the merge-condition gate fix (a retractions-only/chain_notes-only delta is dropped today — silent data loss that becomes first-order under delta); (2) a truncation-only fallback that re-runs S4 under the DELTA contract with an elevated cap (`_S4_DELTA_FALLBACK_CAP = 2 × _S2_S4_MAX_TOKENS`) when the delta truncates — partial-accept OR truncated-without-prefix (a truncated delta loses gap ADDITIONS — facts that exist nowhere else — strictly worse than the pre-delta loss profile; the complete-list retry was REJECTED because it is a strict SUPERSET of the delta output and at the same cap truncates at the SAME point, recovering nothing — the elevated-cap delta retry recovers precisely the delta's lost tail ADDITIONS at strictly fewer tokens (tail corrections of attempt-1-unreached items follow the pre-delta loss profile — the S2 original stands — parity, not a new loss mode; I-A); (3) measurement: per-stage token accounting + a `s4_delta_reemit_suspect` compliance flag + replay gates, since the whole value rests on the model honoring "do not re-emit" (the #1787 Task 5 harness did not land — Task 1 builds the minimal version).

## Part 1 — Scoping (issue-scoping double diamond)

### 1.1 Confirmed problem (Phase 2 converge, post problem-verify + second-model fixes)

**S4's template-mandated complete-list re-emission is a real structural tax — S4 output is the full embed list plus gaps plus corrections (≈ 1.4–2× S2 output), and the delta contract is the structural fix, with #1787's cap raise owning the truncation component.**

Evidence (verified in code, reval artifacts, and the #1787 plan):

- **The contract compels re-emission:** `S4_TMPL` (extractor_v2.py:1300) says "OUTPUT — ONE JSON object, the **COMPLETE embed list (S2 + gaps)**, SAME contract" (:1331) and "**Re-emit the S2 items you keep**, corrected where the search results show they already exist (lifecycle changed/unchanged + supersedes = the existing id)" (:1335). `render_s4_prompt` (:1432) injects the full S2 list via `{embed_list_json}` — so S4's input carries the list AND its output re-emits it. The tax is in the template contract, not an inference.
- **The merge already implements delta-apply semantics:** `merge_embed_lists` (:1506, E4 #1536 "merges-not-replaces") is a programmatic union — S4 wins on `_merge_key` identity collision (correction → replace), S2 items S4 omits are PRESERVED (no silent drops), S4-only items append (gap → add). `_merge_key` (:1481): entities by (name, kind); events/points by normalized content; operators by full tuple; retractions by (content | id). **This is the load-bearing fact: the "merge in code" the issue asks for already exists** — the delta contract is a prompt-contract change plus bounded call-site fixes, not a merge rewrite.
- **The D5 coupling (#1746) does NOT fire:** `_OUTPUT_SCHEMA` (:4133) + `_validate_output_shape` (:4158) are hand-derived from `OUTPUT_CONTRACT`; a same-shape delta keeps the same sections and item keys, so the schema and the ladder's partial-accept rungs are unchanged. The issue's #1746 blast-radius worry is avoided by design (see §1.5 rejected S-B).
- **Truncation attribution is structurally real but not stage-measured:** reval checkpoint: 12/46 qids `llm_truncated > 0` (15 calls, 9×1 + 3×2), 9 `partial_parse` census events; the checkpoint does NOT attribute S2 vs S4 ("S4 fails 8 vs S2 6" is the #1746 pilot observation). #1787's structural analysis (S4 output ≈ 2× S2 → S4 truncates first) stands; the "≈ 2×" ratio itself is [unverified] — Task 1 measures it. **Division of labor:** #1787's cap raise (merged, 16000) owns "truncation → near 0"; this issue owns output size / cost / latency + non-regression. **Indicator (2) re-scoped (deliberate):** the issue's indicator (2) says truncation "drops further"; #1787 owns the truncation→near-0 target, so THIS plan's truncation gates are NON-REGRESSION (≤ baseline) PLUS an expected-direction note — further reduction is expected and recorded when observed, but the gate floor is non-regression. Unit approximation recorded: LongMemEval questions map 1:1 to `extract_session_v2` sessions, so per-session R_new ≈ per-chunk.
- **The ≥ 40% target is ratio-anchored (post-verify fix):** baseline S4/S2 ratio R_b is unverified (expected [1.4, 2]). Two constants share the 0.5 value by design: the runtime flag's item-ratio `_S4_REEMIT_SUSPECT_RATIO = 0.5` and the E2E token-ratio threshold `_S4_R_NEW_THRESHOLD = 0.5` (falsification red-wins FAIL when mean R_new ≥ 0.5; acceptance green when mean R_new < 0.5); the aggregate verbatim ratio uses `_S4_VERBATIM_AGG_RATIO = 0.5` (I-2-11). The three quantities share a COINCIDENTAL numeric value and DIVERGE BY DESIGN — the "single source of truth" claim is scoped to the ITEM-RATIO measures only; a compliant high-gap session trips the token ratio but not the item-ratio flag (the I-8 disambiguation exists for exactly this). Since R_b ≥ 5/6 ≈ 0.8333 expected (the exact anchor bound: reduction = 1 − R_new/R_b, so at R_b = 5/6, R_new = 0.5 ⟺ exactly 40% — I-2-2), R_new < 0.5 IMPLIES ≥ 40% reduction in all cases — the two anchors are non-overlapping and coherent. An R_b measured BELOW 5/6 would itself trigger falsification (1): the ≥ 40% target is unattainable from such a baseline (I-2-2). The measured R_b is still recorded (documents the actual tax magnitude + feeds the S-D follow-up decision).

### 1.4 External research (Phase 1.5 artifact)

#### Axis Research (Architecture — the rated high axis)

**A1 — Competitor delta/ADD-only contracts (canonical):**
- **Mem0 v3 = single-pass ADD-only extraction**: retrieves top related memories for context, ONE LLM call to extract distinct new facts, dedups exact duplicates, inserts without overwriting — new facts coexist with old. v2 (paper) was two-pass extract→compare→ADD/UPDATE/DELETE/NOOP with "replace when a richer fact is found" (upsert semantics). Sources: docs.mem0.ai/migration/oss-v2-to-v3, docs.mem0.ai/migration/platform-v2-to-v3, mem0.ai/blog/mem0-the-token-efficient-memory-algorithm, arxiv.org/html/2504.19413.
- **Zep/Graphiti = bi-temporal episodic delta**: data ingested as discrete episodes; each episode extracts only NEW entities/relationships incrementally; graph edges carry temporal validity windows (created_at, expired_at, valid_at, invalid_at); new episodes INVALIDATE old edges — never re-emit, never delete. Sources: getzep.com/ai-agents/temporal-knowledge-graph/, help.getzep.com/graphiti/getting-started/overview, blog.getzep.com/beyond-static-knowledge-graphs/, arxiv.org/abs/2501.13956.
- **Letta = memory blocks + paging + partial updates**: structured persisted blocks with size limits, always in context; `client.blocks.update()` is a PARTIAL update; `client.blocks.list()` is cursor-based paginated — bounded emission, never dump everything. LangMem = background extract/consolidate/update manager. Sources: letta.com/blog/memory-blocks/, docs.letta.com/v1-sdk/memory/memory-blocks/, deepwiki.com/letta-ai/letta-python/7.1-memory-blocks, langchain-ai.github.io/langmem/.
- **Pattern takeaway:** every production memory system bounds per-call extraction units and never re-emits the full entity list — our S4 full re-emit is the documented anti-pattern. The delta OUTPUT is always paired with a deterministic merge/reconcile/dedup layer — our E4 union IS that layer (this design's key advantage over a naive "emit deltas and hope").

**A2 — ADD-only pitfalls (pitfalls framing — drives the corrections channel):**
- Mem0's ADD-only surfaces stale/contradictory facts; contradicting facts are LINKED (linked_memory_ids), not deleted; supersession/contradiction is declared an open challenge requiring temporal modeling. Sources: github.com/mem0ai/mem0/issues/4956, github.com/mem0ai/mem0/issues/4536, mem0.ai/blog/state-of-ai-agent-memory-2026.
- **Implication:** pure ADD-only (F2/S-D) without an explicit correction/retraction channel causes exactly the staleness our lifecycle/supersedes/E7 machinery prevents — the delta contract must KEEP a corrections channel (full-item corrections under identity) and the E7 retractions array. This is the direct response to the Mem0 pitfall.

**A3 — Structured-output extraction best practices (canonical + pitfalls):**
- Microsoft best-practices for structured extraction recommend "iterative field updating to reduce drift, omissions, and noisy overwrites". Source: github.com/microsoft-partner-solutions-ai/best-practices/blob/main/structured_output_extraction.md.
- Instructor: schema shape / field naming measurably affects structured-output accuracy — an argument against the wrapper-bucket shape change (S-B) and for the same-shape delta. Source: python.useinstructor.com/blog/2024/09/26/bad-schemas-could-break-your-llm-structured-outputs/.
- HN: structured outputs create false confidence — early/cheap validation recommended; supports the replay compliance gate + falsification pair. Source: news.ycombinator.com/item?id=46345333.
- arXiv 2606.22030v2: "the delta of an update is the primary stored artifact — change records rather than only final observed state" — validates the delta-as-output-contract direction and the future delta-journal. Source: arxiv.org/html/2606.22030v2.
- aiworkflowlab.dev (cited in #1787 as the Letta-paging source): production agent-workflow journal (n8n/LangGraph/MCP) — verified reachable; homepage confirms the production-agent engineering focus.

### 1.6 Solution converge (Phase 5) — recommendation

**Choose S-A with the bounded fallback slice (I-2-2), NOT the full S-C runtime two-shot, NOT S-D.**

Rationale (quality-over-convenience):

1. **It fixes the root mechanism with zero merge/schema surface:** the same-shape delta reuses the verified E4 union (collision = update, append = add, omit = preserve) and leaves `_OUTPUT_SCHEMA`/`_validate_output_shape` byte-identical (the ladder's rung-4 mirror widens to all 7 `_OUTPUT_SCHEMA` sections — Task 3, I-E). The issue's "merge in code" is honestly satisfied by existing machinery — the wrapper (S-B) would ADD a new merge path, a schema edit (D5 coupling), and id-based refs the model cannot reliably produce.
2. **The I-2-2 partial-accept fallback is non-negotiable, not nice-to-have:** a truncated delta loses tail ADDITIONS (facts that exist nowhere else) — strictly worse than the pre-delta profile (truncated full-list loses only tail corrections, S2 union intact). The delta→**elevated-cap delta retry** (fires on ACTUAL-LOSS signals only — `stats["partial"]` OR an S4 `_ParseError` with `truncated=True`; a truncated-but-clean rung-1 parse with balanced JSON is ZERO loss and does NOT fire — I-B/I-3; rare post-16K cap) restores the #1787 "no silent tail-entity loss" guarantee: the retry re-runs the DELTA contract at `_S4_DELTA_FALLBACK_CAP = 2 × _S2_S4_MAX_TOKENS`, NOT the complete-list contract — the complete-list output is a strict SUPERSET of the delta output, so at the same 16K cap it truncates at the same point and recovers nothing; an elevated-cap delta retry recovers precisely the delta's lost tail ADDITIONS at strictly fewer tokens (I-A — a retry CORRECTION of an item attempt-1 never reached collides with the S2 ORIGINAL in `attempt1_merged` and is dropped: the S2 original stands — parity with the pre-delta loss profile, NOT a new loss mode; the retry's job is recovering facts that exist nowhere else; pinned by Task 4 test (n5)). `_scaled_deadline` scales with `max_tokens`, so the retry's deadline adapts automatically. Skipping the fallback would regress the exact reliability property the pipeline just established.
3. **The full S-C runtime two-shot is correctly rejected:** the false-trigger mode is a COMPLIANT high-gap session (large legit delta trips the ratio heuristic and wastes a costly re-run), plus `_scaled_deadline` budget interaction. The replay gate + env revert covers the compliance risk offline at zero false-positive surface. A cheap runtime census flag (`s4_delta_reemit_suspect`, observability only) gives online visibility.
4. **S-D is the measured F2 end-state, not a cold ship:** moving corrections off the model before measuring their composition (mechanical vs judgment-heavy) risks the accuracy hold-at-baseline. Task 1's census + Task 10's fidelity sampling gate the F2 decision.
5. **The env toggle + scoped revert** gives fail-closed rollout: unset → delta (default-on); `TORTOISE_S4_DELTA=0` → template render byte-identical (behavioral fixes — merge-gate, measurement — apply in both modes; I-2-7).

**Rejected alternatives:** S-B (identity unsolvable, D5 coupling, double surface); full S-C (false triggers, deadline interaction — escalation path if compliance < 80%); S-D (F2 follow-up); F2-cold / pure ADD-only (Mem0 staleness pitfall, correction channel loss); F5 chunking (#1787 refuted).
