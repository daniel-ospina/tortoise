# M3+M4 — Extractor Reliability Implementation Plan

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

**Goal:** Make the v2 extractor's LLM calls retry transient failures and bound generations (`_complete`), and make the eval harness report per-question extraction integrity (valid flag, error-class census, `invalid_rate` printed before the score) so the retry-then-fix run protocol has the evidence it needs — without any publish-gate machinery.

**Team:** epistemic-team
**Role:** (not set)

**Architecture:** M3 hardens the single LLM seam `tortoise/extractor_v2.py::_complete` (currently: wall-clock deadline only — no retry, no 4xx fail-fast, uncapped generations; the v2 void-run root cause per `/tmp/v3-setup/02`). It gains (a) exponential-backoff retry on transient classes (429/5xx/network/timeout), (b) no-retry on fatal 4xx (401/402/403), (c) bounded `max_tokens` per stage with truncation detection. Error classification is consumed from P2's ported adapter export when present, with an interim module-local classifier of identical semantics (one taxonomy — MECE). M4 adds a per-question `valid` flag + per-question error census through the harness (`ingest_v2` → `run_evaluation` outcomes → `build_report`), an `integrity` block (`valid`, `invalid_rate`, `threshold`, `error_census`) in the eval report, and prints it **before** the score in `_print_summary`. All report/return-shape changes are additive; no ontology, no graph-schema change, no new kinds/edges.

**Issue:** #1524 · **Epic:** #1509 (03-scope M3/M4; 04-plan §5 comp.1 + §6 eval-report row) · **Tier:** Standard · **Dependencies:** M1 (#1522 dead-code fix — assumed merged at implementation time)

## Design Decisions

### D1 — Retry/backoff lives in `_complete`; classification consumed from P2's taxonomy seam

`_complete` (extractor_v2.py:1566) is the single LLM contact point for S1/S2/S4. Per the epic (04-plan §5 comp.1), retry/backoff goes here, not in the adapters (P2 owns adapters).

- `_complete(model, system, user, *, deadline_s=600, max_tokens=None, retries=2, backoff_base=2.0, backoff_cap=30.0) -> str`
- **Retry classes (transient):** HTTP 429, 5xx, connection/network errors, `TimeoutError` (deadline exceeded). **No-retry (fatal):** 401/402/403, other 4xx. **Unknown:** treated as transient (mirrors `run.py::_call_with_backoff`'s blanket retry precedent; the census records the class so the retry-then-fix loop can tighten).
- **Classification** via `_classify_error(e) -> str` returning a census-class key. Implementation: duck-typed — `st = getattr(getattr(e, "response", None), "status_code", None)`; `TimeoutError` builtin; class-name substring checks for `Timeout`/`Connection` (keeps the extractor free of a hard `requests` import). **Taxonomy seam:** try `from tortoise.provider import is_fatal_error, is_transient_error` (P2's ported export); on `ImportError` use the module-local classifier with identical semantics (⛔ GATE-1).
- **Per-attempt deadline:** each attempt gets its own `deadline_s` (a wedged call staying wedged across retries is the failure mode we're buying time against). Total worst-case wall clock = `attempts × deadline_s` — documented. The abandoned daemon thread keeps running (provider still billed) — accepted, bounded per attempt.
- Backoff mirrors `run.py` constants (`base**attempt`, jitter ×[0.5,1.0), cap 30s) — one in-repo pattern, not a second invention.

### D2 — Bounded `max_tokens` per stage, plumbed through the `complete()` interface (no shared-mutable fallback race)

The void-run root cause is uncapped generations → 600s deadline timeouts. The #1468 capture-path comment ("capped 4000-token adapters truncate and silently lose chunks") is the *truncation* failure mode — the fix is a cap **paired with truncation detection**, not a return to uncapped.

- `_complete(..., max_tokens=None)`: `None` → stage default cap. Stage constants: `_S1_MAX_TOKENS = 1500`, `_S2_S4_MAX_TOKENS = 8000` (matches the in-registry 8000 precedent for reasoning models; S2/S4 JSON must clear the 4000-token truncation floor). Single env override `TORTOISE_EXTRACTOR_MAX_TOKENS` (int) read at call time, sets both stages — the mechanical-fix loop raises caps without a code change. Explicit `max_tokens=0` = truly uncapped (documented escape hatch).
- **Enforcement is interface-driven:** `_complete` calls `model.complete(system=..., user=..., max_tokens=cap)`. Capability detection once per model instance (cached): `inspect.signature` → if `complete` accepts `max_tokens`, use the kwarg; elif the model has a writable `max_tokens` attribute, set it before the call; else log a loud warning and record `unbounded_adapter` in stats (fail-open with visibility — never a silent no-op).
  - **Why not mutation-only:** the eval shares one extractor model across worker threads (`--workers>1`); S1 (1500) and S2/S4 (8000) caps racing through `model.max_tokens` would corrupt each other. Per-call kwarg is race-free.
- **Truncation detection:** read `getattr(model, "last_finish_reason", None)` after the call; `"length"` → `truncated=True` recorded in stats. Add `last_finish_reason` to the adapters this plan touches (`OpenRouterModel`, `DeepSeekDirectModel`, `_Compat` — from `choices[0].finish_reason`; `OllamaModel` — from `done_reason`). For S2/S4, `_parse_json`'s existing tail-cut tolerance already recovers truncated JSON; the census still records the truncation so the fix loop knows. (⛔ GATE-2: P2's adapter port must carry `last_finish_reason` forward.)
- **Stale-comment fix:** the sdk.py:1995–2004 uncapped-default comment ("#1468") becomes stale — the default capture model is now bounded by `_complete`'s stage caps. Update the comment to point at M3's bounded-default + env override (documentation only; the `max_tokens=None` constructor default remains, the bound applies at the `_complete` seam).

### D3 — Per-call stats → additive extractor return contract

`_complete` gains an optional `stats: dict | None` param; stage callers (`run_s1`/`run_s2`/`run_s4`) accept and forward it; `extract_session_v2` passes one shared per-session dict. The dict accumulates `{"attempts": n, "retries": n, "truncated": bool, "last_class": str}` per stage. `extract_session_v2` then returns, **additively**:
- `stats["llm"]`: `{"calls": n, "retries": n, "truncated": n}` (rolled up),
- `error_census: dict[str, int]` (top-level key, class → count across S1/S2/S4 failures — includes the top-level catch in `extract_session_v2`'s per-stage handlers),
- existing `errors: list[str]` **unchanged** (backward-compatible — `ingest_v2` and `sdk._extract_session_v2` read it).
- Also wire the hardcoded `telemetry.retry_count = 0` (extractor_v2.py:1430) to the real retry count (trivial, same line).

**Census class vocabulary (stable keys):** `fatal_401_auth`, `fatal_402_billing`, `fatal_403_forbidden`, `fatal_4xx`, `transient_429_rate_limit`, `transient_5xx`, `transient_timeout`, `transient_network`, `transient_unknown`, `parse_error`, `truncated`. `parse_error` is produced by `_parse_json` callers (`run_s2`/`run_s4` catch and class it — today they raise `ValueError` into the per-stage handlers; the handlers map `ValueError`/parse context to `parse_error`).

### D4 — Per-question `valid` flag + per-question census (harness)

- `ingest_haystack_v2` (ingest_v2.py:174): roll each session's `out["error_census"]` into `stats["error_census"]`; the session-level `except` (currently `stats["errors"].append(...)`) also classifies the exception and increments the census. New stat keys are additive.
- `run_evaluation` outcome (run.py:133): add `"valid": len(ingest_stats.get("errors") or []) == 0` and `"error_classes": ingest_stats.get("error_census", {})`. **`valid` is extraction integrity only** (S15 pipeline state) — reader/judge failures stay in the top-level `failures` list (orthogonal; `n_failed` reported separately). Deterministic ingest mode has no LLM → always `valid` (uniform computation).
- The outcome fields must survive checkpoint round-trip (`_save_checkpoint`/`_load_checkpoint` are JSON-generic — verify with a test).

### D5 — Report `integrity` block + print before score

`build_report` (report.py:67) gains an additive `integrity` key:

```json
"integrity": {
  "valid": <bool>,            // invalid_rate <= threshold
  "invalid_rate": <float>,    // n_invalid / n_completed (extraction-invalid only)
  "n_valid": <int>, "n_invalid": <int>,
  "n_failed": <int>,          // cross-ref: question-level failures (reader/judge)
  "threshold": <float>,       // recorded, default 0.0
  "error_census": {<class>: <count>}   // rolled up across questions
}
```

- **Threshold:** CLI `--integrity-threshold` (default 0.0 — a run with any extraction-invalid question reports `valid=false`). The E2E-2 "or justified" path: operator passes a nonzero threshold + documents justification in the run notes. **No publish-gate machinery** (scope): `integrity.valid` is reported, never blocks publication.
- `_print_summary` (run.py:344) prints the integrity block (valid / invalid_rate / top census classes) **before** the accuracy lines.
- **Census scope:** extractor/ingest classes only (S15). Top-level `failures` remain in `report["failures"]` with their `repr(error)` — M2's Verify-gate judge-reliability fix (retry judge on transient during scoring) is tracked on #1523, not here.

### D6 — Retry-then-fix protocol: census → mechanical-fix triage (documented, not gated)

The run protocol (03-scope steps 3–8) is "retry-then-fix": mechanical failures get fixed, not published around. M4's deliverable is the evidence the fix steps read, plus a documented triage mapping:

| Census signal | Mechanical fix (run-protocol steps 4/6) |
|---|---|
| `fatal_402_billing` > 0 | M2 pre-flight probe missed it → check budget (A6), re-run pre-flight; not a code bug |
| `transient_429_rate_limit` spike | reduce `--workers` / raise backoff cap / provider load |
| `transient_timeout` spike | raise `TORTOISE_EXTRACTOR_MAX_TOKENS` or reduce `chunk_size` (S1 output bound) |
| `parse_error` spike | S2/S4 prompt/OUTPUT_CONTRACT regression (fix prompt, not retries) |
| `truncated` > 0 | cap too low for the stage → raise the stage cap |
| `fatal_401_auth` / `fatal_403_forbidden` | key rotation / provider config — pre-flight (M2) should have caught |

This mapping ships as a short section in the plan and as a comment block in `report.py` next to the `integrity` builder (no separate doc file — the report JSON + summary ARE the protocol surface).

### D7 — `_call_with_backoff` gains fatal-class awareness (small, same taxonomy)

`run.py::_call_with_backoff` currently retries every exception class (reader/judge at question level). A 401/402/403 there burns `retries+1` attempts per question. Add: if the classification seam (D1) says fatal → raise immediately, no sleep. Same one-taxonomy import. Keeps the harness honest without scope creep into M2's judge-reliability work.

```python
# module constants (mirror run.py's harness backoff)
_COMPLETE_RETRIES = 2
_BACKOFF_BASE_S = 2.0
_BACKOFF_CAP_S = 30.0

def _classify_error(e: BaseException) -> str:
    """One taxonomy (P2 seam): fatal 401/402/403 (+other 4xx), transient 429/5xx/network/timeout, unknown→transient."""
    try:
        from tortoise.provider import is_fatal_error, is_transient_error  # P2's ported export
        if is_fatal_error(e):  # pragma: no cover - P2 path
            ...
        if is_transient_error(e): ...
    except ImportError:
        pass
    st = getattr(getattr(e, "response", None), "status_code", None)
    if st is not None:
        if st == 429: return "transient_429_rate_limit"
        if 500 <= st < 600: return "transient_5xx"
        if st in (401,): return "fatal_401_auth"
        if st == 402: return "fatal_402_billing"
        if st == 403: return "fatal_403_forbidden"
        return "fatal_4xx"
    name = type(e).__name__
    if isinstance(e, TimeoutError) or "Timeout" in name: return "transient_timeout"
    if "Connection" in name or "Network" in name: return "transient_network"
    return "transient_unknown"
```

## ⛔ Conditional Gate Notes

- **GATE-1 (P2 taxonomy export):** if `tortoise.provider` (P2's ported adapter + error-class export) exists at implementation time, `_complete` / `_call_with_backoff` / `ingest_v2` MUST import `is_fatal_error`/`is_transient_error` from it and drop the local `_classify_error` fallback (one taxonomy, MECE). If P2 has not landed, the interim local classifier (identical semantics: 401/402/403 fatal, 429/5xx transient) ships, and the plan does NOT design a second taxonomy — the seam is the only consumption point.
- **GATE-2 (adapter surface):** bounded max_tokens + truncation detection depend on adapters accepting the per-call `max_tokens` kwarg and surfacing `last_finish_reason`. This plan adds both to the three known adapters + `_Compat`. P2's adapter port MUST carry these forward — if P2 lands first with a `complete()` that lacks the kwarg, `_complete`'s capability-detection fallback (attribute set) still applies the cap (single-model-per-run → benign), and truncation detection degrades to stats-only (documented limitation).
- **GATE-3 (no ontology / no graph-schema change):** this issue introduces zero new point kinds, edge types, or point properties. All new fields are eval-report JSON keys and extractor return-dict keys (additive, non-persisted). If any implementation step appears to need a graph-schema field (e.g., persisting per-question validity into the graph), STOP — that is out of scope and must be raised to the epic owner, not designed around.

## Open Questions

1. **Stage cap values (1500/8000) are initial defaults** validated at the 50-Q pilot (run-protocol step 3/4 — "retries, keys, marking, context caps"). If the pilot shows S2/S4 truncation (`truncated > 0` in the census) at 8000, raise via `TORTOISE_EXTRACTOR_MAX_TOKENS` and record the chosen value — no code change needed. Should the defaults be recorded in `report.methodology`? (Suggestion: yes, when M7 lands the methodology extension — out of scope here.)
2. **`valid` denominator:** `invalid_rate = n_invalid / n_completed` — completed = outcomes with a `valid` key (all completed outcomes). Question-level `failures` (reader/judge) are excluded from the denominator by design. Confirm this matches the operator's intent for E2E-2's "invalid_rate≤threshold".
3. **Unknown-error class → transient:** an unrecognized adapter exception retries (mirrors the harness precedent). The census records it as `transient_unknown` so the retry-then-fix loop sees it. Acceptable, or should truly-unknown classes fail fast?
4. **S1 truncation semantics:** a truncated S1 narrative is accepted (soft degradation; evidence-marking threshold absorbs it) with a census marker. If the pilot shows S1 truncation correlating with evidence loss, the fix is raising `_S1_MAX_TOKENS` — confirm the marker + fix path is sufficient vs. a hard retry-on-truncation for S1.
