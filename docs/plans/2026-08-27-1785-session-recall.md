**Team:** epistemic-team

**RAG retrieval failure taxonomy** — 3+ calls, web_search (sonar):
- Canonical: RAG failures decompose into "missing content" (answer absent from the corpus — **this issue's class**), "not in context" (retrieved but dropped in consolidation), and "rank-too-low" (retrieved but below top-k). Source: arXiv 2401.05856 "RAG failure modes"; Label Studio "Seven ways your RAG system could be failing" (rank-too-low + truncation).
- Competitor precedent: production debugging guides converge on the same ordered playbook — verify corpus presence FIRST, then hybrid search, then reranking, then query reformulation (HyDE/multi-hop only for query types that need them). Source: AWS dev.to "Why RAG gives wrong answers"; Redis "RAG debugging guide" (inspect actual retrieved chunks to distinguish retrieval vs generation); Ankor "Why your RAG is retrieving the wrong documents" (semantic mismatch, top-k too small, metadata filter mismatch → hybrid + query expansion + parent-document + rerank).
- Known pitfall: "wrong evidence in → confident wrong answer out" (AWS); negative/absent-evidence questions are a distinct evaluation class that tests correct abstention vs guessing (Galileo "8 scenarios"; Milvus on negative examples). **Directly relevant:** our 5 misses are "missing content" — no retrieval remedy fixes a corpus that lacks the evidence; a content-presence check is the first-line diagnostic.
- Adversarial: "A Study of Points of Failure in RAG" (arXiv 2407.12216) attributes many failures to poor user-intent understanding — for OUR data the intent is unambiguous (single-hop fact questions with strong lexical overlap); the absence is physical, not semantic.

**Session/chat-log memory retrieval (competitor practice)** — 2 calls:
- Mem0: extract facts → vector store → cosine retrieval, with `user_id`/`agent_id`/`run_id` **filters** and a **temporal-reasoning metadata pass** (when an event occurred, ongoing/completed/plan/preference) used at retrieval time. Source: arXiv 2504.19413; docs.mem0.ai.
- Zep/Graphiti + Letta + LangMem: conversation history is a **first-class searchable surface** ("recall memory"), separate from the extracted-facts surface; Zep adds validity windows per fact and semantic search over episodes. Sources: agentmarketcap.ai (2026-04-08 comparison), datapace.ai.
- **Implication for us:** the "session must be found" primitive maps to their "recall memory / episode search" surface. Their metadata-filtering (user/run/date) and time-aware ranking are the mature versions of our candidate levers (b)/(date-boost) — noted as future options, not this fix. None of them solve "the episode's content was never indexed" — that is an ingestion-integrity failure everywhere.

**Hybrid-search leg weighting** — 1 call (rate-limit recovered):
- Canonical: weighted RRF `Σ wᵢ / (k + rankᵢ)`, k=60 common, weights tuned on the eval set; equal weights let one retriever dominate (Qdrant docs); Microsoft Azure documents vector-weighting semantics. Elastic's weighted-RRF blog gives the production formula.
- Known pitfall (jatinbansal.com): "small candidate pools are a frequent bug in hybrid search" — RRF is rank-position-based, so a shallow pool starves fusion. Our `DEFAULT_POOL_MULTIPLIER=3` (60 candidates) is the current bound; expanding it helps ONLY if the answer session exists in the graph (it did not here).

### Why this framing (issue's framing rejected)

The issue asserts "genuine misses on a healthy run" and scopes retrieval-side fixes. That framing is **refuted**: the retrieval never had the opportunity to rank the answer session because its nodes were not in the corpus. Fixing retrieval (query expansion, weighting, pool size) would have changed nothing for these 5 questions. The root cause is upstream of retrieval (graph-write integrity / environment), per the "fix root causes, not symptoms" principle.

### Falsification check

If a **clean** re-validation (healthy FalkorDB, single population) still shows ≥1 session@20=0.0 question **with the answer session present in the graph at and after retrieval** (run-time gate green — ratio = 1.000 and presence green — AND the **post-retrieval census** still green; see Task 5), the integrity hypothesis is falsified for that question and retrieval-side work is warranted — the C3/weighted-RRF/pool-size levers from §4 become the fix. The post-retrieval census is required because H6b/H6c can remove nodes between the post-ingest gate and retrieval; a miss with a green run-time gate but a RED post-retrieval census is attributed to loss-location (H6), not retrieval. The falsification trigger fires ONLY on ratio = 1.000 + presence-green + per-session-floor-green + post-retrieval-green + legs-healthy misses (a strategy-timeout outcome — empty evidence, non-empty `answer_session_ids`, gate green — carries a `strategy_timeout` reason and suppresses the trigger; the leg-health predicate is CONSERVATIVE: legs healthy requires each leg's return count ABOVE the stated per-leg result-count floor F_leg (derived from the healthy distribution — Task 1 Step 2 constants; NOT a threshold-from-noise constant) AND no leg exception/timeout — a leg is degraded ONLY on an OBSERVABLE signal: count below F_leg, an exception, or a timeout; a leg with count > F_leg and no exception/timeout is classified HEALTHY even if it is a silent partial short-read (the "partial-result suppresses regardless of count" arm is DROPPED — with no exception and no timeout there is NO detection signal for a silent mid-cursor short-read; it would mis-attribute a genuine retrieval miss to leg-health and slip it past the falsification test; second-model P2). The fail-safe direction: the trigger stays ARMED for the retrieval investigation rather than suppressing it. 118b2229 has never been observed healthy (crash-resumed pilot, truncated reval) — it is the canary for this falsification test.

## 4. Solution Approaches (diverge) → Converged Choice

### A. Run-integrity gate + clean re-validation (**CHOSEN** — root cause)
Post-ingest, pre-retrieval per-question integrity check in `run.py` (where `pool_size` is already computed), re-invoked post-retrieval (Task 1 Step 2): (1) **census-ratio check** `pool_size / (ingest.turns+chunks+points)` → **gated truncation flag** when < 1.0 (any sub-1.0 ratio is a truncated graph; healthy is exactly 1.000 — there is NO clean separation below 1.0, §1 bullet 1); ratio > 1.0 (census counting leftovers from a prior partial run) is an integrity anomaly → fail-closed with the distinct reason `census_overflow` (P2-4), never silently passed. **Tier resolution (threshold-from-noise, stated explicitly): the hard-reject tier is PRESENCE-driven (item 2 — primary, exact); the ratio is a secondary sub-1.0 truncation flag. The 0.25 ratio reject constant is RETRACTED** — it was derived from the observed miss span (0.005–0.196) inside the overlapping hit/miss range (e47becba 0.026 and af8d2e46 0.148 were HITS; 0.026 is the lowest presence-green ratio, so no ratio constant below it cleanly separates) — the only clean boundaries are presence (item 2) and ratio = 1.000. (2) **direct answer-session-presence check** — `MATCH (p:Point {lme_question_id:$q}) WHERE p.lme_session_index IN $idxs` over ALL mapped answer-session indices (dataset `answer_session_ids` → position within `haystack_session_ids`; **red when ANY mapped answer-session index has zero points** — green only when every mapped answer session has ≥1 point; matches the acceptance and the recall-denominator semantics, where session_recall@k = len(intersection)/len(all) caps at 0.5 if one of two answer sessions is lost while "ANY present" stays green and launders the loss) → hard reject if absent, reason `answer_session_absent`; **alongside the ≥1-point presence threshold, a per-session node-count floor (or per-session evidence census) is a gate input: an answer session reduced below its evidence-bearing node set passes presence green but fails the floor — attributed to H6 loss-location, NOT retrieval; the floor is DERIVED per question at gate time from a NEW per-session evidence-point count added to the write-path stats (ingest_v2 `_write_payload` / legacy `ingest_haystack` — the existing stats are per-QUESTION aggregates with no per-session evidence counts, so the floor cannot come from them) — floor = max(1, expected evidence-bearing points for the mapped answer session − tolerance) — the tolerance is a FIXED CONSTANT (Task 1 Step 2 constants list, fingerprint-excluded knob); **floor source COMMITTED (P2-4, §11 decision 5): the NEW write-path per-session evidence-point stat is the ONE floor source — the dataset-derived fallback (session turns × observed points/turn) is DELETED (a pure hedge with duplicate fixtures/docs/maintenance; the stat is already justified by P1-1 parity + the trigger's floor arm); Task 3 runs AFTER Task 1 and replays one question; it cannot be the floor's source of truth; Task 3's per-session census serves as post-hoc calibration/validation of the stat derivation (recalibration is a knob, excluded from the fingerprint like the other gate knobs), not its source of truth**; answer-session indices are resolved at dataset-join time with a distinct fail-closed reason `dataset_join_error` (ids absent from `haystack_session_ids` or out-of-range — verified 0 against the pinned dataset, but kept fail-closed as defensive code: ids missing/out-of-range must still fail closed, and a containment-invariant test pins the count so it cannot silently drift; never crash, never silently match nothing); (3) **evidence-mark census** (write-observed — count `has_answer` among this run's actually-created point ids: **`_write_payload`'s returned `stats` will be extended to include `created_point_ids` — the set is currently LOCAL inside `_write_payload` (built at ingest_v2.py:124, added at 201, used at 243-244; the function returns only `stats` at line 312, which NEVER includes it); Task 1 exposes it (P1-2)**, the query takes an `IN $ids` param with the D5 filter applied on the same set, instead of comparing the `evidence_points` stat against the graph's total `has_answer` count — immune to the cross-session content-collision OR-in (ingest_v2.py:148/348/509/653/817 — the five OR-in sites), the NOOP-fold OR-in (`_apply_noops`), leftover marks, and id collisions simultaneously, all of which mutate graph `has_answer` WITHOUT incrementing the stat; P1-1) — **pinned to the D5 pointKind-filtered semantics: `coalesce(p.pointKind,'') <> 'session-transcript'`** (excludes session-transcript chunks in BOTH ingest modes; a naive `MATCH has_answer=true` count EXCEEDS evidence_points on healthy v2 questions because v2 session-transcript chunks carry `has_answer = contains_evidence` — false-positive gating of a clean run); the D5 query is **extracted into a shared helper in retrieve.py** (it currently lives INSIDE `retrieve_for_question` at retrieve.py:1254, which runs after the gate site) so the pre-retrieval gate, the post-retrieval census, and Task 3's per-session census all call the same helper. A failed census/presence query → reason `census_error`, fail CLOSED (excluded, never silently passed, never crashes the run). **Premise-validation deferral (P2-1, GOOD > EASY): the read-verify premise ('partial reads happen') is UNVALIDATED — the 24 strategy timeouts fail closed via `census_error` and are not themselves partial reads; silent-count-truncation is the only scenario the two-read consensus buys, and the checkpoint shows 31/31 counts exact under load. `Deferred: read-verify machinery retained as defense-in-depth — the premise-validation probe is folded into the existing docker lane as a POST-HOC VALIDATION DATA POINT, NOT a budget-conditional: a documented probe test in `tests/test_integrity_gate_docker.py` that short-reads a controlled COUNT query and asserts the result — DECIDED (cycle2-P2-14): the probe-collapse branch (base 10 → ~5 queries if counts are atomic-or-error) and the 'either way' hedge are DELETED — the machinery is already committed by 15+ docker fixtures, so the collapse branch is unreachable — and base = 10 is the SOLE stated budget constant.`** **Read-verify protocol: every gate census is a single-shot read, and a partial read under load is indistinguishable from a swallowed write (24 strategy timeouts prove partial reads happen) → each census issues a second independent read (different query shape / access plan) and retries on mismatch (N retries); the two consensus reads may be built by ONE shared query builder with a parameterized shape or by independent builders — the binding requirement is the SHAPES DIFFER (different access plans), not that the builders differ (second-model P3: an anti-DRY independent-builder mandate is over-engineering for the threat model — server-side partial-read faults are defeated by the fresh-session third-shape probe + presence-ratio cross-check, and client-side builder bugs are covered by fixture-pinned unit tests; see Task 1 Step 2); for the evidence-mark census the second read is ALSO pointKind-filtered (shaped differently, not a naive label-only count); when both reads agree on ABSENCE, a discriminating third-shape probe (a raw query not via the shared helper) confirms before anything is labeled absent/lost; only a stable two-read consensus counts as "absent/lost"** (Task 1 Step 2 + Task 3). All gated questions (ratio < 1.0 OR presence red OR evidence-mark red OR census_error OR dataset_join_error) never enter the accuracy/recall aggregates; they stay in the integrity attempted set and are still graded for the hard veto (Task 1 Step 4). **Gated questions STILL run retrieve_for_question — the gate flags, never skips (final-verification P2): the "hard reject" language in §4A item (2) and Step 1 means the question is gated (excluded from aggregates, graded for the veto), NOT that retrieval is skipped; skipping retrieval would produce an outcome with empty legs/answer that is shape-broken → routed to the veto-escape guard (~943), the exact laundering path Step 4 warns against ("a tampered gated outcome launders a fatal class"), and the census-class veto mapping + answer-grade via grade_by_qid (~921) hold only if retrieval ran and the outcome stays shape-OK (passes _outcome_shape_ok, report.py:340). Pinned: a Step-1/docker fixture asserting the post-gate flow — a red question still runs retrieve_for_question and its outcome passes _outcome_shape_ok and is graded via grade_by_qid, never the veto-escape guard.** Then infra remediation + clean 50-Q re-validation. **Best fit if:** the goal is a trustworthy session@20 baseline and a gate that prevents a third contaminated aggregate. **Files:** `tools/longmem_eval/run.py`, `retrieve.py` (check placement), `report.py` (reason surfaced), `run_protocol.py` (pre-resume scan parity).

### B. Verification-annotated write path (fail-loud writes)
Make the ingest write path verify each batch: after Phase A/C writes, run the existing idempotent existence probes (`_existing_point_ids`) and assert count matches; on mismatch, raise loudly instead of recording success. **Best fit if:** we want the WRITE path itself to fail on server-side loss (H6a) rather than detecting it later at retrieval. **Risk:** doubles write-path query volume on a saturated DB (the run's actual bottleneck) — could worsen the very failure it detects. **Rescoped:** fold into A as the loss-location diagnostic (per-session census on a replay), not a permanent write-path assertion.

### C. Retrieval-side tuning now (query expansion / weighted RRF / pool size)
Ship the issue's implied fix. **Rejected:** data-false premise (see §3); tuning against a two-population aggregate would overfit to degradation artifacts. Documented as the post-baseline follow-up path.

### Converged choice: **A** (with B's diagnostic folded in). Quality-over-convenience: A is more work than C but addresses the proven root cause; C would ship a phantom fix and leave the aggregate contaminated.
