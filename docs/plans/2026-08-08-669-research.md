## 0. Reframe (CORRECTED — research-review P0)

**Reframed problem:** "**Consolidate** the control-plane master list into Supabase — it is ALREADY dual-store today. Supabase migrations 0001–0004 ship `user_teams`→`team_memberships` (api_key one-time-reveal plaintext + key_hash + trigger + RPCs + RLS), `audit_events`, `analytics_events`; the `tenant-provision` Edge Function already writes BOTH FalkorDB (Team/APIKey/Membership via /internal/provision) AND Supabase (`update_user_team` RPC). The migration retires the FalkorDB registry half so the master list has ONE home: managed backups/PITR, constraints, RLS-as-defense-in-depth — before beta, while both stores are empty."

**Domain:** Complex. **Assumption mapping (re-verified):**

RLS bypassed for service-role queries → honest benefit = constraints/transactions/PITR + defense-in-depth.

## 2. External Research (validated)

1. **RLS access path:** service_role bypasses RLS entirely (Supabase docs); anon+RLS for client-scoped reads; server-side admin = service_role. **Middle path:** a shared non-bypass app role + `current_setting('app.current_team_id')` GUC — already the repo's audit policy pattern — gives RLS-enforced isolation for backend queries without per-user connections. Per-user JWT for a psycopg2/FastAPI backend effectively means PostgREST or per-user connections (large rework).
2. **API keys:** deterministic hash for indexed O(1) lookup + short prefix (apikeys.guide). Our salted-scan is legacy; `team_memberships.key_hash` is already the indexed column — migrate to deterministic SHA-256 lookup hash + keep one-time-reveal semantics.
3. **Migration:** dual-write/CDC for live data; zero-tenant → direct cutover with scripted precondition on BOTH stores + dual-write fallback.

## 3. Adversarial (CORRECTED)

- **Invitations share the salted-scan scheme** — `invitations.lookup_hash` (SHA-256 of raw token, partial unique index on pending) or HMAC-signed tokens.
- **Invite placeholders (`user_id='invite-{iid}'`)** violate `team_memberships.user_id uuid NOT NULL FK` — invited state lives in `invitations` only, or user_id nullable + check reconciled.
- **Plaintext-reveal contract** must survive (welcome page depends on it) — keep a column-REVOKEd reveal column scoped to owner rows; align the test target.
- **Backup pipeline stamps WRITE to the registry** — move the two stamp sites into the Supabase transaction (or `backup_metadata` table) with the seam swap, or they silently write to a retired graph. E2E: backup completes AND stamps `teams.backup_latest_at` in Supabase.
- **MCP auth is a second security surface** — `TeamResolutionMiddleware.apikey_verify` + quota from registry must flip with the REST path or MCP stays on the registry (partial cutover).
- **/health/security** hardcodes pbkdf2 — stale after the lookup-scheme change; **/health/ready** probes the registry — must probe Supabase (new availability dependency).
- **GitHub OAuth token** (`Team.github_token_enc`, encrypted) + `_GITHUB_STATES` (in-memory CSRF) — migration must specify the encrypted-credential table + column protection + rotation.
- **Dual-store inconsistency** is possible TODAY (placeholder rows with/without api_key; key-hash scheme disagreement) — the cutover gate must reconcile, not assume.
- **Backup-sweep seam** + **onboarding state/email** (first post-provision flow) — E2E targets.

## 4. Open Decisions (updated)
1. **Access path:** service_role + defense-in-depth at cutover (recommended); the **GUC app-role middle path** as the concrete future option (pattern already in-repo); per-user JWT/PostgREST as the large-rework tail.
2. **API-key + invitation lookup:** deterministic `lookup_hash` (SHA-256) on BOTH `team_memberships`/`api_keys` AND `invitations`; keep the one-time-reveal plaintext column (column-REVOKE, owner-scoped).
3. **Target schema (three shapes — cycle-2 P2):** (a) extend `team_memberships` only — REJECTED: team-level props (tier, stripe, backup flags, ops_allowance, email, onboarding_state, github_token_enc) cannot live on membership rows (UNIQUE(user_id,team_id), single api_key column); (b) **extend memberships + add `teams` + `api_keys` tables (RECOMMENDED)** — keep the live trigger/RPC/reveal machinery, add `teams` (team-level props) and `api_keys` (session/API keys: team_id FK, lookup_hash, key_prefix, created_via, expires_at, revoked_at; team_memberships.api_key stays the long-lived one-time-reveal credential); (c) full replace — larger rewire, no benefit at zero scale. **Source→target field map is a scope-mandate** (Team/APIKey/Membership/Invitation → target columns, incl. session keys → api_keys, github_token_enc → column-protected table with rotation path).
4. **Audit events:** point `TORTOISE_AUDIT_DSN` at Supabase (audit_events already exists + GUC RLS); no new table.
5. **Registry fate:** retire after verification; read-only mirror during cutover.
6. **Edge Function contract:** the full surface — auth hook + `handle_new_user` trigger + `update_user_team` RPC + `reveal_api_key` + placeholder semantics + **emit `lookup_hash` to both stores**.
7. **Cutover:** single-deploy flip (owner decision) with the 3 non-negotiables in scope-mandate 5; a scripted pre-check still confirms both stores are empty before the flip; no dual-write phase.
8. **Invite placeholders:** invited state in `invitations` only; `accept_invite` creates the real membership.
9. **MCP + backup stamps + health endpoints:** in the same cutover (no partial flips on security/auth surfaces).

## 5. E2E Proof Targets (extended)
- Provision → team row in Supabase (RLS-visible), registry graph untouched; welcome reveal still works.
- API-key + invitation auth → O(1) lookup via `lookup_hash` (REST **and MCP** paths); revoked rejected.
- Backup sweep enumerates from Supabase `teams` AND stamps `teams.backup_latest_at` (both directions of the seam).
- Onboarding state/email read-patch from Supabase `teams`.
- /health/security reports the real scheme; /health/ready probes Supabase.
- Cutover precondition fails closed on either store; rollback = registry mirror read-only until verified.


## 6. Scope-Mandates (cycle-2 P2/P3 — carry into epic-scope verbatim)
1. **Schema shape (b)** + source→target field map (decision 3).
2. **Session keys** → `api_keys` table; state which table each of `apikey_verify` (REST + MCP) reads (decision 9).
3. **RLS exercise:** define the principal — either a test role + `current_setting('app.current_team_id')` GUC (in-repo audit pattern) with policy assertions, or reword "RLS-visible" to the `update_user_team`/`reveal_api_key` contract and ship RLS definitions exercised when the GUC app role lands (decision 1).
4. **Trigger contract:** reconcile `handle_new_user` placeholders with invite-placeholders; precondition predicate distinguishes placeholder rows from real ones in BOTH stores.
5. **Cutover — OWNER DECISION (2026-08-09): single-deploy flip, not phased.** Zero tenants → no dual-write/CDC phase; no per-surface sequencing. Non-negotiables that make it safe: (1) full pre-deploy test coverage of every flipped surface (signup→Supabase row, API-key auth REST+MCP, backup seam enumerate+stamp, invitations); (2) the FalkorDB registry is FROZEN read-only, NOT deleted, until the new path is verified live (rollback = redeploy; old data intact); (3) the #596 monitoring (Telegram alerts, staleness) is the post-flip safety net for silent breaks — fix-after is acceptable because failures are loud. Registry retirement happens as a separate, later, explicit step after verification.
6. **github_token_enc:** column-protected table + `_github_index`/`github_status` read path + rotation documented (E2E target).
