# Issue #1541 — R2: OR-tolerant/BM25 sparse + search_keys query expansion

**Epic contract:** 03-scope R2 · **Test alignment:** E2E-1 · **Test-design:** #1515 surfaces 8 (FTS index), 11 (FTS-vs-TFIDF dual stack) · **Dependencies:** P3 (#1531, rebase), E3 (#1535, search_keys) · **Complexity:** standard · **Lane:** D (retrieval), after M6/R1/R3.

## Problem (confirmed)

1. **Strict-AND zeroes paraphrased points.** `run_fts_query` passes the raw query string straight to `db.idx.fulltext.queryNodes('Point', $query)`. RediSearch default semantics: whitespace-separated terms are ANDed. A point whose content differs from the question by ONE token (e.g. point "gym schedule 6pm" vs question "...gym schedule 5pm…") matches on only the shared tokens and is **zeroed** — RediSearch AND requires all query terms present in the doc. This is the measured R2 gap (epic findings #6: "RediSearch strict-AND zeroes paraphrased points").
2. **search_keys (E3) are inert at retrieval.** E3 writes 2–4 aliases + verbatim tokens per extracted point. Today nothing reads them. A question "what's my fastest 5k" can never match a point whose *content* is "personal best 5K time is 27:12" — the alias text ("fastest 5k", "running pb") lives on the point but is not indexed. The issue's "query expansion from question ∪ search_keys" is realized by **indexing search_keys** so unqualified query tokens match content ∪ search_keys.
3. **Dual-stack skew (surface 11).** Real runs get RediSearch FTS; embedded runs (FalkorDBLite, no RediSearch module) fall through to the sklearn TF-IDF path (`fallback_tfidf` → `search_points` / `fallback_snapshot`). The two sparse scorers behave differently (strict-AND vs tolerant cosine), and the eval cannot tell *why* a leg is missing — the index-missing branch logs at `info` and records breaker SUCCESS, so "fts skipped (no index)" is indistinguishable from "fts ran, no results". **Legs must be recorded, never silent** (E2E-1 owned negative).

## Design decisions

### D1 — Shared OR-union query builder (one tokenizer for both stacks)

New module `tortoise/sparse.py` (keeps `search_engine.py` focused; both stacks import it):

```python
SPARSE_STOPWORDS = frozenset({...})   # small English set: articles, be-verbs,
                                      # prepositions, question words
                                      # (what/when/where/who/which/how),
                                      # pronouns (my/your/i/you/me), did/do/does/have/has

def tokenize_sparse_query(query: str) -> list[str]:
    """Lowercase; split on non-alphanumeric; drop tokens <2 chars, all-digits,
    and stopwords. Deterministic order (source order)."""

def build_or_query(query: str, *, max_terms: int = 12) -> str:
    """tokenize_sparse_query → sort by length DESC (specificity), cap at
    max_terms, join with '|' (RediSearch OR). Empty result → return the RAW
    query unchanged (byte-compatible with today for degenerate inputs —
    never send an empty query string to queryNodes)."""

def index_text(*parts: str) -> str:
    """' '.join of non-empty parts — the dual-stack index-text builder
    (content ∪ search_keys), used by the TF-IDF fallback paths."""
```

- **Why OR-union not phrase fallback:** the tolerance requirement is per-token. OR-union + RediSearch's TFIDF scorer ranks docs by term-overlap, which is the BM25-style behavior we want at the rank level (see D2). Single-token queries and stopword-only queries fall back to the raw string — behavior byte-identical to today.
- **Token cap (12) + length-desc ordering:** bounds pathological queries (breaker protection, #249) and prefers specific tokens over generic ones. A "one-token-drop" paraphrase loses nothing (cap only bites ≥13-token questions, which the eval never produces).
- **Escaping is structural:** tokens are alnum-only, so RediSearch reserved chars (`|` included) cannot be injected. The raw-query fallback path can carry punctuation — acceptable: it is the *legacy* string, and degenerate-input callers today already pass it verbatim.
- Used by BOTH `run_fts_query` (real) and the TF-IDF fallback paths (embedded) → **surface-11 normalization is a shared code path, not a magic parity layer.**

### D2 — "BM25-style" = OR-union matching + RediSearch TFIDF scoring + RRF rank fusion

- `rrf_fusion` uses **rank only** (scores ignored), so in the fused path the exact scorer is secondary: what matters is that OR-union makes more-overlap docs rank higher, which RediSearch's TFIDF scorer already does.
- **Verification spike (step 1, ~15 min):** on the pinned docker image (`falkordb/falkordb-server:v4.16.7`), test whether `db.idx.fulltext.queryNodes` accepts optional args to select the BM25 scorer (RediSearch exposes `SCORER BM25` in `FT.SEARCH`; the procedure's optional-arg surface is version-dependent). If supported, add an env knob `TORTOISE_FTS_SCORER=bm25|tfidf` (default `bm25` when supported, `tfidf` otherwise) threaded into `run_fts_query`. If unsupported, **document and proceed with the default scorer** — the tolerance fix is the measured gap; exact scorer is polish in single-leg mode only. Do NOT block on this.
- Single-strategy mode (no RRF) benefits: `fused = {pid: score ...}` ordering improves via overlap ranking.

### D3 — search_keys indexed via a multi-field Point FTS index (no new property)

- Extend the Point FTS index at index-creation time in `tortoise/projection/__init__.py`:
  `CALL db.idx.fulltext.createNodeIndex('Point', 'content', 'search_keys')`.
  Unqualified query terms then match content **or** search_keys — this IS the "question ∪ search_keys" expansion, at the index level, with zero query-time cost.
- **Existing DBs** need the drop→recreate migration, exactly the #244 Event marker pattern: `MERGE (m:Meta {key:'point_fts_v2'}) SET m.v = true` guards a one-time `dropIndex('Point')` + `createNodeIndex('Point', 'content', 'search_keys')`. FalkorDBLite lacks `dropIndex` — leave embedded as-is (embedded has no FTS index anyway; its sparse path is D4).
- **No derived `_searchText`-style Point field.** A concatenated field would be a NEW property beyond the approved field list → gated (see ⛔ CONDITIONAL GATE). Multi-field indexing of an *approved* property (`search_keys`) is not a schema change.
- **E3 contract dependency:** `search_keys` must be a **flat space-joined string** in the graph (FalkorDB node properties are scalars; a Python list property may not index/match). Cross-lane with E3 (#1535): coordinate BEFORE implementation — if E3 has already landed with a list value, R2 normalizes at index time via `" ".join(...)` in the projection (write-path touch → owner flag, see Cross-lane).
- Event/Subject/Document FTS indexes untouched (search_keys is a Point property; the tokenizer benefits every label automatically).

### D4 — Embedded-stack parity: search_keys joins the TF-IDF corpus text

- `fallback_snapshot._SNAPSHOT_QUERY` gains `n.search_keys`; the snapshot's indexed text becomes `index_text(content, search_keys)` so embedded sparse matches the same union the real stack indexes.
- Legacy fallback path (`sdk.py` `self.query(...)` → `fallback_tfidf` → `search_points`): `fallback_tfidf` builds the indexed text per point via `index_text(p.get("content"), p.get("search_keys"))` (points dicts from `self.query` carry `search_keys` when present — additive; absent → byte-identical to today).
- **Normalization contract (surface 11):** after D1+D4 both stacks are (a) OR-tolerant at the token level (cosine is inherently overlap-tolerant; FTS via D1) and (b) search_keys-aware. Absolute scores still differ (RediSearch TFIDF vs sklearn cosine) — that is inherent and acceptable; the eval's *leg record* (D5) makes the stack explicit per question, which is what E2E-1 asserts ("leg-mix … never null", "FTS index missing → leg recorded tfidf").

### D5 — Leg recording, never silent (additive `leg_trace`)

- `tortoise_fts_query` gains a private, default-`None` kwarg `leg_trace: list[dict] | None` (exactly the `_elevated_timeout_ms` pattern — default-off, zero behavior change for existing callers). When provided, the engine appends per-leg entries:
  `{"leg": "fts", "ran": bool, "degraded": bool, "reason": str|None, "count": int}` — reasons: `index_missing` | `breaker_open` | `query_failed` | `timeout` | `empty_results` | `ok`, plus a final `{"leg": "fallback", "degraded": ..., "reason": "tfidf_snapshot"|"tfidf_legacy"|None}` entry when the whole chain fell through.
- Threading: `degradation_chain(..., leg_trace=...)` → `run_fts_query(..., leg_trace=...)`. `run_fts_query`'s *breaker* semantics stay untouched (index-missing still records breaker SUCCESS — a healthy deployment with one index-less label must not disable FTS globally, #249); the *trace* is a separate, truthful record: `{ran: False, degraded: True, reason: "index_missing"}`.
- `tools/longmem_eval/retrieve.py`: `retrieve_for_question` passes a `leg_trace` list, stores it as `"legs"` in the per-question result (feeds M7's leg-mix report, surface 11 → surface 19/22). This makes E2E-1's "match_source records which leg found it (fts/vector/structural/tfidf), never null" and its owned negative ("FTS index missing → loud warning + leg recorded tfidf") assertable in the eval.
- The existing `match_source` per-hit values (`fts`/`rrf`/`tfidf`) are unchanged — additive trace only.

### D6 — Scope guardrails

- OR-union applies to every text query through `run_fts_query` (all entity types) — this is the intended product-level fix. Full-scan mode (`query=None`) and structural-only queries are untouched (no text → no tokenizer).
- S3 extraction dedup (`extractor_v2.search_graph` → `_fts_rows`) inherits OR-tolerance — a **positive** side effect (E7 consolidation finds same-fact-different-words better). Note: S3's `limit=3` + dedup bounds any recall broadening; no S3 change needed.

## Implementation steps

Ordered; each step is independently reviewable.

1. **Verification spike (D2):** on the pinned docker image, probe `queryNodes('Point', 'a|b')` (OR recognized, score shape) and optional-arg scorer selection. Record result in the PR description; drives whether `TORTOISE_FTS_SCORER` is wired or documented-off.
2. **`tortoise/sparse.py` (new):** `SPARSE_STOPWORDS`, `tokenize_sparse_query`, `build_or_query`, `index_text` — pure functions, no graph access.
3. **`run_fts_query` (search_engine.py):** replace the raw `$query` passthrough with `build_or_query(query)` for the `queryNodes` path (all labels); add optional `leg_trace` param; record trace entries in all branches (success / index-missing / failure / breaker-open). Operator path (label CONTAINS) unchanged.
4. **`degradation_chain` + `sdk.tortoise_fts_query`:** thread `leg_trace` (additive, default None); record the fallback decision in `sdk.py` (snapshot vs legacy, per #1375).
5. **`projection/__init__.py`:** Point FTS index → `('Point', ['content', 'search_keys'])` with the #244-pattern Meta-marker migration for existing DBs; guard the drop for engines without `dropIndex`. Confirm `_ensure_indexes` runs before eval FTS usage (P3 rebase dependency — real backend).
6. **`fallback_snapshot.py`:** `_SNAPSHOT_QUERY` + `search_keys`; snapshot build concatenates via `index_text`. **`search_engine.fallback_tfidf`:** index-text via `index_text` (content ∪ search_keys).
7. **`retrieve.py`:** pass `leg_trace`, surface `"legs"` per question. (Report shape/leg-mix rendering is M7's — R2 emits the data only.)
8. **Battery/harness touch:** none in this issue beyond retrieve.py — E2E-1 runs in the eval (capstone #1549). R2 lands after R3 (vector leg present) so OR-union recall broadening is tempered by RRF.

## Tests

**Unit — `tests/test_sparse.py` (new):**
- `build_or_query`: multi-token → `a|b|c` union; stopword/pronoun/question-word filtering; token-length cap (12) with length-desc truncation; min-length-2; empty/stopword-only input → raw query passthrough (never empty string).
- `tokenize_sparse_query`: punctuation/reserved-char stripping (`gym's, 5pm!` → `gym`, `5pm`); alnum-only tokens (no `|`, `(`, `@` injection — a query containing `|` cannot change operator semantics).
- `index_text`: content ∪ search_keys; absent search_keys → content only.
- `fallback_tfidf` (mocked points): point with `search_keys` surfaces for an alias-only query (content does not contain the alias token) — the embedded-stack counterpart of the D3 index test.

**Integration — live FalkorDB (`tests/test_search_engine.py` style, `FALKORDB_AVAILABLE` gate):**
- **One-token-drop tolerance (the R2 regression test):** seed points "gym schedule 6pm" and "gym schedule 5pm"; query "gym schedule" (paraphrase dropping one token) → **both** points in top-k (strict-AND would zero the non-exact one). Assert the previously-zeroed point by id.
- **search_keys index:** point content "personal best 5K time is 27:12" + `search_keys: "fastest 5k running pb"`; query "what's my fastest 5k" → point surfaces via FTS (matches on `search_keys` field).
- **Multi-field migration:** open a DB with the legacy single-field Point index; run `_ensure_indexes`; assert the Meta marker is set once and the two-field index answers a search_keys-only query; re-run `_ensure_indexes` → no drop/recreate churn (marker guards).
- **leg_trace:** (a) index dropped → `{ran: False, degraded: True, reason: "index_missing"}` + fallback entry with reason `tfidf_*`; (b) breaker forced OPEN → `reason: "breaker_open"`; (c) healthy → `ran: True, degraded: False, count ≥ 0`; (d) default-None callers → no trace, byte-identical behavior.

**Eval/E2E (capstone #1549 harness):**
- E2E-1: per-question `legs` recorded, never null; FTS-index-missing case records `fts degraded=index_missing` and `match_source="tfidf"` on hits (owned negative).
- Dual-stack parity smoke: same small corpus through embedded (TF-IDF) and real (FTS) retrieval — assert the paraphrase point surfaces in BOTH (top-k overlap, not score equality).

**Regression:** full `tests/test_search_engine.py`, `test_search_engine_gaps.py`, `test_index_surfacing.py`, `test_tortoise_search.py`, `test_integration_search.py` — single-token FTS queries must behave identically (OR-union with one token == the raw token).

## ⛔ CONDITIONAL GATE notes

1. **⛔ Point FTS index migration on the shared read path.** The multi-field index change touches `projection/__init__.py` — every deployment's index-creation path, hosted included. The #244 drop→recreate pattern carries a documented drop→recreate crash window. If the implementer judges this too risky for existing DBs, **STOP the lane** and present options to the owner (e.g., new-index-name + dual-query, or a derived `_searchText`-style Point field — which is a NEW field beyond the approved list and therefore owner-gated on its own).
2. **⛔ No new ontology.** No new kinds, edge types, expansion packs, or point properties beyond `search_keys` (already approved via E3). In particular: do NOT add a `_searchText` concatenation property on Point as an implementation convenience without owner approval.
3. **⛔ Index OPTIONS.** Any RediSearch index-level option (phonetic `dm:en`, custom stemmers, custom stopword lists, field weights) that requires re-creating indexes with options unsupported on existing deployments → owner review first. Default: no options; index config untouched.
4. **⛔ Write-path normalization.** If `search_keys` arrives as a list from E3 and R2 must flatten it in the projection (write path), that is a cross-lane deviation → flag to the owner (E3 should emit the flat string; R2 should not own E3's write format).
5. **No gate expected:** OR-union tokenizer, leg_trace, TF-IDF text concat are additive/reversible, confined to retrieval surfaces, and introduce no fields.

## Open questions

1. **Scorer selection:** does the pinned FalkorDB image accept a BM25 scorer through `db.idx.fulltext.queryNodes` optional args? (Step-1 spike decides; documented-off acceptable — RRF makes it secondary.)
2. **Precision in the eval:** does pure OR-union flood single-token matches in the eval corpus? Mitigation is RRF-with-vector (R3 landed). If pilot data shows sparse-leg noise, knob = raise `max_terms`/min-token-length — a follow-up R5-adjacent tuning, not a blocker.
3. **Prefix matching** (`term*` for morphological variants: "running"/"run") — intentionally OFF for precision; worth a later measure-vs-baseline experiment (V4 follow-up), not this issue.
4. **Cross-point alias propagation:** query-time two-phase expansion (aliases of top hits re-ORed) — NOT implemented (the index-level union covers the primary use case; two-phase only helps alias-of-found-point cases and doubles FTS cost). Candidate for the V4 follow-up run if E2E-1 shows a gap.
5. **`search_keys` cardinality in the index:** confirm E3 emits ≤4 keys (per 03-scope E3 "2–4 aliases + verbatim tokens") so indexed field size stays bounded (no index bloat on the shared Point label).
