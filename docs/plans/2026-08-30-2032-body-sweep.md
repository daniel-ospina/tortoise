# #2032 — Apply `_read_capped_body` to all request-body read sites (body-size sweep)

**Goal:** Close the memory-DoS buffering class on all 16 remaining `request.json()`/`request.body()` sites in hosted_api.py by applying the #2029 streaming-cap helper with per-surface caps, with zero behavior change beyond the 413 cap.

**Team:** epistemic-team
**Architecture:** per-site inline `_read_capped_body(...)` at the old read's position (inside existing try blocks with `except HTTPException: raise` first on the 9 try-wrapped sites); 3 module constants + detail strings; no middleware, no imports, no schema changes.

> **Findings date:** 2026-08-30

One external query fired during scoping on Stripe webhook payload sizing (~256 KB typical → 1 MiB cap; 413 → Stripe retries with backoff).

## 1. Approach decision

**Recommended: Approach 1 — per-site inline capped reads.** The issue's own
prescription (`_read_capped_body` per endpoint, per-surface caps, parse
contract preserved verbatim) survives scrutiny on outcome quality, not just
diff size:

1. **Contract preservation is structural, not aspirational.** Each of the 16
   sites keeps its own parse logic byte-for-byte; only the wire read changes
   from `request.json()`/`request.body()` to `_read_capped_body(...)` +
   `_json.loads(raw)` / `parse_qs(raw.decode())`. There is no shared copy to
   drift. A centralized helper family (Approach 2) would have to encode
   email_signup's long 422 detail, commit_session's 400 text, the 3
   conditional content-type sites, the 2 form sites, and the non-dict-coerce
   sites as flags/modes — every one of those is a silent-copy-drift risk.
2. **Limiter/ordering preservation is by construction.** The capped read is
   inserted at the exact source position of the old read. Every ordering that
   matters today (rate-limit-before-parse on register/email_signup/
   agent_signup/oauth_dcr_register; auth-depends-before-body on
   create_api_key/commit_session/agent_token_revoke/claim_team; internal-gate
   before body on provision_tenant/create_demo_graph; 503-before-parse on
   oauth_* (email_signup's 503 runs AFTER the read — see Site 4 note);
   rate-limit-before-parse on register/email_signup/oauth_dcr_register,
   cap-before-limiter on agent_signup/agent_recover (#1709: parse precedes the
   mint/recovery limiters) — is identical because the read never moved.
3. **The 413 is free and correctly shaped.** `_read_capped_body` raises
   `HTTPException(413)`; FastAPI renders the exact `{"detail": ...}` shape
   every other HTTPException produces. A middleware (Approach 3) would have to
   consume the request stream to count bytes — and BaseHTTPMiddleware cannot
   re-inject the consumed bytes into the downstream endpoint's
   `request.stream()`, so every endpoint would still need a code change to read
   from a stash (collapsing the middleware's zero-churn advantage); it would
   also need content-type inspection for the 3 conditional sites plus an
   `/mcp` skip — three silent-failure surfaces.
4. **Cost is bounded.** 16 × ~3-line transforms + one constants block + tests.
   Not meaningfully larger than the DSL variant, and every hunk is
   independently reviewable.

### Rejected alternatives (with when each WOULD have been better)

**Approach 2 — shared helper family (`_read_capped_json_body(malformed=...)`).**
*When it would have been better:* if the issue required a UNIFORM parse
contract (e.g., all malformed → 400 with one copy). It does not — it requires
preserving each site's distinct contract. The conditional content-type sites
(agent_signup/recover/token_revoke) and the 2 form sites do not fit a
JSON-parse helper at all, so the DSL would cover 13/16 and leave 3 orphans,
making the "shared" logic partial and the contract table still necessary.
Rejected.

**Approach 3 — pure-ASGI per-path cap middleware.**
*When it would have been better:* if the issue had asked for a global uniform
cap with uniform error shape, ACCEPTED reordering (413-over-401 on auth-gated
surfaces), and a single future-proof choke point. The issue explicitly forbids
"response codes beyond the cap", requires THREE distinct per-surface caps
(middleware would need a per-path cap table anyway, reintroducing per-site
config), and must skip `/mcp` + content-type-inspect 3 sites. Rejected.

**Approach 1 variant — add the #2029 Content-Length pre-check fast-path to
each site.** *When it would have been better:* if any site had a pre-existing
size gate whose ordering must be preserved (the manifest path's 64KB YAML
check) or if CL-framed oversized requests were so hot that skipping even a
256KiB drain mattered. Neither holds for the sweep: there is no pre-existing
size check on any of the 16 sites, and the streaming cap already bounds
buffered bytes at the cap (256KiB max, not the claimed size). The streaming
cap alone is correct; the CL pre-check is an optimization, noted as a
follow-up, out of scope.

## 2. Problem statement

`tortoise/hosted_api.py` still has 16 `request.json()` / `request.body()`
call sites (plus the two already-migrated surfaces, the import-artifact and
pack-manifest paths) that buffer the ENTIRE request body into memory before
any validation — the same unbounded-buffering (memory-DoS) class #2029 fixed
on the manifest path with `_read_capped_body`, a streaming helper that 413s
as soon as the running total exceeds a hard cap — WITHOUT buffering or
draining the remainder (draining would consume attacker bandwidth) and
before any parse work.
This sweep applies the same streaming cap to all 16 remaining sites with
per-surface caps (256KiB for the 14 small JSON/form surfaces, 8MiB for
commit_session's session-content payloads, 1MiB for Stripe webhook events),
while preserving each site's malformed/empty parse contract and limiter
ordering EXACTLY — no payload-semantics changes, no response-code changes
beyond the cap itself.

## 3. Proposed solution

### 3.1 Constants block (new, at `tortoise/hosted_api.py` ~line 7650)

Insert between the `_ImportVerifyError` class (ends ~line 7649) and
`async def _read_capped_body` (line 7653). Follow the existing two-blank-line
top-level convention:

```python
# ── Request-body size caps for JSON/form surfaces (#2032) ─────────────────
# Streaming cap applied to every remaining `request.json()`/`request.body()`
# site via `_read_capped_body` (the #2029 helper): reject oversized bodies
# BEFORE buffering/parsing — the memory-DoS class #2029 closed on the import
# + manifest paths. 256 KiB covers every small JSON/form surface (register,
# login, signup, claim, oauth, keys); commit_session carries session-content
# payloads (8 MiB); Stripe webhook events are signed JSON of Stripe-controlled
# size (typically up to ~256 KB per webhook guides, well under the 1 MiB cap
# even for expanded invoice/dispute payloads — the bound primarily protects
# the HMAC/verify path and defends against oversized replay bodies; note a 413
# is non-2xx, so Stripe retries with backoff, hence the generous headroom) (1 MiB).
_BODY_MAX_BYTES = 256 * 1024
_COMMIT_SESSION_MAX_BYTES = 8 * 1024 * 1024
_STRIPE_WEBHOOK_MAX_BYTES = 1024 * 1024

_BODY_413_DETAIL = "request body exceeds the size cap (256 KiB)"
_COMMIT_SESSION_413_DETAIL = "commit session request body exceeds the size cap (8 MiB)"
_STRIPE_WEBHOOK_413_DETAIL = "Stripe webhook body exceeds the size cap (1 MiB)"
```

Optional (nice-to-have): extend `_read_capped_body`'s docstring's last
sentence to mention it is shared by the import path, the pack-manifest path
(#2029), and the #2032 body-sweep. No behavior change.

No new imports anywhere: `_json` (`import json as _json`) already exists at
line 13; `from urllib.parse import parse_qs` is already imported locally in
the two form endpoints; `_read_capped_body` is a module-level function
resolved at call time (proven in production by the #2029 manifest call at
line 3251, which also precedes the helper's definition in source order).

**Memory bound (honest worst case, 8 MiB commit cap):** `_read_capped_body`
holds `chunks` + one `b"".join` copy + the parsed object tree; a max-cap
commit transiently holds raw-side buffers (~2×8 MiB: chunks + join copy) plus
the parsed object tree (~5–15× raw ≈ 20–60 MiB) → ≈ 30–70 MiB per in-flight
max-cap commit. Realistic concurrency is low — commit is
auth-gated (`Depends(get_current_team)`), per-key 300/min, per-team budget —
so this is accepted; 8 MiB is chosen because the schema-bounded portion of a
Layer-1 payload is ~150–300 KB (50 points × ≤1000 chars + 500 entities + 500
operators) but `summary`/`story_arc`/`sources`/`provenance_refs` are UNBOUNDED
in the schema — a Layer-1-valid payload with a long story_arc must not
false-413 (verifier P3). Folding a `max_length` on summary/story_arc into
#2048 is noted there.

## 4. Per-site implementation notes (before → after)

### Site 1 — provision_tenant (893), `/internal/provision`
No try today (500 contract: JSONDecodeError propagates). Internal-gated
(`_check_internal` runs before the body read; the Supabase 503 check also
precedes it — ordering preserved).

```python
# before
    body = await request.json()
    team_id = body.get("team_id")
# after
    raw = await _read_capped_body(request, _BODY_MAX_BYTES, _BODY_413_DETAIL)
    body = _json.loads(raw)
    team_id = body.get("team_id")
```

Contract: malformed → 500 (unchanged, `_json.loads` raises uncaught exactly
like `request.json()` did); empty → 500 (unchanged, `json.loads(b"")` raises
— see Site 7 note); oversized → 413 (new). `body.get(...)` unchanged — a
non-dict JSON body still raises AttributeError → 500 exactly as today.

### Site 2 — session_login (2948), `/v1/session/login`
try/except → coerce `{}`. Public, per-IP limiter (5/hr) runs AFTER the parse
today; cap sits at the parse position, so oversized → 413 before the limiter.
**Ordering nuance (review #2053 P2):** TODAY an oversized junk body also
failed `json.loads` → coerce `{}` → limiter → prefix-gate 401 (CHARGED —
consuming a 5/hr slot); AFTER the sweep it 413s uncharged before the limiter.
The #1719 charge semantics hold (a 413 is a client error that never reaches
authz work — uncharged, like 429), and the 413 path stays bounded per-IP by
the global RateLimitMiddleware (100/min, hosted_api.py:679) — so the memory
bound (256 KiB drain) + the middleware rate bound replace the old 5/hr
policing of oversized junk. Accepted residual: oversized spam no longer
consumes the login bucket — documented, not a blocker (security reviewer:
"no new amplification; pre-PR these requests buffered unbounded bytes").
Unauthenticated empty/malformed bodies never reach Supabase (token coerced to
`""` → 401 prefix gate).

```python
# before
    try:
        body = await request.json()
    except Exception:
        body = {}
# after
    try:
        raw = await _read_capped_body(request, _BODY_MAX_BYTES, _BODY_413_DETAIL)
        body = _json.loads(raw)
    except HTTPException:
        raise
    except Exception:
        body = {}
```

Contract: malformed/empty → `{}` → 401 (unchanged); non-dict → `{}` (the
`if not isinstance(body, dict): body = {}` line below is untouched); oversized
→ 413 (new, propagates via `except HTTPException: raise`); mid-read stream
failure → `{}` (unchanged — was caught today too).

### Site 7 — commit_session (5665), session commit
try → 400 `"Request body must be a JSON object"`. Auth-gated (401 first).
Cap is 8MiB. **Variable rename:** today the local `raw` holds the PARSED
value (used downstream by `validate_payload_dict(raw)`). Introduce
`raw_bytes` for the wire bytes; keep `raw` as the parsed value so the rest of
the handler is untouched.

```python
# before
    try:
        raw = await request.json()
    except Exception:
        raise HTTPException(  # noqa: B904
            status_code=400, detail="Request body must be a JSON object")
# after
    try:
        raw_bytes = await _read_capped_body(
            request, _COMMIT_SESSION_MAX_BYTES, _COMMIT_SESSION_413_DETAIL)
        raw = _json.loads(raw_bytes)
    except HTTPException:
        raise
    except Exception:
        raise HTTPException(  # noqa: B904
            status_code=400, detail="Request body must be a JSON object")
```

Contract (verified empirically against Starlette 1.6.0 in this repo):
- Malformed JSON → 400 (unchanged).
- **Empty body → 400 (unchanged).** Note: `request.json()` on an empty body
  raises `JSONDecodeError` in Starlette 1.6.0 (source has no empty-body
  special-case; `json.loads(b"")` raises) — it does NOT return `None` as the
  issue note speculated. `_json.loads(b"")` also raises → both land in the
  same try → same 400. The outcome the issue cares about (empty → 400) holds
  either way.
- Non-dict JSON (`[1,2]`) → `validate_payload_dict([1,2])` → its existing
  result (unchanged — same parsed value passed in).
- Oversized → 413 with `_COMMIT_SESSION_413_DETAIL` (new, propagates via
  `except HTTPException: raise`); mid-read stream failure → 400 (unchanged).

- JSON + oversized → 413 (new).
- `signup_token` normalization lines and the `_agent_recover_flow` call below
  are untouched.

    except Exception:
