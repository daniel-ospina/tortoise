# Plan — #2134: v2 extractor truncation (R2: calibration-first + durable call-level escalation core)

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.
> **R2 (2026-09-06, owner-directed):** this revision supersedes the R1 escalation-net architecture (git history at 1b9c7c31 holds the full R1 review record). The R2 destination is **bounded extraction units** (segment-the-write-path, filed as **#2335**) — the industry-standard pattern every surveyed memory system uses (mem0 per-message-pair extraction + write-time ADD/UPDATE/DELETE; Graphiti episodic ingestion + `invalid_at` edge-closing; Hindsight auto-chunk at retain time; Letta bounded state blocks). Tortoise ALREADY runs that pattern *between* sessions (per-session commit → S3 search → S4 gap-review merge → resolve_entities → REVISES/supersede); #2335 extends it one level down (into oversized sessions). **#2134 (this plan) delivers: (1) the calibration study whose data sizes #2335's segments and decides the geometry, and (2) a SIMPLIFIED durable escalation core** — one-shot retry at a bigger budget + fail-loud residual + telemetry — that survives the transition to #2335 unchanged (it lives at the call level, so it is the same code whether the unit is a whole session or a segment). The R1 exotic whole-session-envelope machinery (esc-budget 3rd-call re-prompt, sloppy 4th-bucket taxonomy, the sticky-flag clearing chains that only existed for the 3-call episode, the 7200s wall-clock defense) is **cut** — it optimized an envelope the destination abandons (do-then-replace cost, owner direction).

**Goal:** Stop v2-mode ingest (`--ingest-mode v2`) from silently truncating the S2/S4 embed list on large multi-session haystacks — via a **calibration study** (the deferred #1787 revalidation + input-size↔overage curve, made real) that decides geometry by DATA, a **simplified durable one-shot escalation** at the S2/S4 + S1 seams (the #2280 mirror, call-level so it survives #2335), **permanent telemetry** for the later cost optimization, and a **fail-loud residual** policy (partial lists never silently pass; the raw-chunk leg stands).

**Team:** epistemic-team
**Tier:** standard (`complexity:standard` — Architecture domain)

**Architecture (R2):** Three legs, sequenced by DATA not assumption, and by destination not by stopgap:
1. **Leg 1 — the calibration study (Task 1):** re-run the truncation census at the CURRENT 16K cap on the #2134 recorded-failure set + a fresh mini-set, AND record each truncating session's **input size** (EDU/turn count, computable offline from the source data) alongside its **output overage** (Task 0's per-call token capture). The result is the **calibration curve**: which session sizes fit a single-call envelope, where it breaks, and how big the mega-tail is. This decides BOTH the go/no-go (raise-vs-escalate-vs-#1778-trigger) AND the **geometry** (single-call envelope mainline with #2335 as a tail-router, vs. segmentation mainline).
2. **Leg 2 — the durable call-level escalation core (Tasks 0, 2-5):** on `finish_reason == "length"` at S2/S4 (`_complete_parsed`) and the S1 seam (`run_s1`), re-attempt **ONCE** at an escalated output budget (`TORTOISE_EXTRACTOR_ESCALATION_TOKENS`, default 32000, range [16000..64000]). Residual truncation after the one escalation **fails loud** (`truncated_parse_error`, `valid=false`), never a silent partial. **Four outcome buckets** make every escalation event accounted: `recovered` / `residual` / `abort` / `partial`. **The escalation episode adds exactly ONE call** (the escalated `_complete` at `esc`), and the escalated response is parsed **once, terminally** — the pre-existing base-cap ladder re-prompt NEVER runs post-escalation (R3: it would run at the BASE cap, re-truncate, and leak a truncation-attribute rung-4 partial). The pre-existing #1746 ladder semantics for NON-length paths are unchanged (incl. its own pre-escalation error-informed re-prompt, which can precede escalation on the `[stop-unparseable → length]` path — that is existing behavior, not an escalation-episode call). Permanent telemetry (escalation count + per-bucket + token delta) makes the upfront-vs-escalation cost question answerable from real runs. Because this lives at the `_complete`/`_complete_parsed` level, it is scale-invariant: **when #2335 lands, the same code guards each segment's calls.**
3. **Leg 3 — segment-the-write-path (#2335, filed, parallel-scoped, NOT built here):** the geometry fix. Executed when Task 1's curve says where the envelope breaks and how to size segments (starting from the existing 50-EDU S1 chunk boundary for byte-identity/eval parity).

**Explicitly NOT built here:** the segment-the-write-path re-architecture (#2335), the structural S4 gaps-only delta (#1778, trigger-gated), WS1 read-side ordering, question-type routing, and any whole-session-envelope machinery beyond the one-shot call-level net.

## Pattern Research

> **Findings date:** 2026-09-05 (R1) + 2026-09-05 (R2 external). **Gate skipped:** plan touches ZERO new third-party dependencies — `os`/stdlib + in-repo patterns only. Step A (prior research intake) ran: `/tmp/2134-scope.md` §1-§5 + `/tmp/2281-scope.md` §1.6 + #1787's Axis Research (model ceilings) + industry write-path research (R2).

- **Industry — how memory systems handle very long conversations (R2, verified 2026-09-05):**
  - **mem0** (arxiv 2504.19413): extraction unit = ONE message pair, with context = an async-maintained rolling conversation summary + the last ~10 raw messages. A separate update call retrieves the top-10 similar stored memories and picks ADD/UPDATE/DELETE/NOOP per fact. Never whole-conversation analysis; output per call is small BY CONSTRUCTION; "latest wins" is a write-time update of the stored memory.
  - **Zep/Graphiti:** episodic ingestion (each message batch = an episode) → incremental triplet extraction → per-edge `valid_at`/`invalid_at`; a contradicting fact closes the old edge's validity window and opens a new one. Nothing deleted; "now" = open-validity filter.
  - **Vectorize Hindsight:** facts extracted at retain time with entity resolution; documents auto-chunked; growing conversations re-retained per message (auto-chunked); recall = 4 parallel strategies reranked to a token budget.
  - **Letta/MemGPT:** current state in small size-limited in-context blocks (updated); the rest to archival storage with recursive summarization on eviction.
  - **Unifying rule to copy:** bound the input per call; keep the past as a compressed/resolved artifact; reconcile new facts against stored facts AT WRITE TIME. Tortoise runs this pattern between sessions already; #2335 extends it inside sessions. **What NOT to copy:** mem0's per-turn-pair granularity (live streaming preference memory — we ingest whole transcripts offline and can batch to a segment); Letta's agent-driven memory tools (live-agent paradigm).
- **Canonical (from #1787's Axis Research, re-verified):** OpenAI/Anthropic canonical truncation handling = **retry with a higher `max_tokens`** when `finish_reason="length"` — the #1746 skip-on-length is the documented anti-pattern for a raiseable cap. DeepSeek V4 max output 384K (the 16K cap is self-imposed, not a model ceiling).
- **Codebase precedent (#2280, the shape to mirror):** `_ask_reader_complete` (sdk.py:181-241) fires ONE cost-bounded retry at `TORTOISE_ASK_ESCALATION_TOKENS` on `length`, then fails loud. The extractor analog: one retry at `TORTOISE_EXTRACTOR_ESCALATION_TOKENS` on `length`, then fail loud — never a silent partial.
- **Order-stability (no byte-identity risk):** the label-order shuffle seed derives from the story (`_label_order_rng`), so a same-prompt re-emission reproduces the SAME ordered list — escalation adds headroom without changing output shape on the common path (escalation never fires on non-`length` calls, so non-truncated calls are byte-identical).
- **Cost bound (from the issue's OWN 0100672e evidence, NOT an average):** 13/139 ≈ 9.4% of calls truncated at 16K on the worst question (~40× the #1787 reval's 0.22% healthy rate — "rare" is the wrong prior). Per event at deepseek-direct rates (~$0.01-0.04/event); the fire-rate is the dominant unknown — **measured by Task 1, never assumed**.

## Design decisions

### D1 — Escalation trigger + seam: fire ONCE on `finish_reason == "length"`, BEFORE any parse
Trigger = `finish_reason == "length"` at ANY pre-escalation attempt (attempt 1 OR the base-cap error-informed re-prompt attempt 2), regardless of parse outcome — `length` is the deterministic signal the model exhausted its output budget, and a rung-1 "successful" parse of a truncated JSON is NOT proof of completeness (tail-cut recovery can turn a mid-list cut into a valid shorter list — the silent-loss class). Seams: S2/S4 via `_complete_parsed` (both call it), S1 via `run_s1` (which calls `_complete` directly, bypassing the ladder), and — the THIRD production `_complete_parsed` caller — the classify-later **kind_classifier adjudication** path (kind_classifier.py:405, `max_tokens=ADJUDICATION_MAX_TOKENS=1500`). **Escalation is SCOPED OUT of the kind_classifier seam:** `_complete_parsed` gains `escalate: bool = True` and `kind_classifier._adjudicate_batches` passes `escalate=False`. Rationale: 32000 ≈ 21× the 1500 adjudication budget (disproportionate headroom); a residual fail-loud `_ParseError` would be swallowed by the adjudicator's fail-open `except Exception` → kNN top-1 fallback (kind_classifier.py:409-416) — invisible-by-design damage; and the `finally` (:418-434) forwards only `attempts`/`retries`/`truncated`/`deadline_aborts` into `usage` → `_rollup_llm`, so `recovery.*` escalation counters would never reach `recovery_stats`. A length-truncated adjudication therefore keeps TODAY's behavior verbatim (pinned by `test_kind_classifier_adjudication_length_no_escalation`). Fire **once** (the `escalated` flag) on the FIRST `length` at any pre-escalation attempt; never on a post-escalation attempt.

### D2 — Escalation budget: `TORTOISE_EXTRACTOR_ESCALATION_TOKENS`, default 32000, valid range [16000..64000]
New helper `_extractor_escalation_tokens(base: int | None) -> int` in `extractor_v2.py`, mirroring `ask_env_int` (retrieval.py:147-160) **exactly** — valid value in [16000, 64000] used AS-IS; below 16000, above 64000, or garbage → default 32000. NO clamp-to-bound arm. `_stage_cap`'s inline env-read pattern supplies the fail-open warning (invalid env never crashes). The caller escalates **only when `esc > (base or 0)`**. **When `esc ≤ base`** (e.g. a future base-cap raise not in lockstep), the length-truncation is **RESIDUAL — fail-loud `truncated_parse_error`, never rung-4 partial-accept** — an un-escalatable truncation must be honest; the escalation knob must move in lockstep with any base raise (go/no-go note).

**Lane policy:** escalation is **default-ON on every lane** that calls `extract_session_v2` — eval (`tools/longmem_eval/ingest_v2.py`), SDK capture (`sdk.py:2213` + `_extract_session_v2` :2818), hosted capture (`hosted_api.py:6228`). Lane-agnostic mandate. **Hosted-capture kill model (verified):** there is NO outer request envelope — `capture_session` (hosted_api.py:5879) runs `_extract_session_v2` SYNCHRONOUSLY (plain uvicorn, no per-request timeout middleware; fly.toml only a 15s health-check timeout). A platform/worker kill mid-escalation records NOTHING (same honesty class as today's long extractions). The abort bucket's fallback is tied ONLY to `_complete` raising.

### D3 — Residual policy: fail-loud, never a silent partial; four outcome buckets; terminal post-escalation parse (R2 + R3 delta-review fixes)
After the ONE escalation, if `finish_reason` is STILL `"length"` (residual truncation): **do NOT partial-accept — and do NOT let any ladder rung clean-parse a shorter parse.** Rungs 1-3 (`_parse_json` progressive tail-cuts, `_repair_candidates` `}`-closers, `_validate_output_shape` treating ABSENT sections as valid) can clean-parse a TRUNCATED response cut at a section boundary → a silent tail-drop with `valid=true`. The fix makes the invariant airtight: **a residual (`escalated and finish == "length"`) is treated as truncated UNCONDITIONALLY — the residual branch has NO parse-acceptance path.** A strict canonical full-parse (`_parse_canonical_strict` — fence-strip + brace-balanced `json.loads`; NO progressive tail-cut, NO sanitize, NO repair closers, NO absent-section shape gate, NO rung-4) runs **only to enrich the error `excerpt`, never to accept**. `_parse_canonical_strict(response) -> dict | None` is a NEW named helper (NOT `allow_partial=False` — that only gates rung-4 while rungs 1-3 still clean-parse).

**R2/R3 four-bucket accounting (supersedes R1's recovered/residual/abort/sloppy + the 3-call episode):** every escalation event lands in EXACTLY one bucket. The escalation episode adds exactly ONE `_complete` call; the escalated response is then parsed **once, on a terminal path — the ladder's error-informed re-prompt is DISABLED post-escalation** (R3-1: in the real `_complete_parsed` loop, a parse raise with `finish != "length"` triggers the re-prompt at the loop's ORIGINAL base `max_tokens` → a re-truncation → rung-4 partial-accept → a truncation-attribute `partial_parse` that violates Task 6's acceptance; the terminal path closes that leak):
`escalated == escalated_recovered + escalated_residual + escalated_abort + escalated_partial`
- `escalated_recovered` ⟺ the escalated call returned AND `finish != "length"` AND the terminal parse returned FULL. `stats["partial"]` is structurally False on a full return (`_parse_json_robust` returns at first success; rung-4's `partial=True` only ever accompanies a partial-head RETURN, never a raise-then-continue — so no flag can leak onto a full terminal; R3-5 dropped R1's dead full-override machinery).
- `escalated_residual` ⟺ the escalated call returned AND `finish == "length"` (unconditionally truncated → fail-loud `_ParseError(truncated=True)` → census `truncated_parse_error`). NO `stats["partial"]` clear is needed on this branch — in the simplified machine no parse ever runs before the residual raise (escalation fires before parsing the base attempt; the residual check precedes parsing the escalated response; rung-4 partial always RETURNS rather than continuing), so the flag is structurally False here (R3-4 removed R1's dead clear; a defensive `stats["partial"] = False` before the raise is optional belt-and-braces against future reordering, not load-bearing).
- `escalated_abort` ⟺ the escalated `_complete` call RAISED (transient-after-retries / deadline kill / fatal 4xx / adapter read-timeout) → D3b fallback.
- `escalated_partial` ⟺ the escalated call returned `finish != "length"` and the TERMINAL parse ended in the ladder's own honest failure class — a rung-4 partial-accept head returned with `partial_parse` recorded, OR a `_ParseError(truncated=False)` → census `parse_error` (complete-but-garbage with no valid prefix). **These are the EXISTING recoverable census classes, unchanged** — the escalation event is additionally bucketed so the accounting invariant holds, never an unaccounted escalation.

(R1's `escalated_sloppy` bucket + its esc-budget 3rd-call re-prompt, the `[base, esc, esc]` arm, the P1-40 re-prompt guard, the P2-42 sticky-flag chains for the sloppy intermediate head, and the 7200s wall-clock math are **CUT in R2**: the simplified episode cannot produce that state machine — after the ONE escalated call there is no third call, so there is no intermediate sloppy head to guard. A stop-but-malformed escalated response is parsed ONCE on the terminal path (no re-prompt) → honest `partial_parse`/`parse_error` terminal via `escalated_partial`. Recorded trade-off vs R1: the escalated response gets NO second full-list chance when it emits malformed-but-completable JSON — accepted: that arm is a model-quality issue, not a budget issue, and the recovery-path loss is marginal on a rare arm; if Task 1's curve later shows it matters, the R1 3-call arm is recoverable from git history (1b9c7c31).)

**The accepted exception (cross-ref D2 lane policy):** a process/platform kill mid-escalation on the hosted-capture lane bumps `escalated` in-memory but produces NO outcome row → all four buckets read 0 — accepted (same honesty class as today's long extractions).

### D3b — Escalated-call failure policy (abort bucket)
The escalated `_complete` call can raise: transient 429/5xx exhausted its retries, a deadline kill, a fatal 4xx, or the fixed adapter read timeout (model_adapters.py:149/:254 `timeout=(10, 60)` — a stalled socket read dies at a fixed 60s). Without a policy, the truncating pre-escalation attempt's retained response is never parsed, the recoverable head is discarded, and the census shifts to a KILLER for a transient failure. **Fallback (three parts):**
1. **Re-parse the truncating pre-escalation attempt's ALREADY-CAPTURED retained response under a TRUNCATED-HEAD parse — canonical-then-rung-4 ONLY, ALWAYS classed partial** (never rungs 1-3 on a known length-truncated input — a section-boundary cut would clean-parse to a shorter valid dict): run `_parse_canonical_strict`, then `_longest_valid_prefix` (rung-4). The recovered head is ALWAYS recorded `partial_parse` (recoverable, `stats["partial"]=True` set UNCONDITIONALLY) and `escalated_abort` is bumped — never a silent `valid=true` return. Both fail → fail-loud `truncated_parse_error` + the raw-chunk leg stands. (On the re-prompt path this is **attempt 2's** response — the response live at the moment escalation fired.)
2. **Keep the adapter read timeout at its fixed `(10, 60)` — do NOT scale it.** `(10, 60)` is a PER-READ inactivity bound (60s between bytes), NOT total duration — scaling it to ~1600s would remove the socket-layer stall bound (~26× regression).
