# #3525 — CSP for the app origin + a `no-store` regression guard

**Issue:** daniel-ospina/tortoise#3525 · `complexity:standard` (Level `task`, inferred — the issue carries no fractal fields)
**Stage:** SCOPE + PLAN (task-workflow-standard) · 2026-09-22 · branch `fix/3525-csp-no-store`
**Pipeline:** scope-verify ran 6 fresh-context cycles (findings all fixed; the last cycle's were dev-server invocations and surface-list precision); plan-verify ran 2 parallel reviewers.

## Problem definition (converged)

The issue names two cross-cutting hygiene gaps on the Cloudflare Pages surfaces:

1. **No `Content-Security-Policy` exists on any Pages surface.** `website/_headers`
   and `website/apps/dashboard/public/_headers` carry HSTS only. The MCP consent page
   (`tortoise/hosted_api.py`) already ships a nonce CSP, so the migrated Pages surfaces
   are strictly weaker than a surface we already ship.
2. **Cookie-setting responses must never be cacheable.** Cloudflare can strip `Set-Cookie`
   from a cached response, and **Pages Functions bypass `_headers`** (confirmed by CF docs:
   "Custom headers defined in the `_headers` file are not applied to responses generated by
   Pages Functions") — so a cookie-setting Function cannot rely on `_headers` for
   `Cache-Control: no-store`.

Root cause for (1): CSP adoption was deferred because the pre-#3501 pages carry inline
`<script>`, inline `<style>` and inline event handlers (`onclick=`/`oncancel=`/…), which a
strict `script-src 'self'` would break — shipping a broken page is worse than no CSP.

Root cause for (2): the guarantee was only a convention at each call site. #4104 already
wired `no-store` into the shared `json()`/`redirect()` builders, but nothing fails if a new
cookie-setting path is added without it.

## Policy definitions (the actual strings this change ships)

Four constants, one per trust level. **`style-src` carries `'unsafe-inline'` in every policy**
— both React apps render inline style attributes (the dashboard SPA has ~133
`style={{…}}` props in `src/main.jsx`) and the static pages carry inline `<style>` blocks,
so omitting it would ship an unstyled page. `script-src` is where the trust levels differ.

**`RELAXED_CSP`** — static assets default (`/*` in both projects) and the Function HTML on
the pre-#3501 pages (`auth/index.ts`, `welcome.ts`, blog `ok()`, marketing root rewrite):

```
default-src 'self';
script-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://us-assets.i.posthog.com https://www.googletagmanager.com https://connect.facebook.net https://challenges.cloudflare.com;
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https:;
font-src 'self' data:;
connect-src 'self' https://*.supabase.co https://api.premiselabs.co https://us.i.posthog.com https://us-assets.i.posthog.com https://www.googletagmanager.com https://www.google-analytics.com https://region1.google-analytics.com https://connect.facebook.net https://www.facebook.com https://challenges.cloudflare.com;
frame-src https://challenges.cloudflare.com;
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
form-action 'self'
```

**`STRICT_CSP`** — the dashboard SPA document (`/`, `/team`, `/team/`, `/index.html`
overrides in `website/apps/dashboard/public/_headers`):

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self' data:;
connect-src 'self';
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
form-action 'self'
```

**`ADMIN_CSP`** — the `/admin` console shell (all three HTML return paths in
`admin/[[path]].ts`). Differs from `STRICT_CSP` by the Supabase origins the console itself
talks to (supabase-js data/storage from `blog-admin/src/lib/blog-api.ts`) **and** by a
broad `img-src`, because the console previews author-supplied image URLs — `ImageNode.tsx`
renders any TipTap image `src`, `PostEditor.tsx` renders `form.cover_image_url`, and the
publish API accepts any absolute URL. Narrowing `img-src` to Supabase would blank those
previews:

```
img-src 'self' data: blob: https:;
connect-src 'self' https://*.supabase.co wss://*.supabase.co;
```

**`STRICT_CSP` + nonce** — the `/auth/confirm` interstitial only (`confirm.ts`): identical
to `STRICT_CSP` except `script-src 'nonce-<per-response>'`; its single inline `<script>`
carries `nonce="<per-response>"`. This is the one surface migrated to the MCP consent
page's own nonce treatment, and it is deliberately **stricter** than that precedent (the
consent page also allows `cdn.jsdelivr.net`; the interstitial needs no external script).

## `_headers` semantics (verified empirically with `wrangler pages dev`, and in CF docs):
- A header applied by more than one matching rule is **joined with a comma**, not overridden.
- A header can be detached with `! <Name>` inside a later matching block, then re-added.
- Path rules do **not** apply to Function responses.

**The exact chosen `_headers` block was exercised, not assumed.** A scratch Pages project
with `/*` relaxed + detach/re-add strict on `/`, `/team`, `/team/` and a `/team → / 200`
rewrite returned, over the wire:

```
/            -> STRICT
/team        -> STRICT     (200-rewrite: matching uses the REQUEST path)
/team/       -> STRICT
/index.html  -> STRICT     (this row originally read RELAXED; the rule was added and re-run)
/signup      -> RELAXED
/signup.html -> RELAXED
/nonsense    -> RELAXED
```

The detach does remove the inherited value (no comma-join observed), and the failure
direction stays safe: even if a detach silently did not apply in production, the browser
intersects the two policies and the SPA remains strict (its relaxed superset adds nothing
the strict policy does not already deny); no legacy page matches a strict rule.

## Alternatives considered (solution-diverge → converge)

**A — strict CSP everywhere, `unsafe-inline` nowhere.** Rejected: it breaks every legacy
auth/marketing page today (inline handlers cannot be nonced; they need `'unsafe-hashes'` +
per-handler hashes, or deletion). The issue itself sequences this after #3501, which is
still OPEN. Shipping it now = broken signup page.

**B — project-wide `_middleware.ts` per Pages project that stamps one policy.** Rejected:
`website/apps/dashboard/functions/auth/index.ts` records a decision of record *against* a
project-wide middleware in that project ("the blast radius of a middleware is the whole
project; the blast radius of this file is one path"). The contradiction test applies: a
common pattern that contradicts a recorded decision is not adopted. (The HSTS precedent in
both projects is also per-site stamping, not middleware-wide.)

> **Alternative B is the only approach that would remove the policy-string duplication
> below, and it is closed by that decision.** So the chosen design accepts duplication and
> pays for it with the drift guard in deliverable **5(d)**: a test parses both `_headers`
> files and asserts their `Content-Security-Policy` values are byte-identical to the
> exported constants. Drift therefore fails CI instead of silently weakening the policy —
> provided the job actually runs, which deliverable 5's CI path-selection note handles.

**C — Report-Only CSP.** Rejected: no enforcement, and no `report-uri` sink exists, so it
would be a no-op gate.

**D (chosen) — one policy per trust level, applied where the response is produced.**
- A shared module defines the policies once per Pages project.
- `_headers` carries a **relaxed, inline-tolerant default** for static assets, with a
  **strict** override on exactly the SPA-document paths (`/`, `/team`, `/team/`,
  `/index.html`) via detach+re-add.
  Failure direction is safe: if detach silently did not apply in production, the two
  policies intersect (browser enforces both) — the SPA is still strict, and no legacy page
  ever receives the strict policy because it does not match the strict rule.
- Functions that produce HTML stamp the matching policy explicitly (they bypass `_headers`).
- The Function-rendered security interstitial (`/auth/confirm`) gets a per-response
  **nonce** strict policy, matching the MCP consent page precedent.
- A dashboard unit guard fails if a cookie-setting response is cacheable, or if a new
  `Set-Cookie` writer appears outside the two audited files.
- The same test file also asserts each policy constant is **present** on the response
  helper paths it owns (negative guard: a silently-absent policy fails CI), and that both
  `_headers` files carry the same value as the constants (drift guard).

The `unsafe-inline` in the relaxed policy is a **declared, temporary relaxation** tied to
#3501: when #3501 has removed the inline handlers/bridge, the relaxed policy is tightened.
This is recorded in the doc deliverable and in the policy module's comment.

## `### Adversarial Threat Surface`

**Declaration: (not adversarial).** The adversarial domain is defined as gate/enforcement
code whose correctness is *"an attacker cannot make it fail open"* — code that consumes
**attacker-controlled input** and could be made to accept it (argv/path/symlink resolution,
working-tree discard, merge/verification gates). The criterion does not reach a response
header: a CSP is declarative browser policy with no attacker-controlled input path in our
code, so there is no input that can be forged to defeat it. Its realistic failure mode is
**misconfiguration** (a policy silently absent, or a mismatched path), and that class is
covered by tests rather than by a threat list: guard (e) makes a missing stamp on any
enumerated HTML-producing Function a CI failure, and the `_headers` design was exercised
over the wire rather than assumed. The adversarial 2-cycle cap therefore does not apply;
the standard review cycle count governs.

**Rejected reading:** if *any* security control with a fail-open failure mode were
adversarial, the domain would swallow config, headers, TLS policy and dependency pins — the
domain's own examples are procedural gates, and the bounded exit (`THREAT SURFACE COVERED`,
2 cycles) is calibrated to attacker-bypass enumeration. The fail-open **concern** is real,
which is why it is met with tests rather than with a threat list here.

## Deliverables

1. `website/apps/dashboard/functions/_shared/security-headers.ts` — policy constants
   (`RELAXED_CSP`, `STRICT_CSP`, `ADMIN_CSP`, `strictCspWithNonce(nonce)`).
2. `website/apps/dashboard/public/_headers` — relaxed default + strict override on `/`,
   `/team`, `/team/`, `/index.html` (the `/team/ → / 200` rewrite in `public/_redirects`
   serves the same SPA document, and `/index.html` is the raw SPA shell; all four must
   carry the same policy).
3. Function stamping on the app origin: `auth/index.ts`, `welcome.ts`, `auth/confirm.ts`
   (nonce), `admin/[[path]].ts`. The admin file has **three** HTML-producing return paths,
   and all three must be stamped — the `env.ASSETS.fetch` passthrough, the constructed
   shell, and `notAnAdmin()`'s 403 page (`admin/[[path]].ts:233-245`). The admin policy is
   exactly `ADMIN_CSP` as defined above — in particular `style-src 'self' 'unsafe-inline'`
   (React inline styles) and the **broad** `img-src 'self' data: blob: https:` (author-supplied
   image previews). Do NOT narrow `img-src` to Supabase.
4. `website/functions/_shared/security-headers.ts` + marketing stamping:
   `website/_headers`, `functions/_middleware.ts` (root rewrite), `functions/blog/_lib.ts`
   (`ok()`).
5. Regression guard: `website/apps/dashboard/src/securityHeaders.test.js` (runs under
   the dashboard's own `node --test src/*.test.js`, which CI already executes). Every check
   is anchored to a fact the runtime uses, not to a string that merely appears in a file —
   the distinction matters because a string check also passes on a commented-out line and on
   a value moved to a block nobody visits:
   (a) `json()`/`redirect()` with cookies always carry `Set-Cookie` + `no-store`;
   (b) the cookie-writer scan is an **umbrella over a bare `set-cookie` substring**
   (any case, any quote style, any construction) after comments are removed by
   deleting the exact ranges **`@babel/parser`** reports — a real parse, not a
   hand-rolled quote/regex scanner, because the scanner version desynced three
   times in review (a quote inside `/[&<>"']/` in `confirm.ts`, a nested template
   literal in `blog/_lib.ts`, and a `//` after a `:`), silently leaving comments
   in and letting a commented-out stamp count. `esbuild`'s `transform` was tried
   and rejected: it preserves comments **inside object literals**, which is exactly
   where every stamp lives. So a call (`headers.append("Set-Cookie", …)`), an
   object key (`"set-cookie":`), an array-of-pairs `HeadersInit`
   (`new Headers([["Set-Cookie", v]])`), an indirection
   (`const H = "Set-Cookie"; headers.set(H, v)`) and a template-built
   `` `set-cookie${""}` `` are ALL caught, while the three hop-by-hop
   STRIP-LIST proxies (`"set-cookie",` array items in `api/v1/[[path]].ts`,
   `api/provision.ts`, `blog/api/[[path]].ts`) are exempted **by path** and pinned
   **by shape** — each must name the token EXACTLY ONCE, as a comma-terminated
   entry, and match no write form — so an aliased writer added to one of them
   fails the exactly-once rule whatever shape it takes. The scan walks **both**
   projects' `functions/` trees over every JS/TS extension, and the audited-module
   exemption is paid for **per write**: a cookie write inside a function that builds a
   `Response` must pair it with `no-store`. That is anchored on the write, not on a
   file-level count (which missed an aliased header name and reddened CI on a harmless
   extraction of the two append loops) and not on top-level functions only (which missed
   a class method, a `Response.json` helper, an aliased constructor and a top-level
   callback — all shapes the count had caught). A helper that only appends a cookie to
   its CALLER's `Headers` builds no `Response` and is correctly exempt, and a renamed
   or wrapped `no-store` constant still passes because the policy identifier is resolved
   to its `"no-store"` initialiser rather than matched by name. (`no-store` resolution
   is what lets a pure refactor pass; the guard's remaining false-positive direction —
   building the header NAME as an expression — is fail-closed and named in the
   residuals.) The stripper has its own test (trailing `//`, `/* … */` blocks,
   object-literal comments, URLs and quotes in strings, regex character classes,
   nested templates, idempotence). (The umbrella is deliberate: a shape-anchored
   regex loses the indirection and array-of-pairs forms the bare-token scan used to
   catch — a regression found in this guard's review.)
   (c) the `/auth/confirm` interstitial is **called** (the function is exported for this)
   and the real response is asserted: `Cache-Control: no-store`, the flow `Set-Cookie`, a
   base64 nonce in `script-src` with no `unsafe-inline` fallback, and the inline
   `<script>`/`<style>` carrying that same nonce — a commented-out header cannot satisfy it;
   (d) each policy constant is byte-identical to its `_headers` counterpart **after
   normalising whitespace and a single optional trailing `;`**, compared **inside the block
   that applies** — `website/_headers` `/*` for marketing (a file-wide scan would miss the
   value being moved to another block), and `/*` plus the four SPA-document paths for the app
   — with detach+strict asserted on all four, so a selector edit that silently downgrades the
   SPA to `RELAXED_CSP` fails CI rather than passing green;
   (e) an explicit **per-file allowlist** of the six HTML-producing sites — dashboard
   `auth/index.ts`, `welcome.ts`, `auth/confirm.ts`, `admin/[[path]].ts`; marketing
   `functions/_middleware.ts`, `functions/blog/_lib.ts` — each asserted to carry a CSP
   **stamp** in the expected **count** (3 for the admin file), so deleting any single stamp
   fails. The stamp is counted from **AST shape** — an object property
   `"Content-Security-Policy": <const>`, or a `headers.set/append("Content-Security-Policy", <const>)`
   call — because a whole-file regex also counted a stamp-shaped STRING, REGEX or template,
   which let a file with zero live stamps pass (review deleted a file's only stamp and added
   `const NOTE = 'x "Content-Security-Policy": RELAXED_CSP'`; every text stand-in was tried and
   each is now caught). This is a named list, not a heuristic: `welcome.ts` serves
   `/welcome.html`
   through `env.ASSETS.fetch` — it names the `.html` path and has no `text/html` literal —
   so no `text/html`-keyed scan would find it. Two completeness cross-checks keep the list
   honest in the other direction: every JS/TS file under both `functions/` trees whose
   comment-stripped source **builds `text/html` or names a `.html` asset** must appear in
   the list, and every `_redirects` rule that 200-rewrites to the app document
   (`… / 200`) must be pinned to `STRICT_CSP` — so a new HTML producer or a new
   app-document rewrite fails here instead of shipping unguarded.

   **The guard must also run when only the MARKETING files change.** The `dashboard-js-tests`
   job is path-selected (`.github/workflows/ci.yml:97-106`), so a PR touching only a
   marketing file would skip it and the marketing CSP could drift silently. The `dashboard`
   surface predicate gains `startswith("website/functions/")` plus `isfile("website/_headers")`.
   The prefix is deliberate, not laziness: the guard SCANS both projects' `functions/` trees
   (cookie writers, `text/html` producers, the middleware), so the predicate has to be a
   superset of the guard's input set. A list of filenames disarms on a pure ADD — a new
   marketing Function is scanned by the guard but matches no literal, so the job is skipped
   and the guard fails only where it never runs. The superset direction is the fail-closed
   one (a few extra `dashboard-js-tests` runs on blog edits), and `website/_headers` is a
   sibling of `functions/`, so it is named explicitly. The precedent is the
   `website/assets/supabase-session.js` entry already in THAT predicate (#3485); the
   `tests/test_blog_markdown.mjs` entry at `ci.yml:176` is the same class of fix in the
   **`website`** predicate (#4481), cited as a sibling example, not as a same-predicate
   precedent.

   - `/admin` shell: requires an admin session; **not browser-verified**. The local dev
     server answers the pre-existing `unavailable()` **503** because `SUPABASE_URL`/
     `SUPABASE_ANON_KEY` are unset, so the shell header is not observable over the wire
     here. Fallback: the guard asserts `admin/[[path]].ts` carries **three** `ADMIN_CSP`
     stamps (one per HTML return path), and `ADMIN_CSP`'s origin coverage is read from
     `blog-admin/src/**` — recorded as a residual (not enforced). This limitation is stated
     in the PR body.

## Rollout / rollback

- **Atomic per project.** `_headers` applies to the whole project at once; there is no
  canary. The app-origin change is protected by the W2 `_headers` design being exercised
  over the wire before the PR, and the failure direction is declared above (detach failure
  still leaves the SPA strict; no legacy page matches a strict rule).
- **Rollback is a revert.** Removing the CSP header or a stamp is fail-safe — no data, no
  migration, no state. The `no-store` guarantee is already in the code and is unchanged by
  a revert of the CSP half.
- **GTM is an open origin set.** The container can load new tag origins at any time; a new
  tag whose origin is not in `RELAXED_CSP` will be blocked with no test and no warning.
  This is recorded in `### Integration Docs` as a known operational constraint: adding a
  GTM tag means updating the policy in the same change.

## Residuals (accepted, named — not silently deferred)

- **`ADMIN_CSP`'s origin set is derived, not enforced.** It was derived once by reading
  `website/apps/blog-admin/src/**` (the console's own `blog-api.ts`), and the guard asserts
  the stamp count, not the origin coverage. `website/apps/blog-admin/**` also sits in **no**
  path-gated JS surface, so a future console change that loads a new external origin (a
  font, a CDN, another API) is silently **blocked** by the strict policy with every gate
  green. This is recorded so the derivation is not read as CI-enforced. A source scan was
  considered and rejected as brittle: it would have to distinguish `fetch`/`script`/`font`
  positions from `href` navigation (which no directive in `ADMIN_CSP` governs) and exclude
  test fixtures that name fake hosts.
- **`tools/ci_selection.py` `SOURCE_PATTERNS` covers only 6 of the 16 files under
  `website/functions/`** — `blog/[[path]].ts`, `blog/_shared/admin-auth.ts` and
  `blog/api/**`, but **not** `_middleware.ts`, `blog/_lib.ts`, `blog/_shared/`
  (`cloudflare-purge`, `meta-contract`, `seo-constraints`, `seo-keywords`, `slug`),
  `blog/feed.xml.ts`, `blog/sitemap.xml.ts`, or this PR's new
  `_shared/security-headers.ts`. So a PR touching any of those ten selects no
  marketing-tree surface and their guard tests do not run —
  `tests/test_admin_origin_redirect.py` (which drives the real middleware) is the
  instance that matters here. **Pre-existing and already tracked as OPEN #4186**
  (also found in PR #4104's review); this PR patches the inline `ci.yml` gate for
  the guard it adds, not that manifest — and the guard it adds scans both
  `functions/` trees itself, so the new test is selected by the `ci.yml` prefix
  predicate regardless of this manifest. The `Gaps: none open` line in the
  scoping comment is corrected by this section.
- **`esbuild` and `@babel/parser` are imported by the guard but not declared in
  `website/apps/dashboard/package.json`** (both resolve through vite's hoisted transitive
  dependencies). The sibling `src/bffCsrfGuard.test.js` has the esbuild reliance already, so
  that one is not introduced here. `@babel/parser` is used *only* as the comment-range source
  for the scans — it replaced a hand-rolled comment scanner that desynced three times in
  review (see design bullet (b)) — and its absence would fail the guard loudly at import
  rather than silently weaken it. Recorded rather than fixed here: declaring either needs a
  lockfile update, which this change should not smuggle in.
- **A cookie header name obfuscated past the token spelling escapes the umbrella**
  (`"set-" + "cookie"`). The umbrella scans for the `set-cookie` substring, so every
  construction that still *spells* the token is caught — including a template-built
  `` `set-cookie${""}` `` — but a name assembled from fragments is not, and closing it
  would need evaluation, not a scan. Same class as the dead-stamp residual below:
  the guard is a cheap per-commit tripwire over the source, and the *live* endpoints are
  independently covered by the e2e `no-store` assertions (`tests/e2e/auth/*`).
- **The cookie-writer scan is per-write, but a write is only judged against the function that
  contains it.** A cookie write inside a function that builds a `Response` must pair it with
  `no-store` — that covers a top-level helper, a class method, a static, an aliased
  constructor, a `Response.json` helper and a top-level callback (all proven by mutation).
  What it does NOT cover is a `Headers`-returning helper whose CALLER builds the `Response`
  (the write and the response live in different functions, which would need interprocedural
  reasoning), and a helper in a file that never spells the token at all. Driving every
  exported response helper is not possible in this environment (several of `session.ts`'s
  exports touch the database), which is why the guard pins what a source scan can pin and
  the e2e suite owns the rest.
- **The stamp count is structural but file-wide, so it cannot see PLACEMENT.** It detects a
  deleted stamp only when the total drops: a stamp deleted from an HTML path and re-added on
  a non-HTML response in the same file (e.g. a 503) keeps the count and passes. This is the
  same limitation as the dead-stamp note below — a count is not reachability, and anchoring
  each stamp to the HTML response it decorates would need the handler driven. All six
  handlers' HTML paths do carry their stamp today (verified by reading each site, and by the
  three-return-path count in `admin/[[path]].ts`).
- **The stamp-count check is source-level**, so a deliberately dead stamp
  (`if (false) headers.set("Content-Security-Policy", CONST)`) still counts. Accepted: no
  harness here drives all six handlers, and the mutation is contrived. A stamp whose header
  NAME was refactored into a local constant also stops matching — a fail-closed false
  positive that names the file, and extending the `STAMP` regex is part of that refactor.
- **The `/admin` shell is not browser- or curl-observable locally** (see the Wiring row):
  the local dev server answers the pre-existing `unavailable()` 503 because Supabase
  bindings are absent. Verified instead by the guard's stamp count and by reading the
  console's own origin usage.

## `### Integration Docs`

**Cloudflare Pages `_headers` does not apply to Pages Functions.** Verified against
Cloudflare's own documentation: *"Custom headers defined in the `_headers` file are not
applied to responses generated by Pages Functions, even if the request URL matches a rule
defined in `_headers`."* Consequence: any header a Function response needs — HSTS, and now
CSP — must be stamped **inside the Function**. Both Pages projects already do this for HSTS
(`website/functions/_middleware.ts`, `website/apps/dashboard/functions/auth/index.ts`,
`admin/[[path]].ts`, `blog/_lib.ts`); this change extends the same stamping to CSP.

**A cached response can have `Set-Cookie` stripped by Cloudflare.** The edge caches
responses; `Set-Cookie` is not a cacheable-safe header, so a cached response carrying it
either loses the cookie or is served to another visitor without it. The observable symptom
is an *intermittent* missing session — the same shape as the #3485 sign-out loop, which is
why it would be misdiagnosed. The guarantee therefore lives in the response, not in the
cache policy documented anywhere: **every response that issues or clears a session/flow
cookie sets `Cache-Control: no-store` from inside the Function.**

**Where the guarantee is implemented (single choke point).**
`website/apps/dashboard/functions/_shared/auth/session.ts` exports
`NO_STORE = "no-store, no-cache, must-revalidate, private"` and applies it inside the only
two cookie-carrying response constructors — `json()` (`:229`) and `redirect()` (`:236`).
The only other `Set-Cookie` writer is the `/auth/confirm` interstitial
(`auth/confirm.ts:205`), whose `new Response` sets `Cache-Control: no-store` explicitly. All
other cookie paths (`/api/session` GET+DELETE, `/api/profile`, `/api/provision`,
`/api/v1/*`, `/blog/api/*`, `/auth/api-key`, `/auth/password`, `/auth/signup`,
`/auth/callback`, `/auth/link`, `/auth/start`, `/welcome`) route through those two builders.
A regression guard (deliverable 5) fails CI if either builder loses `no-store` or a third
`Set-Cookie` writer appears.

**CSP trust levels are per-surface, not per-origin.** The app origin carries three levels
because three different things are served there: the dashboard SPA (no inline script →
strict), the console shell (no inline script, but talks to Supabase → strict + Supabase),
and the pre-#3501 auth pages (inline handlers → relaxed). A single origin-wide policy would
have to be the weakest of the three. The relaxed `script-src` is the only concession and it
is temporary: #3501 deletes the inline handlers, after which `RELAXED_CSP` is tightened.

**GTM is an open origin set — a known operational constraint, not a closed allowlist.**
`RELAXED_CSP` pins the origins the loaders use today, but the GTM container
`GTM-WQR34GSC` can be configured to load additional tag origins at any time, and a tag
whose origin is not listed will be blocked with no test and no warning. **Adding a GTM tag
therefore means updating `RELAXED_CSP` in the same change.** This is recorded here so the
next lane does not rediscover it from a silently-dead tag. (The `.pages.dev` preview hosts
are covered by the same `website/_headers` rules; there is no per-branch CSP variant.)
