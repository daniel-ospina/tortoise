# Strategy Alignment — #669 Control-Plane Metadata Migration to Supabase

**Date:** 2026-08-08 | **Gate:** epic-align (full: adversarial + Eisenhower + profit growth)

## Step 1 — Adversarial Strategy Test

**Alternatives considered:**

1. **Keep the control plane in FalkorDB and ship #596's registry backup/restore** (the pre-decision plan) — build custom backup + restore-and-rotate + restore endpoint for the registry graph.
   - *Rejected:* permanently inherits no-RLS/no-constraints/no-managed-PITR in the one system that gates auth; every DR property is custom code that must be maintained; duplicates protection Supabase already provides. The cost of the custom machinery exceeds the cost of the migration.
2. **Move control-plane metadata to Supabase relational tables + RLS (CHOSEN)** — teams, memberships, api_keys, invitations as tables; Supabase managed backups/PITR; RLS for tenant isolation; constraints/transactions; API-key verification becomes an indexed relational lookup.
   - *Chosen because:* industry best practice (relational for tenant/entitlement metadata; graph for the knowledge-graph data plane — AWS/Microsoft/Memgraph consensus); Supabase's own B2B SaaS pattern (tenants + memberships + RLS); removes an entire class of custom DR + security work; the pre-launch window is the cheapest possible time to migrate (zero production tenant data, no paying customers, no migration-of-live-data risk).
3. **Hybrid: Supabase source of truth + read-only FalkorDB mirror** — keeps graph-adjacent queries on the registry.
   - *Rejected as primary:* adds sync machinery (dual-write or CDC) for a query pattern the app doesn't currently need; the app's registry queries are simple lookups (team by id, keys by hash), not multi-hop traversals. A mirror is a later optimization if a graph-shaped control-plane query ever appears.

**Strongest arguments AGAINST building this (anti-post-rationalization):**

- The registry works today. Migration rewrites auth paths (get_current_team, provision, register, reconcile, invites, session keys), the Edge Function, #582's stamp wiring, and a large test surface — real effort and regression risk, pre-launch.
- Opportunity cost: the effort could go to #596's knowledge-graph protection (which is urgent and independent).
- RLS misconfiguration is a classic way to *introduce* a security hole while removing a perceived one — the migration must be treated as a security-critical change with review gates, not a plumbing move.
- Supabase's PITR covers the Supabase DB, but the app still needs its own operational discipline (the migration doesn't remove the need for #596's alerting on the *knowledge graphs*).

**Access-path reality (cycle-2 P1 fix — security-critical):** the FastAPI backend (`SUPABASE_SERVICE_KEY`, hosted_api.py:2266) and the Edge Function (`SUPABASE_SERVICE_ROLE_KEY`, tenant-provision/index.ts:128) run on **service_role**, which **bypasses RLS for app queries**. The honest security benefit of the migration is therefore: **constraints, transactions, managed backups/PITR, and RLS-as-defense-in-depth** (protects against direct DB access, leaked service keys, and accidental admin-client exposure) — NOT "RLS for tenant isolation" (tenant isolation continues in API code, as today). **Scope-time gate (must be decided in epic-scope):** keep service_role with RLS-as-defense-in-depth, or move tenant-scoped queries to per-user JWT (authenticated role) so RLS actually enforces isolation — the latter is a larger auth rework with its own tradeoffs; recommend service_role + defense-in-depth for the migration, per-user-JWT as a follow-up.

**Cutover preconditions (cycle-2 P2):** (a) **zero-teams at cutover is a BLOCKING scripted check** — registry count query + abort guard before the flip (re-verified immediately pre-cutover; first beta signup may occur any day). (b) **API-key lookup is a hashing-scheme change, made cheap by zero keys**: current per-key random salt makes exact-match lookup impossible (scan-based); the migration adds a **deterministic lookup column** (e.g., HMAC with a fixed pepper) for indexed verification — recorded as an explicit design decision, and the registry-graph-schema.md drift reconciled.

**Vendor baseline (honest):** FalkorDB Cloud provides AOF durability + automated snapshots (entrypoint.sh) covering all graphs; the gain is **operator-controlled PITR/restore, RLS, constraints, and managed backups** — precision/control/security, not "from zero backups."

## Step 3 — Profit Growth Alignment

**Causal chain:** control-plane in Supabase → managed backups (no custom DR code) + RLS (security by default) + constraints (data integrity) → lower ongoing ops cost + fewer incident classes + launch readiness → trust + reliability → retention. Indirect but foundation-level: every downstream feature (billing #296, team management, multi-user) builds on this layer. The migration removes a permanent custom-code liability (registry backup/restore/observability) that #596 was about to build.

**Magnitude:** not a direct revenue driver — it's a **risk/cost removal** (avoiding a permanent custom-DR + custom-security maintenance burden, and avoiding a far costlier post-launch migration). Order of magnitude: tens of hours of one-time effort now vs. hundreds of hours + incident risk later.

## Step 4 — Decision Rationale

## Strategy Alignment Decision

**Feature:** Control-plane metadata migration to Supabase (#669)
**Decision:** PROCEED

- Zero-tenants now = no live-data migration risk — confidence: high (verified: no teams exist).
- Migration is security-critical (RLS misconfig is a real failure mode) — treated as such with review gates — confidence: high.

**Recommendation:** PROCEED to research/scope. Sequence as its own epic (#669) parallel to #596's knowledge-graph protection; the API-key verification rewrite and auth-path changes carry full review gates (security-critical).
