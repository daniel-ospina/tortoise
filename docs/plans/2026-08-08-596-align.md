# Strategy Alignment — #596 Hosted backup: scheduled cron + failure alerting + control-plane backup

**Date:** 2026-08-08
**Issue:** #596 (parent #305 — hosted backup pipeline, shipped & merged)
**Gate:** epic-align (project depth — adversarial lite, 2 challenges)

## Step 1 — Adversarial Strategy Test

**Alternatives considered:**

1. **External cron (GH Actions scheduled workflow OR scheduled Fly Machine) calling new internal backup endpoints** — a `.github/workflows/backup-cron.yml` (or a `schedule`-configured Fly Machine) that POSTs to `/v1/internal/backup/*` (auth: `FASTAPI_INTERNAL_KEY`). **This is the established codebase pattern**: `/v1/internal/reconcile` (hosted_api.py:1936) is literally commented "Called by an external cron; internal-key protected." (**CHOSEN as primary.**)
   - Why it wins the primary scenario: the primary failure mode is the **app being down** — fly.toml documents that this app OOM-crash-loops on cold boots (#545: memory 512→2048→4096MB, "the app consistently OOM-crash-loops on 2GB cold boots"). An external driver has an **independent failure domain**: when the app is down, the cron's pre-flight staleness check fails loudly instead of silently skipping. It also needs no in-process loop, so there are no duplicate-run/leader-election concerns if the app ever scales past 1 replica, and the run history is visible in GH Actions.
   - *Rejected concerns:* GH Actions schedule drift/silent workflow failure — mitigated because the workflow itself carries a **staleness pre-flight** (check `Team.backup_latest_at`/R2 listing before running; fail loudly if stale), so a broken workflow and a missed backup are both loud. The internal endpoints are a small delta (mirror `reconcile`'s shape).
2. **In-process asyncio scheduler in the app lifespan** — a background task in `_lifespan` running daily team backups + hourly registry backup + prune, with catch-up-on-startup.
   - *Rejected as primary:* shares the app's failure domain — the exact crash-loop scenario in which backups are needed. In-process alerting is also blind during total outage (the "missed backup" check lives in the process that isn't running). Zero new infra, but it only closes the #101 class while the app is healthy. **Kept only as a documented fallback** if external cron proves unreliable.
3. **Dedicated scheduled Fly Machine running the backup entrypoint directly** — *co-primary with option 1* (equivalent failure-domain independence; slightly more deployable-unit surface than a workflow). Decision deferred to scope: workflow vs machine is an implementation choice; both are external drivers.

**Strongest arguments AGAINST building this (anti-post-rationalization):**

- The backup machinery is proven (#582, 181+ tests); a scheduler is small — but alerting + freshness checks touch production flows (restore) and could introduce regressions in a pipeline that was just hardened over 5 review rounds. Scope must keep restore-freshness **warn-level, never a hard block**.
- The registry graph's hourly cadence is a new R2 write pattern — cost is negligible (small graph, retention pruning already ships), but the sweep must not double-run (idempotent keys: timestamped object names make re-runs harmless).
- External cron adds a dependency the app doesn't control; if GH Actions is disabled, backups stop. Mitigated by the staleness pre-flight failing loudly + the cadence being daily (an operator notices a missed day).

**Assumptions being bet on:** pricing.json lists `daily_backups` as not-yet-delivered on Pro/Team — #596 is what converts the planned pricing checkbox into a shipped deliverable (pricing integrity). The registry graph is worth hourly DR (platform continuity). R2 cost of daily archives is negligible. External-cron pattern is already proven in this codebase (`reconcile`).

## Step 4 — Decision Rationale

## Strategy Alignment Decision

**Feature:** Hosted backup: scheduled cron + failure alerting + control-plane backup (#596)
**Decision:** PROCEED

**Alternatives considered:**
1. External cron (GH Actions workflow / Fly Machine) calling new `/v1/internal/backup/*` endpoints — **chosen as primary** (independent failure domain — the OOM crash-loop scenario; established codebase pattern via `/v1/internal/reconcile`; run history visible).
2. In-process lifespan scheduler — rejected as primary (shares the app's failure domain; blind during outage); documented fallback.
3. Dedicated scheduled Fly Machine — co-primary implementation option with 1; decided in scope.

**Profit impact:** pricing integrity (delivers the `daily_backups` checkbox) + registry DR (currently zero coverage) + loud alerting = trust/renewal/continuity; ~$100s–$1000s/month protected. High ROI on a small delta.

**Eisenhower placement:** Important / Not Urgent → **Schedule** (active DR gap, low current exposure).

**Key assumptions:**
- External-cron pattern proven in this codebase (`/v1/internal/reconcile`) — confidence: high (verified in repo).
- pricing.json lists `daily_backups` as not-yet-delivered; #596 delivers it — confidence: high (verified).
- External cron with staleness pre-flight fails loudly when the app is down (no silent no-backup window) — confidence: medium (design detail validated in scope).
- R2 storage cost of daily archives is negligible — confidence: high (retention pruning already ships).
- Registry (control-plane) graph is a platform DR surface worth hourly backups — confidence: high (issue scope + #582 review agree).

**Recommendation:** PROCEED to research/scope. Primary architecture: external scheduled driver calling internal backup endpoints (mirroring `reconcile`); restore-freshness stays warn-level (never a hard block); alerting must be loud on failure AND missed-backup, with the staleness check living OUTSIDE the app process.
