# #1880 — Registry Invite Fake-Membership Cleanup Implementation Plan

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

**Goal:** Delete the fake `Membership {user_id:'invite-{iid}'}` row when a registry invite reaches a terminal state (accept, owner-rescind, invitee-decline), so `list_members` never shows ghost 'invited' members.

**Team:** organisation-design-team
**Role:** product-implementer

**Architecture:** A single shared helper `_delete_fake_invite_membership` (Cypher `MATCH (m:Membership {team_id:$tid, user_id:$fake}) DELETE m`, `$fake = f"invite-{invitation_id}"`) called from the registry accept success + except paths and the rescind path in `hosted_api.py`. The decline path (#1875, in parallel) consumes the same helper — one implementation, three call sites (DRY). Backend-only; no UI, no schema change.

### Pattern Research

> **Findings date:** 2026-08-28

> Gate skipped: plan touches zero third-party dependencies (Cypher + in-repo SDK wrappers). Backend-only bug fix — the UX-research requirement does not apply (no user-facing surface changes; the pending-invite visibility in list_members is preserved).

### Failure Modes
- **Accept max_users 402**: pre-existing bug verified by review — `accepted_at` is written BEFORE `membership_create` (hosted_api.py:6508-6515), so a 402 leaves a consumed invite + NO real membership + a PERMANENT fake row. Fix: delete the fake row in the `except` path too (the invite is dead either way). 402 test added.
- **Rescind after accept** → 409 before deletion (existing check; fake row already deleted at accept).
- **Unknown invitation_id** → 404 before deletion (existing check).
- **`reg` scope**: the rescind branch has only `sdk = _make_sdk(namespace="registry")` — the helper takes the sdk and uses `sdk._get_registry()` (matching list_members/remove_member).

## Task 1: Shared helper + accept-path cleanup (TDD)

**Intent:** One deletion helper; accepting an invite never leaves the ghost row — in any outcome.
**Acceptance:** After registry accept (success AND max_users-402), `list_members` has no `invite-*` ghost.

**Files:**
- Modify: `tortoise/hosted_api.py` (registry accept branch ~6478-6515)
- Test: `tests/test_invites_http.py` (registry lane is the default — no env var needed)

**Step 1 — Failing tests:** add to `tests/test_invites_http.py` (use the file's fixtures — `client`/`reg`, `_seed_team_with_owner`, `_as_user`, `TestInviteAccept._invite`):
```python
def test_registry_accept_removes_fake_invite_row(client, reg):
    # mint invite for email X (TestInviteAccept._invite) → assert list_members
    # (GET /v1/teams/{id}/members) has a user_id startswith('invite-')
    # accept as the invitee (_as_user) → assert NO user_id startswith('invite-')
```
Plus a 402 variant (seed a team at max_users, attempt a second member accept, assert the fake row is gone and the invite is consumed).
Run: `TORTOISE_DB_URI='docker://:falkordb@localhost:6379/tortoise_test_matrix' uv run pytest tests/test_invites_http.py -k "registry_accept" -q` — expected FAIL (ghost row present).

**Step 2 — Implement:** add the shared helper near the invite functions:
```python
def _delete_fake_invite_membership(sdk, team_id: str, invitation_id: str) -> None:
    """#1880: drop the fake Membership(user_id='invite-{iid}') row on a
    terminal invite state (accept/rescind/decline) — else registry
    list_members shows ghost 'invited' members forever."""
    sdk._get_registry().query(
        "MATCH (m:Membership {team_id:$tid, user_id:$fake}) DELETE m",
        params={"tid": team_id, "fake": f"invite-{invitation_id}"},
    )
```
In the registry accept branch: after `sdk.membership_create(...)` succeeds → `_delete_fake_invite_membership(sdk, invite["team_id"], invite["id"])`; in the `except` path (the max_users 402 case — invite is consumed but no membership) → delete the fake row too (with a comment noting the pre-existing accepted_at-before-create ordering).

**Step 3 — Green:** re-run — PASS; supabase invite tests unaffected.
