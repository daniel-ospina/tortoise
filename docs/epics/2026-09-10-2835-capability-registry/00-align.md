### Is the problem real? — measured, method inlined

**Re-runnable measurement.** The complete method is inlined below — no external script, no repo code, nothing to
install. Paste it into `python3 -` with `SKILLS_ROOT` pointing at a checkout's `skills/` directory and it
reproduces the numbers quoted here verbatim (verified by extracting this block from the file and running it).
Run 2026-09-10 against `agent-infra/skills`; the `--top 5` output is quoted in full below:

```python
import glob, itertools, re

SKILLS_ROOT = "/path/to/agent-infra/skills"   # <- set me

# Phrases removed before tokenising. Every entry is a template mandated by the
# writing-skills convention, NOT shared function.
BOILERPLATE = [
    r"returns structured issue blocks or no issues found\.",
    r"use when reviewing [^.]*complexity axis\.",
    r"use when asked to [^.]*\.",
    r"reuses patterns from [^.]+?\.",
    r"inlined from [^.]+?\.",
    r"\(inlined from[^)]*\)",
]
# Function words + template residue, dropped after tokenising.
STOP = frozenset("that this when with from into they them their will have been also each "
                 "over only more most some such than then there these those very what "
                 "which while your yours used using uses user".split())

def tokenise(desc):
    for pat in BOILERPLATE:
        desc = re.sub(pat, " ", desc, flags=re.IGNORECASE)
    return frozenset(t for t in re.findall(r"[a-z]{4,}", desc.lower()) if t not in STOP)

desc = {}
for path in sorted(glob.glob(f"{SKILLS_ROOT}/**/SKILL.md", recursive=True)):
    raw = open(path, encoding="utf-8", errors="replace").read()
    fm = re.match(r"^---\n(.*?)\n---", raw, re.S)
    if not fm:
        continue
    d = re.search(r"^description:\s*(.+)$", fm.group(1), re.M)
    if not d:
        continue
    n = re.search(r"^name:\s*(.+)$", fm.group(1), re.M)
    desc[n.group(1).strip() if n else path] = d.group(1).strip().strip('"')

toks = {k: tokenise(v) for k, v in desc.items()}
rows = []
for (n1, t1), (n2, t2) in itertools.combinations(toks.items(), 2):
    if t1 and t2:
        rows.append((len(t1 & t2) / len(t1 | t2), len(t1 & t2), n1, n2))
rows.sort(key=lambda r: (-r[0], r[2], r[3]))

print("skills_with_description:", len(desc))
print("pairs:                  ", len(rows))
print(f"max_jaccard:             {rows[0][0]:.3f}")
print("pairs_ge_0.5:           ", sum(1 for r in rows if r[0] >= 0.5))
print("pairs_ge_0.4:           ", sum(1 for r in rows if r[0] >= 0.4))
print("pairs_zero_overlap:     ", sum(1 for r in rows if r[0] == 0.0))
print("\ntop 5 by jaccard:")
for i, (j, sh, a, b) in enumerate(rows[:5], 1):
    print(f"  {i:3d}. {j:.3f}  shared={sh:2d}  {a} <-> {b}")
for a, b in [("define-strategy", "define-product-strategy"),
             ("define-strategy", "define-team-strategy"),
             ("define-vision", "define-team-vision"),
             ("test-review", "plan-review"),
             ("find-bugs", "security-review"),
             ("architectural-soundness", "integration")]:
    hit = next(((i, r) for i, r in enumerate(rows, 1) if {r[2], r[3]} == {a, b}), None)
    if hit:
        i, (j, sh, _, _) = hit
        print(f"\nnamed: {a} <-> {b}  jaccard={j:.3f} shared={sh} "
              f"rank={i}/{len(rows)} (top {100.0 * i / len(rows):.2f}%)")
```

1. **Absolute scores are low: max 0.389, and zero pairs ≥ 0.4.** Even the closest of 7,503 pairs is ~61% dissimilar on this token measure. So no pair *scores* as a duplicate.
2. **The metric is not blind to the candidates.** Three pairs read here and left **unadjudicated** all land inside the top 0.6% of 7,503 — ranks **38–44** (see the accounting block below). **This is direct evidence FOR alternative 2 (the deterministic index) and against any claim that the naive baseline is useless.** A TF-IDF/Jaccard check used as a *ranked review queue* — "here are the 50 closest pairs, adjudicate them" — is plausibly adequate for *finding candidates*, and needs no graph.
3. **But there is no usable cut point, and the score ordering runs backwards.** **37** pairs outrank `define-strategy`↔`define-team-strategy` (42 outrank the `define-product-strategy` pair; 43 outrank `find-bugs`↔`security-review`) — and the top of the list is led by pairs that read as separations rather than duplicates: `content-reviewer-breadth`↔`content-reviewer-depth` (0.389, sibling reviewers) and `plan-review`↔`test-review` (0.378, a *documented* deliberate mirror) are ranks 1 and 2. The unadjudicated candidate pairs score about **half** what that documented deliberate mirror scores. ## Alternatives considered

1. **Do nothing — accept silent duplicate accumulation.** Cheapest; zero new surface. Rejected, but the rejection is now *weaker than the epic claims and must be stated honestly*: the measured evidence does **not** show a pile of near-duplicates. What it shows is (a) one live unadjudicated candidate component — `define-strategy`, which nothing dispatches, pairing with `define-team-strategy` and `define-product-strategy` at ranks 38 and 43 of 7,503 — (b) one adjudication that exists only as prose in a skill file (`test-review:459`), and (c) **no mechanism at all** to answer "does something already serve this function?" — so the duplicate count is *unmeasured*, not proven large. **Counter-argument, stated plainly: if the honest count is 1-2 pairs among 123 components, "do nothing" plus a one-off cleanup is the rational choice, and this epic is over-engineering.** What defeats that argument is not the current count but the *trend* (123 components today in one distributed tree, growing) plus the fact that **no mechanism exists to measure the count at all** — you cannot run the one-off cleanup you cannot scope. *(An earlier draft also leaned on the degradation contract here. Removed: that clause contradicts the "Why not ELIMINATE?" section, which forbids using indicator 4 to justify the registry.)*
2. **Static deterministic index in agent-infra — `manifest.json` extension + TF-IDF/`check-skill-lint.mjs` CI predicate, no graph.** *This is the serious rival, named deliberately — and the measurement above strengthens it.* It is cheap, deterministic, CI-runnable, needs no graph availability, no ingest, no degradation contract, no multi-repo topology decision, **and it already finds the three unadjudicated candidate pairs, at ranks 38–44 of 7,503 (top 0.6%) on a plain Jaccard pass** (the inlined method). **Rejected as the v1 substrate for this epic on two grounds only:** (a) it cannot hold a *why-separate* rationale — the epic's indicator 3, and per finding 1 the thing that is actually missing (the existing rationale lives in prose at `test-review:459`); and (b) **its *CI-predicate* form cannot separate signal from boilerplate** — the candidate pairs (0.188–0.200) score about half what the documented deliberate mirror `plan-review`↔`test-review` (0.378) scores, so any threshold low enough to include rank 43 also admits **≥42** higher-ranked pairs (a derivable count; how many are true duplicates is unadjudicated). **Ground (b) disqualifies the threshold form only, not the ranked-queue form** — and this doc concedes above that the ranked-queue form is "plausibly adequate for finding candidates". So the ranked-queue form is rejected on ground (a) — which, stated precisely, is not "cannot hold a rationale" but **"has no sanctioned home for a first-class, queryable rationale"** (the owner direction is explicit that this belongs in the graph, not in markdown ADRs) — and the graph's entire claimed advantage rests on testing (i) the rationale edge and (ii) composed structural retrieval (bullets below). **If R1 cannot show those, the honest outcome is to adopt the ranked-queue index and drop the graph substrate.** *(An earlier draft rejected this alternative partly because a git-tree walk "cannot span 6 repos" — a v2 objection used against a v1 decision; the Recommendation constrains v1 to one repo, so it is withdrawn. It re-enters only at v2.)*
   - **What this does NOT establish:** that the graph will do better on the same text. Tortoise retrieves over the same short descriptions, so the *ranking* advantage is not established. ## Anti-post-rationalization (strongest reasons NOT to build)

- **The only harm analysis in this doc is about false negatives — the false-positive harm is worse and was missing.** Everything above bounds the "registry says nothing / says stale" failure. But the highest-harm output is a confident *wrong* "these two are duplicates": it invites an agent to unify or supersede two components that a recorded adjudication keeps separate, and given the tombstone/resurrect hazard (next section), that is hard to undo. This is why constraint 1 now pre-declares a **precision** bar alongside the two lever criteria (and reports a recall reference value), and why constraint 6 requires every adjudication to carry its rationale — but it should be stated that the *advisory* posture is also justified by this asymmetry, not only by availability risk.
- **A stale adjudication silently blocks a justified unification — the mirror of the false-positive harm.** The doc models staleness only for the *inventory* (constraint 3's three cases; D3 freshness authority). It requires every separation to carry its rationale (constraint 6) and notes that the edge is a *standing* pairwise relationship (R4). **Nothing addresses the edge going wrong after it is written:** if either component is edited after adjudication, a recorded "keep separate because X" can become false, and the registry then suppresses a unification that is now correct — harming in the same direction the doc calls the highest-harm output. Removal of one side is covered by indicator 1's "no orphans"; a stale-but-non-dangling edge is not. **R2 must define an invalidation trigger** (e.g. re-adjudicate on content-hash change) and the surface must mark the record **stale**, not current.
- **The measured problem is smaller than the epic's framing suggests, and I had to correct my own inflated version of it twice.** The measurement (method inlined above) shows max Jaccard 0.389 with zero pairs ≥ 0.4, and ranks the legitimate separations *above* the unadjudicated candidate pairs. **The epic's premise survives on "no mechanism + inconsistent practice + unknown count", not on "measured duplication".**
- **The epic's first deliverable is a measurement, and the measurement may fail.** R1 (recall@k over near-duplicate component descriptions) is unproven. Tortoise retrieval is tuned on transcripts and documents; a 15-word reviewer description is a different text distribution. And the bar is not trivial: the deterministic baseline already ranks the three unadjudicated candidate pairs in the top 0.6% (finding 2 above), so lever (ii) must beat a baseline that *works*, not a strawman. **If the graph cannot retrieve lever (i) as a first-class rationale record and cannot beat the baseline on composed retrieval (ii), it adds cost and no value over alternative 2.** A bare `recall@k` result does not decide this (constraint 1).

The idempotency primitives (deterministic `obj-<sha26(name)>` id, MERGE upserts, supersession folds — §4.3 L394-404) make re-ingesting an *unchanged* corpus converge; they say nothing about the removal property the indicator names. *(The §5 L593-600 table is the **Point** status lifecycle and does not govern Objects — see the R2 routing bullet.)* **This is the epic's sharpest technical unknown, and it must be resolved in R2 before any writer ships.**

## Key assumptions

- **Tortoise retrieval generalizes to short component descriptions** — confidence: **low-medium**. This is the epic's central bet and it is explicitly unproven. `search_engine.py` RRF fusion is tuned on transcripts/documents. **R1 decides it. R1 is the kill-switch, and its trigger is the two structural levers — not this generalization** (constraint 1).
- **The graph stack beats the naive deterministic baseline by enough to justify the substrate** — confidence: **low, revised down twice.** The baseline is *not* blind: a plain Jaccard pass puts all three unadjudicated candidate pairs at ranks 38–44 of 7,503 (top 0.6%). What it cannot do is threshold (0.389 max; no separation between the candidate pairs at 0.188–0.200 and the documented deliberate mirror at 0.378) or hold a rationale. **R1 must beat that baseline on the composed-retrieval lever (ii) over a hand-labelled fixture set — and it may not.**
- **Text-overlap similarity is a valid proxy for functional equivalence — i.e. "does something already serve this function?"** — confidence: **low, and this is the epic's deepest unexamined risk.** `agent-infra#688`'s own prior art (cited in the Profit section) states that **Type-4 semantic clones — same behaviour, no shared tokens — remain an open research problem**, with learned-embedding detection characterized as the research direction, not a shipped capability. Every measurement here is lexical. R1 can therefore pass while the registry still cannot answer the epic's actual question for a functionally-equivalent-but-differently-worded component. **Mitigation: R1's fixture set must include at least one lexically *dissimilar* known-equivalent pair**; if it does not, R1 validates the wrong property.
- **Hand-labelling the R1 fixture set is bounded** — confidence: **medium, unmeasured.** The doc calls the fixture set "the hard part" while also calling R1 "genuinely cheap"; those are consistent only if the labelling effort is scoped. **Constraint: cap it (e.g. ≤30 components, one session) and descope R1 to description-bearing classes if the cap is exceeded.**
- **The R1 fixture set is large enough for its pass/fail not to be sampling noise** — confidence: **medium, unmeasured, and this is load-bearing.** R1 is the kill-switch, and its trigger is **failing the pre-declared bar on the two structural levers** (constraint 1) — with a handful of labelled pairs that call can turn on noise. `recall@k` is a non-regression **reference metric** (reported, not gating), not the trigger. **Constraint: pre-declare, alongside both bars, a minimum number of labelled pairs and a required margin, and report a confidence interval rather than a point recall@k.** Without this, R1's verdict is not evidence.
- **Idempotent re-ingest of an unchanged corpus converges** (no duplicate Objects) — confidence: **high**. Deterministic `obj-<sha26(name)>` ids + MERGE upserts + supersession folds.
- **Removal/rename converges with no orphans or dangling edges** — confidence: **low**. The epic's indicator 1 requires it; ONTOLOGY §4.3 L404 documents that delete leaves no tombstone and the entity **resurrects** on rebuild. Unresolved — R2 must design for it (supersede vs retract vs explicit tombstone) before any writer ships.
- **Adjudication records are invalidated by component change** — confidence: **low, and unaddressed by the epic.** A "keep separate, because X" record is a *standing* edge between two live artifacts; the epic requires the rationale to be stored but never requires it to be re-validated when a component changes. Stale records then suppress *correct* unifications. **R2 must pair the record's write path with an invalidation trigger** (content-change detection is an ingest concern; R4 owns the record's *shape*, R2 owns its *freshness*), or indicator 3 produces a confidently wrong artifact.
- **"Similar but stay separate, because X" rides the existing decision machinery** — confidence: **medium**. `file_decision` is atomic and shallow (no EP, no calibration, decision-*event* shaped); a *standing pairwise relationship between two live artifacts* is a different shape. Whether it needs a chain (à la `agent-ops:ruleLifecycle`) is R4 — **and it is the same question as `agent-infra#688` D4.**
- **Degradation to advisory is cheap to build and holds under test** — confidence: **medium-high**. Design-simple; the risk is consumers ignoring the signal, a contract-test problem the epic already names.
- **Retrieval generalizes from skill descriptions to description-less components** — confidence: **low, and the epic does not currently address it.** The measurement corpus is `SKILL.md` `description:` strings (123 of them). Extensions, scripts, and hooks carry no such field, so nothing here says they are retrievable by text similarity at all — yet `CAPABILITY_CATALOG` rows already point at code modules, and the volume assumption implicitly treats them as retrievable. **R1 should either cover one description-less class (code embeddings) or explicitly bound its claim to description-bearing components.**
- **The fleet's component volume is within the graph's comfort envelope** — confidence: **low-medium, and the epic's "count per repo × 6" multiplier is wrong** (the skill tree is distributed by symlink, not copied — see the Fleet volume grounding row). True volume is **unmeasured (R3)**.
