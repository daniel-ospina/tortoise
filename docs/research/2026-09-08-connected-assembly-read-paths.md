# Research — Entity-Centric "Connected Assembly" Read Paths in Agent-Memory Products

**Date:** 2026-09-08 · **Mode:** external research (docs, blogs, source code, papers), read-only
**Problem context:** Tortoise read today = top-k similarity over isolated Points + one reader LLM call. We are designing an ASSEMBLER (zero-LLM): resolve subject(s) → walk connected subgraph (Object state + dated Events + aboutObject-linked Points w/ EP/provenance) → render dense structured block (state + timeline + evidence) for the reader.

## A. Zep / Graphiti (open-source; source-verified read side)

Representation at read: entity **nodes** (name+summary), fact **edges** (name + `fact` text + `valid_at/invalid_at/expired_at` + `episodes[]` provenance), **episodic nodes** (raw episodes), **community nodes** (precomputed GraphRAG-style summaries). `[source]` graphiti_core search scopes: github.com/getzep/graphiti/blob/main/graphiti_core/search/search.py, search_config.py.

**(a) Structure queried.** Three searchable scopes per query — edges (facts), nodes (entities), communities — plus episodes (BM25-only scope). High-level `graphiti.search(query)` returns **edges only** (facts as strings), default `num_results=10` (`DEFAULT_SEARCH_LIMIT = 10`); advanced `search_()` returns edges+nodes+episodes+communities with per-scope configs and 15 prebuilt "recipes". `[source]` github.com/getzep/graphiti/blob/main/graphiti_core/search/search_config.py; graphiti.py `search()`.

**(b) Expansion / traversal.** Three search methods per scope, fused: `cosine_similarity`, `bm25`, `breadth_first_search`. **BFS is the connected-assembly mechanism**: if no `bfs_origin_node_uuids` are given, hits from the other methods become "land and expand" seeds (`edge_search` seeds from the *source endpoints* of hit edges; `node_search` from hit nodes), then BFS traverses `-[:RELATES_TO|MENTIONS*1..{depth}]` — i.e., fact edges AND episode-mention edges — collecting distinct edges/nodes, `MAX_SEARCH_DEPTH = 3` default, candidate cap `2 * limit` per method. Callers can pass explicit origin node UUIDs (e.g., a known entity). Traversal is **edge-type-agnostic** at walk time; edge-type restriction exists only as a final `WHERE e.name IN $edge_types` filter. `[source]` graphiti_core/search/search_utils.py (`edge_bfs_search`, `node_bfs_search`, `MAX_SEARCH_DEPTH`); graphiti_core/search/search.py; blog "How do you search a Knowledge Graph?" (blog.getzep.com/how-do-you-search-a-knowledge-graph/).
- **Entity-focal rerank:** `graphiti.search(query, focal_node_uuid)` / `node_distance` reranker reorders candidates by shortest-path distance to the focal entity (direct `RELATES_TO` neighbors score 1.0; center boosted; others tie near 0) — "particularly useful for entity-specific queries." `[source]` search_utils.py `node_distance_reranker`; `[vendor doc]` help.getzep.com/graphiti/working-with-data/searching.
- **episode_mentions reranker:** re-ranks by how many episodes mention the entity/edge (conversation-salience bias). `[source]` search_utils.py.
- **Temporal as-of filtering is caller-supplied, not default:** `SearchFilters` supports `valid_at`, `invalid_at`, `created_at`, `expired_at` comparison lists (incl. `IS NULL`) and `edge_types`/`node_labels` — applied as Cypher WHERE clauses in every method. Nothing filters invalidated facts automatically. `[source]` graphiti_core/search/search_filters.py.
- **Invalidated facts remain in the graph and surface by default.** Write-side contradiction handling *sets* `invalid_at` (+`expired_at`) on the superseded edge; the maintenance path does not delete it (github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py). So a default BFS/BM25/vector search can return facts that are no longer true; correctness for "now" queries requires the caller to add validity filters. Docs say "updates or invalidates outdated knowledge instead of deleting it" (historical states stay queryable) — but the *filtering burden is on the caller*. `[source]` + `[vendor doc]` help.getzep.com graph docs.

**(c) Linearization / budget / compression.** High-level search returns a flat, score-ranked list of `fact` strings (limit 10 default) — **no section structure, no grouping by entity, no timeline ordering, no token budget** is imposed by the library; ordering = RRF fusion (default) of BM25/vector/BFS lists, or MMR (diversity, λ=0.5) or cross-encoder or node-distance. Each candidate method over-fetches `2*limit`; similarity min-score default 0.6. Communities exist so high-level context (entity-interconnection summaries) can be returned **without on-the-fly LLM summarization at read** ("building community summaries during processing rather than retrieval… without the extra latency overhead of using an LLM to build these summaries on the fly" — vendor blog). Episode text is a first-class searchable scope (BM25) and `get_episode_mentions(episode_uuids)` returns all nodes/edges/communities mentioned in given episodes (episode-centric lookup that skips embedding). `[source]` search_config.py, search_utils.py `get_episodes_by_mentions`/`get_mentioned_nodes`; `[vendor doc]` help.getzep.com/graphiti/working-with-data/searching; `[vendor blog]` blog.getzep.com/how-do-you-search-a-knowledge-graph/.

**(d) Read-side LLM cost.** Base/high-level search: **zero LLM calls** (embedding + BM25 + BFS + RRF). Cross-encoder reranking is opt-in (recipes `*_CROSS_ENCODER`) and costs one reranker API call over `2*limit` candidates (OpenAI/Gemini/BGE reranker clients). MMR and node-distance add DB round-trips (embedding fetches, distance queries) but no LLM. Write side is LLM-heavy (extraction, entity resolution, fact dating, summary/community updates) — cost is skewed to write. `[source]` search.py.
- **Latency (vendor, flag):** "Zep's own Graphiti implementation achieves … retrieval … P95 latency of 300 ms … avoiding any LLM calls during retrieval" — Zep CEO writing on the Neo4j blog; self-reported, no protocol/corpus, treat as upper-bound claim. Also flags GraphRAG-style community retrieval as "often taking tens of seconds" (competitive framing). `[vendor blog]` neo4j.com/blog/developer/graphiti-knowledge-graph-memory/ (Daniel Chalef, Zep, Mar 2025).
- **FalkorDB note:** Graphiti has a full FalkorDB driver + search ops — same DB family Tortoise runs on; their BFS/hybrid patterns are directly portable. `[source]` repo tree `graphiti_core/driver/falkordb/operations/search_ops.py`.

**(e) Documented failure modes.** OSS-side: no validity default (stale/contradicted facts returned unless caller filters — `[source]` as above); entity-resolution errors at write are hard to undo ("a wrong merge corrupts identity" — Zep; cited in in-repo prior). BFS is blind/unweighted: vendor blog lists as *future work* "paths favored based on semantic similarity or node/relationship types" — i.e., they know depth-3 BFS over all edge types causes topic drift today. `[vendor blog]` how-do-you-search-a-knowledge-graph/. Zep paper (arXiv:2501.13956) describes episodic/entity/community subgraph + hybrid search + context assembly; the 94.8% DMR + "18.5% LongMemEval" numbers are self-reported (prior in-repo doc: Zep later self-corrected its LoCoMo number to 75.14±0.17). No public docs describe a product-side prompt-packaging/linearization step beyond "facts are returned" — `[absence]`.

## B. Mem0 — OSS (source-verified) + Platform graph/temporal (vendor)

### B1. OSS v3 read path (source-verified; graph layer = entity-boost, not BFS)

**(a) Structure queried.** Two vector collections: memory collection (semantic) + `{collection}_entities` entity collection. Memories are flat text records with payload (`created_at`, `updated_at`, `expiration_date`, metadata). `[source]` github.com/mem0ai/mem0/blob/main/mem0/memory/main.py.

**(b/c/d) Read pipeline (exact, source):** search steps in `_search_vector_store`: (1) lemmatize query for BM25 + extract entities via spaCy heuristics (proper nouns/quoted/noun-compounds — **no LLM**; `mem0/utils/entity_extraction.py`); (2) embed; (3) **semantic search over-fetches `max(limit*4, 60)`**; (4) BM25 over the same limit; (5) entity boost: for each of ≤8 query entities, embed + search entity store (`top_k=500`/entity, similarity ≥ 0.5), then boost each entity's `linked_memory_ids` by `sim × 0.5 × 1/(1+0.001(n−1)²)` (hub-penalty: entities linking many memories are damped); (6) **candidate pool = semantic hits only** (minus expired) — BM25 and entity matches are *additive scores on semantic candidates*, they never expand the pool; (7) `combined = (semantic + bm25 + entity) / max_possible` (divisor adapts 1.0/2.0/1.5/2.5), **with a hard semantic pre-gate: candidates below threshold (0.1) are dropped even if keyword/entity would boost them**. LLM read cost: **zero** (spaCy + embeddings; rerank optional). `[source]` mem0/memory/main.py `_search_vector_store`/`_compute_entity_boosts`; mem0/utils/scoring.py `score_and_rank`; mem0/utils/entity_extraction.py. Temporal params (`reference_date`) raise an error in OSS; temporal reasoning is platform-only (a "feature notice" is returned). `[source]` main.py `search()`.

### B2. Platform "Graph Memory" (native, always-on; vendor doc only)

Entities extracted from each memory become graph **nodes** (each stored once + embedded); memories are connected through shared entities; **no typed/labeled relationship edges** ("it won't record a 'manages' edge"; connections inferred from co-occurrence). At search: query entities are matched to the graph and **memories connected to matched entities get a ranking boost combined with vector + BM25 into one score**. Two load-bearing vendor claims: "Graph Memory affects ranking, not the response shape" (no separate graph payload — the graph does not expand the returned result set's shape), and it "contributes to gains on multi-hop and temporal benchmarks" (no eval shown on the page). This replaces the earlier external-graph-store mode (Neo4j/Memgraph/Kuzu/AGE/Neptune via `enable_graph`), which previously returned a `relations` field — now always empty; graph is native, no schema. `[vendor doc]` docs.mem0.ai/platform/features/graph-memory; docs.mem0.ai/migration/platform-v2-to-v3 (migration note: "relations field change").

### B3. Platform "Temporal Reasoning" read path (vendor doc/blog)

Write: separate async temporal pass tags each memory with type (event/state/plan/relationship/preference/absence + timeless), ongoing/completed, precision, event dates; ongoing facts carry a **`state_key`**; when a new state supersedes, the old memory's `event_end` is set automatically (nothing deleted). Read: query classified into temporal intent (current_state, historical_range, duration_state, upcoming, soft_recency…) **with no extra LLM call**; intent is **not** a filter — it is an **additive rerank** over already-retrieved candidates; "semantic relevance always dominates"; explicitly refusing pre-filtering because it would "silently drop memories with imprecise or missing dates." "Current state" questions surface the *latest dated instance by reranking*, not by hard resolution. `[vendor doc]` docs.mem0.ai/platform/features/temporal-reasoning; `[vendor blog]` mem0.ai/blog/introducing-temporal-reasoning-in-mem0. Search API: `POST /v3/memories/search` with query/filters/top_k/reference_date; results are flat memories w/ combined score. `[vendor doc]` docs.mem0.ai/api-reference/memory/search-memories. Self-reported gains (LoCoMo 86.1→92.5 etc.) — flag; independent third-party eval puts Mem0 at 49.0 vs Zep 63.8 on LongMemEval `[independent]` vectorize.io/articles/mem0-vs-zep (from in-repo prior). Admitted weakest category: knowledge-update/contradiction ("older semantically similar facts can still appear near newer facts"). `[vendor blog]` (as above).

**(e) Failure modes:** vector pool is the gatekeeper (keyword/entity never rescue a memory outside top-~60 vector hits — `[source]`); semantic pre-threshold drops weak-embedding hits; additive rerank can't fully fix stale-fact competition (vendor admission); platform graph has no typed relations or multi-edge reasoning (vendor limitation).

## C. Letta (MemGPT lineage) — read side is agent-managed, not assembled

Current docs (this env) describe **MemFS**: a git-backed memory filesystem the agent reads/edits with file tools. Files under `system/` are **loaded into the system prompt on every turn**; the file tree itself is always in the system prompt so filenames act as signposts; other files stay out of context until the agent reads them. **No semantic/vector index by default** — keyword/hybrid search is an optional "mod". Conversation-history search is separate (`letta messages search`: full-text/vector/hybrid on cloud). "Dreaming" = background subagents consolidate lessons at sleep time (write side). There is **no automatic entity-centric assembly**: the agent decides what to read; ordering/linearization = prompt ordering of files; budget = context management + compaction. Read LLM cost = the agent loop itself. `[vendor doc]` docs.letta.com/concepts/memfs, docs.letta.com/configuration/memory, letta.com/blog/context-repositories, github.com/letta-ai/context-constitution. Earlier tier model (core/recall/archival blocks) from the prior doc is superseded by this file-based model in current docs; archival passage-search API may persist for SDK but is no longer the documented memory surface — treat tier-model read details as legacy. Temporal correctness = whatever the agent infers from file contents/dates; no time-indexed invalidation layer. `[absence]` of a connected-assembly step.

## D. LangMem / LangGraph Store — namespaced semantic recall

LangMem = tools + patterns over the LangGraph `BaseStore`. Read path A ("hot path"): in the prompt function, `store.search(namespace, query=<last message>)` — semantic search over namespaced memory items — and results are injected into the system prompt inside an XML `<memories>` block. Read path B: `create_search_memory_tool` lets the agent search mid-loop (results = tool output). Namespaces (`("memories", user_id)` …) are the only scoping; items carry timestamps but there is **no recency/temporal scoring, no entity linking, no graph traversal** at read. Read LLM cost: zero for retrieval (embeddings only); background "subconscious" extraction (write) uses an LLM memory manager. `[vendor doc]` langchain-ai.github.io/langmem (hot-path quickstart, memory-tools guide). No documented multi-hop assembly, no entity store — `[absence]` (checked docs + repo tree).

## E. OpenAI (Agents SDK + Responses) — session memory, not entity assembly

Current SDK memory = **sessions**: the runner auto-retrieves stored conversation history and prepends it to each run's input items; retrieval size is capped by session settings; **compaction sessions** (`OpenAIResponsesCompactionSession`) auto-summarize when the window grows (an LLM compaction step in the read path, blocking streaming while it runs); manual `pop_item` for corrections. Backends: SQLite/Redis/Postgres/Mongo/Dapr etc. Hosted continuation via `previous_response_id` for server-side context. **No entity extraction, no knowledge graph, no cross-session fact assembly** in the documented SDK/hosted memory surface — a separate memory layer is the vendor-agnostic answer (mem0's own integration guide says exactly this). `[vendor doc]` openai.github.io/openai-agents-python/sessions/, /context/, /running_agents/; developers.openai.com conversation-state guide. A hosted long-term auto-extraction "memory tool" was not found in the current developer-docs index (`/api/llms.txt`, `llms.txt`) — `[absence]` (either removed or folded elsewhere; do not rely on it).

## F. Amazon Bedrock AgentCore Memory (fully managed; vendor doc)

Two tiers. **Short-term**: raw per-turn events keyed by `sessionId` (CreateEvent/ListEvents w/ metadata filters/GetEvent) — reload conversation as-is. **Long-term**: asynchronous background extraction + **consolidation**: for each newly extracted memory, retrieve top semantically-similar existing records (same namespace + strategy) and send new+old to an LLM with a consolidation prompt that decides ADD/UPDATE/NO-OP — so supersession happens by LLM judgment at *write*, and reads see the consolidated record. Read ops: `GetMemoryRecord` / `ListMemoryRecords` / `RetrieveMemoryRecords` — the last is **semantic search** over memory records with `searchQuery`, `topK`, `namespace` prefix / `namespacePath` hierarchical filters, metadata filters, and `memoryStrategyId`; records carry `createdAt`, namespaces, content. maxResults default 20 (max 100). **No graph, no entity-centric assembly** — flat semantically-retrieved records, though namespace + strategy + metadata filters + structured content give users a way to pre-scope. Read LLM cost: 0 at retrieval; write path uses LLM for extraction + consolidation. `[vendor doc]` docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.md, memory-types.md, API_RetrieveMemoryRecords.html; `[vendor blog]` aws.amazon.com/blogs/machine-learning/building-smarter-ai-agents-agentcore-long-term-memory-deep-dive/ (consolidation mechanics).

## G. Research systems with documented connected assembly (read side)

### G1. HippoRAG 1 (arXiv:2405.14831) — PPR as the assembler `[paper]`
Offline: LLM OpenIE → schemaless KG of noun-phrase nodes + retrieval-encoder "synonymy" edges (cosine > τ, tuned 0.8) + a passage↔phrase incidence matrix. **Online (single-step):** 1-shot LLM extracts query named entities → retrieval encoder links them to KG nodes (query nodes) → **Personalized PageRank seeded at query nodes** (damping/restart probability tuned 0.5) → node activations → passages scored by aggregating node PPR scores × node-specificity (IDF-like) → top passages to the reader. Read LLM cost: 1 small LLM call (NER) + embedding linking + PPR; **10–30× cheaper and 6–13× faster than iterative retrieval (IRCoT)** at comparable multi-hop accuracy (self-reported, benchmarked). Key idea for us: a *graph algorithm replaces multi-step retrieval loops*; PPR reaches arbitrarily far but restart bias keeps it entity-local — no explicit hop cap. `[paper]` arxiv.org/abs/2405.14831 (+ full text for hyperparameters). Reimplementations exist on Neptune/Neo4j (`[independent]` aws.amazon.com/blogs/machine-learning/hipporag-neurobiologically-inspired-rag-using-amazon-bedrock-amazon-neptune-and-personalized-pagerank/).

### G2. HippoRAG 2 (arXiv:2502.14802) — concept nodes + passage nodes `[paper]`
Fixes HippoRAG 1's "entity-centric context loss": KG now holds **phrase (concept) nodes AND passage (context) nodes joined by "contains" edges**. Query → LLM generates query-to-triples + "recognition memory" filters candidates; if no triples, fall back to plain top-k embedding. Seed nodes = top-k phrase nodes (by rank in filtered triples) **plus all candidate passage nodes** ("broader activation improves multi-hop reasoning"); reset probabilities assigned by rank for phrases and by embedding similarity × a weight factor for passages; PPR over the mixed graph; passages ranked by PageRank score. Comprehensive gains over plain RAG on factual/sense-making/associative memory; claims +7% over SOTA embedder on associative tasks (self-reported). Read LLM: query→triples generation (1 call). `[paper]` arxiv.org/abs/2502.14802. **Concept/context node split is the closest analog to Tortoise's Object-vs-Point split in a non-temporal system.**

### G3. Microsoft GraphRAG — local & global search `[vendor doc]`
**Local search (entity-based, closest to an assembler):** LLM-extract entities from query → they become "access points" → pull connected entities, relationships, covariates, community reports (entity→report mapping) AND raw text units (entity→text-unit mapping) → **prioritize + filter all candidate source types to fit one context window of predefined size** → single response call. **Global search (whole-corpus):** map-reduce over precomputed community reports — chunk reports, produce *rated* intermediate responses per chunk (shuffled to avoid position bias), then reduce over the top-rated points. Config surfaces token budgets per step. Community summaries are built **offline at index time** — read avoids re-summarization but pays offline LLM cost; global search is heavy (tens of seconds per Zep's competitive note; GraphRAG is not an interactive-memory engine). `[vendor doc]` microsoft.github.io/graphrag/query/global_search/, /query/local_search/. No temporal layer, no state semantics; static corpus, batch rebuilds on update (well-documented limitation vs agent memory).

### G4. A-MEM (arXiv:2502.12110) — vector recall + linked-note auto-expansion `[paper]`
Zettelkasten-style memory notes (`content, timestamp, keywords, tags, context description, embedding, links`). **Retrieval:** embed query → search memory DB for relevant matches → **linked/similar notes in the same box are "also automatically accessed"** (i.e., retrieval result = matched note + its link neighborhood). Notes are enriched/self-edited at write by LLM (link generation, attribute updates — "memory evolution"). Assembly = 1-hop link expansion of hits, no traversal budget documented. `[paper]` + code link in abstract. Useful only as evidence that "retrieved note + linked notes" is a cheap, effective assembly primitive in agentic memory benchmarks.

### G5. Generative Agents (arXiv:2304.03442) — scored memory stream `[paper]`
Retrieval score = weighted sum (min-max normalized) of recency (exponential decay 0.995 per hour since last *retrieval*), importance (LLM 1–10 at write), relevance (cosine to query embedding). Retrieved records feed the action/planning context; **reflection performs recursive retrieval** (LLM generates "most salient questions" from observations, each becomes a query → retrieve → synthesize) — an early documented retrieval→assemble→re-retrieve pattern. No entity graph; the decay-on-retrieval and reflection-as-query-generator ideas are the durable takeaways (both already partially in in-repo 1657/autoMem levers).

### G6. Newer episodic-memory research touching this axis (context evidence)
- **REMem** (arXiv:2602.13530): two-phase episodic memory — offline hybrid memory graph of "time-aware gists + facts"; online **agentic retriever with curated tools iterating over the memory graph**; reports +3.4/+13.4 abs. pts over Mem0 and HippoRAG 2 on episodic recollection/reasoning benchmarks. `[paper]` (single source; arXiv 2602 = 2026 — treat numbers as self-reported).
- **CatRAG** (arXiv:2602.01965): criticizes static PPR as a **"Static Graph Fallacy"** — fixed transition weights drift into high-degree **hub nodes** ("semantic drift") before reaching evidence; proposes query-adaptive edge weighting + weak entity anchoring. Independent evidence that *unweighted/static graph walks on hubby graphs degrade multi-hop evidence chains*. `[paper]`.
- **ReFind** (arXiv:2608.12888): agent-controlled lexical search over *raw* chat logs (no KG/summaries at all) beats HippoRAG 2 (58.2 vs 53.2 mean accuracy) on conversational-memory tasks including event ordering and fact consolidation. Independent evidence that structure only pays when retrieval over it is competent; raw turn-indexed logs + an agentic search loop can rival graph memory. `[paper]` (preprint, single source — flag).

## Cross-system patterns (what the better assemblers share)

1. **Entities are the anchor, but the graph is only an access/expansion layer — final evidence is still flat text for the reader.** Graphiti returns fact strings; Mem0 returns flat memories; HippoRAG/G2 return passages; GraphRAG local returns a packed single context window. Nobody ships a rendered "state + timeline" block — the reader always gets a list to reason over. Tortoise's structured block would be novel among these.
2. **Expansion depth is shallow and budget-capped.** Graphiti BFS depth 3 with 2×limit candidates/method, limit ~10; A-MEM 1-hop links; Mem0 entity boost only within an over-fetched vector pool (4×top_k, min 60); HippoRAG/G2: PPR restart keeps activation local (implicit depth control). "Assembling" in shipping systems = tens of facts, not subgraph explosion.
3. **Read-side LLM calls are avoided or minimized everywhere.** Graphiti high-level = 0; Mem0 = 0 (+classifier); Bedrock retrieve = 0; LangMem = 0; HippoRAG = 1 tiny NER/triple call; only agentic systems (Letta, reflection, REMem) and GraphRAG global spend multiple calls. The expensive LLM work is pushed to write time (extraction, dating, dedupe, summaries, communities).
4. **Ranking is additive & semantic-dominant when multiple signals exist** (Mem0: semantic+BM25+entity/temporal, normalized; Graphiti: RRF over 3 legs; generative agents: weighted sum) — and hard pre-filtering is explicitly avoided (Mem0 temporal "would silently drop memories").
5. **Precomputed high-level summaries ride alongside granular facts** (Graphiti communities; GraphRAG community reports; Mem0 state projection artifacts; Bedrock consolidated records) — read pays latency ~0 for them, LLM cost is deferred to background/write.
6. **Supersession is resolved at write (invalidation/consolidation) OR at read (dated instances + intent rerank), never by deletion** — Mem0 keeps state_key chains + event_end; Graphiti keeps invalid_at-marked edges; Bedrock rewrites via consolidation; all preserve history as queryable context.
7. **Entity hubs are a known failure and are actively damped**: Mem0 1/(1+0.001(n−1)²) hub penalty on linked-memory count; CatRAG documents PPR hub drift. Frequency/salience rerankers (Graphiti episode_mentions; generative-agents importance) counterweight hubs.
8. **When a graph walk is used, it is seeded from semantic/keyword hits ("land and expand") or from resolved query entities — never run blind.**
9. **Multi-hop reasoning is mostly handed to the reader LLM over retrieved evidence; only HippoRAG encodes it in retrieval** (and pays for it with KG-construction cost + known failure modes). Even Zep flags their BFS as unweighted/unrefined.

## Anti-patterns / pitfalls specific to connected assembly

1. **No validity default → stale/contradicted facts reach the reader** (Graphiti OSS returns invalidated edges unless caller filters — confirmed in source). Any assembler must mark or filter superseded items itself.
2. **Semantic pool as gatekeeper with a hard pre-threshold** (Mem0: candidates below cosine 0.1 dropped even if entity/keyword strong) — a deterministic entity/object-ID hit can be starved by embedding weakness. Don't gate graph-resolved evidence on embedding score.
3. **Hub-node semantic drift**: static walks on uneven graphs sink into high-degree entities (CatRAG critique; PPR tuning sensitivity — restart 0.5 was tuned, robustness claims aside).
4. **"Structure beats nothing" is not automatic**: ReFind shows raw-log agentic search rivaling graph memory; structure pays only if the traversal + filters are actually better than competent flat search for the question type.
5. **Pool-adjacent-only boost** (Mem0 entity boost can't surface memories outside the vector candidate pool) quietly undercuts the "graph connects facts across memories" pitch.
6. **GraphRAG-style community map-reduce as an interactive-memory read path**: tens-of-seconds latency, batch rebuild on every update — wrong shape for a memory read path (vendor-competitive note + known architecture limits; communities only work when precomputed incrementally like Graphiti).
7. **Over-assembly / no budget**: unlimited BFS or PPR over a large graph without per-method caps and a final token budget produces context flooding; every shipping assembler caps at ≤ ~10–100 items before the reader.
8. **LLM-judgment supersession at write is irreversible-ish** (Bedrock consolidation ADD/UPDATE, Graphiti invalidation) — wrong merges corrupt the entity's state history; an assembler should prefer reversible, dated supersession it can re-derive at read (Tortoise's fold already does this).

## Implications for Tortoise's assembler (design takeaways + what NOT to copy)

1. **The deterministic zero-LLM assembler is a differentiator, not a gap.** Every comparable system either (a) pushes assembly cost to write-time LLM passes (Graphiti/communities, Bedrock consolidation, Mem0 platform graph) or (b) accepts 1+ small read LLM calls (HippoRAG query→entities/triples). Tortoise already stores what others build: Object state + dated Events + aboutObject Points with EP. A pure-graph assembler from resolved Objects to a structured block has **no direct competitor** — Zep's node-distance rerank + Graphiti communities are the nearest ancestors, and neither renders state/timeline structure. The design space is defensible.
2. **Seed the walk from resolved subjects, then budget like Graphiti**: entity-resolution (Objects) → walk ≤ 2–3 hops over *typed* edges (aboutObject primary; IMPL/NAND/supersession on demand) with per-edge-type caps and a hard total-item budget (~10–40 facts), mirroring Graphiti's depth-3 + 2×limit discipline `[source]` — but improve on it by restricting traversal to *relevant* edge types (Graphiti walks RELATES_TO|MENTIONS indiscriminately and vendors admit drift — do not copy that; walk aboutObject + supersession first, IMPL/NAND only when the question needs logic chains).
3. **Apply a hub penalty before rendering**: high-degree Objects (many aboutObject points) must not crowd the block — adopt Mem0's hub-damping shape (1/(1+0.001(n−1)²)) `[source]`, or cap per-Object points and rank within by EP/recency.
4. **Render supersession deterministically at read (Tortoise's fold) rather than copying any vendor**: Graphiti's no-validity-default (`[source]` — invalidated facts returned) and Bedrock's irreversible LLM consolidation are the two poles to avoid; dated instances + explicit current-state projection (already in Tortoise ontology) is Mem0-platform's *intent* achieved more rigorously.
5. **Timeline + state blocks are the assembly ordering competitors lack**: Graphiti returns score-ranked facts; Mem0 returns score-ranked flat memories (temporal = rerank only). Ordered dated events + projected state-as-of-{question date} convert ordering questions into reader problems — consistent with the prior doc's Option 1/2 and with ChronoQA (retrieval failure is the dominant error) from the in-repo prior.
6. **Keep a vector/BM25 complement with the graph hit, but never let embedding threshold gate graph-resolved evidence** (Mem0's pre-gate is the anti-pattern). Two-tier: graph walk (exact) ∪ semantic pool (recall) with additive EP/recency/entity scores; don't zero out weak-embedding but graph-certain hits.
7. **Read-side LLM cost = 1 reader call is achievable and already better than HippoRAG's 1-NER + reader; do not add a query→graph LLM step** unless entity resolution from the question fails rule-based matching — then a *fallback* resolution call is the right escalation (mirrors HippoRAG2's fallback-to-embedding when triples fail `[paper]`).
8. **Precompute nothing new at write for the assembler's sake** — communities/summaries are the other camp's answer to read latency; Tortoise's event/state structure already renders cheaply at read (per prior doc). If multi-Object "themes" ever need global context, incremental community summaries (Graphiti-style, background) are the pattern — not GraphRAG batch.
9. **Evaluation framing:** treat vendor claims (Zep p95 300ms, Mem0 94.8@top50, "multi-hop gains from graph") as upper bounds; the honest benchmark bars are independent evals (Vectorize 49/63.8) and the new episodic preprints (REMem/ReFind) — none of which test a rendered state+timeline assembler. Absence-of-evidence to record: **no shipping agent-memory product documents a zero-LLM entity→state→timeline→evidence assembler**, so our design has no direct precedent to converge on — the closest verified parts are Graphiti's scoped search budget and HippoRAG2's concept/context node split.
