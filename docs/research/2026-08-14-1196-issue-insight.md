# Research — Issue #1196: graph insight on GitHub issue creation ('there's more in the graph' hook)

> Scoping research artifact for issue #1196 (issue-scoping Phase 1.5 + diamond-phase framing research).
> Findings date: 2026-08-14. Provenance tags: [canonical] / [competitor-precedent] / [pitfalls] / [adversarial] / [unverified-internal].

## Confirmed Problem

At issue-creation time in a connected repo, the creating agent files the issue without consulting
prior graph knowledge — nothing pulls related decisions/claims/past issues at the creation moment.
The gap is **invocation + output shaping**, not a missing retrieval primitive (verified: 85 unique
`tortoise_*` tools in `tortoise/tool_registry.py`; `tortoise_fts_query`, `tortoise_search`,
`tortoise_recall`, `tortoise_suggest_entry_points` all exist; `skills/issue-creation/SKILL.md`
contains zero `tortoise_*` calls — NOTE: `skills/` is a tracked SYMLINK to
`agent-infra/skills`, so the skill-layer invocation edit is an agent-infra deliverable, not a
tortoise-PR change).

## Axis Research

### Axis: Architecture (rated complex)

**Canonical — GitHub native just-in-time duplicate detection.**
GitHub shipped similar-issue detection in public preview (github.blog changelog 2026-06-18): up to 3
possible matches surfaced **inline while the reporter fills the form** — i.e. at composition time,
pre-submit. This occupies the highest-intent slot for humans. A post-creation comment is therefore a
strictly worse slot (arrives after intent passed; must beat the platform's own matcher to be
non-redundant). Direction: if we surface graph hits, do it where GitHub does not (cross-session
decisions, EP-tagged claims, "we already decided this") — not a re-run of textual similar-issue search.

**Canonical — GitHub webhook delivery contract.** GitHub delivers webhooks with `X-GitHub-Delivery`
(unique per delivery) + `X-Hub-Signature-256` (HMAC-SHA256). Redelivery on non-2xx is a documented
behavior: any comment/event emission keyed on webhook receipt MUST dedupe on delivery ID or it
duplicates on retry. In-repo precedent: `tortoise/hosted_api.py` `/webhooks/stripe` (#310) does
signature verification + event-ID dedup + `is_first` delivery marker — the pattern exists in-repo.

**Competitor-precedent — Linear similar-issue placement.** Linear surfaces similar issues **inside
the create modal** (2023-08-03) and, per their docs, has moved similar-issue detection *earlier*
(triage/support inbox): creation time was deemed too late for triage value. This supports
"context at the moment of capture is weak; context at moment of use (pickup/planning) is strong."

**Pitfalls — proactive comment reception.** CrossFix (Wiley JSEP): 40 open issues received relevant
recommendations, 8 positive feedback (~8/40 — low reception). GitHub maintainer-survey guidance
("AI should not intervene unless asked") points the same way: unsolicited post-hoc comments are
noise and train users/agents to ignore the surface. [unverified-internal]: the Sprint user study
claim ("false positives were users' #1 complaint") is NOT supported by the paper (users were largely
positive; some extra non-duplicate suggestions noted) — retagged internal observation, direction
independently supported by CrossFix + maintainer survey. [unverified-internal]: the "ghrag eval"
claim (local semantic layer > GitHub search, pull-based) has no identifiable public source in this
record — treated as an internal directional observation only.

**Pitfalls — tool-surface bloat.** Epic 888 research: tool count is a real cost (each tool adds
context + decision load). Registry currently has 85 unique `tortoise_*` tools. A new one-off read
tool is a weak argument; prefer parameterizing existing query tools or a thin insight-specific
wrapper that shapes existing primitive output.

## Surface Feasibility (for solution-diverge)

|---|---|---|
| (a) GitHub webhook/app comment | LOW | No hosted GitHub webhook route (only `/webhooks/stripe`); SDK connector webhook binds `127.0.0.1` (`tortoise/connectors/github.py`); integration is OAuth-App only (`scope=repo`), token acts as the authorizing **human** → comment misattribution; no `X-GitHub-Delivery` dedup in `github.py`; webhook path creates only `EventRecorded`, not the issue Object/Points chain (entity extraction runs only in poll-path `ingest()`) |

| (c) Session-start augmentation | HIGH (already shipped) | `tortoise_session_context` MCP tool + REST `/v1/context` + `tortoise context` CLI; adding an open-issues/insight section is incremental — but this is pickup-time, not creation-time |

## Key Decisions Recorded (controller, problem-verify fixes)

1. **Surface (a) rejection legs (restated accurately):** (i) OAuth-App token posts comments as the
   connected human → attribution confusion + author notification noise; (ii) ecosystem noise
   evidence (GitHub JIT dup detection 2026-06-18, CrossFix, maintainer "don't intervene"); (iii)
   reactivity — a post-creation comment cannot prevent graph-blind filing (the confirmed root
   cause). NOT rejected on "infra-dead": the Stripe precedent proves hosted webhook ingress is
   buildable — it is simply not warranted for beta scope (multi-week build, no acceptance-criteria
   payoff that surface (b) doesn't already satisfy).
2. **Scope narrowing (agent-created issues):** issue #1196's objective says "when an issue is
   created in a connected repo"; scoping narrows to "when the creating agent files the issue."
   Recorded decision: beta promise targets the agent fleet (README/launch roadmap position agents
   as the primary consumer; GitHub-native JIT covers the human-UI path). Human-UI webhook surface
   deferred — revisit when non-agent users are the beta population.
3. **Fail-closed conditions re-scoped to surface (b):** empty graph / graph-service failure /
   stale index — NOT "GH API down" (the MCP leg reads the graph, not GitHub; GH API state is out
   of path).
5. **Skill-layer invocation is a cross-repo deliverable:** `skills/` is a tracked symlink to
   `agent-infra/skills` (git mode 120000). The invocation edit to `skills/issue-creation/SKILL.md`
   lands in agent-infra's working tree and is committed THERE via the skill-sync skill — it does
   NOT ride in the tortoise PR. The tortoise PR carries the tool + tests + docs; the agent-infra
   commit carries the skill step. Both are required for the beta hook to fire (hard dependency,
   absorbed; tracked as separate commits).
4. **Freshness is a companion issue, not absorbed:** manual one-time indexing backfill
   (`_INDEX_JOBS` in-memory, 1h TTL) means empty/stale graphs are the common onboarding case; the
   insight must fail closed to "no prior knowledge — graph empty" and render gracefully. Continuous
   sync / webhook ingress = separate workstream (filed separately if no issue exists).
