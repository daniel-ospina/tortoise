Shipped surfaces confirmed live (2026-09-10, TestClient against the real hosted app, fake
Supabase plane per the suite's established pattern):
- `GET /.well-known/oauth-protected-resource[/mcp]` → 200, RFC 9728 body (resource,
  authorization_servers, scopes `mcp`, bearer_methods `header`).
- `GET /.well-known/oauth-authorization-server[/mcp]` → 200, RFC 8414 body (issuer,
  authorization/token/registration/revocation endpoints, `code`, grants
  `authorization_code` + `refresh_token`, auth methods `none` + `client_secret_post`, PKCE
  `S256`, scope `mcp`).
- DCR `POST /register` with a ChatGPT-style `https://chatgpt.com/...` redirect URI → 201
  `ct_` client (public client, PKCE-bound).
- PKCE `S256` code exchange with **no `resource` param** (ChatGPT sends none) → 200
  `oat_` access token + rotating `ort_` refresh token (30-day TTL, rotation extends).
- `POST /mcp` `tools/list` with that `oat_` token → 200, `tortoise_*` tools returned.

OpenAI conformance cross-check (external): ChatGPT reads AS metadata from
`/.well-known/oauth-authorization-server`, requires PKCE `S256`, and expects refresh tokens
for long-lived connectors — our metadata advertises both grants and `S256`; refresh tokens
are issued and rotated.

## Remaining work (this branch)

### R1 — Server gap: multi-team accounts dead-end for resource-less clients (ChatGPT)
Confirmed live: a user in **two teams** hits `400 invalid_resource` on both
`GET /oauth/consent/preview` and `POST /oauth/consent` when the client sends **no RFC 8707
`resource`** (exactly what ChatGPT does — there is no resource picker in its connector UI).
The #524 D4 design said "client-declared resource, no picker UI"; that assumption is false
for ChatGPT. Fix (additive, no schema change): the consent page preview lists the user's
teams when a resource-less request resolves to multiple teams, the page offers a team
picker, and the consent POST carries the chosen `team_id` → existing team-scoped-resource
code path. Single-team behavior unchanged. See scoping doc for the design.

### R2 — Wizard ChatGPT tab (Indicator 5)
The onboarding wizard's harness chooser (dashboard `main.jsx` live connect step + the
`harnesses.js` 6-harness vocabulary) has no ChatGPT entry. ChatGPT connects via
**Developer mode** (Settings → Security and login → Developer mode) → **chatgpt.com/plugins**
→ new **Developer-mode app** → server URL `https://api.premiselabs.co/mcp` → **OAuth** →
Scan Tools → authorize → tools appear in the composer's Developer-mode tool. Auth is
**OAuth only** (no static headers), so the tab must **not** require the API-key mint that the
other 6 tabs gate on, and must carry the skills-as-prompt copy (ChatGPT has no local skills;
the Claude Web pattern applies). OpenAI UI research (2026-09-10) confirms the current flow —
the issue's 2026-08-25 research note is broadly accurate but the create surface is now
"chatgpt.com/plugins → + → Developer-mode app", not a generic "custom connector".

### R3 — ChatGPT human E2E (Indicator 2)
OpenAI's ChatGPT connector creation is a human-in-the-loop UI. Deliverable = precise
recorded E2E script + evidence template (PR-body manual step), not the human click.

## Explicitly NOT gaps (audited, no change)
- **Refresh-token TTL policy:** rotating refresh (30 d TTL, extends on each use) is
  sufficient for "long-lived connectors" — any connector active at least monthly
  self-sustains. Documented, no code change.
- **CORS/origin:** ChatGPT connects server-to-server (DCR + token exchange, no browser
  origin); the consent page is same-origin on `api.premiselabs.co`. No CORS change.
- **Bearer-key regression risk:** none — all server changes ride additive OAuth tables/
  prefixes; this branch's server diff is confined to the consent-preview/consent API +
  consent page, plus `oauth.py` helpers.
