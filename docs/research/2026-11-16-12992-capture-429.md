# #12992 — a refused capture: lost, or deferred?

**Severity verdict: P0** — not because bytes are dropped, but because a refused capture is deferred
into a substrate **with no running consumer on the reporting box**: measured, `122,378` records /
`968 MB` / `102` day files with **no cursor store, ever** (`~/.tortoise/store-sync/` absent). The
issue's promote-to-P0 condition #2 is "the backlog never clears ⇒ unbounded delay, P0 for a memory
product"; the measurement is stronger than the condition — the drain has never run at all, so nothing
clears it. Nothing is *deleted* (the bytes are on disk and recoverable), which is why this is not a
data-loss P0; it is a *silent absence from recall* P0.

> Citations are by **symbol**, not line number (`path.py::symbol`), per this repo's recorded rule.

## 1. Lost or deferred? — **deferred, into a substrate nothing drains**

The chain, in the order it runs:

1. `reflect-hook.ts::session_shutdown` → `writeFallback(payload)` **appends the record to
   `~/.tortoise/session-events/<UTC day>.jsonl` synchronously, BEFORE the network call** (the call
   site's own comment: *"Durable local record FIRST (synchronous) — a quit teardown mid-fetch must
   never lose the session silently"*). The 429 cannot lose it: the bytes are on disk before the POST
   exists.
2. The POST is classified by `tortoise-capture.ts::captureOutcome` — `429` ⇒ `retryable`, so the spool
   entry is **kept**, never unlinked (`mayKeepEntry`).
3. `session_events_drain.py::_file_one` → `capture_spool.classify_failure` ⇒ `retry`:
   `drain_session_events` leaves the record **un-consumed** and ends the pass (`stopped = "refused"`).

Reproduced by an existing test — the brief's "refusal-then-drain" leg:

```bash
uv run python tools/test_lane.py run -- tests/test_6388_session_events_drain.py -v
# 38 passed, exit 0
```

`test_a_transient_refusal_stops_the_pass_and_loses_nothing` is the pin: a `429` on 4 records ⇒
`stopped == "refused"`, `filed == 0`, `queued == 4`; a second pass with a working transport **files
them**. A refusal is a deferral, and the deferral is retried.

**So the answer to Q1 is (a) retried — subject to (3): the retry only happens when someone runs the
drain, and on this box nobody does.**

## 2. Does the spool have a ceiling that drops? — **no; it refuses new work and keeps the backlog**

Read at `tortoise/capture_spool.py` (module docstring + the three constants):

| bound | value |
|---|---|
| `SPOOL_MAX_ENTRIES` | 20,000 |
| `SPOOL_MAX_TOTAL_BYTES` | 256 MiB |
| `SPOOL_MAX_ENTRY_BYTES` | 16 MiB |

At a ceiling with nothing reclaimable, the spool is **SATURATED**: `write_spool_entry` **REFUSES** the
new write, records the refusal (`spool_total_bytes_exceeded` / `spool_count_exceeded`), keeps the
backlog, and reports `capture: SATURATED`. The oldest undelivered entry is **never** reaped to make
room — the recorded 2026-11-01 capture-loss decision. Only an **already-filed** entry is evictable.

```bash
uv run python tools/test_lane.py run -- tests/test_capture_spool.py -k "byte_bound or saturat" -v
# 6 passed, exit 0
```

`test_the_byte_bound_REFUSES_new_work_when_only_undelivered_remain` is the pin. ⇒ the issue's
promote-to-P0 condition #1 ("the spool has a ceiling that **drops**") is **FALSE**. A capture refused
for capacity is never dropped by the spool.

## 3. Is the drain starved by the same gate? — **yes, same gate; and it is not running at all**

**Same gate: confirmed.** The drain's transport is `tortoise/__main__.py::_session_post`, which posts
to `{api_url}/v1/sessions`. That route (`hosted_api.py::capture_session`) takes the admission slot at
its first statement: `_reserve_capture_slot(_capture_session_key(org, body.session_id))`. So a
backlog drain competes for the **same 8 global slots** as live sessions — one consumer starving the
other is structural, not incidental.

**Cursor semantics on `429`: the day is KEPT.** `drain_session_events`'s `verdict == "retry"` arm
charges a strike, sets `stopped = "refused"`, and `break`s — `cursor.consume(...)` is only reached for
`filed`/`dead-lettered` (terminal) verdicts. The cursor is then persisted (`_write_cursor`) and the
record is **still queued**. After `MAX_STRIKES = 3` passes it is skipped for the rest of each pass
(reported `stuck`), with `STUCK_RETRIES_PER_PASS = 1` rotating probe re-attempting it — never crossed,
never dropped.

**But the drain never runs on the reporting box.** Measured:

```bash
uv run python -c "from tortoise.session_events_drain import cursor_dir; p=cursor_dir(); print(p, p.exists())"
# /Users/danielospina/.tortoise/store-sync False

python3 - <<'PY'
import json, pathlib
d = pathlib.Path.home()/".tortoise/session-events"
tot = files = 0
for p in sorted(d.glob("*.jsonl")):
    files += 1
    tot += sum(1 for line in p.open(encoding="utf-8") if line.strip())
print(files, "day files", tot, "records")
PY
# 102 day files 122378 records      (du -sh ~/.tortoise/session-events → 968M)
```

- `~/.tortoise/store-sync/` — the cursor AND the dead-letter substrate — **does not exist**. The
  module's own docstring records the same absence as the proof that nothing consumed this substrate
  when #6388 was filed (`61,997` records / `516 MB`); it is now **`122,378` / `968 MB`** and the
  directory still does not exist. The backlog has **doubled since the drain landed**.
- `~/.tortoise/session-events/archive/` does not exist — no seal has run either.
- `~/.tortoise/capture-spool/entries/` holds **5 undelivered entries dated 2026-09-22/23** — a second,
  independent proof that no sweep has flushed this box's spool.
- **Nothing invokes it.** `store_sync.run_sweep` is the only caller, reached only through the
  `tortoise store-sync` CLI. On this box: no `crontab` entry, no `launchd` job
  (`launchctl list | grep tortoise` → reaper/hygiene/ci/auto-rail only), and **neither deployed hook
  invokes it** (`rg 'store-sync' ~/.pi/agent/extensions/reflect-hook.ts \
  ~/.pi/agent/extensions/tortoise-capture/index.ts` → **exit 1, no match** — ⛔ the paths are
  listed one per line on purpose: an earlier cut of this sentence wrote the brace form with
  `…/tortoise-capture.ts` in it, and on this box that path does not exist, so the command the
  reader pasted exited **2** with `No such file or directory` while the prose reported "no
  match" — a command that ERRORS is not a command that answered). The repo's own spool-aware hook (`tortoise/pi-hooks/tortoise-capture.ts`) *does*
  spawn the sweep on `session_start` — it is simply not what is deployed here.

⇒ the issue's promote-to-P0 condition #2 is **TRUE**, and worse than stated: not "a busy fleet starves
the drain" but "this box's drain has no trigger at all".

## 4. What saturates the gate? — 8 slots, 4 workers, and an 800 s worst-case hold

```bash
uv run python - <<'PY'
import tortoise.hosted_api as ha
from tortoise.extractor_v2 import _scaled_deadline
from tortoise.mcp_auth import _TRANSPORT_WAIT_BOUND_S, _TRANSPORT_WAIT_RETRY_AFTER_S
print("max in flight:", ha._CAPTURE_MAX_IN_FLIGHT)          # 8
print("capture workers:", ha._CAPTURE_EXECUTOR._max_workers) # 4
print("scaled deadline(600,16000):", _scaled_deadline(600, 16000))  # 800
print("client wait bound:", _TRANSPORT_WAIT_BOUND_S, _TRANSPORT_WAIT_RETRY_AFTER_S)  # 10.0 10
PY
```

- `_CAPTURE_MAX_IN_FLIGHT` = **8** (`TORTOISE_CAPTURE_IN_FLIGHT`, clamped `[1, 16]`), a
  **process-global** locked int — verified: the served CMD is a single-process
  `uvicorn tortoise.hosted_api:app` (`Dockerfile.hosted::CMD`), so one counter serves every tenant and
  every org.
- `_CAPTURE_EXECUTOR` runs **4** workers (`TORTOISE_CAPTURE_WORKERS`, clamped `[1, 8]`). The gate
  admits **8**, so under a burst 4 extractions execute and 4 more hold slots while queued.
- **Slot lifetime is the extraction's duration, not the request's.** The route's own transport wait
  bound is **10 s** (`mcp_auth._TRANSPORT_WAIT_BOUND_S`), and `tests/test_hosted_api.py` records the
  measured consequence in prose: *"a 504'd sibling still completing server-side holds
  `_CAPTURE_IN_FLIGHT` … so once abandoned siblings reach the cap the next capture answers 429"*. The
  worker's slot is released by `_CaptureSlot.worker_done` on the pool future, i.e. when the extraction
  finishes — up to `800 s` (`_scaled_deadline(600, 16000)` = max(600, 0.05 × 16,000)).
- **Fleet census (measured on this box, 2026-11-16T08:39Z):** `19` cmux workspaces; `120` capture
  records written today (61 `pi-session-quit` + 59 `pi-agent-end`) in ~8.6 h ≈ **14 captures/hour**;
  `6` session files touched in the preceding 3 h. So the **arrival rate alone cannot saturate 8
  slots** — a burst or a set of long-running extractions must.

**The `8` is not obviously too small, and raising it is contraindicated.** The hold is up to **80×**
the client's wait bound; a bigger ceiling would park more MB-scale transcripts on the documented 4 GB
VM (`hosted_api.py`'s "Reject instead of enqueueing" rationale) without making the consumer faster.
The measurement does **not** support a fair-share or a ceiling change; it supports making the condition
*visible* and the refusal *typed*.

**Gap — stated, not filled:** the concurrency *at the moment of a refusal* is **not measurable**, by
anyone: no counter for it exists on any surface (`rg -n 'capture' hosted_api.py | rg -i 'health|metric'`
→ one hit, an unrelated log comment). That absence is defect #3 of the issue and is what §7 fixes.
What would answer it: the `capture` block added in this lane's fix (`refused_total`, `in_flight`,
`max_in_flight`, `last_refused_at`) plus a refusal rate read over a day.

## 5. Does the caller honour `Retry-After: 30`? — **no. The client is outside this repo.**

Three clients reach this box, and **none** reads the header:

| client | where | behaviour on `429` |
|---|---|---|
| `reflect-hook.ts::captureToHosted` | `~/.pi/agent/extensions/reflect-hook.ts` — **a farmed copy of an agent-infra TRACKED file**, not an orphan: `git -C "$AGENT_INFRA_PATH" ls-files | grep reflect-hook` -> `extensions/reflect-hook.ts`, `extensions/reflect-hook.test.ts`, `pi-bootstrap/pi-config/extensions/reflect-hook.ts`, and `cmp` reports the deployed copy **byte-identical** to `extensions/reflect-hook.ts` (added `62097adf7`, 2026-07-31). ⛔ An earlier cut of this row said "not in this repo and not in agent-infra (verified by name)" — that was FALSE, and it moved the follow-up to the wrong repo: the client IS editable, so honouring `detail.retry_after` there is a two-line change rather than an external contract | **one** `fetch`, `!res.ok` ⇒ throw, log `Hosted capture FAILED (<detail>) — a manual-recovery JSONL record was kept at <path>`. **No retry, header ignored** |
| `tortoise-capture.ts::postCapture` | `~/.pi/agent/extensions/tortoise-capture.ts` — ⛔ **NOT deployed under that name on this box**: the directory holds `tortoise-capture/` and `tortoise-capture.ts.disabled`. The behaviour below is read from the `.disabled` copy / the lineage's `postCapture`, not observed from a live hook here, so treat it as `unchecked` in the same sense §5.1 uses | **one** POST, `!res.ok` ⇒ `warn("capture FAILED for session … — it was NOT filed")`. **No retry, header ignored** — this is the second log line in the issue |
| `tortoise/pi-hooks/tortoise-capture.ts` (in repo) | shipped hook | classifies `429` as `retryable` and **retries** — but the delay is `backoffDelay(attempts)` = `RETRY_BASE_MS (30 s) × 2^(n-1)`, capped at 6 h. **The `Retry-After` header is never read** (the string does not occur in any `tortoise/pi-hooks/*.ts`) |

Two consequences worth recording separately from the fix:

1. **The observed 429 reached a client with no retry path at all.** Acceptance bullet 1 of the issue
   ("a capture refused with `429 + Retry-After` is retried by the client after that delay, and lands")
   **cannot be satisfied inside THIS repo** — the two clients that produced the issue's log lines are
   deployed extension files under `~/.pi/agent/extensions/`. ⛔ **They are not ownerless, and an
   earlier cut of this bullet said they "live in neither this repo nor agent-infra" — that was false
   for `reflect-hook.ts`**, which is a farmed copy of agent-infra's tracked
   `extensions/reflect-hook.ts` (`cmp` reports the two identical; `git -C "$AGENT_INFRA_PATH" log
   --diff-filter=A -- extensions/reflect-hook.ts` -> `62097adf7`, 2026-07-31, months before this
   research). So the §5.1 contract has a REAL home: **agent-infra**, in a repo the fleet already
   edits, and the retry + `detail.retry_after` read is a two-line change there rather than a
   negotiation with an unknown owner. (`tortoise-capture.ts` was NOT verifiable from this box — no
   such file under `~/.pi/agent/extensions/` at the head this was measured — so it is stated as
   unchecked rather than assumed to share `reflect-hook`'s provenance.)
2. **The in-repo hook retries but is blind to the server's instruction.** Today that is harmless
   (`Retry-After: 30` coincides with `RETRY_BASE_MS`), and it stays harmless only by coincidence: if
   the server's advertised delay changes, or a different refusal on the same path advertises a
   different one, the client keeps its own clock. Publishing the delay as a **machine-readable body
   field** (§7) is what lets that client honour it without prose-matching.

### 5.1 The contract for the client repo — agent-infra (`extensions/reflect-hook.ts`), not implemented here

A capture client MUST:

1. On `429` (and `409` in-flight, `504` wait-bound — all `retryable`), **retry** rather than log-and-drop,
   with a bounded attempt count and a persisted next-attempt time (so a process exit does not lose the
   intent). Never treat a `429` as terminal.
2. Read the advertised delay from **`detail.retry_after` (body)** first, falling back to the
   `Retry-After` header, and wait **at least** that long — never less. Clamp it to a configured
   maximum so a hostile/typo'd value cannot strand an entry.
3. Keep the durable record it already writes (`session-events` day file): it is the reason a refusal is
   a deferral rather than a loss.
4. Report the refusal to the operator as a typed condition (`code`, `retry_after`), never as a bare
   `HTTP 429` line.

## 6. What this measurement could **not** establish

- **The concurrency at the moment of the two refusals.** No counter existed; the fix adds one. Until a
  day of data exists, "8 was exceeded because of a burst" vs "because of `800 s` orphan holds" is
  undecided — both are consistent with every datum here.
- **The typical (not worst-case) extraction duration.** Nothing measures it: no test times a real
  extraction end-to-end, and no surface records capture duration. The bound `≤ 800 s` is from the
  deadline, not from an observation; the mean is unknown.
- **Whether the two refused captures ever reached the graph.** Their day file records exist, but the
  drain never ran, so they did not reach the graph *by this path*. Whether another path filed them
  (a different box, a manual run) is unverifiable from here.
- **Why the deployed extensions are not the repo's `pi-hooks/`.** They are a different implementation
  (no spool, no sweep spawn). Recording this as deployment drift; not investigated further here.

## 7. What this lane changes (in repo)

Only what the measurement supports, and each piece individually justified in the PR:

1. **The capacity `429` becomes a TYPED refusal** — `detail` gains `code: "capture_capacity_saturated"`,
   `retry_after`, `in_flight`, `limit`, alongside the existing `message` and the `Retry-After: 30`
   header. Precedent and shape: `hosted_api.py::_ingest_rate_limited` (the sibling `429` on the same
   route already answers a dict with `code`/`retry_after`; the capacity `429` answers a bare string, so
   a client must prose-match it — #11225).
2. **A `capture` block on `GET /health`** — `in_flight`, `max_in_flight`, `refused_total`,
   `last_refused_at`, `refusing` (windowed). **Reported, never folded into `status`**, the same rule as
   `change_feed` / `record` / `wait_bound_breaches`: a saturated capture gate is not liveness, and a
   cumulative counter must not pin a deployment degraded for the life of a process.

Not changed, deliberately: `_CAPTURE_MAX_IN_FLIGHT`'s default (§4 — no measurement says the consumer
is fast enough to raise it), the pricing/quota lane, and no migration or backfill.
