# Research Brief

## Raw Notes

### Axis Research

- **2026-08-13T09:59:25** [canonical] Two-stage retrieval production best practices: candidate pool sweet spot 50-100 (gains plateau by 200; cap at 50 per 72technologies); RRF fusion BEFORE rerank stage (cheap dense/sparse disagreement fix first); truncate docs at index time to fixed max-token budget (latency is bimodal — p50 vs p99 driven by doc-length distribution); cross-encoder score is a LOGIT not a probability — use for ranking only, never as relevance threshold; weighted fusion of first-stage + reranker scores often beats reranker alone; keep max_length 512 (BERT truncation) and chunk <=1500 chars. (Sources: Hybrid Search Book; superteams.ai production RAG course; devtechtools; Pinecone; Vespa docs — Vespa defaults 100 candidates 2nd-phase / 20 global phase; TREC DL top-100 rerank standard.)
- **2026-08-13T09:59:26** [pitfalls] ms-marco-MiniLM-L-6-v2 (22.7M params, ~80-90MB) latency — CPU-only deployment is the binding constraint: Metarank GPU avgt 12.3ms/1, 58.7ms/10, 740ms/100; CPU (DadOps): ~210ms/10, ~410ms/20, ~980ms/50, ~2.1s/100 docs; OneUptime CPU batch=1 2500ms/100, CPU batch=32 800ms/100. ONNX qint8 (temsa, i7-9750H): 210ms/20, 578ms/50 avg (~30-40% faster than fp32 ONNX). Production latency-failure case study (tianpan.co): offline +4 nDCG@5 but p99 +700ms over SLO — user-perceived quality DOWN. QPS collapse: cross-encoder at 30 QPS p50 -> 6.7s, 40 QPS p99.9 > 21s (towardsdatascience queue simulation). So top-100 rerank on CPU violates 300ms target by 3-8x.
- **2026-08-13T09:59:26** [pitfalls] When reranking HURTS (canonical diagnostic, multi-source): corpora under ~1,000 documents where top-k is already high precision; recall@3 already > 0.9 ('shuffling cards that are all correct'); single-keyword/exact-match queries BM25 already nails; sub-50ms real-time budgets. Value window: recall@50 high but ordering poor (right doc buried rank 20-30). Practitioner diagnostic: label 100 production queries, measure where correct docs land — in top-50 >90% but top-5 <60% => reranker moves the needle; missing from top-50 => fix retrieval first, no reranker can save it. arXiv 2411.11767: rerankers frequently UNDERPERFORM strong retrievers; 53.3% of datasets scaling candidate K hurt Recall@10. (Sources: bigdataboutique; folarin.dev; 72technologies; adaptiverecall; theneuralbase; arXiv 2411.11767.)
- **2026-08-13T09:59:26** [competitor] Late-interaction (ColBERT) is the latency alternative: ~2 orders of magnitude faster than cross-encoder at near-parity MRR (170x faster, 14,000x fewer FLOPs/query at k=1000, Khattab&Zaharia 2020; +5 nDCG@10 over MiniLM rerank on BEIR with little added latency, arXiv 2302.06589); precomputed token embeddings => sub-linear rerank cost (500 candidates in cross-encoder's 50-candidate time). BUT: index 50-100x larger than dense (ColBERTv2 residual compression -> 5-10x), storage overhead not worth it under ~100K chunks; wrong choice for small corpora and for teams without inference-service engineering. Selective/conditional reranking (route only 15-20% of queries; gate on score gap) cuts latency 57% with <2% quality loss (clawrxiv 2604.01082; thread-transfer). LLM listwise = quality ceiling for reasoning-heavy agent queries but 2-3 orders slower. (Sources: datarekha; thread-transfer; tianpan.co; hybridsearchbook; arXiv 2004.12832/2302.06589.)
- **2026-08-13T09:59:26** [pitfalls] sentence-transformers CrossEncoder production gotchas: (1) device not pushed until predict() called (HF #3078) — explicit device param required; (2) tokenizer NOT thread-safe — ThreadPoolExecutor raises 'Already borrowed'; GIL means threads don't parallelize CPU inference, use process pool (HF #993); (3) model init ~2s; 22.7M params ~80-90MB fp32; (4) ONNX/OpenVINO qint8 quantization via Optimum gives ~30-40% CPU speedup (sbert efficiency docs); (5) model-loading lifecycle precedent: lazy-init singleton with load timeout + HF_HUB_OFFLINE degrade + Dockerfile pre-download + pre-warm (repo: tortoise/embeddings.py pattern); (6) fallback strategy required when reranker unavailable — feature flag off must mean pipeline never re-tuned for reranker-on (tianpan.co trap).
- **2026-08-17T09:35:00Z** [canonical] RRF k and candidate-pool depth are SEPARATE knobs (#1348): k is the RRF smoothing constant (Azure AI Search: RRF best at k=60; Milvus: k 10-100, optimal varies by dataset → an in-house sweep is justified); pool depth is the candidate window (Elasticsearch: search k beyond rank_window_size truncates → pool directly constrains fusion output; Doris: 50-200 typical, 100/side reasonable default, smaller pools miss docs that rank modestly in one retriever but high in another). RRF fusion is rank-based — deeper pools add recall (docs recovered from modest mid-list ranks) at the cost of decoration budget; k controls score flatness, NOT recall. **Reconciliation with the 2026-08-13 [pitfalls] entry (arXiv 2411.11767, "53.3% of datasets scaling candidate K hurt Recall@10"):** that result measures TRAINED RERANKER candidate-K scaling (more candidates → more chances for a learned reranker to misfire) — a different mechanism from RRF pool depth, where rank-based consensus across 3 retrievers filters mid-list noise rather than learning on it. The two claims are not in conflict; the empirical question (does deeper RRF pooling help at corpus ≈2000/24 topics) is exactly what #1348's pool-depth × k sweep on the #1144 eval set answers. (Sources: Azure AI Search; Elasticsearch; Apache Doris; Milvus; Spice AI; Arc Labs; arXiv 2411.11767)
- **2026-08-17T09:36:00Z** [competitor-precedent] Graph-informed reranking has positive prior art (#1348): Gar (Graph-based Adaptive Re-ranking, arXiv 2208.08942) improves nDCG up to +8% on MS MARCO over BM25/monoT5 baselines, robust to hyperparameters, minimal added cost; TopoRAG (ACL 2026 findings) improves precision via topology-aware retrieval; graph-embedding entity retrieval (ECIR 2020) shows graph encodings beat plain word embeddings for ranking. **Adversarial balance:** positive prior art is not a free pass — the caveat stands that all cited approaches are TRAINED/adaptive, whereas Tortoise's GraphRanker (#25) is a hand-weighted heuristic (α=0.5/β=0.35/γ=0.15) that can also add noise (a high-degree operator-heavy point surfacing on graph boost alone, or recency dominating when similarity ties are weak) — an adopt/hybrid/reject verdict therefore requires in-house measurement on the #1144 eval set, not literature transfer, and the sweep should report per-tier (easy/medium/hard) deltas so a topology boost that helps ambiguous queries but hurts exact ones is visible. (Sources: arXiv 2208.08942; ACL 2026 TopoRAG; ECIR 2020)
