## Epic Research Brief — Pro-tier multi-graph teams: per-graph API keys + graph provisioning

### Strategy Context

- **Product decision is made and priced (2026-09-01, Daniel):** pro tier and above get multi-graph teams; API keys are per-graph; provisioning via key capability returns graph + key. Developer-customer model: each app end-customer = one graph = one key = isolated memory.
- **Pricing already commits to it:** `product/pricing.json` — `per_graph_keys: "planned"` on pro ($25) and team ($149); pro segments include `app_builder`; `max_graphs_per_team`: free=1, solo=2, pro/team=null (unlimited). The feature is *advertised* to a segment that could sign up against it — delivery once started is time-boxed.
- **Market precedent — graph DBs treat the graph/database as THE tenancy unit:** Neo4j Aura (instance=1 database, free=1 DB), Memgraph (per-DB isolation in-instance), TigerGraph MultiGraph (graph-scoped privileges), Redis (per-DB ACL). Tortoise's "each graph = isolated unit with own key" matches graph-DB convention exactly. [HIGH]
- **Agent-memory vendors never bill per graph — they gate count per tier and meter usage:** Zep projects 2→5→10→unlimited while graph storage = 0 credits (ingestion billed); Mem0 projects 1→1→unlimited (request quotas); Letta per-active-agent; Neon gates projects (100/1,000/5,000) + branches (10/25) with `$0.002`/branch-hr overage. Unit count = tier gate; usage = the meter. [HIGH]
- **Billing model implication (align-review fix):** write_ops pool is per-team (50k included on pro, $5/10k overage on the team pool). Graph count is the *driver of scale*, not a per-graph billing line. Recommended model (matches market): keep count as a tier gate with loose limits (or unlimited at pro+), meter team-level usage. Avoid a steep count cliff (Mem0 1→1→unlimited anti-pattern) and never charge for graph ownership itself (Zep/Neon precedent).
- **FalkorDB's own position:** multi-graph per tenant on shared infrastructure is the documented pattern ("10,000+ customer graphs per database instance" — CTO multi-tenant blog); database-level isolation = max-security tier at highest cost.

### UX Pattern Research

- **Key scoping UX — the dominant pattern is "one key = one isolated unit" enforced at BOTH layers:** Supabase per-project keys (anon/service_role per project), OpenAI project-scoped keys + service accounts (key carries scope; server attributes usage via `OpenAI-Project` header), Vercel project-scoped tokens (deny anything outside the project), Stripe restricted keys (per-resource Read/Write/None matrix). Implication: per-graph key embeds graph scope (prefix scheme like `rk_live_` / `sb_secret_`) + server-side key→graph binding check + graph already being the storage-isolation unit. [HIGH]
- **Provisioning endpoint UX — one-time plaintext reveal is the universal contract:** AWS CreateAccessKey, GitLab PAT create ("shown once"), OpenRouter, Resend, Zuplo all converge: plaintext credential appears exactly once in the 201 create response; only a one-way hash is stored; no "show key" UI. Stripe: "secret keys are displayed once when created and cannot be revealed later." [HIGH]
- **Migration UX — "no forced migration" is the prevailing pattern:** the existing resource becomes the primary/default; existing credentials stay valid and resolve to it; new resources are additive. Heroku Postgres (first DB = primary `DATABASE_URL`, others get color-named URLs, `pg:promote` to switch), Neon (default branch `main` + default DB `neondb`, cannot delete default branch), GCP (default project, per-command `--project` override), Supabase (org-based billing, existing project becomes one-of-many). [HIGH]
- **Quota UX:** Cloudflare distinguishes soft quota (warn + bill) vs hard_cap (reject); Stripe advises notifying before cap. Supabase excludes paused projects from the 2-project cap (deleted/archived graphs should free quota). Tortoise already returns 402 on quota (`tortoise/quota.py`) — add a soft-warning window before graph-count rejection.
- **Anti-patterns:** steep count cliff (Mem0), killing the free tier (PlanetScale 2024 backlash), app-layer-only isolation without a data-layer boundary (Qdrant warns per-tenant collections get expensive; Neon recommends project-per-user because shared-schema RLS gets complex), silent hard caps.

### Workflow Pattern Research

- **Provisioning flow (mint):** `POST /v1/teams/{team_id}/graphs` (or `/v1/provision`) with `{name, ...}` — body must NOT accept capabilities. Authorized iff caller key holds the `graphs:create` scope (all-None default — Stripe allowlist). Response (201): graph metadata + key metadata + `key_plaintext` revealed exactly once + `revealed_once: true`. Errors: 409 `LimitExceeded` on quota (AWS semantics), 404 unknown team, 401 revoked key. [HIGH]
- **One-level-deep is enforced by construction, not by a runtime depth counter:** the minted credential is bound to a fixed policy chosen by the platform that omits `graphs:create`/`graphs:delete`/`keys:manage` (and any minting path). Vault (child tokens get the policy the parent assigns; token lacking `auth/token/create` can't mint), AWS (permission boundaries intersect every grantable policy), SPKI RFC 2693 (`deleg` field: absent = depth 0; `deleg=1` = one-level-deep). Never let "can this key provision?" be a caller-passed property — the platform stamps minted keys with the fixed child policy (no escalation scopes). [HIGH]
- **Capability representation:** per-key permission set `{ graph_id, scopes: { graphs: { read, write, create, delete }, team: { manage }, keys: { manage } }, delegation_depth: 0 }` — the scope matrix IS the capability (no separate provision field; mint/delete gated by `graphs:create`/`graphs:delete`, key management by `keys:manage`). Store scopes with the key row (Vault-policy style), not computed from caller identity.
- **Revocation semantics:** per-request opaque-key lookup → instant 401 (GitHub/GitLab/Vault); append-only audit of revocations (who/what/when/why); cascade is trivial at depth 0 (no descendants); rotation-first (mint new, mark old deprecated, grace window, then revoke — skip grace only on suspected compromise); treat a graph's keys + its minting team key as a family (GitLab token-family reuse detection as state of the art, optional).
- **Delivery-shape tenancy alignment (#2080 D3):** the parallel epic #2080 owns the delivery-shape decision for the `/v1/context` + `POST /v1/sessions` tenancy contract; its D3 resolution is that tenancy resolves against the requesting key's scope. This epic's per-graph key must be the tenancy unit for both endpoints — `/v1/context` (GET, hosted_api.py:11042) currently resolves `get_current_team` → team graph with no graph parameter; `POST /v1/sessions` (hosted_api.py:4810) is team-scoped. Contract requirement: both must stay contract-compatible with #2080 (scope-by-team today, per-graph key later without breaking the contract — per #2082 indicator 3). The epic must add graph-scope resolution to both surfaces without breaking the existing team-scoped callers.
- **`session_recording` flag (open question W4):** today it is a **team-level** flag (default-ON, #1927, ToS-covered, opt-out via dashboard "Memory sources > Agent sessions" or `tortoise_onboarding_session_recording`), checked in `POST /v1/sessions` before capture. Per-graph scoping is the open decision; leaning per-graph with team-level default per #2082 Q5. Research finding: no precedent conflict — OpenAI/Stripe scope *keys* per project, but *settings* typically live at the account/org level with per-project override (OpenAI project-level rate/spend limits). A per-graph `session_recording` override inheriting the team default is the cleanest shape.

### Tech Stack Research

- **FalkorDB multi-graph: CONFIRMED.** Multiple graphs in one instance; graph selection is client-side (`select_graph()` is a client wrapper that embeds the graph name in every command — no server-side SELECT GRAPH). TortoiseSDK already uses this pattern (`projection/__init__.py:809`, `mcp_server.py:1811/1898`, `__main__.py:4916`). Tortoise's `SUPPORTED_URI_SCHEMES` accepts `docker://`, `redis://`, `rediss://` and REJECTS `bolt://` (the AGENTS.md mention of bolt:// is stale) — good, because Bolt auth hardcodes username `falkordb` (#1827, fix PR closed without merge): a dead end for per-graph credentials.
- **FalkorDB per-graph ACL: PARTIALLY-CONFIRMED (the core technical claim).**
  - ✅ Works at the data-access layer: `ACL SETUSER <user> on ><pw> ~tenant_a +GRAPH.QUERY +GRAPH.RO_QUERY +PING` — verified empirically (4.20.4): every graph-scoped command against another graph returns NOPERM; GRAPH.COPY cross-graph denied; no DB-switch bypass; cannot squat a new graph outside the pattern.
  - ❌ NOT a hermetic wall: GRAPH.LIST leaks all graph names (#2652, OPEN, confirmed — registers firstkey=0 so key-pattern ACL never applies); KEYS/SCAN leak names + internal `telemetry{...}` keys; GRAPH.CONFIG/DEBUG/UDF are unkeyed (GRAPH.CONFIG SET is mutating AND global); `%R~`/`%W~` fine-grained perms are documented-but-broken (every GRAPH command declares access+update key specs; only `%RW~`/`~` works; read-only = command-level `+GRAPH.RO_QUERY`); default user is fail-open until secured (creating ACL users does NOT disable unauthenticated default access); ACL users are memory-only until `aclfile` + `ACL SAVE`.
  - ⚠️ Bolt: experimental, single username, not for production.
  - **Design consequence:** FalkorDB ACL is defense-in-depth beneath the app layer, NOT the authoritative wall. App-layer registry scope enforcement (key → graph binding verified on every request; graph ownership check on every `select_graph`) remains the spine — which is what Tortoise already does per-team (`mcp_auth.py` middleware, `resolve_api_key`). The ACL adds a hard data-access boundary; escalation path for regulated tenants = separate instances (FalkorDB's "maximum security" tier).
  - **Gaps to track:** #2652 fix; cluster/sharded ACL behavior; hosted-cloud custom ACL strings (presets are `~*`, custom strings presumably same engine); telemetry keys; GRAPH.UDF/DEBUG surface.
- **Supabase control-plane gap (the hosted-mode delta — align-review P1):** migrations 0006 (`teams` — HAS `max_graphs`, `graph_name`), 0007 (`api_keys` — NO `graph_id`; team-scoped only; lookup_hash SHA-256(pepper+key); created_via enum provisioned|bootstrap|recovery). No `graphs` table anywhere. `graph_metadata` (supabase_control.py) derives only the default graph from `teams.graph_name`, explicitly does NOT list custom graphs. `graph_count()` (sdk.py) queries the registry graph unconditionally — no Supabase branch, so quota is NOT enforced in hosted mode (registry empty by design under the #765 zero-registry-writes contract: "registry node count == 0"). The epic MUST add: `graphs` table (or equivalent), `api_keys.graph_id` (nullable = team-wide key resolving to default graph), and a Supabase-mode quota-count source. Control-plane backend is env-gated (`TORTOISE_CONTROL_PLANE=supabase|registry`) — selfhost stays registry-backed.
- **Tenancy resolution surface (the isolation touch-map, both modes):** `resolve_api_key(token)` → team_id + limits (supabase_control.py:494) → `_make_sdk(namespace=team_id)` everywhere in `hosted_api.py` (~20 call sites, all `team["team_id"]`), MCP `_current_team_id` ContextVar → `_get_team_sdk()` (mcp_auth.py), `/v1/context` (GET, hosted_api.py:11042) resolves `get_current_team` → team graph, `POST /v1/sessions` (hosted_api.py:4810) team-scoped with team-level `session_recording` flag. The default graph namespace: hosted `team_<team_id>`, selfhost `team_<name>`. Custom graphs already mint `team_{team_id}_{gid}` namespaces (lazily — not until a consumer exists, E2E-11 decision).
- **Migration pattern (recommended):** primary/default graph. Existing team keys keep resolving to the default graph (no `X-Graph-Id` header → default). New per-graph keys carry graph scope. Add explicit graph routing (`X-Tortoise-Graph-Id` header or `?graph_id=` param) for multi-graph. Guard: default graph not deletable (Neon precedent). No data migration, no key rotation, no forced action.
