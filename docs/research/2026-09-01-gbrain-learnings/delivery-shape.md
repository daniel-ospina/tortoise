# Research — Delivery Shape: Volunteering-Memory Reflex + Why-Ready Recall as an Embeddable Component

**Findings date:** 2026-09-01
**Epic:** #2080 (W4 headline) — "the reflex + why-recall must be usable as an embeddable microservice/component for third-party custom apps (event-in → context-out), not just an MCP tool inside Tortoise"
**Question:** how should the volunteering-memory capability be *built* so a third-party custom application can consume it — SDK callback, HTTP service, event pipeline, or MCP server?
**Method:** code reads of gbrain + gbrain-evals (cloned 2026-09-01, `/tmp/gbrain-delivery`, `/tmp/gbrain-evals-delivery`), Tortoise surfaces (`sdk.py`, `mcp_server.py`, `ep.py`, `retrieval.py`, `ranking.py`, `hosted_api.py`, `onboarding/AGENT_ONBOARDING.md`), Tortoise latency artifacts (`benchmarks/README.md`, `docs/scoping/2026-08-24-1656-*`, `docs/research/2026-08-24-1657-retrieval-levers/research.md`), and external web research (accessed 2026-09-01).
**Scope discipline:** this feeds a scope decision, not an implementation plan. No code touched.

---

## Executive Summary

1. **The delivery question is packaging, not a new surface.** The W4 fit audit (research-brief, 2026-08-31) already established that `search` / `recall_state` / `analyze` carry the why-layer in place (support counts, contested flags + counter-evidence, NANDs, mitigations, supersession markers all exist in `recall_state` today). "Embeddable microservice" means: compose those existing surfaces behind a **deterministic event-in → context-out contract** and ship it in multiple topologies — it does **not** mean a duplicate recall tool.
2. **gbrain's own architecture is the strongest precedent and it is already a microservice-shaped seam.** The claude-code hook is a thin subprocess that speaks a narrow IPC protocol (newline-delimited JSON over a local unix socket, shared-secret-gated) to a long-lived `serve` process; the openclaw seam is an in-process plugin with a *narrow contract* (candidates in → pointer block out, no raw SQL across the boundary); the codex row is the cautionary tale (contract-only, no shipped injection path — "the full production flip is a filed follow-up").
3. **The reflex is cheap enough to be a synchronous service.** gbrain budgets: resolve 250 ms, turn_context 600 ms client / 400 ms server, hook ≤800 ms / ≤10 000 chars, all zero-LLM and fail-open. Tortoise's measured envelope (FTS <50 ms, vector <100 ms, hybrid RRF <200 ms, E2E ≤300 ms p95, 500 ms collective cap) fits a per-turn synchronous call with the why-block assembled from **reads** (EP `compute_confidence` is a single-node α/β read; the subgraph is bounded by `_select_subgraph(anchors, max_hops)`).
4. **Four viable topologies, one recommendation: SDK callback + synchronous HTTP endpoint first, event pipeline second, MCP as the harness seam (not the primary third-party surface).** The hosted API already has the tenancy (team namespaces), auth (Bearer `tt_` API keys), capture (`POST /v1/sessions`, `session_id` idempotency), and consent (`session_recording` opt-out) machinery — a `POST /v1/context` endpoint is an assembly of existing parts, not greenfield.
5. **What graph gives you that vector stores can't is exactly what makes the service contract interesting:** why-context requires traversal + EP scores, so the microservice sells a *reasoned* context block (support chain, active NANDs, supersession, trade-offs, dig-deeper pointers), not a retrieval result — retrieval is a sub-step, not the product. Zep's "asynchronous precomputation → deterministic low-latency retrieval" is the managed-service precedent for caching that assembly.

## Viable Delivery Topologies for the Tortoise Reflex + Why-Recall

### Topology A — SDK callback / embedded component
The reflex + why-assembly ships as a library method on the existing `TortoiseSDK`; the third-party app embeds Tortoise's Python package (or the thin `tortoise-client` driver, #526) and calls it per turn.

- **Integration contract (request/response):**
  ```
  volunteer_context(window: list[Turn], session_id: str | None,
                    prior_context: str | None, min_confidence: float = 0.7,
                    max_pointers: int = 3, why: bool = True)
    → ContextBlock { pointers: [{id, label, synopsis}],
                     why: [{point_id, support_chain, ep_weight,
                            contested, nands, superseded_by, dig_deeper: [...]}],
                     degraded_reason: str | None }
  ```
  Mirrors gbrain's `turn_context` request/response shape (`resolve-ipc.ts`: `{kind, window, priorContextText, maxPointers}` → `{ok, block}`), with `prior_context` driving re-mention suppression and `why` gating the why-assembly.
- **Latency budget:** in-process; regex/entity pass ~sub-ms; search fast-path ≤300 ms p95 (measured E2E-8); EP `compute_confidence` = single-node α/β read (µs–ms); why-block assembly from already-annotated `recall_state` output (contested / counter_evidence / nands / mitigations keys exist today) — **total typically 50–200 ms, worst case bounded by the 500 ms collective search cap**.
- **Statelessness:** fully stateless per call (window passed in, nothing persisted server-side); session state lives in the app.
- **Tenancy/auth:** in-process — the namespace parameter (`TortoiseSDK(namespace=...)`) is the graph slice; no network auth. Per-team scoping is a constructor concern.
- **Failure mode:** fail-open (return `{pointers: [], degraded_reason}` on any error) — gbrain's exit-0 contract ported to an exception-safe wrapper. Never break the caller's turn.
- **What it takes to build:** extract the reflex (salience → resolve → gate → budget → suppress) as a pure function over the existing search/EP code; add the why-block assembler over `recall_state`'s existing annotations (fill the 4 documented gaps: contentiousness-as-signal, support-chain narrative, trade-offs join, dig-deeper pointers — all in-place, no new tool); ~1–2 weeks on top of the W4 in-place work.

### Topology B — Synchronous HTTP service (event-in → context-out, latency-bounded)
The same code path exposed as a hosted API endpoint; the app POSTs the turn and receives the block to inject. The gbrain serve socket is exactly this shape for localhost — Tortoise already runs the hosted FastAPI.

- **Integration contract (request/response):** `POST /v1/context` with `{window: [Turn], session_id?, prior_context?, min_confidence?, max_pointers?, why?}` → `200 {pointers, why, degraded_reason}` (or `204`/`{pointers: []}` when silent). Content-type/JSON; ~15 KB request cap mirroring `SessionRequest.conversation` (max_length=1000 turns).
- **Latency budget:** must commit to a synchronous SLO. The measured envelope (hybrid RRF <200 ms, E2E ≤300 ms p95, encode 10–50 ms offloaded via `asyncio.to_thread` — the #1676 pattern already in `search`) supports **≤300 ms p95** on the existing deployment class; the why-block is read-only assembly. No LLM in the hot path (zero-LLM reflex; why-block is graph reads, not generation).
- **Statelessness:** stateless; `session_id` only for dedupe/continuity bookkeeping. The app stays the source of truth for its conversation.
- **Tenancy/auth:** reuse the existing model wholesale — Bearer `tt_` API key (hashed, `auth.py`) → team namespace graph slice (`_make_sdk(namespace=team_id)`); rate limits via existing quota/metering; the onboarding `session_recording` flag is the consent surface (default-ON opt-out, ToS-covered; `409` when disabled) — for a *third-party app*, the app's team key is the consent principal (the app opted in; its users' capture follows the app's ToS, mirroring #1927's framing).
- **Failure mode:** fail-open for the *content* (empty block on retrieval error → the app just gets no injection, exactly gbrain's "push noise is worse than pull silence"); fail-closed for *auth* (401/403 — never serve cross-team context). Degraded-response contract (`degraded_reason`) so the app can log quietly.
- **What it takes to build:** one endpoint wrapping the Topology-A function; reuse `get_current_team`, `_make_sdk`, `asyncio.to_thread` (the #1676 pattern), metering; contract test + a W3-style know-to-ask/false-fire replay against the HTTP seam. The hosted `ask` gating (#2013) does **not** block this — the reflex is deterministic and the why-block is reads, not the reader model; the #2013 decision stays confined to the `ask` surface.

### Topology C — Event pipeline / async push (sessions → precompute → webhook/SSE)
The app streams session events (already shipped: `POST /v1/sessions` with `session_id` idempotency, harness vocab, receipts); Tortoise ingests, runs EP updates, **precomputes** per-point why-context, and pushes context back via webhook or SSE.

- **Integration contract (event shape):** in = existing `SessionRequest` (`conversation`, `session_id`, `harness`, `source`); out = webhook `POST <app-url>/context` with `{session_id, turn_range, points: [{id, why_block}]}` or an SSE stream for live turn-by-turn; subscription registered per team key (`POST /v1/context/subscriptions {url, events}`).
- **Latency budget:** async — no per-turn synchronous SLO; precompute runs on the EP/dream cycle (already a background worker per team, `_dream_worker`); push delivery is best-effort with retry. The per-turn *read* path stays <300 ms for apps that poll.
- **Statelessness:** the service holds session/graph state; the app holds none beyond the subscription. This is the biggest trust inversion vs Topologies A/B.
- **Tenancy/auth:** same team-key model; webhook signing (HMAC with the team key) so app endpoints can verify; per-team subscription store.
- **Failure mode:** fail-open for content (a failed precompute emits nothing, never an error page); delivery is at-least-once with idempotent blocks (`point_id`-keyed, dedupe on the app side). Webhook failure → retry/backoff, then drop (never block the session capture path — capture receipts must stay 2xx regardless).
- **What it takes to build:** subscription registry + webhook dispatcher + SSE route; hook the why-assembly into the post-EP pipeline (dream cycle) instead of the hot path; Zep's async-precompute precedent is the reference architecture. Medium build; **defer to phase 2** unless a pilot app needs push.

### Topology D — MCP server (the existing surface, evaluated honestly)
Tortoise already ships MCP (`tortoise_search` / `tortoise_recall` / `tortoise_ask` (gated) / `tortoise_analyze` / `tortoise_session_capture`), team-scoped via `mcp_auth` (Bearer `tt_` in HTTP mode, `SELFHOST_TEAM_ID` for stdio).

- **Integration contract:** tools, not events. A `tortoise_volunteer_context(window, ...)` tool would mirror gbrain's `volunteer_context` op (one call per turn) and the why-block rides the existing search/recall tool output.
- **Latency:** tool-call round trip; stdio = process-per-call overhead in some hosts, HTTP = same ≤300 ms envelope.
- **The honest limit:** **MCP is a pull surface — the protocol has no push channel for a per-turn reflex** (until MCP notifications mature); the reflex's whole job is deciding *when* to inject, which a pull tool cannot do by itself — the app still has to call it every turn and trust the reflex to say "nothing." That is workable (gbrain's op channel is exactly this) but it is a *second-best* shape for the "embeddable microservice" requirement, and the W3 harness should keep MCP as the *graded seam* regardless.
- **Tenancy/auth/failure:** unchanged from today; fail-open tool semantics (already the `_safe` wrapper pattern).

## Recommendation: "SDK + HTTP first, event pipeline second, MCP as the graded seam"

**The reflex + why-recall should be built as ONE deterministic pipeline with three transports** — the same way gbrain's `volunteer.ts` core feeds the reflex channel, the op, `watch`, and the hook. For third-party custom apps the primary shapes are:

1. **Phase 1 (build now, alongside the W4 in-place work):** Topology A + B together — the reflex/why-assembly as an SDK method (`volunteer_context`) **and** a synchronous `POST /v1/context` endpoint on the hosted API (and the self-host FastAPI), sharing one implementation. Rationale: (a) the hosted tenancy/auth/consent machinery is already built and team-scoped — the endpoint is an assembly, not greenfield; (b) Claude Code's hooks support HTTP endpoints, so `POST /v1/context` is consumable by harness apps with zero Tortoise dependency; (c) latency envelope is proven (≤300 ms E2E measured); (d) the Cat-34-style harness (W3) grades this contract directly with the know-to-ask / false-fire / push / why suites — the harness seam and the product seam are the same HTTP/SDK contract.
2. **Phase 2 (defer, gate on a pilot):** Topology C event pipeline — async precompute of why-blocks on the EP/dream cycle + webhook/SSE push. Zep's async-precompute architecture is the reference; `POST /v1/sessions` idempotent capture is the existing ingest half. Build only when a third-party app actually needs push (vs poll).
3. **MCP stays the harness seam (W3) and a delivery option for MCP-native apps** — `tortoise_volunteer_context` tool if W3 scoping wants the op-channel parity, but it is **not** the primary third-party microservice surface (pull-only, no push).

**Reconciliation with the W4 no-new-tool constraint:** the microservice is a *delivery contract* over the existing recall surfaces — `POST /v1/context` composes `tortoise_fts_query`/`recall_state` + EP reads, and the why-block is the same in-place work the fit audit already scoped (contentiousness-as-signal, support-chain narrative, trade-offs join, dig-deeper pointers). No duplicate tool, no new graph surface; the only new artifact is the endpoint/method + the reflex decision layer (which gbrain's port was already going to build as the pushed channel).

**The why-layer does the hard work, and that is the product:** retrieval gets you candidates; the why-block needs traversal (support chain, NANDs, supersession via `valid_from/to`) + EP scores (`compute_confidence` reads, `variance`/`contested` from `ranking.py`) — the reason a vector store can't copy this is that the context block is *argued*, not retrieved. That argues for owning the assembly server-side (precompute in phase 2) rather than shipping raw subgraphs to apps.

## Open Questions / Decisions Needed from Daniel

1. **Phase-1 surface scope:** SDK method + `POST /v1/context` on hosted API (recommended) — or also a standalone self-host container/package in phase 1 so third parties can run the reflex against their own FalkorDB without the hosted API? (gbrain's local-first precedent suggests self-host matters for the audience, but it doubles the phase-1 packaging work.)
2. **Sync vs async as the primary contract:** is the "custom application" use case per-turn synchronous context-out (latency-bounded POST, phase 1) or session-streamed push (webhook/SSE, phase 2)? This decides whether the event pipeline is build-now or gated on a pilot.
3. **Who is the tenant:** does each *third-party app* get one team namespace (existing model — the app's users share a graph slice, matching today's tenancy), or do the app's *end-users* each need graph slices (new per-user tenancy inside a team — a real auth/data-model change)? The current `namespace`/team model supports the former; the latter needs a design decision before the endpoint's tenancy contract is locked.
4. **Latency SLO commitment:** adopt ≤300 ms p95 for `POST /v1/context` (matches the measured E2E-8 band, deployable today) — or a looser "no worse than search" statement? An SLO changes what can run on the hot path (e.g., rules out any LLM arm).
5. **Reflex decision model:** EP-scored salience (brief assumption A3 — the differentiator) vs gbrain-style regex/arm-confidence first (proven 0.000 kta but commoditizable)? Phase-1 build order differs materially; W3's know-to-ask suite gates either way.

### 2026-09-01T10:00Z — [gbrain] The delivery architecture (what this research is actually about)

- `docs/guides/push-context.md` — the push-channel taxonomy: **one zero-LLM core (`src/core/context/volunteer.ts`) feeding four channels**: `reflex` (automatic, in the context engine), `op` (`gbrain volunteer-context` / MCP `volunteer_context`, one call per turn), `watch` (stream transcript in → volunteered pages stream out), `claude-code`/`codex`/`opencode` (`gbrain hook user-prompt`, registered by `gbrain bootstrap`, per-prompt injection). **This is the "one pipeline, many transports" template for Tortoise's recommendation.**

Zero-LLM, deterministic, precision-biased: "push noise is worse than pull silence (#2095)". At the default gate, slug-suffix (0.6+0.05 < 0.7) never volunteers — needs an explicit lower gate.
- `src/commands/hook.ts` header — the FAIL-OPEN CONTRACT, verbatim: "a hook failure must never break the user's session. Every event exits 0 (empty stdout on failure) and records a heartbeat line; only a CLI usage error (unknown event) exits non-zero. The `GBRAIN_HOOKS=0` env kill switch short-circuits every event." Engine-free by construction (never imports the engine — per-turn context comes from serve's resolve-IPC socket). Events: session-start (file reads only, ≤1.5 s), user-prompt (stdin hook JSON → IPC turn_context → additionalContext stdout, ≤800 ms, ≤10000 chars), stop, session-end.
- `src/core/context/resolve-ipc.ts` — the IPC protocol, verbatim shapes: local unix socket (`.gbrain-resolve.sock` in a 0700 dir on the brain data dir, socket mode 0600, shared secret `.gbrain-ipc-secret`, `timingSafeEqual` compare), newline-delimited JSON, discriminated union on `kind`; ABSENT kind means 'resolve' (back-compat). `resolve` (v1, secret-free): `{kind?: 'resolve', candidates, priorContextText?, maxPointers?, sourceId?}` → `{ok, block|error}`. `turn_context` (v2, secret-gated, source-bound): `{kind: 'turn_context', protocol: 2, secret, window, priorContextText?, sessionId?, sourceId?, maxBytes?}` → `{ok, protocol: 2, block?, degradedReason?, error?}`. The protocol:2 echo is the stale-serve detector (a v1 server answers turn_context as resolve → client degrades to `{degraded: 'stale_serve'}`). `IPC_UNAVAILABLE` symbol when no server reachable. Budgets: resolve 250 ms client; turn_context 600 ms client / 400 ms server; context_pack 1000 ms client / 600 ms server (session-start packs — "overrun returns a PARTIAL pack (degradedReason 'deadline'), never an empty hard failure"); sync 1500/1000 ms. "Both ends are gbrain code; raw SQL never crosses the wire (closes the trust hole)." "Local-only (unix socket …) — no network surface."
- `src/core/bootstrap/host-specs.ts` — `CLAUDE_HOOK_OUTPUT_CAP_CHARS = 10000`; session-start ≤1.5 s, user-prompt ≤800 ms so the harness timeout is the bound.
- `src/openclaw-context-engine.ts` — in-process plugin: `registerContextEngine(ENGINE_ID, factory)`, host provides optional `resolveEntities`/`brainQuery` (narrow contract: "candidates in, a pointer block out (no raw SQL crosses the boundary)"); absent → falls to the serve-IPC / Postgres-direct ladder. "Additive + guarded, so older hosts keep working unchanged."
- `src/core/context/reflex.ts` — orchestrator: `DEFAULT_WINDOW_TURNS = 4`, `TIMEOUT_MS = 1500` per-turn ceiling, zero-candidate fast path (regex only, no brain touch), fully fail-open (`catch { return null; }`).
