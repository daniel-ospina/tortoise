# Research — GraphRAG-Family & KG-Enhanced RETRIEVAL: Evidence-Assembly Best Practices for Entity-Centric Readers

**Date:** 2026-09-10 · **Mode:** external research, evidence-grounded (web, read-only)
**Axis:** graph-retrieval / GraphRAG-family **assembly** — what a connected reader that walks a graph and assembles context looks like, and what demonstrably fails.
**Problem context:** Tortoise assembler = deterministic (zero-LLM) traversal over a property graph (Objects w/ lifecycle+supersession, Points w/ EP confidence, dated Events, aboutObject links); Question → resolve subject(s) → walk connected subgraph → render dense state+timeline+evidence block → one reader LLM call.
**Extends (not duplicating):** `docs/research/2026-09-02-temporal-reasoning-competitors.md` (write-side/competitor temporal stacks: Mem0 state_key, Graphiti validity-window invalidation) and `docs/research/2026-08-24-1657-retrieval-levers/research.md` (search-side RRF/fusion/recency levers). This doc owns the **read-side subgraph-selection and context-assembly** layer. Cross-references into both are marked **[prior-1657]** / **[prior-0922]**.

## 1. What the connected readers assemble (mechanisms, with sources)

### 1.1 Microsoft GraphRAG — community summaries (global) vs entity-neighborhood (local)

**Index side (one-time cost, LLM-heavy):** chunk → LLM entity+relation extraction (structured JSON per chunk) → merge duplicates by name normalization/coreference (relationship weights accumulate across supporting chunks — "evidential strength" signal) → Leiden hierarchical community detection → per-community LLM summary reports at every hierarchy level → embeddings for entities/text units/reports. **[vendor docs + code]** (microsoft.github.io/graphrag; AnyLearn code walkthrough). The community-summary pass is the dominant index cost: on a ~1M-token corpus with ~500 level-2 communities, ≈1 LLM call + ~1k-token report per community per level. **[arXiv, vendor + 3rd-party]** (LightRAG paper Table 2 reports 1,399 communities / 610 level-2 reports ≈ 610k tokens just to serve retrieval; community-walkthrough cost estimate $2–10/MB index vs ~$0.05/MB vector-only).

**Local query path (the closest production analog to Tortoise's assembler)** — dataflow (Microsoft local-search docs, mermaid): query (+ conversation history) → embed against **entity-description** embeddings → top-N semantic entities (implementation **oversamples 2×** to hedge invalid IDs) → fan out through stored mappings to candidate **text units, community reports, entities, relationships, covariates** → each candidate list is **ranked + filtered to fit a single fixed context window** → LLM reads. **[vendor docs]**
- Context-window budget defaults (v0.x code walkthroughs, code-grounded): `max_tokens = 12,000`; reserved by type — `text_unit_prop = 0.5` (raw chunks), `community_prop = 0.1` (reports), remainder 40% for entity+relationship descriptions. Community reports and text units are admitted **all-or-nothing (no truncation)**; relationships admitted in-network-first ordered by `combined_degree` (sum of endpoint degrees), then out-network by link-count-to-in-set; text units ordered by their matched entity's query-similarity then relationship count. **[3rd-party, code-grounded]**.
- Global search (whole-corpus/thematic Q): map-reduce over shuffled batches of community reports, weighted by occurrence/`community_weight` — many LLM calls, 5–30s. **[vendor + 3rd-party]**.

**Documented costs/failure modes (their own + ecosystem):**
- Index is the cost wall: per-chunk extraction calls + per-community-per-level summary calls; **any corpus change requires re-running community detection and regenerating reports** (LightRAG's cost table: adding a same-size corpus ≈ 1,399 × 2 × 5,000 tokens of report regeneration; GraphRAG docs advise "start small"; official repo warns indexing is expensive). **[arXiv, vendor; vendor docs]**
- Local search is **entity-anchored**: if the query's vocabulary diverges from how entities were named/described at index time, entity matching degrades — Microsoft's own DRIFT follow-up was motivated by this ("queries that may not fully align with the original extraction templates defined at index time"). **[vendor docs]** DRIFT adds a community-report primer + iterative local follow-ups (defaults: primer top-10 reports, depth ≤ 3, ≤ 5 follow-ups, confidence threshold 0.7, `max_data_tokens ≈ 8,000`) and self-reports beating local search on comprehensiveness 78% / diversity 81% on 50 local questions over 5k AP news articles — **self-reported, single experiment**. **[vendor docs / MSR blog]**
- Wrong query-mode selection (local vs global) is a recurring production failure (entity queries answered globally over-summarize; thematic queries answered locally under-reach). **[3rd-party]** (dataaihub; dataaspirant). ABSENCE: no peer-reviewed quantification of mode-routing error cost.

### 1.2 LightRAG — dual-level retrieval (entities vs relations as two recall surfaces)

Mechanism (paper + repo): graph over chunks/entities/relations; at query time an LLM pass extracts **low-level keywords** (entities) and **high-level keywords** (relations/topics) from the query. **Local** mode = low-level keys → entity vector search → admit matched entities + **1-hop relations** + their chunks. **Global** mode = high-level keys → relation vector search → admit relations + their text units/neighborhood. **Hybrid** = run both, **dedup merged results**. Token budget via `top_k` + per-surface caps (`max_token_for_text_unit`, `max_token_for_local/global_context`). **[arXiv, vendor; repo; DeepWiki; HF mirror]** One LLM key-extraction call per query (<100 tokens retrieval overhead) vs GraphRAG's community-traversal cost — their central efficiency claim (own benchmark, win-rate vs GraphRAG overall ~54–56% on Agriculture/CS/Legal, ~48% on Mix — **self-reported, LLM-judged win rates**). **[arXiv, vendor]**
Implication for us: **two resolution surfaces (things and relation-types) is cheap and real**; dedup after merging surfaces matters (GraphRAG-family methods are known to leave cross-surface duplicates — see DEG-RAG in §3.2).

### 1.3 HippoRAG (1 & 2) — Personalized PageRank as the expansion operator

Mechanism: corpus → **open/schemaless KG** (HippoRAG 1: OpenIE triples over passages) + offline PPR matrix; at query time extract query concepts/NER → entity-link to graph nodes (embeddings) → run **PPR seeded at those nodes** → return the top-scoring nodes/edges/passages in **one shot** (no iterative LLM retrieval). Claims: multi-hop gains up to +20% over baselines; **single-step PPR matches or beats iterative IRCoT-style retrieval at 10–30× lower cost, 6–13× faster** — **[arXiv, vendor, NeurIPS 2024]**. HippoRAG 2 (NeurIPS 2025) makes it schema-agnostic + passage-as-node, late chunking, scores passages and triples jointly; error analysis (independent, on the family): **recall losses concentrate on 2–4-hop questions; "triple filtering" and "the graph search algorithm" are the main error sources.** **[arXiv, vendor; independent error analyses]** (MemGraphRAG; HippoRAG2 companion paper). Implication: PPR = principled node admission score (random-walk reachability × seed relevance) that bounds the "which neighbors deserve context" question; but its precision depends on extraction quality (noise in the KG flows straight into PageRank scores). **[independent]**.

### 1.4 GraphRAG survey taxonomy — the three dials every assembler turns

Peng et al., "Graph RAG: A Survey" (arXiv:2408.08921) **[PEER-adjacent, arXiv]**: all graph retrievers decompose along (a) **retriever type** (non-parametric heuristics/graph algorithms; LM-based; GNN-based), (b) **paradigm** (once / iterative [adaptive vs fixed] / multi-stage), (c) **granularity of the admission unit** (node / triple / path / subgraph). Surveyed expansion rules include: topic entities + 2-hop neighbors as subgraph; paths between all topic-entity pairs ≤ k; ego-network embedding retrieval; PCST (G-Retriever, prize-collecting Steiner tree); PPR ranking (several); expand-then-prune (1-hop, then similarity top-k); and **knowledge merging** (merge entity-dedup of overlapping subgraphs, triple-aggregation condensation) to control context length. The one-line consensus across the survey: **expansion breadth is bounded by what you then admit; every non-parametric mechanism pairs expansion with a prune/rank/filter stage.**

### 1.5 RAG-Fusion / RRF — fusion mechanics (context)

RRF (Cormack et al., SIGIR 2009; in-repo fusion stack **[prior-1657]**) with per-query **multi-query generation** = RAG-Fusion: generate several query phrasings, retrieve each, RRF-fuse. Failure documented by its own author: **generated queries that drift from intent pull the fused list off-topic** (answers "accurate and comprehensive but strayed"); latency dominated by the extra LLM call. **[arXiv, vendor]** (RAG-Fusion, 2402.03367). For Tortoise (zero-LLM): multi-perspective is achievable without an LLM by resolving *all* canonical subjects/aliases (search_keys **[prior-1657]**) and fusing per-subject lists — the RRF machinery already exists.

### 1.6 kAG (OpenSPG) — "logical-form-guided hybrid reasoning"

Mechanism: mutual indexing of KG and chunks (every triple points back to its source chunk); question decomposed into an executable **logical-form** with retrieval + reasoning operators; if multi-hop structured reasoning answers, return it; else reflect + retrieve chunks. Claims +19.6% F1 HotpotQA, +33.5% 2Wiki vs SOTA RAG **[arXiv, vendor, self-reported]**. Named motivation: traditional RAG has "a gap between vector similarity and relevance of knowledge reasoning" and is "insensitive to… temporal relations, expert rules"; KAG README explicitly cites the **noise problem of GraphRAG introduced by OpenIE**. Implication for Tortoise: the "structured answer if graph-sufficient, else fall back to text" **routing decision is a first-class design choice with published rationale** — and the same source independently flags extraction noise as the main graph weakness (see §3).

## 2. Context assembly best practices (what the strongest systems converge on)

1. **Admit by type-slice with a hard total token budget, not by count.** GraphRAG local search splits one window (12k default) into typed proportions (raw text / community summaries / entity+relation descriptions) and fills until full; **no truncation mid-item**. **[vendor + 3rd-party, code-grounded]** LightRAG caps per-surface tokens. Practical upshot: budgets should be *typed and hierarchical* (state block / timeline block / evidence block), with each block allowed to shrink rather than each item being truncated.
2. **Subgraph expansion ≠ admission.** Best-in-class non-agentic systems all expand a bounded neighborhood (1–2 hops / entity+relations / PPR top-k) and then *score and filter* what enters context (degree, PPR, query-similarity, combined-degree ordering). Survey consensus; GraphRAG local-search candidate ranking; HippoRAG PPR top-k. **[survey + §1 sources]**
3. **Prioritize in-network over out-network; use structural degree as the cheap relevance prior.** GraphRAG local search admits relationships between matched entities before relationships leaving the neighborhood, ordering by combined degree. **[3rd-party, code-grounded]** This is the graph-native version of "evidence on the resolved subject's own chain beats evidence hanging off it."
4. **Dedup across surfaces before rendering.** Community reports re-state entity/relationship facts; local search mixes text units + graph descriptions of the same fact. DEG-RAG (§3.2) shows unresolved duplication measurably degrades QA. Tortoise's risk is the same triple represented as Point, Event, and Object-lifecycle annotation.
5. **Keep provenance edges (text→triple) for the reader.** KAG's mutual indexing and GraphRAG's entity↔text-unit mapping both ensure every graph statement can cite its source chunk; Graphiti's episodic provenance is the memory-system analog **[prior-0922]**. Assembled context that cites sources is more verifiable; kAG treats this as load-bearing for hybrid reasoning. **[arXiv, vendor]**
6. **When evidence is spread across distant regions, seed from coarse summaries then refine** (DRIFT primer→local follow-ups; GraphReader coarse-to-fine exploration). Entity-anchored single-pass is the failure regime DRIFT was built to fix. **[vendor docs]** Tortoise's mid-range questions ("days between two events in different subgraphs") map to this regime.
7. **Order the linearized context deliberately.** Lost-in-the-middle (TACL 2024, Liu et al.) **[PEER]**: reader accuracy is U-shaped vs position — relevant material buried mid-context can score *below closed-book* (GPT-3.5-turbo drop >20% at 20–30 docs; middle placement < no-docs). Reader performance **saturates well before retriever recall** (20→50 docs ≈ +1.5%): "more context" has near-zero marginal value and real cost. Explicit recommendations: re-rank relevant to the start; truncate. For a state+timeline+evidence reader this argues: **highest-confidence current state first; then dated evidence ordered to make the target relation easy** — and a hard cap well below the model's context window.
8. **Deterministic pre-render assembly beats in-prompt selection for budget control.** All LLM-gated expansion schemes (ToG beam search with LLM pruning, IRCoT/ReAct iterative loops, DRIFT follow-ups) pay per-step LLM calls — ToG alone uses ≤ 2·N·D + D + 1 calls per query and shows accuracy rising with depth and width up to tested limits (depth 1–4). **[PEER, ICLR 2024; arXiv]** GraphRAG-Bench timing data: LLM-invoking retrievers (ToG/KGP/DALK) carry 26–89s retrieval latencies vs 0.02–2.4s for non-parametric/PPR/GNN retrievers. **[independent, arXiv 2506.02404]** A zero-LLM expansion phase (rule-based subject resolution + fixed budget) trades a few points of adaptive precision for determinism and 2–3 orders of magnitude less latency — the correct trade for Tortoise's stated architecture.

## 3. Documented failure modes (who demonstrated what)

### 3.1 Over-expansion / structural noise kills graph readers
- **GraphRAG-Bench** (Tsinghua/industry, arXiv:2506.02404, GPT-4o-mini across 9 graph methods) **[independent]**: **DALK and G-Retriever actively degraded LLM performance vs no-retrieval** — cause named as "over-reliance on structural information at the expense of semantic content introduc[ing] excessive noise"; LightRAG/ToG/KGP gave only marginal gains; HippoRAG/GraphRAG/GFM-RAG and (best overall) RAPTOR gave significant boosts. Takeaway: **structural context is not free — methods that flood the reader with subgraph/structural content measurably lose to plain QA** on the same LLM.
- Nuance from the text-RAG side: Cuconasu et al., SIGIR 2024 "The Power of Noise" **[PEER]** found *irrelevant* passages can sometimes *help* (up to +35% reported in the abstract) and relevant-last placement can hurt — but a SIGIR-2026 reproduction reports the effect **fragile/confined to constrained prompt-decoding settings**. **[PEER]** Net: noise tolerance exists but is not a license to over-expand; precision remains the safer default (and precision of admission ≠ precision of answer when budget caps force truncation anyway).

### 3.2 Extraction/entity-resolution errors are the upstream tax on every LLM-built graph
- DEG-RAG (arXiv:2510.14271) **[arXiv, independent of vendor systems]**: LLM-extracted KGs carry redundant/duplicate entities (string-match merging used by MS GraphRAG/LightRAG/HippoRAG leaves many duplicates). **Removing ~40–50% of entities+relations via entity resolution + triple reflection consistently *improves* QA across four graph-RAG variants**; even ~70% reduction is tolerated before degradation. Direct quote-level finding: "KG quality over size." **Graph noise is therefore not merely tolerated — it is currently the dominant correctable defect in LLM-graph retrieval.**
- Cai & O'Connor (Applied Network Science 2025) **[PEER-adjacent]**: real text-extraction errors inflate node counts (spelling splits, entity conflation, spurious nodes); downstream metric bias ≈ 0 only when extraction F1 is high.
- Rigel-E2E (EMNLP 2021) **[PEER]**: replacing gold query entities with a learned resolver costs only ~3% QA accuracy; residual errors are mostly genuine context ambiguity (15–17% of questions unanswerable from the question alone). Entity resolution is worth doing well but is not the dominant loss once decent.
- Vollmers et al. (ISWC 2025) **[PEER]**: for KGQA linking, **high recall even at the cost of precision wins** — "LLMs are resilient to input noise." Complements Rigel: when in doubt, over-resolve subjects rather than under-resolve; the reader can discount weak matches if you hand it confidence.
- Transitive-merge cascade (arXiv 2607.26298 — future-dated; corroborates Zep's "a wrong merge corrupts identity in ways that are hard to undo" **[prior-0922, vendor docs]**): one false-positive link chains unrelated clusters (F1 0.540→0.000 in the worst corpus). ABSENCE: no independent study specifically measuring *query-time* cost of a wrong merge in a graph-read pipeline — the Zep claim and the ER-practice paper are the nearest evidence.

### 3.3 Stale / contradictory facts inside assembled context
- In-repo prior already owns this cluster: stale-blend failures in plain RAG **[prior-0922: sentra, LlamaIndex checklist]**; knowledge-update hardest category for additive memory (Mem0, self-reported) **[prior-0922]**; contradiction handled at *write* time by invalidation in Graphiti **[prior-0922]**; retrieval failure dominant error class on temporal QA (ChronoQA) **[prior-0922]**; TA-RAG time-filtered retrieval beats plain RAG on diachronic questions **[prior-0922]**. Graph-family add-on from this sweep: **temporal relations/validity are called out as a first-class weakness of vector+KG RAG** in kAG's own motivation **[arXiv, vendor]**; HippoRAG-2-era error analyses attribute failures to the graph layer (triple filtering/search), not to the reader **[independent]**. ABSENCE: no peer-reviewed benchmark yet measures *reader confusion caused specifically by contradictory facts both admitted into one graph-read context* — closest is Lost-in-the-middle (positional) and the RAG-trustworthiness survey's "conflicting-info integration" category (survey-level only). **[PEER-adjacent]**

### 3.4 Cost / freshness failure modes of the summary-first approaches
- Community-summary pipelines rebuild wholesale on update (GraphRAG: re-cluster + re-report; LightRAG's Table 2: ~14M tokens to regenerate 1,399 reports twice). **[arXiv, vendor]**
- Wrong-mode routing (local vs global) and stale graphs after incremental ingestion are repeatedly listed as production failure domains. **[3rd-party]** (dataaihub). ABSENCE: no peer-reviewed routing-error measurement.
- Community reports *repackage* facts and can bury the specific dated fact a local question needs — DRIFT's "expand the breadth of the starting point" and GraphRAG-Bench's "GraphRAG needs community info for retrieval → time-consuming" both gesture at this. **[vendor docs; independent]**

## 4. Implications for Tortoise's assembler (evidence-ranked, concrete)

Ranked by strength of evidence × fit with the zero-LLM, one-reader-call, state+timeline+evidence design. These are findings→implications; design remains separate.

1. **[HIGH] Admit typed slices under one hard token cap; never count-based.** Every credible graph reader (GraphRAG local, LightRAG, kAG) budgets by type with a global ceiling, all-or-nothing per item, order by relevance. Implication: render state block / timeline block / evidence block with per-block proportions and a total cap (order-of-magnitude anchors in the wild: 8–12k tokens total for graph+chunk context — GraphRAG 12k window; DRIFT `max_data_tokens` 8k). Don't truncate a timeline mid-event; drop whole low-priority events instead.
2. **[HIGH] Cap expansion depth at 1–2 structural hops for admission, and prefer in-chain over out-chain facts.** Non-agentic SOTA converges on 1–2 hops + rank/filter (survey taxonomy; GraphRAG entity+neighbors). GraphRAG admits in-network relationships before out-network and orders by combined degree. Implication: Tortoise's walk should stop at events/objects *directly* aboutObject-linked to the resolved subject, plus at most the supersession chain (a form of in-network priority — the object's own lifecycle is the strongest evidence for its state), with PPR-style or degree-style scoring only if 2nd-hop admission is ever needed. Evidence that going deeper without scoring kills answers: GraphRAG-Bench (DALK/G-Retriever degrade) **[independent]**.
3. **[HIGH] Resolve subjects recall-first, mark confidence, and let the reader discount.** Query-entity linking is the single entry gate into the graph; linking studies find recall-oriented resolution beats precision-oriented even at the cost of noise, because readers tolerate weak matches (Vollmers ISWC'25; Rigel EMNLP'21: learned resolver costs only ~3 pts vs gold; over-resolution on ambiguous aliases is the safer failure). Implication: resolve all aliases/search_keys **[prior-1657]**; when a subject match is uncertain, admit the connected neighborhood of all plausible candidates and *tag each with a match-confidence + EP confidence*, rather than silently picking one. Under-resolution = guaranteed miss; over-resolution = reader-discountable noise. This directly contradicts "fewer, cleaner subjects" intuition — the evidence says otherwise for QA accuracy.
4. **[HIGH] Dedup aggressively across the three node families before rendering.** Duplicate entity/fact representations are the top correctable graph defect (DEG-RAG: −40–50% entities/relations *improves* QA on four graph-RAG variants) and duplication across surfaces (Point content vs Event text vs Object annotation) is Tortoise's structural twin of the DEG-RAG finding. Implication: dedup keyed on (subject, predicate-ish, date) before linearization; prefer the dated Event as the canonical evidence carrier since Tortoise's ontology makes events the truth **[prior-0922]**.
5. **[HIGH] Linearize with the answer-critical ordering at the ends, and cap context far under the model window.** Lost-in-the-middle: U-curve, mid-context placement < closed-book, reader saturates before recall (20→50 docs ≈ +1.5%). Implication: for current-state questions put resolved state first; for ordering questions put the dated timeline in strict chronological order *as the spine* (evidence also from in-repo: time-ascending rendering already shipped **[prior-1657]**) and keep total assembled tokens conservative — marginal tokens past saturation buy nothing and cost latency on every call.
6. **[MEDIUM] Date ordering within the evidence block is a reader-relevance decision, not a cosmetic one — but note evidence quality is positional, not semantic.** No study directly isolates "date-sorted vs relevance-sorted graph evidence" (ABSENCE); the transferable evidence is positional (lost-in-the-middle) + temporal-intent retrieval (TA-RAG; R5 machinery **[prior-1657]**). Implication: choose ordering per question-type gate (temporal-reasoning → ascending startedAt spine; current-state/KU → newest-valid first, superseded facts demoted not deleted), because both orderings are cheap and the wrong one strands the decisive fact mid-context.
7. **[MEDIUM] Contradiction/staleness must be resolved in the block, not left for the reader.** Write-side invalidation (Graphiti) and read-time latest-state resolution (Mem0 state_key) are the production answers **[prior-0922]**; the reader-LLM should not arbitrate conflicting versions. Implication: assembler should render supersession explicitly (promoted/deprecated markers, CORRECTS edges) so the one reader call sees *why* a fact is stale — never two same-validity-window contradictions without a supersession marker. Tortoise already stores the markers; the assembler must not flatten them away.
8. **[MEDIUM] Reject community-summary-style pre-rollups; they are the wrong abstraction for dated, low-cardinality graphs.** Summary-first indexing exists to compress corpora too big for raw context; its costs are wholesale rebuild-on-update, LLM-pass index, and report re-packaging that can bury specific dated facts (LightRAG cost table; DRIFT motivation; GraphRAG-Bench timing) **[arXiv, vendor; independent]**. Tortoise's per-question subgraph is small and already structured; the entire community-summarization layer is evidence-against, not for. ABSENCE: no study comparing summary-rollup vs raw-dated-evidence on temporal/multi-event QA specifically — flag before treating this as settled.
9. **[MEDIUM] Keep a source/provenance pointer on every rendered item.** kAG mutual indexing and GraphRAG text-unit mapping make graph facts cite-able; provenance is what lets a "state" claim be checked against the event that produced it. Tortoise already owns this (Event → source); render it.
10. **[LOW/MEDIUM] The assembler should be deterministic (zero-LLM) *because* adaptive gating's accuracy gains are marginal and its costs are extreme.** LLM-gated expansion (ToG beam prune) buys accuracy with ≤ 2ND+D+1 LLM calls/query; iterative retrievers (IRCoT) buy +11–21 recall pts over one-shot on corpus multi-hop — the strongest adaptive-retrieval result in this sweep — but at multi-call latency and only when the needed knowledge isn't already parametric (IIRC: retrieval +21 recall, QA +0). Tortoise's alternative — enrich the deterministic walk with cheap graph-native admission signals (PPR/degree/EP-confidence/validity-window) — is the direction all non-agentic production graph readers converged on. IRCoT's real lesson transfers as: **if one deterministic pass proves recall-insufficient on a question class, the fix is a second targeted pass seeded by the first pass's highest-confidence finding — not an LLM deciding what to retrieve.**

## 5. Absence-of-evidence register (checked, not found)

- No peer-reviewed study isolating **date-order vs relevance-order** within linearized graph evidence for a reader LLM. Closest: lost-in-the-middle (position), 2402.11541 (unordered vs ordered *triple-set* semantics — not temporal ordering), and KG-to-text format papers (serialization format ≈ performance-neutral; `head|rel|tail` marginally best).
- No independent (non-vendor) measurement of **wrong query-mode routing cost** in GraphRAG-style systems.
- No peer-reviewed quantification of **reader confusion from contradictory facts co-admitted** in one graph-read context (only RAG-trustworthiness survey categories + positional evidence).
- No benchmark comparing **community-summary rollups vs raw dated evidence** on temporal/multi-event QA.
- HippoRAG's "10–30× cheaper / 6–13× faster" and LightRAG's win-rates are **self-reported** (single-lab, LLM-judged); treat as upper bounds. GraphRAG-Bench is the best independent cross-method check to date and it *reverses* several vendor-tier rankings (RAPTOR > GraphRAG/HippoRAG; DALK/G-Retriever sub-baseline).
