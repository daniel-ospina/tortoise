### Confirmed Problem

**The ask lane's retrieval misses gold turns on long haystacks because the gold can (a) be semantically distant from the question's tokens — "Veja", "chain and cassette", dollar amounts — and the sparse leg cannot match it (the tokenizer even drops all-digit tokens, so `$185` carries zero retrieval signal), (b) sit outside the 40-item / 8k-token context caps even when it ranks inside the 120-item pool (ceb54acb's answer turn ranks ~70), (c) lose the vector leg entirely in the degraded embedded env the spot-check ran in (sentence-transformers is an optional extra — `EmbeddingModel.get()` returns None → the vector strategy is never submitted, `leg_trace` records `no_embedder`, and the ask lane is genuinely FTS-only there), and (d) be re-rankable by levers that exist in the repo but are not applied on the ask lane (evidence-mark boost is product code but OFF and never called by `ask()`; the eval's proven cross-encoder + MMR rerank is eval-only; `search_keys` query expansion is unwired). The reader never sees the evidence, so it cannot answer — a retrieval problem, not a model problem.**

### Alternative Framings (problem-diverge)

**(a) The FTS query itself is the gap (lexical mismatch).** The sparse leg matches tokens, not meaning. `1de5cff2` (Veja), `1d4e3b97` (chain/cassette), and `gpt4_d84a3211` (dollar amounts) all fail because the gold turn shares no (or tokenizer-stripped) tokens with the question. Smoking gun: `tokenize_sparse_query` (tortoise/sparse.py:91-111) drops **all-digit tokens** as "numeric noise" — a price question can never retrieve a price turn. R2's OR-union tolerance (tortoise/sparse.py:113+) fixes one-token-drops, not synonym substitution. The vector leg exists to fix this but is absent in the degraded env and weak (bge-small, 33M params) when present. **Fits: the three lexical-mismatch failures.**

**(b) The hard 40-item / 8k-token cap (gold in pool, cut off).** Pool floor is 120 (`DEFAULT_POOL_SIZE`, retrieval.py:53; `resolve_pool_size`), the ask lane retrieves with `limit=DEFAULT_CONTEXT_ITEM_CAP=40` and assembles under `max_context_tokens=8000` + `context_item_cap=40` + 32 KiB byte cap (sdk.py:10585-10617). ceb54acb at rank ~70 is **in the pool but cut by the item cap**; the per-session chunk cap 3 (`dedup_pool`) can drop raw chunks too. **Fits: ceb54acb only.** Fails the other three (raising caps does not add "Veja" to the pool — no lexical overlap).

**(c) Naive scoring (right turns rank 70).** Equal-weight RRF dilutes the strongest leg — the #1657 in-repo measurement (fused 0.835 < vector-only 0.855, −1.95 nDCG pts) and the shipped fix `fusion_weights = {"vector": 1.5}` (sdk.py:10127-10138) already exist. The residual scoring weakness is: no cross-encoder rerank (eval-only R6), no evidence-mark boost on the ask lane (product function, OFF), and 40-item context truncation after fusion. **Fits: ceb54acb's rank; partially the others once in pool.**

**(d) Capability-transfer gap (the ask lane doesn't use the eval's proven hybrid+rerank path).** The eval (`tools/longmem_eval/retrieve.py` + `rerank.py`) has a measured cross-encoder + MMR rerank stage (R6 #1545), the C2 evidence-mark boost (now product code), the #1947 pool-depth finding (66% of marked evidence never entered the 60-item pool → 120), and the #1657 weighted fusion (now shipped). The product ask lane wires none of the rerank/boost/expansion material. **Fits: the "why didn't we already fix this" framing — the transfer is the work.**

### Adversarial Queries + Pre-mortem

**Adversarial web_search (3+ run; each returned independent sources):**

1. *"hybrid search RAG long-context retrieval top-k cutoff misses gold evidence recall@k"* → Dense embeddings weak on exact-match recall (rare tokens, IDs, version strings, negation — "vectors fail when intent depends on literal tokens"); BM25 misses paraphrases; dense returns close-but-wrong neighbors for precise strings; long-document failure categories in retrieval benchmark literature (arXiv 2604.01733). Sources: optyxstack.com/rag-reliability/hybrid-search-reranking-playbook; letsbuildsolutions.com; supermemory.ai/blog/hybrid-search-guide; sphereinc.com; arxiv.org/html/2604.01733v1; devtechtools.org (Vespa BM25+dense).
2. *"BM25 vs semantic vector retrieval long documents failure modes lexical mismatch"* (second adversarial run absorbed the first query's rate-limit; results above) + *"RAG reranking when to use cross-encoder reranker top-k candidate pool"* → Standard two-stage pattern (fast top-K pool → slow reranker), K=50–200 / N=5–20; add rerank when recall@top-20 > 0.8 but precision@top-3 < 0.6; rerank AFTER hybrid/RRF fusion, not before; skip when shortlist already strong or latency capped <200 ms; default shortlist ~30. Sources: kunwar.page/chapter/062; fareedkhan-dev.github.io/rag-cookbook-2026; ixprt.com; bigdataboutique.com; mudassirkhan.me/blog/rag-reranking; superml.org.
3. *"reciprocal rank fusion pitfalls hybrid search failure modes"* → RRF pitfalls: missing dedup across lists; mismatched id schemes; damping too low amplifies noise; **truncated lists bias fusion (a longer retriever's candidates never get competition from shorter lists)**; retriever-dominance diagnosis (one retriever contributes most top results); RRF cannot distinguish score magnitude within a rank and favors consensus over one strong signal; **convex-combination fusion (CC) is more robust and beats RRF in- and out-of-domain** (arXiv 2210.11934); score normalization is fragile (distributions shift per query). Sources: emergentmind.com; bigdataboutique.com/blog/reciprocal-rank-fusion-...; arc-labs.ai; blog.serghei.pl; redis.io/blog/reciprocal-rank-fusion; arxiv.org/abs/2210.11934.
4. *Competitor/industry queries* (see Axis Research): Mem0, Zep/Graphiti, Cognee, Pinecone/Qdrant/Vespa, Cohere Rerank/LlamaIndex (6 more queries).

**Pre-mortem — "we shipped the retrieval fix and gold still missed — why?" (3 scenarios):**

1. **Pool-membership failure (the rerank-empty-pool trap).** We shipped rerank + cap review, but the gold never entered the pool: the lexical trio (Veja / chain-cassette / $ amounts) has no sparse overlap and the vector leg was still absent/weak at runtime (embedder extra not installed in the serving env, or bge-small misses the paraphrased turn on a 50-session haystack). Diagnosis rule from #317: *"missing from top-50 → fix retrieval first, no reranker can save it."* **Mitigation: fix membership first (numeric tokens, vector leg, search_keys expansion), then rerank; measure gold-in-pool at the 120-depth before any rerank work.**
2. **Cap/token-survivorship failure.** Gold lands top-40 in the pool but the 8k token budget drops it (an oversized rival hit starves it — `assemble_context` skip-not-starve keeps later hits' chance, but a dense premium-40 can still exceed 8k; the 32 KiB byte cap binds first on CJK-heavy pools) or the per-session chunk cap 3 drops the raw chunk carrying the evidence. **Mitigation: gold-turn-inclusion asserts on the ASSEMBLED context ids, not the pool; measure context_tokens headroom per fixture.**
3. **Answer-correctness failure (false success on recall@k).** Recall@k passes (gold in context) but the reader still answers wrong/abstains — the reader-MODEL content-error class from the runbook (deepseek-v4-flash arithmetic/ordering/recency), or the rerank surfaced related-but-wrong turns that flooded the 40-slot. **Mitigation: acceptance is gold-IN-CONTEXT (indicator 1) not answer-correctness (that's #2069); keep the two classes separable in the benchmark, and add a control asserting the assembled context's top-40 recall, not just membership.**

### Problem-Converge Rationale + Falsification + Confidence

**Confirmed problem (one sentence):** The ask lane's retrieval misses gold turns on long haystacks through a combination of a sparse-only lexical surface (FTS on docker / TF-IDF in the embedded env) that cannot match discriminative content absent from the query (brand names, chain/cassette, gold-side dollar amounts), a 40-item/8k-token context cap that truncates in-pool gold (ceb54acb at rank ~70), and the lane's non-use of the repo's own re-rank/boost/expansion levers — so the reader never sees the evidence and cannot answer.

**Why this framing (vs the single framings):** each single framing fails falsification on at least one recorded failure: (a) lexical-mismatch does not explain ceb54acb (which HAS lexical overlap and ranks 70 — a scoring/cap problem); (b) cap-raising does not explain the lexical trio (raising caps cannot add "Veja"); (c) naive-scoring alone does not explain why the vector leg never runs; (d) capability-transfer alone does not explain the degraded-env reality. The combined framing is the only one whose mechanism covers all four recorded failures and whose fix order is falsifiable.

**Rejected alternatives with rationale:**
- *Pure cap-raising (framing b):* rejected as the fix — fails the lexical trio by construction; risks re-introducing the R1 #1540 whole-session token flood (35k measured) and TR flood-control regression. **Better when** measurement shows all failures are ceb54acb-shaped (in-pool + lexical overlap) and context-token headroom exists.
- *Rerank-only (framing c's strongest variant):* rejected as the fix — the #317 diagnostic ("missing from top-50 → fix retrieval first") and arXiv 2411.11767 (rerankers frequently underperform strong retrievers; 53.3% of datasets hurt by scaling candidate K) directly disconfirm a rerank-first posture for the lexical trio; also CPU latency (~410 ms/20 docs) vs the 500 ms product cap. **Better when** the vector leg is guaranteed and pool recall@50 is already high (the genuine two-stage sweet spot).
- *Embedder-swap-first:* rejected for this issue — dimension change is a coordinated re-embed/reindex (#265), and the MemDelta +6.2pp claim is single-source; the same-384-dim question (arctic-xs/s vs bge-small) is a re-embed but not reindex and can be part of the measurement, not the fix.
- *LLM query expansion (HyDE):* rejected — not budget-compatible in the hot path (#1657 L1); the budget-compatible variant is rule-based `search_keys` PRF.

**Falsification check:** this definition is wrong if (a) all 4 golds rank ≤40 once the vector leg is enabled on the docker lane (→ the gap is purely the degraded-env dependency absence — an ops/CI fix, not a retrieval design change), or (b) raising the item cap to 120 with no other change fixes all 4 (→ purely a cap review), or (c) the long-haystack recall@k subset already ≥ the short baseline when measured with the vector leg ON (→ no gap to fix). **Each of (a)/(b)/(c) is cheap to test and is step 1 of the plan** (measurement-first), so the framing is falsifiable before any design work is locked.

**Confidence: 78/100.** High on the mechanism (verified code + dataset + runbook); medium on the magnitude of each lever (unmeasured vector-leg-enabled baseline, unverified mark coverage, unverified rerank latency under the product budget).

**Architecture axis** (external):
- Two-stage retrieval is the production norm: fast candidate pool K=50–200, final N=5–20, cross-encoder rerank second (kunwar.page/chapter/062-reranking-with-cross-encoders; RAG Cookbook 2026 — default shortlist 30; ixprt.com — pool from the recall@k curve). Trigger rule: recall@top-20 > 0.8 with precision@top-3 < 0.6 → add reranker (mudassirkhan.me/blog/rag-reranking). Rerank AFTER hybrid/RRF fusion (same source).
- **RRF mechanics and pitfalls** (canonical): Cormack et al. 2009, k=60 "not critical"; RRF rank-based, scale-invariant — cannot distinguish a #1 scoring 0.99 from 0.51, favors consensus over one strong signal (redis.io/blog/reciprocal-rank-fusion); **truncated lists bias fusion** and retriever-dominance must be diagnosed (arc-labs.ai/learn/reciprocal-rank-fusion); dedup across lists + id-scheme consistency are implementation prerequisites (bigdataboutique.com); convex-combination fusion more robust than RRF (arXiv 2210.11934 — *An Analysis of Fusion Functions for Hybrid Retrieval*); RRF insensitivity to score-distribution drift is why vendors default to it (OpenSearch docs via #1657).
- **Weighted fusion precedent:** MongoDB `$rankFusion` per-retriever weights; Weaviate `alpha`; OpenSearch normalization-processor `weights` "when judged data shows one retriever should dominate" — tortoise's own #1657 measurement + shipped 1.5× vector weight already satisfy that bar (in-repo).
- **Pitfalls (latency/quality):** cross-encoder CPU latency is the binding constraint — ~210 ms/10, ~410 ms/20, ~980 ms/50 docs (Metarank/DadOps via #317); p99 +700 ms over SLO made a rerank rollout user-perceived-negative (tianpan.co via #317); **rerankers frequently underperform strong retrievers; 53.3% of datasets scaling candidate K hurt Recall@10** (arXiv 2411.11767); rerank hurts when top-k already high precision ("shuffling cards that are all correct"); ColBERT late-interaction is the low-latency alternative (index-size cost); ONNX qint8 ~30–40% CPU speedup (sbert efficiency, #317).
- Sources: web_search queries 1–3 above + in-repo #317/#1657/#1348 research docs.

### Solution-Converge Rationale + Rejected Alternatives

**Chosen: Approach A (retrieval-first), sequenced measurement-first with the rerank (A7) as a gated phase 2.** Rationale, quality-over-convenience:
1. **Falsification first.** A0 (measurement, no code change): (a) vector-leg-ON docker baseline for the 4 golds; (b) cap-raised-120 probe; (c) long-haystack recall@k subset definition + short-baseline. If (a) clears, the issue shrinks to an ops/dependency fix + a cap review; if (b) clears, Approach B; if (c) is already green, close. This satisfies the issue's own indicator 2 ("measured before/after") and makes every subsequent lever's contribution attributable.
2. **Fix membership before ordering.** The four failures are a pool-membership problem (vector leg + expansion attack the numeric-invisible and thin-overlap cases) plus one in-pool-outside-cap (ceb54acb — boost/weights promote it) — rerank (C) cannot save membership; caps (B) cannot add it. A1 (numeric tokens, same-value questions) + A2 (vector leg) + A4 (search_keys expansion) attack membership directly; each is small, budget-compatible, and revertible.
3. **Free/cheap reordering first.** A3 (weighted RRF — already shipped, k-sweep) is the ~0ms reordering pillar; A4's evidence boost is a SECOND reorder lever that needs real mark wiring (1-field select + seeding writes — small, not zero-code). ceb54acb at rank ~70 needs promotion into the retrieval window — boost/weights may do it without touching caps.
4. **Rerank only when the data says so.** A7 is gated on the #317 diagnostic (recall@50 high + top-40 ordering poor) and on CPU-budget feasibility; it reuses the eval's proven, degrade-safe implementation and adds NO third-party dependency (cross-encoder ships in sentence-transformers).
5. **Cap review is measurement-gated, never first** (B's trap: flood + cost + no lexical fix).

**Rejected alternatives (with "when this WOULD have been better"):**
- *Approach B (caps/second-pass as the fix)* — **better when** falsification (b) clears (all golds in-pool-with-lexical-match at 120) and context-token headroom + meter cost are confirmed; then it is a 2-line knob change. Otherwise it re-introduces the R1 flood and misses the lexical class.
- *Approach C (rerank-only)* — **better when** falsification (a)+(b) both clear and the residual gap is top-40 ordering on a vector-leg-enabled lane; then the cross-encoder is exactly the two-stage second stage (K=50–100, N=5–20 per the playbook). It is also the right *phase 2* of Approach A under those conditions.
- *Embedder swap to arctic-xs/s (same 384-dim)* — **better when** the A2 measurement shows bge-small is the binding constraint (re-embed within-dim, no reindex); *swap to 768/1024-dim (nomic/Qwen3)* — **better when** #265 coordination + a reindex event are accepted; out of #2070 (the #1349 domain, measured here only).
- *HyDE / LLM query expansion* — **better when** the corpus is niche (low leakage per the ACL-2025 finding) and a non-hot-path deferral is acceptable; not budget-compatible in the ask hot path (#1657 L1). The rule-based `search_keys` PRF is the in-scope subset.
- *Cohere Rerank / hosted reranker* — **better when** GPU/API-served inference exists (the #317 "gated on GPU" note) or CPU latency proves intractable; adds an external API dependency + key + per-call cost + vendor SLO — not v1.
