# #2789 — One free organization per person

**Complexity rating:** Complex (tier=Complex)
**Issue:** [#2789](https://github.com/daniel-ospina/tortoise/issues/2789)
**Predecessor:** #1877 (the implicit heuristic being replaced)
**Written:** 2026-09-10

---

## 1. Problem Framing

### Problem statement

The product decision (2026-09-10) is: **any single user may have a maximum of one
free organization.** Today that rule is encoded as a **membership** heuristic —
`_count_active_free_memberships(user_id) >= 1` (`hosted_api.py:9141`, twin at
`:9246`, invite-side at `:11278`, onboarding-lane gate at `:17355`) — which
conflates two different relationships a user can have with an organization:

- **owner** — the person who created/bought the org (the thing the entitlement is about), and
- **collaborator** — someone invited into an org that already exists.

The heuristic counts both. A user who accepted an invite into a friend's free org
therefore cannot create their own free org — the exact trap that motivated the
issue. Worse, the failure is silent until the moment of intent: the user types a
name, submits, and only then learns they are blocked, by a 402 whose *only*
machine-readable surface is a human string.

And the blocked state offers no real exit. The dialog's only action is "Upgrade",
which lands on the **current** org's Billing tab; the product decision requires a
second path — *purchase a subscription for a new organization* — that does not
exist, because checkout is team-scoped
(`billing_checkout(..., team=Depends(get_current_team_session))`,
`hosted_api.py:20559`) and a not-yet-existing org has no team session to
authenticate with.

### Who is affected

| Actor | Today | Required |
|---|---|---|
| Collaborator-only user trying to create their first org | 🚫 402, "upgrade an existing team first" | ✅ create succeeds |
| Free-org owner trying to create a second org | 🚫 402, bare string | 🚫 guided three-option dialog |
| Free-org owner who wants a *paid* second org | 🚫 no path exists | ✅ checkout → real paid org |
| Free-org owner who clicks "+ Create new organization" | types a name, then rejected | dialog opens immediately |
| Dashboard/API client code | string-matches `detail` | reads a machine-readable code |

### Why it matters now

Multi-org is a launched capability (a user can be in several orgs), the dashboard
already has an org switcher, and the onboarding wizard already re-enters the
second-org lane (`POST /v1/onboarding/team`). The entitlement is the last piece of
the multi-org story that is still enforced by accident rather than by design.

### What "done" means (from the issue's O/I/T)

1. A user who already **owns** one free org cannot create another free one (server-enforced); a user who owns none can.
2. Being a mere **collaborator** no longer blocks owning your own.
3. Attempting a second free org shows a dialog with exactly three options, and the third one leads to a working checkout producing a real paid org.
4. No org is ever left dangling/un-enterable by an abandoned checkout.

## 2. Problem Definition Diamond — Verify

**Method:** code trace of every call site of the current heuristic + the two
control-plane lanes, plus a read of the checkout/webhook machinery it must plug
into. No external research needed (the decision is settled; the interfaces are
in-repo).

### Call sites of `_count_active_free_memberships` (all must be classified)

| Site | Meaning today | #2789 disposition |
|---|---|---|
| `hosted_api.py:9141` `_create_team_supabase_lane` | create-org gate | **replace** with ownership-based count |
| `hosted_api.py:9246` `_create_team_registry_lane` | create-org gate (selfhost) | **replace** |
| `hosted_api.py:17355` `create_onboarding_team` | second-org gate (wizard lane) | **replace** (issue: "the onboarding-lane twin") |
| `hosted_api.py:11278` `invitation_accept` (token path) | invite **join** gate | **leave** — explicitly out of scope |
| `hosted_api.py:11693` `invitation_accept` (v2 path) | invite join gate | **leave** — out of scope |
| `hosted_api.py:12205` `invitation_accept` (by-id path) | invite join gate | **leave** — out of scope |
| `supabase_control.py:1202 / :3052` | the two control-plane accept paths | **leave** — out of scope |

> Line numbers in this table are the **pre-#2789 trace** (as found on
> `origin/main` at `dae9dfb41`). After this change the three create-org gates moved
> and the three invite-JOIN gates renumbered to `hosted_api.py:11393 / 11808 /
> 12320` — their *semantics* are unchanged, which is the point.

The out-of-scope list in the issue is explicit: *"Whether two free users may join
each other's orgs (the invite-side gate at `hosted_api.py:11278`)"*. Changing the
**shared** helper would silently change invite semantics too. Therefore #2789
**adds** a new, ownership-scoped twin and leaves the existing membership-scoped
helper (and every invite path) exactly as it is.

### Counting rule (authoritative, from the issue)

Count = rows where **all** of:

1. membership is **active**, and
2. membership role is **owner**, and
3. the team exists (dangling memberships excluded — never a 500), and
4. the team's subscription is **not** active/paid (`active` / `past_due` / `trialing`), and
5. the team is **not** `pending_payment` (a not-yet-real org must not consume the allowance).

Selfhost (registry lane) has no subscription model, so `tier` is the proxy —
same shape as the #1877 helper (`tier='free' OR tier IS NULL`), plus a
`subscription_status = 'pending_payment'` exclusion for parity.

### Confirmations from the trace (things that would have bitten)

- `teams.id` is **text** with *no format CHECK* (`0006_teams.sql`) — a pre-minted
  26-hex `uuid4().hex[:26]` id is schema-legal.
- `teams.name` has a **unique index** (`0011_teams_name_unique.sql`) — the paid-new-org
  path must pre-check duplicates at checkout time, or a later collision would fail
  provisioning *after* the customer paid.
- `provision_team` is an **idempotent** `ON CONFLICT (id) DO UPDATE` upsert — a
  webhook replay of the same deterministic id converges instead of duplicating.
- `update_team_billing` PATCHes by id and **silently matches 0 rows** when the team
  does not exist — so the webhook must provision *before* applying billing state.
- `_webhook_apply_event` already receives `client_reference_id` as `team_id`; a
  new-org session can therefore ride the **existing** binding mechanism.
- `_billing_default_success_url()` is `…/team?session_id={CHECKOUT_SESSION_ID}`, and the
  dashboard already has a success-return poll (pre-change `main.jsx:2155`; the
  #2789 version of that effect is at `main.jsx:2190`). The new-org return
  can extend it with `&new_org=<team_id>`.
- `FakeControlPlane.rpc("provision_team")` exists — the supabase-lane tests need no
  network and no docker.

**Verdict:** the problem is confirmed and correctly scoped. The fix is a new
ownership-scoped helper in both lanes + a new paid-new-org path + a server-driven
dialog. Nothing in the trace contradicts the issue's framing.

## 3. Solution Definition Diamond — Options

### S-A. Where does the ownership count live?

| Option | Verdict |
|---|---|
| Mutate `count_active_free_memberships` to be owner-only | ❌ changes invite-join semantics → violates the explicit out-of-scope list |
| New `count_owned_free_orgs` / `owned_free_org_ids` pair, mirroring the #1877 shape | ✅ chosen — additive, zero blast radius on invite paths |
| Compute the count client-side only | ❌ must be server-enforced |

### S-B. How does the third option (paid new org) work?

| Option | How | Verdict |
|---|---|---|
| **1. Pending-payment org** | create the team up-front in a `pending_payment` state (no graph/keys), start team-scoped checkout for it, activate on webhook, GC abandoned rows | ❌ requires teaching **every** read surface (switcher list, key mint, graph resolution, quota, billing, invites) to exclude a new state, **plus** a cron GC — six-plus new leak points for a state that should not exist |
| **2. Webhook-provisioned org** | no team row until `checkout.session.completed`; Stripe metadata carries `user_id` + intended name + tier; the webhook provisions the org, then applies billing | ✅ **chosen** — no user-visible half-created org, no GC, no new read-surface state |
| 3. Anonymous "draft org" owned by nobody, adopt later | — | ❌ another dangling state, worse ownership story |

**Chosen: S-B option 2 (webhook-provisioned org)**, per the repo principle
*Good > Easy* and the issue's own preference ("Prefer the design that leaves no
user-visible half-created org").

**Make the idempotency structural, not incidental.** The org id is **pre-minted
server-side** (`uuid4().hex[:26]`, 26 hex chars — matching the minted-id shape) at
checkout-request time, *before* the Stripe session exists, and carried **both** as
`client_reference_id` and in `metadata[team_id]`. (An id derived from the session id
was rejected in plan review: the id is needed *to create* the session, so that part
is circular.)

On the registry (selfhost) lane the pre-minted id is passed as
`sdk.team_create(..., idempotency_key=<id>)` — which is a **replay key, not the
id**: `team_create` still mints its own (`tid = ulid()`) and stores the key as a
`Team` property (#1710). So the lane's id is the **effective** one, and
`_provision_new_org_from_checkout` returns it, with `_webhook_apply_event`
re-binding its local `team_id` to that value before any billing write, marker, or
audit. The two lanes therefore agree on a *replay contract*, not on a literal id —
which is why the helper's return value, not the Stripe-bound id, is authoritative.

Consequences of the pre-minted id:
- replay → same id (supabase lane) → `provision_team`'s `ON CONFLICT (id) DO UPDATE`
  is a no-op; registry lane → same `idempotency_key` → `team_create` returns the
  existing team (`existing: True`, #1710);
- the existing webhook binding (`client_reference_id`) works unchanged;
- an abandoned checkout leaves **nothing** behind anywhere (see §4 abandonment test),
  because the id only ever existed inside Stripe metadata.

**No Stripe customer is created at checkout time.** In subscription mode Stripe
always creates the Customer on completion, so we pass `customer_email` instead of
`customer`. An abandoned checkout therefore leaves literally zero rows/objects —
not even an orphaned Stripe customer. (On completion, `data.customer` is persisted
onto the new team by the existing `_set`.)

**Tradeoff (documented in the PR):** provisioning now happens in the webhook path.
Mitigations: (a) the webhook is already the authoritative money→state path and is
replay-driven by Stripe for up to 3 days; (b) deterministic id + idempotent RPC
means a retry converges; (c) a provisioning failure returns 500 so Stripe retries;
(d) the tier is also carried in metadata so the org lands on a paid tier + paid
limits even if the follow-up `get_subscription` call fails.

### S-C. The blocked response

`HTTPException(402, detail={"code": "one_free_org_limit", "message": …,
"team_id": <owned free org>})`. Dict-valued `detail` is already a supported shape in
this codebase (`_suspended_detail()` → the dashboard's `suspendedFromDetail`), and
it is what makes the dialog server-driven. The dashboard's `api()` learns to lift
`detail.code` / `detail.team_id` onto the thrown Error; no string matching.

### S-D. Dialog UX

Three modes in the existing `.modal` surface (no new component, no new CSS token):

1. **name** (unchanged) — free create, when the user is under the cap;
2. **limit** — headline "You can only have one free organization", body copy from the
   issue, three actions: Cancel · Upgrade current organization · Purchase subscription
   for a new organization;
3. **purchase** — name + plan (paid tiers from `planOptions()` × server-resolved
   `team.checkout_price_ids`) → `POST /v1/billing/checkout/new-org` → popup checkout.

The account-menu item **pre-checks** from the teams list (which already carries
`role` + `tier`; this change adds `subscription_status`) and opens mode 2
immediately at the cap — no name typing before rejection. A 402 from the server
(structured code) opens the same dialog for the drift case (e.g. another tab
created an org).

A11y: reuse `#2392`'s `rememberRestoreTarget(createTeamRestoreRef, accountBlobBtnRef.current)`
focus-return, keep `role="dialog" aria-modal="true"`, keep `Escape = Cancel`, and
`autoFocus` the primary control in **every** mode. The `#2791` `.modal input`
theming and its `modalInputContrastTripwire.test.js` guard must stay green
(the name input keeps no class/style/background).

## 5. Out of Scope (deliberately not touched)

- The invite-join free-cap (`hosted_api.py:11393/11808/12320`,
  `supabase_control.py:1202/3111`) and the free-tier "1 collaborator" semantics.
  Changing the shared helper would change these; #2789 is additive.
- **Other org-owning lanes** — verified during recon and filed as **#2810**:
  `supabase/functions/tenant-provision` derives its team id deterministically from
  `sha256(user_id)[:26]` and `POST /v1/register` is idempotent on email (`409`), so
  neither can yield a second free org for the same person — but `POST /v1/claim`
  has **no** entitlement check and can plausibly hand one user several anon orgs.
  That needs its own scoping pass (one chokepoint + a cross-lane invariant test),
  not a blind addition to this PR.
- **The cancel lifecycle hole** (found in code review; pre-existing, but sharpened by
  the new dialog): after `customer.subscription.deleted` the webhook sets
  `{"tier": "free", "subscription_status": "canceled"}`, which the ownership count
  reads as free — so *upgrade A → create B → cancel* ends with **two free orgs**.
  The path predates #2789 (the old membership count had the same hole) and the fix
  is a product decision (block the create, or auto-close the downgraded org), so it
  is recorded on #2810 instead of improvised here.
- Renaming/re-copying the invite-side message ("You already have a free team …").
- Option-2 naming split (display name vs derived id, #2779).
- A DOM-lane computed-style guard for the dialog (#2793 owns it; not duplicated).
- An org-rename affordance for the (rare) webhook-time name collision.
- Garbage collection of anything: option 2 creates nothing to collect (that is the point).
- The latent-red `test_create_team_success` dashboard e2e (filed as **#2809**; its
  stale copy assertion was corrected as a drive-by while this PR had the file open,
  its blob-switch defect was not).

## 7. Risks

| Risk | Mitigation |
|---|---|
| Webhook provisioning fails after payment | pre-minted id + idempotent RPC + 500 → Stripe retries; tier carried in metadata; PR documents the tradeoff |
| Name collision between checkout and payment | pre-check at checkout (409) **and** deterministic disambiguating suffix + ops log at provision time |
| Invite-side semantics accidentally changed | additive helper only; existing helper and all invite call sites untouched; regression test asserts invite gate is unchanged |
| `#2791` contrast guard regressed | name input keeps no class/style/background; existing tripwire runs in the dashboard test command |
