## Pre-registered Decision Rule (P1 fix from problem-verify; refined cycle 2; co-primary + pilot + ordering fixes cycle 5/Phase 7 — mechanically executable)

**Primary metrics — CO-PRIMARY turn_recall@10 + nDCG@10 (Devil's-Advocate fix, Phase-7 review):** turn_recall@10 is coverage/order-INSENSITIVE — blind to ranking-within-top-10, which is plausibly where the swap's effect lives (evidence at rank 8 vs rank 2 changes end-to-end accuracy without changing recall@10). The gate therefore uses TWO co-primary metrics on the LongMemEval-S category set, each with the SAME procedure: retrieval recall R@10 AND nDCG@10. **A candidate wins iff it clears the procedure on EITHER metric** (FDR corrected across 6 pairwise tests total = 3 model families × 2 metrics). **Escalation rule (pre-registered, scope-verify corrected — fires when NEITHER metric clears):** if BOTH co-primary metrics stay below the bar BUT there is a directional ordering signal — ≥1 family delta positive at p<0.10 pre-FDR on EITHER co-primary metric (turn_recall@10 OR nDCG@10), or control recall ≥ 0.50 (ceiling-compressed so recall is saturated), or the top-2 candidates show large per-category gains — run an end-to-end judged check on the top-2 candidates PLUS control — 3 judged families, control always judged so the vs-control paired criterion is always computable (tools/longmem_eval runner, `--mock` OFF) BEFORE declaring NO-WINNER — the gate must not blind itself to the ordering mechanism. **Escalation PASS criterion (plan-verify P1 fix, synced): the judged top-2 run's winner clears end-to-end accuracy vs control by ≥+5% relative with one-sided paired p<0.10 pre-FDR on the same category set, else NO-WINNER; judge unavailable/non-answers → NO-WINNER.** (If nDCG@10 ALREADY clears the bar, a winner is declared on EITHER — no escalation needed.) P@5 reported as tertiary.

**Pre-burn stage-0 pilot (Devil's-Advocate fix, Phase-7 review):** before the full 12-45h burn, run a CHEAP n≈150 pilot (MiniLM control + the strongest candidate per MTEB-R, e.g. arctic-s) measuring control turn_recall@10 + nDCG@10, empirical paired-delta sd, and rough candidate delta. **Go/no-go (directional read only — at n≈150 the ±5.4pp noise band makes a +2pp delta statistically indistinguishable from null; the decision-relevant outputs are CONTROL LEVEL (ceiling check) and EMPIRICAL sd):** if control recall lands ≥ ~0.50 (ceiling-compressed) OR best candidate < +2pp absolute recall vs control (directional) → escalate to the nDCG@10/end-to-end path or declare the burn's expected value negative and close with the pilot evidence. This bounds wasted effort (the bar's +9.5% is anchored on UNMEASURED control_mean≈0.37-0.40 and sd≈0.40 back-solved quantities — published plain-retrieval baselines suggest control may be 0.5-0.65, which would shrink achievable deltas via ceiling compression).

**Primary metric measurement pipeline (pinned):**
- **Source:** LongMemEval-S split (HuggingFace `xiaowu0162/longmemeval-cleaned` — verified in tools/longmem_eval/dataset.py:36), via `tools/longmem_eval` (the ONLY harness with the temporal / multi-session / single-session / knowledge-update categories; dataset.py docstring: `single-session-user|single-session-assistant|single-session-preference|temporal-reasoning|knowledge-update|multi-session`). **Category set for the primary metric (explicit filter): questions with `question_type` starting `single-session-` OR in {temporal-reasoning, knowledge-update, multi-session}; exclude `_abs` abstention questions.** Per-category breakdowns reported secondarily by the 4 paper categories (report.py PAPER_CATEGORY). The #1144 oracle/authored query sets have NO such categories (oracle = tiers easy/medium/hard; authored = domains) — "sampled per the eval's existing oracle/authored query structure" is superseded by this pin.
- **Retrieval mode:** **vector-only arm** — NEW `vector_search()` in `tools/longmem_eval/retrieve.py` that encodes the query via `EmbeddingModel` and calls `run_vector_query(proj.g, vec, ...)` directly (via `sdk._get_proj()`, already used at retrieve.py:101) + the existing annotation path. **No `tortoise_fts_query` involvement** (it is hybrid RRF-only with no vector-only mode; a fusion flag does NOT exist). Matches the MemDelta "pure embedding swap" premise. Note: in embedded CI mode the vector arm is **unrepresentative-of-HNSW** (MiniLM IS cached in CI — see T1 CI premise), not a no-op; only meaningful in Docker-mode gate runs (live brute-force exact cosine). **Runner mode:** run via `--mock` (reader/judge bypassed) and consume ONLY `retrieval.turn_recall@k` + exported per-question outcomes (or add a named `--retrieval-only` flag).
- **Recall variant:** **turn_recall@10** as a co-primary metric (harness definition: fraction of `has_answer` evidence turns among the top-10 retrieved turns — multiple evidence turns per question possible, values fractional); nDCG@10 co-primary (order-sensitive); session_recall@10 and P@5 reported as tertiary. Per-question export exists (run.py ~:261) — required for paired deltas.
- Rationale: the trigger is LongMemEval; the bound is recall coverage; turn-level recall is the retrieval-quality surface the swap directly moves — but ranking-within-top-10 (nDCG@10) is where the ordering benefit lives, so both gate.

**Significance test (single procedure, no disjunction; applies identically to both co-primary metrics):**
- Per-candidate one-sided bootstrap p-value: p = P(mean resampled paired delta ≤ 0) over per-query paired deltas (extension of `paired_bootstrap_ci`/`paired_deltas` in tests/eval/retrieval/bootstrap.py — **~15 lines of NEW code**, expected, named here).
- **Win criterion (POWER-PRE-REGISTERED — the normative bar, supersedes the nominal +5% floor below):** candidate wins iff (a) aggregate mean beats real-MiniLM control by **≥ +5% relative** (nominal floor) AND (b) BH-FDR at q=0.10 rejects the pairwise one-sided test, on EITHER co-primary metric. **BH family = m=6 (3 candidates × 2 co-primary metrics; win on EITHER) → top-rank p threshold = q/m = 0.10/6 = 0.0167 → z ≈ 2.128.** At n≈500 with per-question sd≈0.40 (the turn_recall@10 assumption), the BH-binding effective bar is ≈ **+9.5% relative** (formula: Δ_rel ≥ z(1−q/m)·(sd/√n)/control_mean = 2.128·(0.40/√500)/0.40 ≈ 0.038/0.40 ≈ +9.5%) — **the actual pass threshold is ≈+9-10% at n≈500, NOT +5%**; +5% alone at this n gives ~16% power and cannot pass BH. **gate_1349.py derives the threshold from the actual per-question data and n** (formula: bar ≈ z(1−q/m)·sd/√n ÷ control_mean, with q=0.10, m=6), unit-tested at n=200/300/500 with the m=6 expected values (**+15.1% / +12.3% / +9.5%**) — the +9.5% is the n≈500 instantiation, NOT a constant; as n falls (--limit subset), the bar rises (n=300 ≈ +12.3%, n=200 ≈ +15.1%). **The bar is procedure-pre-registered but number-empirical — derived from the same data it tests; a mild double-dip, acknowledged in ADR-009** (mitigated by the pre-burn pilot's independent control measurement). Paired 90% CI on the delta excluding 0 is **reported as evidence but is NOT an additional gate** — the win gate is (a) AND (b) only.
- **nDCG@10 co-primary — pinned definition (scope-verify P1 fix):** the LongMemEval harness computes only binary turn/session recall (has_answer) — **the co-primary nDCG@10 is NET-NEW in T2**, defined identically to the #1144 metrics.py primitive but on the LongMemEval-S surface: gain = 1 for a retrieved turn that is a has_answer evidence turn, 0 otherwise (binary gains — the harness has no graded relevance); position discount log₂(i+2); **IDCG = ideal ranking with all evidence turns first, capped at 10** (multiple evidence turns per question supported; questions with >10 evidence turns reach IDCG@10 = Σ_{i=0..9} 1/log₂(i+2) ≈ 4.54 — the earlier "≈3.82" was the k=8 partial sum, corrected second-model-gate P2 — and can still reach nDCG@10 = 1.0 — the pair is complementary: turn_recall@10 ceiling-compresses there, nDCG@10 does not); **questions with ZERO evidence turns → nDCG@10 = 0.0 (matching the harness turn_recall report default), included in the mean**; nDCG@10 = DCG/IDCG per question, aggregated by mean. Computation site: T2's vector arm emits per-question ranked hit ids + evidence-turn matches (same annotation pipeline as turn_recall@10) → nDCG@10 computed alongside in the per-question export; unit-tested against hand-computed cases incl. a zero-evidence-turn case in test_vector_arm.py.
- **Multiple comparisons:** 3 candidates (arctic-xs, arctic-s, bge-small-en-v1.5) vs 1 control (MiniLM) × 2 co-primary metrics = **6 pairwise tests**. BH at q=0.10 across 6 tests (top-rank p threshold 0.0167; z≈2.128).
- Power note (superseded by the win-criterion pre-registration above — the +8-9% figures below are STALE m=3-era arithmetic; the operative m=6 bars are +9.5%/+12.3%/+15.1% at n=500/300/200): the eval README's power math covers P@10 at n=100, NOT relative R@10 on the LongMemEval subset — the pre-registered m=6 effective bar and its n-scaling formula are the operative thresholds; the insufficient-power outcome is the backstop for degenerate/low-n runs. **Planning instantiation assumptions:** per-question sd≈0.40 used as a proxy for the paired-delta sd; control_mean ≈ 0.37-0.40 implied by the +9.5% range (m=6); gate_1349.py computes the bar from the EMPIRICAL paired deltas and n (these are planning numbers only, not execution constraints).

**Secondary gates:**
- E2E-8 latency verdict ≤300ms p95 (achieved band, benchmarks/run_report.py — the `benchmarks` E2E-8, disambiguated from the tests/test_backfill_sources.py E2E-8 contract); hosted feasibility (candidate loads + pre-warms on the 2GB VM class within the existing 30s-300s cold-start window, image size documented); sentence-transformers `>=3,<6` pin compat per candidate.

**Encode protocol (pre-committed, cycle-3 corrected; cycle-5 coherence-corrected):** benchmark candidates in the config that reflects their real deployment, not a uniform handicap. **Per-candidate vendor-aware encode for the gate runs:** bge-small-en-v1.5 / MiniLM — no prefix (v1.5's designed instruction-free mode; MiniLM has no prefix concept); **snowflake arctic-xs/arctic-s — run in BOTH no-prefix AND vendor config (`prompt_name="query"`, query-side prefix, documents plain) as part of T8** (one extra encode pass per arctic model — removes the systematic false-negative risk of measuring arctic below its vendor config). The gate compares each candidate in its best-validated config; the swap lands in the config that measured best. Cross-lens matching stays plain (same single model, prefix applied query-side in the search path only, mirroring mem0's query/doc prefix tagging). This supersedes the earlier "uniform no-prefix with documented arctic penalty + conditional re-validation" framing — the arctic re-validation is now UNCONDITIONAL (both configs measured in T8, not only-if-arctic-wins).

**Outcomes:**
- **Insufficient power:** if the real-model baseline leaves no headroom (near-ceiling R@10 on the LongMemEval subset) or CIs straddle the bar → **judgment tiebreak (pre-registered, Phase-7 fix — not an indefinite deferral on a pre-launch product):** decide via mini-BEIR OOD datasets + labeled-pair calibration + nDCG@10, documented explicitly as judgment-based. **Degenerate baseline:** if control mean turn_recall@10 < 0.05, the relative-delta win criterion is ill-defined (division by ~0) → absolute-delta fallback fires only if a candidate clears absolute turn_recall@10 ≥ 0.30.
- **No winner:** no candidate beats control ≥Δ with FDR-clean CIs on either co-primary → **no swap** with the negative evidence attached. **Re-file destination (Epic-Alignment fix, Phase-7): non-embedder levers (key-expansion, time-aware query expansion, fusion-fix) are filed UNCONDITIONALLY as a NEW retrieval-optimization research issue — NOT to #317** (which is the cross-encoder RERANKING slice only, and its own close-criterion (e) mandates filing retrieval-recall fixes as a separate issue; first-stage levers must not couple to #317's gate). "No swap" and "embedder-bound → re-scope" are distinct outcomes; both named.
- **Multi-winner tie-break:** if >1 candidate clears (a)+(b), land argmax aggregate (turn_recall@10 + nDCG@10 combined rank); ties broken by lower E2E-8 latency, then smaller image size, then family-preserving (arctic-xs vs MiniLM encoder-space proximity — hypothesis-level, final tiebreak only).
- **Vendor-config re-validation:** if an arctic winner's best config (measured in T8) does not itself clear (a)+(b) vs control, keep the config that cleared the gate, else no-swap + re-file the levers issue.
- **BH-FDR validity note:** 6 one-sided tests vs a common control are positively dependent; BH validity requires PRDS, which plausibly holds for one-sided tests against a common control — asserted, and the gate's unit tests include a dependent-deltas case.
- **Abstention exclusion note (Phase-7 fix):** excluding `_abs` questions lowers n below 500 → the bar rises accordingly (formula is n-adaptive, m=6); per-category breakdowns at n≈80-150 are DIRECTIONAL-ONLY in the decision record (bar ≈ +17-24% there at z=2.128, sd=control=0.40 — no narrative over-reading of per-category deltas).
- **Ingest-encode note:** per-encode latency measured and reported on query + add paths (compute_embedding, sdk.py:1418) but NOT a hard gate — E2E-8 is the gate; corpus re-embed is a one-time batch cost.

**Precision@10 secondary (Epic-Alignment fix, Phase-7):** P@10 is added as a named secondary so the swap verdict is comparable to parent #317's precision@10 gate vocabulary (the swap moves recall/ranking; precision may move differently — report, don't gate).

**Ordering vs #317 (Epic-Alignment fix, Phase-7):** if the swap PASSES, it lands BEFORE #317's gate-evidence production — the embedder moves first-stage ranks, so #317's cross-encoder-vs-RRF delta must be measured on the post-swap first stage. Both consume the 300ms budget (swap ≈ +3-5ms encode; #317 CE ≈ +210ms/top-10 CPU — confirmed incompatible with the band unless GPU/API-served; #317's own decision gate already blocks on latency).

## Why This Framing (evidence)

1. **The swap lever is real but bounded** — MemDelta (arXiv:2606.29914): pure embedding swap = +6.2pp LongMemEval-S (p=0.004), largest on temporal (+10.5pp) and multi-session (+11.3pp) — the issue's target categories. ⚠️ single-source preprint. Tortoise stores verbatim turns → write-side gap structurally small → retrieval-side dominant.
2. **The mechanism is misattributed** — arctic-xs (22M, fine-tuned FROM MiniLM) scores 50.15 MTEB-R vs MiniLM 41.95 = **+8.2 at identical size** — the gain is training data (hard-negative mining), not parameters. An open candidate pool is required, not a blind bge-small swap.
3. **The gates are unmeasurable as written** — verified: `baseline-embedded-2026-08-17.json` provenance = `synthetic_query_vectors: True`, `indexes.vector: False` (brute-force, redislite). The vector arm 0.8546 nDCG@10 is model-independent near-ceiling. Docker mode with real model is runnable (run.py:210-226 auto-uses EmbeddingModel; projection recomputes on write) — real baseline is step 0.
4. **Hosted-vs-local resolves as a constraint, not a blocker** — mem0 hosted = server-side baked ("We serve the model ourselves"); Zep removed its bundled local embedding service in CE; LangMem/Letta server-side. Tortoise's current bake already matches the industry hosted answer and is MORE local than mem0's default (no external embedding API call). **Tier-partitioned:** #265 (encryption epic) is **PENDING-MERGE, NOT SHIPPED** (verified: zero `encryptionVersion` hits in tortoise/ code — it is a scoping artifact with its client-embedding path listed "pending merge" and the model-version pin as a P2 design item). Its proposed design pins client embeddings to MiniLM/384 for `encryptionVersion>=1` teams. The open question is only the DEFAULT tier → user product call at the T7→T8 gate.
5. **Cross-issue constraint (#265 encrypted tier) — STATUS-CORRECTED (coherence check):** the 384-dim scope restriction is a **CHOSEN scope cut, not a forced shipped constraint** — #265 has not shipped, so there is no in-code dimension pin today. The restriction rests on: (a) the pending #265 design (encrypted teams would ship client-computed 384-dim MiniLM vectors into a shared index — if that lands before/around a swap, staying 384-dim avoids a coordinated dimension migration); (b) the 2GB VM feasibility budget (768/1024-dim candidates are materially heavier); (c) single `Point.embedding` index dimension-fixedness (any dim change = full re-embed + index rebuild event). **Escape clause (pre-registered): if #265 lands at a different dimension before PR2, the 768/1024 pool reopens** (falsification check below). **Semantic-space note:** dimension equality ≠ encoder-space compatibility — if default and encrypted tenants share a DB/namespace, a non-MiniLM-family server encoder mixes two distributions in one index. "Family-preserving" (arctic-xs fine-tuned FROM MiniLM) is a HYPOTHESIS, not a verified guarantee — treat as a tiebreak consideration, not a ranked preference.
6. **Latency is a real gate, correctly defined** — verdict-band rule (user-confirmed): E2E-8 ≤300ms p95; bge-small's ~1.7-2× encode slowdown is E2E-8-immaterial (≈3-5ms on the query path).

## Falsification Check

This definition is wrong if:
- All candidates ≈ MiniLM within noise on the real baseline (mini-BEIR + hard tier + LongMemEval R@10) → verdict flips to keep-MiniLM + **re-file non-embedder levers as a NEW retrieval-optimization research issue (NOT #317 — see OUT)**.
- E2E-8 p95 > 300ms post-swap → verdict band vetoes the swap.
- MemDelta replication on tortoise's actual pipeline shows the retrieval gap is NOT embedding-bound (recall coverage/reading dominates) → the benchmark still produces negative evidence and redirects.
- The user product-calls hosted-vs-local differently (hosted customers must embed locally as a differentiator) → the candidate class changes entirely (configurable/local embedding support) and the swap becomes moot until architecture resolves.
- #265 encrypted tier ships a dimension change → shared-index constraint dissolves and the 768/1024 pool reopens.

**Confidence: 80.**
