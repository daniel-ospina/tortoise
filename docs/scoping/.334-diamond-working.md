### Axis Research (drafted)
> **Findings-date:** 2026-08-13. Queries: 5 fresh (exa MCP) post-dedup — orphan/dangling-edge cleanup (canonical), BP correctness (canonical/pitfalls), W3C PROV (canonical), one-shot-vs-guardrails (pitfalls/adversarial), stub-relevance counter-evidence (disconfirming). **Axis: Ontology/Provenance (sourceKind, sourceDate) — rated high**
- canonical: W3C PROV-DM (w3.org/TR/prov-dm): provenance is the record for trust judgments; attribution is critical; provenance-of-provenance (bundles); decision justifications must be backed by evidence collected via well-defined procedure. → Tortoise's extractedFrom layered provenance + sourceKind TYPE vocabulary + credibilityTier inheritance aligns with PROV; remediation = completing the attribution record, not creating new vocabulary.
- competitor-precedent: Graphiti temporal-KG memory (arXiv:2501.13956, cited in CRITICAL comment + n26modi head-to-head: staleness 87%→20%, historical-belief 60%→100%) — temporal KG memory beats vector-summary; provenance/event-sourcing is the pattern. (Prior research — deduped, not re-queried.)
- pitfalls: DataAIHub KG best-practices guide (dataaihub.co/learn/knowledge-graph-best-practices): "No provenance = cannot debug or audit — add sourceSystem/assertedAt from day one"; "data quality decay without validation at ingest"; provenance + quality gates (CI-gated SHACL, weekly orphan-rate/validation-failure-rate metrics) are the sustained practice. → one-shot annotation without a measured baseline regresses.

**Axis: Architecture (orphan/dangling-edge cleanup) — rated high**
- canonical: Koza graph operations clean-graph guide (koza.monarchinitiative.org/graph-operations/how-to/clean-graph/): dangling edges = edges referencing non-existent nodes (ID mismatches, filtered subsets, incomplete overlap); prune moves them to archive table, NOT delete; verify 0 dangling edges after prune; keep-vs-remove singletons is a judgment call. → Tortoise stub auto-creation is the ID-mismatch class; remediation should archive/mark stubs non-destructively before removal, with a verify-0 query.
- pitfalls: SchemaApp orphan-node analysis (support.schemaapp.com): orphan nodes weaken analytics (importance/similarity); 3 actions per orphan: CONNECT (valid+useful), FIX (incorrectly modeled), REMOVE (no purpose) + "prevent it from being recreated in the future" — the prevention half is the part one-shot migrations skip.

**Axis: Architecture (confidence/BP correctness) — rated high**
- canonical/pitfalls: Weiss & Freeman 1999 (NeurIPS, "Correctness of Belief Propagation in Gaussian Graphical Models"): loopy BP on cyclic graphs — means may be correct but variances/confidence may be INCORRECT (overconfident); single-loop/dense correlations → worse confidence. Ihler et al. 2005 (JMLR, "Loopy Belief Propagation: Convergence and Effects of Message Errors"): loopy BP not guaranteed to converge; fixed points may be non-unique; message errors accumulate. → Tortoise EP runs on a LOOPY factor graph (damping=0.5 exists in ep.py for this reason): expectation is approximate confidence, and the plan must not over-claim exactness; verification = convergence + stability checks, not ground-truth belief.
- precedent (in-repo, deduped): ep.py damping/quadrature/draft-filter (#780) + 12 test_ep_* files = the engine's known failure modes are already encoded.
- **counter-evidence (disconfirming, adversarial framing):** ISSI 2011 (citation networks, issi-society.org proceedings): deleting/lumping dangling nodes had only LOCAL impact on non-dangling node PageRank (Spearman 0.987-0.99 vs original; null hypothesis retained) — BUT those dangling nodes were aging publications with information value; Tortoise stubs carry NO information (`[missing]`), so deletion is safe where citation-network deletion lost data. Choi et al. 2006 (AAAI, "An Edge Deletion Semantics for Belief Propagation"): BP = exact inference on a polytree from edge deletion; recovering LOW-MUTUAL-INFORMATION edges not worthwhile (complexity without quality gain) → stub-adjacent edges are low-MI; removal should not degrade approximation quality. **Verdict: cleanup's value is primarily graph-as-memory queryability + stopping garbage propagation, NOT guaranteed confidence shift — the falsification check must treat confidence-shift as ONE signal, not the sole signal.**

**Axis: Migration execution (one-shot vs guardrails) — rated high (adversarial framing)**
- pitfalls: Dataconomy "Treat every data migration like it will go wrong" (dataconomy.com/2026/05/25): dry-run by default; idempotent marker tags so scripts are safe to re-run; EVERY import gets a paired verification script; migration log line per apply. GitLab 2017 incident: quiet corruption with no verification.
- pitfalls: DataSemantics "Why data migrations still fail": "clean the data first doesn't work if governance isn't enforced"; define post-migration KPIs + 30/60/90-day check-ins.
- pitfalls: Datachecks (datachecks.io/posts/why-scripts-fail-in-complex-data-migrations): 80% of migrations fail; scripts lack lineage/rollback; continuous validation required. Stackable: pre-migration baseline audit, continuous validation, post-migration reconciliation, "migration endpoint is the start of ongoing operational responsibility". → #334's plan MUST include: pre-migration baseline snapshot (backup + counts), dry-run default, idempotent migration scripts, paired verification queries, and a recurrence guardrail (re-run audit as gate) — otherwise it repeats the exact failure mode that produced the current corruption.
