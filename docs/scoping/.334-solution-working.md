# #334 Solution Diamond — Working Notes (for verifier gates)

## CONFIRMED PROBLEM (from Phase 2, post-verify)
The Tortoise work graph (FalkorDB port 6379) violates its own wiring contract, breaking graph-as-memory guarantees: (a) orphan stub Points (content='[missing]', auto-created by `_create_edges` short-ID stub mechanism #329/#6713) carry dead IMPL/NAND edges from real operators → EP propagates confidence through garbage, Point-FTS surfaces stubs; plus cap-skip class (500-stub cap silently skips edges — partial under-propagation) and Subject-stub class (`_create_about_edges`, subjectKind='other'); (b) work-graph evidence lacks extractedFrom→Source backing (cycle-written evidence stores provenanceSource STRING only) and sourceKind presence is confidence-neutral (registry/credibilityTier/extractedFrom are the real levers); (c) no verified reproducible EP pass under current ep.py engine (legacy deliberate runs exist but no baseline+stability record). **#334 = one-shot data-correctness remediation of the live graph with 8 explicit exit criteria (0 stubs, cap-skip + degenerate-operator remediation, resolved non-neutral tier % with pre-committed persisted registry policy, extractedFrom backing %, EP verified pass with restore-and-re-run determinism, idempotent recurrence guardrail + documented residual hand-off to #348, mitigation backfill count, Subject-stub decision). #348 = tooling+annotation product (audit CLI, skill-enforcer); #903 = ongoing EP; #395/#901 = EP subgraph semantics. Boundary verified by 2 verifier cycles.**

## PHASE 4 — SOLUTION-DIVERGE (3 distinct approaches)

### Approach A — One-shot remediation migration scripts (graph-scripts/ style)
- Description: Migration scripts following graph-scripts/ conventions (pre_migration_snapshot.py pattern, backup-first, dry-run default, idempotent tagged rows): (1) baseline scan (stubs, cap-skip, Subject stubs, Source-tier, extractedFrom, draft/live distribution), (2) DETACH DELETE stubs + incident edges + degenerate-operator pass (<2-input ops superseded/backfilled), (3) extractedFrom/credibilityTier backfill per pre-committed registry policy (persisted config YAML or graph node), (4) EP verified pass (snapshot → run → restore → re-run → compare), (5) verification report vs exit criteria.
- Files touched: graph-scripts/ (new scripts), registry policy config, backup. No SDK changes except optional Source-level audit helper.
- Risks: one-shot scripts drift again (the failure mode that produced the corruption — Dataconomy/Datachecks research); no durable measurement without #348 audit CLI.
- Tradeoffs: fast, focused, reversible (backup); recurrence risk until #348 lands.
- Best fit if: exit criteria must be met NOW on the live graph; #348 timeline uncertain.

### Approach B — SDK-level enforcement + continuous guardrails (engine changes)
- Description: Change write paths: fail-closed on short-ID stub auto-creation (raise instead of create stub), provenance requirements on create_operator/create_point, expose audit CLI, Source-level audit variant in audit.py. Graph heals over time via #903/ongoing cycles.
- Files touched: tortoise/projection/edges.py (stub policy), tortoise/sdk.py (write validation), tortoise/audit.py (Source-level variant + CLI), tortoise/__main__.py.
- Risks: this IS #348's charter (audit CLI, skill-enforcer) + engine-semantics risk (changing stub behavior may break connectors/scripted cycles mid-flight; 'archived'-status changes rejected as graph-wide); does NOT clean the existing 94+ stubs by itself.
- Tradeoffs: root-cause, durable prevention; heavy, overlaps #348, doesn't remediate existing data.
- Best fit if: #334 and #348 were merged (they're NOT — boundary decided split by concern and verified).

### Approach C — Audit-driven incremental cleanup (fix what audit flags, batch by batch)
- Description: Build the Source-level audit variant FIRST (verification instrument), enumerate issues, remediate in small verified batches (10-20 issues/cycle), re-run audit after each batch as the gate. Same pattern as #348's review-status scripted context cycles but with a durable instrument.
- Files touched: tortoise/audit.py (Source-level variant), graph-scripts/ (batch remediation), verification queries.
- Risks: slower for bulk classes (94 stubs is a single batch anyway); audit stays script-internal without CLI exposure.
- Tradeoffs: measured, self-gating; slower, and the audit instrument must be #334-owned per boundary decision (Source-level variant is #334's verification instrument, NOT deferred to #348).
- Best fit if: verification-first mindset; risk-averse to large one-shot scripts.

## PHASE 5 — SOLUTION-CONVERGE

### Chosen: A+C hybrid — "audit-gated one-shot remediation migration"
- Execution vehicle = A (one-shot migration scripts, backup-first, dry-run, idempotent), gating = C (Source-level audit variant built first as the verification instrument; each remediation phase re-runs the audit/verification queries as its gate; exit criteria 1-8 verified by #334-owned queries). NOT B (SDK enforcement = #348 Phase 3 + engine semantics; boundary already decided; enforcement without cleanup leaves current corruption in place).

### Why this approach (quality over convenience)
- Outcome quality: measurable exit criteria (not a migration that "reports success"), idempotent + re-runnable (Dataconomy), docker-aware RDB snapshot + verified restore (not a vacuous "backup"), degenerate-operator pass with reviewed artifact, restore-and-re-run EP determinism with seeded RNG + full-state restore (not vacuous self-consistency), registry policy pre-committed + persisted (not process-state-dependent), residual hand-off + risk-acceptance documented for #348 (not an unattainable recurrence guarantee), identity-validated backfill (no stub-Source manufacturing).
- Failure-mode coverage: cap-skip class with non-escape floor (UNVERIFIABLE blocks close), Subject-stub class decided, event-log normalization with owner/default, #903 quiescence + #395/#901 non-conflict, write-quiescence for ALL writers during destructive phases, mitigation count (criterion 7), stub-Source detector.
- Future extensibility: Source-level audit variant (home: graph-scripts/) is a natural precursor to #348's audit CLI (boundary: #334 owns the variant as its verification instrument; #348 ships it as product).
- Distinctness note (from verify): the surviving distinction between A and C is INSTRUMENT-FIRST GATING, not batch granularity (the batch axis was never a real alternative for the bulk classes — 94 stubs is a single batch); the hybrid = A's execution vehicle with C's instrument-first gating promoted to a first-class phase.
- Rejected: B — would have been better IF #334+#348 were merged (they're not) or if corruption were actively flowing (no evidence — legacy from cross-file wiring scripts); NOT adopted as a minimal guardrail because a mid-migration write-path change races the cleanup — documented as contingency in risk-acceptance (exit 6c). Pure A — faster but repeats unmeasured-migration failure mode. Pure C — fine execution rhythm but bulk classes need the one-shot migration.
