# #3025 — the OAuth token mint is ONE transaction

**Level:** task · **Complexity:** complex · **Lane:** c5-9-mcp-sdk · **P2**

## Problem

`tortoise/oauth.py::_issue_tokens` reaches the control plane as a *sequence* of
independent PostgREST calls, and every `cp.query` is its own HTTP request = its own
transaction (`tortoise/supabase_control.py` `query`/`rpc`). A successful
authorization-code exchange is **4 sequential writes across 3 tables**:

| # | write | table |
|---|-------|-------|
| 1 | claim (`used_at`, `redemption_state='claimed'`) | `oauth_codes` |
| 2 | INSERT refresh | `oauth_refresh_tokens` |
| 3 | INSERT access | `oauth_access_tokens` |
| 4 | settle (`redemption_state='minted'`) | `oauth_codes` |

A failure between them leaves partial state: a live orphan refresh row with the code
burned; two live token families; or a live-but-undelivered pair whose presented
refresh token is already revoked.

**\#2863 answered this with an in-process compensation protocol** (`_rollback_minted` /
`_mint_observably_clean` / `_restore_code` / `OAuthMintAborted.recovered`). That is
explicitly NOT atomicity: the compensation runs against the same control plane that
just failed, so a compensation failure reproduces the partial state. Migration
`20260925000002_oauth_redemption_state.sql` (#3027) added the durable state machine and
the reconciler and said, verbatim, that #2863's in-process confirmation is

> "deliberately NOT removed here … the removal is a follow-up step once the state
> machine is proven."

**#3025 is that follow-up step.**

## Premise check (current `main`, 2026-10-12, base `5fb41c7d5`)

- Holds. `oauth.py` contains **zero `cp.rpc` calls**; all 31 control-plane calls are
  `cp.query`. No `redeem_oauth_code` / `rotate_oauth_refresh` function exists in any
  migration. `_issue_tokens` still performs the 4-step sequence above.
- The issue's own Out-of-scope paragraph ("response-delivery loss … filed separately")
  is now **fulfilled** by #3027 (migration `20260925000002`, the `redemption_state`
  machine, `_settle_redemption`'s delivery gate, `_reconcile_claimed_redemption`).

## Scope boundary (corrects the issue's literal Target bullet)

The Target's `#2863's compensation paths removed` is read as **#2863's in-process
rollback/restore/observability protocol**, NOT the whole `redemption_state` cluster.
The cluster splits in two:

| Cluster | Origin | Under #3025 |
|---|---|---|
| `_issue_tokens`, `_consume_code`, `_restore_code`, `_mint_observably_clean`, `OAuthMintAborted`, the `try/except` + observe/restore lanes inside `exchange_auth_code` | #2863 | **DELETED** — the transaction removes the window they compensate for |
| `_settle_redemption` (delivery gate), `_observe_code`, `_reconcile_claimed_redemption`, `_live_family_for_code`, `_rollback_minted`, the `redemption_state` machine | **#3027** | **KEPT** — a committed-then-lost response is still possible, and a transaction cannot fix it. `_rollback_minted` acquires a second caller: the lost-settle compensator in `exchange_auth_code` |
| `_redeem_code_rpc`, `_rotate_refresh_rpc`, `_new_pair_material`, `_token_response`, `_refuse_observed_code`, `_consume_state`, `_prev_refresh_unclaimed` | **#3025** | **NEW** — the RPC wrappers, the failure classifier (read-only), and the burn path |

Keeping #3027 is required by *this issue's own* Out-of-scope paragraph.

**And the machine does NOT shrink.** A new `claimed` window survives the transaction: the
RPC commits the claim AND the pair, then Python records delivery via
`_settle_redemption`. If the process dies between those two, the code is `claimed` with a
live, never-delivered family — exactly what the reconciler exists to resolve. So
`REDEMPTION_CLAIMED` stays load-bearing and the state machine is unchanged.

## Design

Validation of the code row stays in **Python** (the row's client/redirect/challenge/scope
fields are immutable after `issue_auth_code` writes them, so a read-then-act on them
carries no TOCTOU); the **claim CAS moves into the RPC**, so the claim and the two token
INSERTs are one transaction.

```text
exchange_auth_code
  read code row        → _observe_code (READ-ONLY, full field set)
  classify/validate    → client, redirect_uri, PKCE, resource, org usable, scope
  cp.rpc_value(redeem_oauth_code, …)
                         ├─ CAS-claim the code (`used_at IS NULL AND state='unclaimed'
                         │   AND expires_at > now`) + INSERT refresh + INSERT access
                         └─ returns {'status': 'minted' | 'not_claimable'}
  _settle_redemption   → #3027 delivery gate (unchanged; the only remaining
                         post-commit write, and it is a STATE record, not a mint)
```

`refresh_grant` is the same shape with `rotate_oauth_refresh`: claim the presented
refresh token (`WHERE revoked_at IS NULL`), INSERT the new pair, revoke the previous
access row(s) — one transaction. A zero-row claim returns `not_claimable` and **nothing
was written**, so the "concurrent rotator already claimed it" loser no longer needs an
orphan pair rolled back.

**Failure classification** (the #2863 replacement) is READ-ONLY:

- RPC raised → nothing observable about the transaction: probe with `_observe_code` /
  `_prev_refresh_unclaimed`; `unclaimed` / still-unrevoked ⇒ retryable 503; otherwise
  terminal `invalid_grant`. A retryable signal is only ever emitted on an OBSERVED-clean
  state, never on an unobserved write.
- `_settle_redemption` lost its CAS (a reconciler owns the claim) ⇒ compensate the pair
  with `_rollback_minted` and report terminal — the pair must not be delivered.

## Acceptance

- [ ] New migration: `redeem_oauth_code`, `rotate_oauth_refresh` (one transaction each).
- [ ] `oauth.py` calls them via `cp.rpc_value`; the hand-rolled sequences are gone.
      (README-in-plan: `rpc_value` — NOT `rpc` — because `rpc` sends
      `Prefer: return=minimal`, under which PostgREST does not echo a VOLATILE
      SECURITY DEFINER body. See the Rejected-alternatives row: reading the
      envelope through `rpc` is the P0 that returns `None` in production while
      passing the whole suite.)
- [ ] `FakeControlPlane.rpc` emulates both atomically over the in-memory rows.
- [ ] Real-SQL test (PGlite, the repo's existing real-DB harness) proving a mid-function
      failure leaves ZERO rows and an unset `used_at`.
- [ ] #2863's in-process rollback/restore protocol removed.

## Rejected alternatives

Three forks were live at solution-converge. The chosen one is not the issue body's
first phrasing re-stated — the body prescribed "a `redeem_oauth_code` … and a
`rotate_oauth_refresh`", and that survived comparison, but only after the other two
were priced.

| Alternative | Why it was rejected |
|---|---|
| **One unified `settle_oauth_redemption` RPC** that takes a `kind` ('code' \| 'refresh') and branches inside | Rejected. The two grants claim DIFFERENT rows with different predicates (`used_at IS NULL AND state='unclaimed'` vs `revoked_at IS NULL`), insert different provenance (`code_id` inherited vs bound), and the rotation additionally revokes the previous family's access rows. A single function would carry both branches and both failure taxonomies in one body, so a change to the code grant's CAS could redden the refresh grant's tests and vice versa. Two functions make each transaction's blast radius reviewable in isolation, and the duplication is ~15 lines of INSERT column lists. |
| **Keep the claim in Python and only move the two INSERTs into SQL** | Rejected — it does not meet the acceptance criteria. The orphan-live-refresh-row window (code burned, refresh row live) is created by the gap between the claim PATCH and the refresh INSERT, so a transaction spanning only the two INSERTs leaves the issue's first measured failure mode intact. |
| **Move the whole validation (PKCE, redirect_uri, resource) into the RPC too** | Rejected. It would put a hash comparison and a resource-indicator parser into PL/pgSQL — logic that is already unit-tested in Python and whose SQL port would be a second, untested implementation. It buys nothing: the validated fields (`client_id`, `redirect_uri`, `code_challenge`, `scope`) are written once by `issue_auth_code` and never updated, so the read-then-act carries no TOCTOU to close. Validation can stay optimistic in Python because the RPC's CAS is what makes the mint single-use. |
| **`cp.rpc(...)` and read the envelope (the first draft)** | Rejected during review — and this is the one that would have shipped a production break. `cp.rpc` sends `Prefer: return=minimal`, and PostgREST does not echo a VOLATILE SECURITY DEFINER function's body under it (the repo's own measured precedent: `resolve_signup_token`, `metering_increment`). Reading the envelope through `cp.rpc` returns `None` in production while passing the whole suite, because the double echoed it. Both calls go through `cp.rpc_value` (representation), AND an unreadable envelope is treated as outcome-UNKNOWN (raise → the read-only probe decides) rather than asserted as `not_claimable`; the double now models the transport so the class cannot recur. |

## Out of scope

- Response-delivery loss after a successful commit (needs a redemption/idempotency state;
  #3027 supplies it, and a transaction cannot).
- Collapsing `REDEMPTION_CLAIMED` (see above: it is still reachable).
