# Scope — #9192: the record's tenant has no production caller, and the only reachable arming path is process-global

Status: scoping (double diamond, standard tier). Claim map measured at `origin/main@f80c522a1` on 2026-10-20; the "before" runs below re-measured at `origin/main@f3b0f26a0` (main advanced during the lane; same result).

## Phase 0 — the claim, verified before anything was designed

The issue's claim is *"the tenant ContextVar has no production caller"*. It holds. Measured:

| surface | site | production? |
|---|---|---|
| definition | `tortoise/record_writer.py:376-378` `_RECORD_TENANT: ContextVar[tuple[str,str] | None]` (default `None`) | — |
| setter | `record_writer.py:382` `use_record_tenant(org_id, graph_id)` — context manager, `set`/`reset` | **no production caller.** All **10** call sites are in `tests/test_9078_record_written_by_production_path.py`; `tests/test_record_projection.py` mentions the symbol only in prose (`:1856`, `:1902`). Outside `tests/`, `git grep -n 'use_record_tenant('` matches only the `def` line (`record_writer.py:382`), two docstrings (`record_projection.py:105`, `monitoring.py:1325`) and one warning string (`record_writer.py:762`). |
| reader (scope only) | `record_writer.py:404` `current_record_tenant()` | no production caller |
| reader (resolver) | `record_writer.py:420` `record_tenant()` → scope, else `TORTOISE_RECORD_ORG_ID`/`_GRAPH_ID`, else `None` | **one** production read site: `record_writer.py:756` inside `write_live_record` |

The record's write path therefore resolves tenant identity as: request scope (never set) → **process-global env pair** → `None` ⇒ `no_tenant` refusal (counted on `monitoring.metrics()["record_write_failures"]`, warned, no row). It never guesses, which is the good half. The bad half is that the env pair *is* a successful arming path and env is process-global.

Who writes records today (after #9231, merged): three doors, `TortoiseSDK._emit_event`, `EventAPI._emit`, `ConversationMiner._emit_event`, each calling `record_writer.write_live_record(record, durable=…)`. In the hosted lane the only door that actually fires is the SDK one (`capture_session`). So a hosted deployment that sets the DSN **and** the env pair files every tenant's rows under one `(org_id, graph_id)`: a well-formed row, an FK that only checks the graph exists, no error.

⇒ the hazard is **reachable**, not hypothetical: nothing in this repository arms it today (`git grep -E 'TORTOISE_RECORD_(DSN|ORG_ID|GRAPH_ID)'` outside `*.py`/`docs/` hits only the commented-out `.env.example` block and one comment in `config/ci-surfaces.yml`), so it is one DSN plus one pair away from live in any process that serves more than one org — and it is silent when it fires. **While the caller is missing the misfile cannot be avoided** (the env pair is then the only arming path); wiring the caller makes it avoidable, and wiring it *alone* still leaves the pair reachable outside any request scope. The damage is not one mislabelled row: `record_projection._identity_statement` writes `public.node_identity` "first, always" with the same pair, so tenant B's node keys are minted inside tenant A's graph and a later legitimate tenant-A write for the same `(label, key)` merges onto them. Closing only the caller (ask 1) leaves the env pair as a one-flag cross-tenant write; closing only the env hazard (this lane) leaves the record refusing until the caller lands. Both are needed; ask 1 is owned by **#9188** (its own body lists *"Arming + DSN for the hosted deployment … and whether hosted and self-host differ"* and its components are `tortoise/sdk.py`), and this issue's own triage comment moved it there. Duplicating it here is the #3061 collision class, so this lane takes ask 2's second half and adds the production caller where #9188 does not reach: **the MCP lane's per-request tenancy chokepoint**.

## Phase 1 — problem-diverge (framings)

- **F1 (issue's framing):** "no production caller" — true, but the caller is #9188's work.
- **F2:** "the tenant is ambient when it must be per-request" — the real defect class: a *process-global* value standing in for a *per-request* fact. This is what makes the multi-tenant misfile possible and it survives any caller wiring.
- **F3:** "the record accepts a tenant it cannot verify" — true but not actionable: the record's `graph_id` is a `public.graphs` row id, unknowable from inside the fold; verification has to live where tenancy is resolved.

**Confirmed problem (F2).** The record's tenant identity is resolved from a carrier that a multi-tenant process cannot use correctly, and nothing installs the per-request carrier at the place tenancy is already resolved. Symptom: cross-tenant rows, no error.

## Phase 2 — solution-diverge (alternatives, and why each was rejected)

- **A — request scope at the tenancy chokepoint + process-global arming only on explicit single-tenant declaration.** ← chosen.
- **B — explicit `tenant=` argument on `write_live_record`, passed by each door.** Rejected: two of the three doors (`EventAPI._emit`, `ConversationMiner._emit_event`) have no control-plane handle at all — they hold a graph handle, not `(org_id, graph_id)`. Threading ids to them means changing `EventAPI`'s constructor and the SDK's, i.e. a public SDK signature change, which is an owner decision and is #9188's to make.
- **C — validate the env tenant against the graph handle's namespace prefix** (`org_{org_id}…`). Rejected: embedded/self-host graphs are named arbitrarily (`tortoise`, `my_graph`, `test_*`), so the check false-blocks the legitimate single-tenant path the env pair exists for (`#9078` scope decision 3), and it is a check-at-use rather than removal of the ambient path.
- **D — the multi-tenant app declares itself by being imported** (a module-level flag flipped by `hosted_api`/`mcp_server`). Rejected: import-order-dependent, and it contaminates a pytest process for every env-arming test (every test module is imported at collection time), making behaviour depend on collection order.
- **F — carry `(org_id, graph_id)` on the graph handle / `EventAPI` instance** (stamped where the MCP chokepoint already knows all three) so a misattribution is structurally impossible rather than refused. Rejected for the same reason as B and named for completeness: it needs `EventAPI.__init__` (`api.py:36`) and/or `TortoiseSDK.__init__` to change, and the doors hold a graph handle, not the control-plane uuid the record keys on.
- **E — delete the env fallback; scope-only tenancy.** Rejected here: it reverses `#9078` scope decision 3 (an owner decision recorded in `record_writer`'s module docstring), which is a *reopen*, not a lane decision. It is the right long-term shape if the owner wants one way to name a tenant; that argument belongs on `#9078`, not in this PR.

## Phase 3 — solution-converge (the decision)

**Where the tenant identity is established: at the tenancy chokepoint that already resolves it per request, not at each write door and not in the middleware that only sees bytes.**

`tortoise/mcp_auth.py::OrgResolutionMiddleware.dispatch` is the ONE place every authenticated MCP request resolves `(org_id, graph_id, graph_namespace, scopes)` into ContextVars (`mcp_auth.py:918-931`) — the same pattern the #2600 actor uses. The record tenant rides that: a `with record_writer.use_record_tenant(org_id, graph_id)` around `call_next`, so

- it is installed once for every tool on the surface — a new tool cannot forget it (contrast: a per-endpoint dependency, which the next endpoint forgets);
- it is request-scoped, so it cannot leak into the next request on the same connection, and it nests;
- it survives the lane's thread hops for free: `call_next` runs downstream work in a **copied** context, and the repo's own offload seam (`hosted_api._submit_off_loop`) copies the context at submit — so a capture that runs on a pool worker still sees the request's tenant.

**Installed only where a graph is NAMED** — `use_record_tenant` raises on an empty id (`record_writer.py:382-395`), so the installer guards: a non-empty `(org_id, graph_id)` ⇒ the scope; otherwise nothing is installed and the armed write refuses. An org-wide credential's request therefore completes normally (no 500) and files no record — pinned.

**And only where the ids are CONTROL-PLANE ids** (round-2 review C1, measured). The record's layer tables FK `(org_id, graph_id) → public.graphs(org_id, id)`, and the two resolvers behind `OrgResolutionMiddleware` do not share an id space: `resolve_api_key` (Supabase control plane) returns `api_keys.graph_id`, declared `REFERENCES public.graphs(id)`; `apikey_verify` (the self-host registry lane) returns the **Falkor `:Graph` node id** (`g_<hex>`, minted by `sdk._graph_create`) and registry graphs are never inserted into `public.graphs`. Installing the registry id would displace a correctly declared single-tenant pair with a value the FK cannot satisfy — every write `write_failed`, cause unattributable — so the installer passes `control_plane_ids=is_supabase_enabled()` (the same predicate that chose the resolver, so cache hits are covered) and installs nothing on the registry lane. That lane keeps its pre-#9192 arming exactly.

**Modes allowed to arm (ask 2), stated and enforced — including the surfaces where no chokepoint exists:**

| surface | who names the tenant | env pair honoured |
|---|---|---|
| **multi-tenant, named graph on the CONTROL-PLANE lane** (hosted MCP with a graph-bound `tk_` key) — the **default** | `use_record_tenant(...)` per request, installed by `OrgResolutionMiddleware` | **no** — the scope wins; the pair is inert |
| **multi-tenant, org-wide credential** (session / legacy / OAuth: `graph_id` is `None`) | nobody — the record's `public.graphs.id` is not in the resolution | **no** — refused (`no_tenant`), counted + warned. Remediation: a graph-bound credential; naming the default-graph tenant is #9188's |
| **self-host `auth_mode=tenant`** (registry lane: `graph_id` is a Falkor `g_<hex>` node id, no `public.graphs` row) | the pair **plus** the declaration — nothing is installed, because no id on this lane can key the record's tables | yes, only with `TORTOISE_RECORD_SINGLE_TENANT=1`; **undeclared ⇒ refused** |
| **undeclared single-tenant** (self-host HTTP `auth_mode=static/none`, stdio, embedded CLI — no chokepoint exists on these) | the pair **plus** the declaration | yes, only with `TORTOISE_RECORD_SINGLE_TENANT=1`; **undeclared ⇒ refused**, counted `no_tenant`, warned with the exact variable to set |
| **declared single-tenant** | the scope (control-plane lane), or the pair | yes |

⛔ **The operational contract DOES change** for an undeclared single-tenant deployment: it armed with the pair before this change and now refuses until it declares. That is #9192's own ask 2 (*"State which modes are allowed to arm, and make sure a multi-tenant process can never silently satisfy it from env"*), so the gate is authorised by this issue — not a #9078 reopen — but #9078's decision-3 text must be relayed (see Decision relay), and the refusal is observable (counter + warning naming the variable), never silent.

Why this makes the wrong answer *impossible* rather than caught: a multi-tenant process has no process-global tenant to fall back to, so the failure mode left is a **named refusal** (`no_tenant` + a warning that names the declaration), never a well-formed row under the wrong organisation. The single-tenant path survives behind the declaration, not unchanged in front of it.

**Decision relay.** #9078's decision 3 lives in its scoping comment, not in `record_writer`'s docstring (which only cites the label): *"a ContextVar (`use_record_tenant`) for a multi-tenant process, falling back to `TORTOISE_RECORD_ORG_ID`/`_GRAPH_ID` for a single-tenant deployment."* The amended sentence — the fallback applies to a deployment that **declared** itself single-tenant — is posted on #9078 so the next lane does not re-derive the ungated fallback from the original text. Same for `.env.example` (the repo's env contract, test-pinned) and `monitoring.record_record_write_failure`'s `no_tenant` remediation, which today tells the operator the pair alone is the fix.

## Deliberately out of scope (recorded, not absorbed)

- **ask 1 — the REST/hosted caller** → `#9188` (open, `lane:c6-durability`, complexity:complex). **File-level split, so two lanes do not converge on one file:** this lane touches `tortoise/record_writer.py` only in the tenant resolver (`record_tenant`/`single_tenant_declared`) and `tortoise/mcp_auth.py`; `hosted_api`, `sdk.py`, and anything else in `record_writer` (the door, the arming, the position handoff) are #9188's. Commented there with two measurements this lane produced: (1) an org-wide/session-authenticated request carries **no** `graph_id` (`_session_user_org` resolves `org_id` + tier only), and the default graph may have **no row** in `public.graphs` (`supabase_control.delete_graph_row`: *"no row exists for the default graph"*), so `_data_sdk` cannot name the record's `graph_id` without a control-plane read; the record's layer tables FK `(org_id, graph_id) → public.graphs(org_id, id)`.
- The env-fallback **reversal** (alternative E) → a `#9078` reopen if the owner wants it.

## Verification plan (as implemented — `tests/test_9192_tenant_armed_by_request.py`)

The spy sits on `record_writer.write_records`, i.e. DOWNSTREAM of every tenant read in the door: a second env read anywhere inside `write_live_record` still shows up as the tenant the seam was called with (or as no call), so a resolver-only assertion cannot pass while the defect persists.

1. **Production caller exists** — structural (AST scan of `tortoise/` for a call to the setter; a test probe cannot satisfy it) **and** behavioural (two tenants, two control-plane resolutions, each write filed under its own request's tenant — the second one from a `asyncio.to_thread` worker, so the context copy the repo's offloads rely on is pinned too). FAILS on `origin/main@f3b0f26a0` (`got [('org-a-cp', …a), ('org-a-cp', …a)]`).
2. **No cross-write, ever** — the same two requests with a DECLARED pair planted as tenant A: measured on `origin/main@f3b0f26a0` both writes are filed under the planted pair; after, `[(A,gA), (B,gB)]`.
3. **No leak across requests** — after `dispatch` returns, in the SAME context, `current_record_tenant()` and `record_tenant()` are both `None` (a bare, never-reset `set` fails this — verified by planting one).
4. **The env pair cannot arm an undeclared process** — `record_tenant()` is `None`, `write_live_record` refuses, `no_tenant` is counted, the seam is never called, and the warning names `TORTOISE_RECORD_SINGLE_TENANT`. The declaration is read as a FLAG: `""`, `"0"`, `"false"`, `"no"`, `"off"` and a typo all mean multi-tenant.
5. **Declared single-tenant still arms by env** (#9078 decision 3), **a scope still beats a declared pair**, and a **half pair is never completed**.
6. **An org-wide credential is refused, not guessed** — the request succeeds (no 500 from the guarded installer) and files nothing, and the warning names the graph-bound credential rather than an installation the lane does itself.
7. **The self-host registry lane installs nothing** and keeps its pre-#9192 arming: undeclared ⇒ refused (never misfiled under a planted pair), declared ⇒ filed under the pair. Both phases through the mounted app.
8. **The env pair has no reader outside the gated resolver** — structural, so a future caller copying `record_dsn()`'s env read is caught.
9. Existing suite re-run: `test_record_writer_seam.py`, `test_9078_record_written_by_production_path.py` (whose decision-3 leg is updated to declare first), `test_record_projection.py`, `test_mcp_http.py`.
