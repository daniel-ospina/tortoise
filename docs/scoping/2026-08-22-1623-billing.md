# Issue #1623 — In-dashboard Billing page (plan + usage + Stripe portal) + signup plan-selection step

**Level:** task · **complexity:** standard (Architecture: medium · UX: medium · Security: low · Ontology: low) · **base:** origin/main

## Confirmed Problem

1. **No Billing page.** Users have no in-dashboard view of their current plan (tier, subscription_status, limits, usage), no plan comparison, and no plan-management surface beyond popups. The Stripe portal only opens in a popup (#310 Task 9) and loses context.
2. **The existing billing UI surface is DEAD CODE on main.** `TeamInfoResponse` (hosted_api.py ~1574) and the `team_info` response build (~2382) NO LONGER return `subscription_status`, `checkout_price_id`, `customer_email`, `current_period_end`, or `grace_until` — these were dropped when `team_info` was refactored (the last commit touching the model is `598b874a`, and a `git log -S checkout_price_id -- tortoise/hosted_api.py` shows only the original #310 commit `f2470789`; the field is absent from the current model). Consequences on the dashboard (main.jsx):
   - `hasActiveSubscription` (line ~330, `ACTIVE_STATUSES.includes(team.subscription_status)`) is always false → the header **"Manage subscription"** button (~2243) never renders.
   - `upgrade()` (line ~334) early-returns on `!team?.checkout_price_id` → the header/`capNotice` **Upgrade** buttons no-op.
   - The `#1147` cap-notice "See pricing" fallback (line ~2395) is what users actually see.
   So the Billing page cannot be built on the current `/v1/team` contract without restoring the billing surface.
3. **No plan-selection moment at signup.** A new user lands in the welcome card (in-app provisioning, #1566) with no plan context beyond the small header badge; the research says free-tier-first with a deferred, non-blocking plan step after activation.

## Solution (converged)

### A. Restore + extend the `/v1/team` billing surface (backend)
Add to `TeamInfoResponse` + the `team_info` response build (hosted_api.py). **Verifier P3: `PriceCatalog()` RAISES `BillingConfigError` in its CONSTRUCTOR when `STRIPE_PRICE_IDS` is unset (billing.py:110-113) — the best-effort helper must wrap CONSTRUCTION in try/except `BillingConfigError`, not just the `price_for` lookup, or registry/selfhost `/v1/team` would 500/503.**
- `subscription_status: str | None = None` — read from the Team node (`team.get("subscription_status")`); the webhook already writes it.
- `customer_email: str | None = None` — for the "billing email" line on the Billing page.
- `checkout_price_id: str | None = None` — restore the #310 server-resolved default (pro monthly via `PriceCatalog.price_for("pro", "monthly")`, best-effort None when the catalog is unconfigured). Reuses the existing `_default_checkout_price_id()` shape (the helper itself was also dropped — re-add it).
- `checkout_price_ids: dict[str, str] = {}` — NEW: tier → monthly price_id for `solo`/`pro`/`team` (server-resolved from `STRIPE_PRICE_IDS` via `PriceCatalog`, best-effort empty dict when unconfigured). This gives the Billing page per-plan Upgrade CTAs WITHOUT hardcoding Stripe price ids in the client (#310 design: price ids stay env-driven; `PriceCatalog.price_for` already exists).
- `current_period_end` / `grace_until` — optional; only include if already on the Team node and cheap (the webhook writes `grace_until`). Not required by the page; skip to keep the surface minimal (P2).

These fields are backward-compatible (all optional with defaults) — the dashboard gate/loop e2e mocks (which omit them) stay green.

**Verifier P2 (subscription_status source):** `subscription_status` is read off the Team NODE (the webhook writes it) — a configured catalog alone yields `None` for it. The backend positive test must SET it on the Team node (pattern: `test_checkout_active_subscription_409` in tests/test_billing.py), separate from the catalog-driven `checkout_price_id`/`checkout_price_ids` tests.

### B. Billing page — new dashboard tab (website/apps/dashboard/src/main.jsx)
- New nav button `Billing` (`tab === 'billing'`), session-only surface (the dashboard is already session-gated for claimed teams; anon teams get the Protect screen — no extra gating).
- Page content:
  - **Current plan card**: tier (humanized), `subscription_status` (humanized: active/trialing/past_due → "Active"/"Trial"/"Past due"), billing email (if `customer_email`), limits line (max_users/max_graphs/API keys from the bundled pricing mirror), usage: `write_ops_used`/`write_ops_limit` progress bar + `point_count` + overage note (`overage_cost_usd`, `overage_eligible`). Usage bar handles `write_ops_limit <= 0` (metering unconfigured → "—").
  - **Plan options grid**: the four public tiers (free/solo/pro/team) from `product/pricing.json` bundled into the dashboard build (vite JSON import — same single-source pattern as product.html's PRICING mirror; no parity test needed because the build imports the file itself). Each card: name, price/mo, headline limits, key features.
  - **States**: the tab renders only when `team` is non-null (loading guard — the rest of the dashboard has the same); usage-bar guard uses `(team.write_ops_limit ?? 0) <= 0` so an absent field renders "—" instead of a NaN bar (Verifier P3).
- **Per-plan CTA**:
    - Current tier → "Current plan" badge (disabled).
    - Paid tier + no active subscription → **Upgrade** → `upgradeToPrice(price_id)` → POST `/v1/billing/checkout` `{price_id}` → popup with the Round-13/16 popup-block fallback (reuse `upgrade()` mechanics, parameterized by price_id).
    - Any plan change for an active subscriber (active/past_due/trialing) → **"Manage subscription"** (per-card + a prominent one) → POST `/v1/billing/portal` → popup (Round-14 fallback). The Stripe portal handles upgrade/downgrade/cancel — matches the existing checkout 409 (active-subscription guard) so the page NEVER calls checkout for an active subscriber.
    - No Stripe env (`checkout_price_ids` empty) → "See pricing" link to `https://tortoise.premiselabs.co/product.html#pricing` (mirrors the `capNotice` fallback).
- The header tier badge/Upgrade/manage buttons keep working (they read the restored fields).

### C. Signup plan-selection step (welcomeMode, after key reveal)
- In the welcome card (`welcomeMode && authed`), show a **"Choose your plan"** section ONLY for first-timers (`welcomeKey` present — freshly provisioned this session; returning users with `welcomeKey` empty keep the current ready card, no plan step).
- Free selected by default (no card, "free forever" line). "Start free" is the primary CTA → closes welcome mode → dashboard (existing handler). Paid tiers render with their value props (price/mo, headline limits); each "Upgrade" → `upgradeToPrice` checkout popup (existing popup-block fallback).
- **Non-blocking**: the section renders after the key-reveal block; "Start free" is always available; the user can skip by proceeding to the dashboard. No new endpoint, no card capture.
- Do NOT touch provisioning (`provisionInApp`) beyond adding the step after the reveal block.

## Key decisions
- **D1 — price ids stay server-resolved**: per-tier price ids ride `/v1/team` (`checkout_price_ids`), never hardcoded in the client (#310). The checkout/portal endpoints already validate (`PriceCatalog.tier_for_price`) and are session-gated (`get_current_team_session`).
- **D2 — pricing display data bundled at build**: the dashboard imports `product/pricing.json` directly (vite JSON import) — single source of truth, no mirror drift, same pattern as product.html.
- **D3 — plan changes for active subscribers route through the Stripe portal**: the checkout endpoint 409s on active subscriptions; the page respects that and never calls checkout for active/past_due/trialing.
- **D4 — plan step is post-reveal + free-default + skippable**: per research (free-tier-first), no card at signup; the step is a progressive-disclosure moment after the key reveal, never a gate.
- **D5 — restore the dropped billing surface**: `subscription_status` + `checkout_price_id` are restored on /v1/team (they are prerequisites for B, and the header UI already depends on them — this is a fix, not new scope).

## Edge cases
- **Active subscriber clicks "Upgrade"**: impossible by construction — active/past_due/trialing cards render "Manage subscription" instead (D3). Belt-and-suspenders: the checkout endpoint 409s anyway.
- **Canceled/expired subscriber (tier free, status canceled, customer exists)**: checkout allowed (re-subscribe); the page ALSO shows "Manage subscription" (portal works for existing customers — invoice history).
- **No Stripe env (registry/selfhost, `checkout_price_ids` empty)**: paid cards show the "See pricing" fallback link; no Upgrade buttons.
- **Metering unconfigured (`write_ops_limit <= 0`)**: usage bar shows "—" instead of dividing by zero.
- **Popup-blocked checkout/portal**: reuse the Round-13/14/16 fallbacks (error banner + 90s reset timer).
- **Returning user hits /welcome**: `welcomeKey` empty → no plan step (only first-timers).
- **anon teams / key-login**: billing is a session surface; anon teams already render the Protect screen; key-login users on claimed teams are redirected to sign-in. No new gating.
- **graph_ready false**: `/v1/team` fails soft (point_count 0); the Billing page still renders usage from metering.
- **Multi-team**: `/v1/team` is per-team; the Billing page shows the SELECTED team's plan (consistent with the overview cards).
- **Success-return (`?session_id=`)**: the existing poll loop refreshes `team` → `subscription_status` flips to active → Billing page re-renders (Manage subscription appears).

## Research summary (from issue, 2026-08-22 — SaaS subscription UX)
- **Free-tier-first, no card at signup** is the product-led standard (Userpilot/Kompassify/Raze): keep signup minimal (email+password), state "free plan / no card", defer plan selection to post-activation.
- **Progressive disclosure**: plan selection as a step AFTER the user sees value (post-provisioning), not a hard gate.
- **Plan management belongs in a dashboard page** (Stripe billing-portal docs): current plan + status, usage/limits, upgrade/downgrade options, "Manage subscription →" portal link; the portal handles hard billing ops; the app page is context + CTA surface.
- **In-context upgrade prompts** (cap notices, usage bars) convert better than a cold billing page — the existing `#1147` cap-notice pattern is right; the Billing page is the destination they point to.

## Rejected alternatives
- **New GET /v1/billing/plans endpoint** returning the full catalog: extra endpoint + extra fetch; `/v1/team` already carries the server-resolved price ids and the display data is public/bundled. Keeps the change surface minimal and the e2e harness simple. (Would be better if the catalog grew auth-dependent fields — not the case.)
- **Hardcode Stripe price ids in the client**: violates #310's "price ids stay env-driven and never leak into the client" — rejected.
- **Fetch pricing.json at runtime from tortoise.premiselabs.co**: cross-origin runtime dependency + CORS on the marketing host; bundling is deterministic and matches product.html's mirror pattern — rejected.
- **Blocking plan selection at signup** (card capture before activation): rejected by research (free-tier-first; would depress activation).
- **Single "Upgrade" CTA without per-plan options**: the issue explicitly asks for per-plan Upgrade CTAs ("an Upgrade CTA per option") — rejected.
