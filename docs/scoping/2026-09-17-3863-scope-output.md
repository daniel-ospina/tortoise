> 1. **The keyword distribution moved.** `config/surface-order.yml` ships `fetch 22 · create 20 ·

>    the source registers, so a tool cannot reach agents by a route that bypasses the registry. Every one of the **99 tool** rows also

>    `observed` by construction, and the field exists to stop a usage-derived `keep` being read as a ruling.

## 1. Confirmed problem definition

> **The declaration that defines the agent-facing surface — the tool registry, plus the public methods of
> `TortoiseSDK` — has no approval step and no lifecycle.** Any contributor extends it by adding one line; nothing
> in the repository can refuse the change or record who agreed to it. Because the declaration is then handed
> whole to every client on every default path, growth is both invisible and free — and every written statement
> about the surface (its size, its groups, which entries exist) silently decays.

**Precisely what the evidence supports** (the verifiers were right to separate these):

- **"No approval step" — directly measured.** The only thing standing between a new entry and `main` is a total
  count, and that count is edited by the person adding the entry (§2.1).
- **"No lifecycle" — directly measured.** `ToolDefinition` has no deprecation, replacement or approval field
  (`tool_registry.py:25-37`), so "this name is retired" exists only as prose inside a description string, and the
  four rows carrying that prose — the **deprecated aliases** — still return silently (§2.1, and #3876).
- **"No owner" — measured as absence, not as a finding about people.** The repository has **no `CODEOWNERS` file
  at all** (`git ls-files | grep -i codeowners` → nothing), and branch protection is declared in
  `.github/settings.yml` as **`enforce_admins: false`**. **Measured live, that file is stale:** the branch
  protection actually in force on `main` requires **seven** checks — `pricing-artifact`, `docs`, `test-isolation`,
  `license-surface`, `legal-e2e`, `python-ci-gate`, `ai-review-gate` — and does **not** require `redis-guard`, the
  one check the tracked file names. So neither the declaration, nor the guard that would protect it, nor the
  settings that make a
  guard binding are owned or reviewed by anyone in particular. The fix is not an "owner field"; it is that the
  named path must resolve to a **named principal** who is asked before it changes. Two limits are recorded here
  rather than discovered later: a **team** principal is not constructible in this repository (§2.1 — the repo is
  user-owned, so `@org/team` cannot resolve), so the principal is a named **individual**; and the human half of
  the rule therefore rests on a **repository ruleset `pull_request` rule with required reviewers** (§8 AC2(b)),
  not on CODEOWNERS. Until that rule exists, "cannot be expanded without explicit human approval" is **not fully
  achievable here** — what is achievable is that expansion is *recorded, attributed and blocked by a
  non-forgeable required check*, and the document says exactly that rather than claiming the stronger thing.

Two consequences, and they are why the owner's two deliverables are the right product:

1. **A written list alone cannot fix this** — three earlier written answers about this same surface decayed (§2.1).
   The list must be a **machine-consumed record**, not prose, or it becomes the fourth.
2. **The rule the owner asked for is the load-bearing half.** "Cannot be expanded without explicit human
   approval" is a statement about the declaration's lifecycle. The document is its baseline.

**The root cause is not "there are 99 tools".** Size is a measurement taken from an unapproved declaration, not
the cause of it. The count has been pinned by a test for a month and still went 58 → 99, because the person
adding the tool is the person editing the pin.

### 2.3 Why this framing was not chosen for convenience

It is the harder framing: it requires the list to be **generated and tested**, and the gate to be a check that
actually binds. The easier framing — "write the list, add a script that compares names" — was rejected because the
measurement shows that shape already exists in degenerate form (`assert len(TOOL_REGISTRY) == 99`) and was
satisfied 21 times by the person adding the tool. §5.2 records the same lesson from the outside: a golden-file
check is a *detector*, not an *approver*.

### 5.1 UX — agent-facing tool surfaces

**Canonical**
- The MCP specification sets **no tool-count limit**; the official guidance is threshold-based: switch to
  progressive discovery once definitions reach **1–5% of the context window**, because loading every definition
  upfront "wastes tokens, increases latency, and degrades model performance" (illustration ~150,000 tokens vs
  ~2,000). — MCP docs, *Client Best Practices*,
  <https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md> — **means:** gate a
  share of context, not `len(TOOL_REGISTRY)`.
- "Claude's ability to pick the right tool degrades once you exceed **30–50 available tools**"; tool search cuts
  definition tokens by >85%. — Anthropic, *Tool search tool*,
  <https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool> — **means:** 99 served down one
  default path is past the stated point before ownership is discussed.
- Hygiene is **curation, not enumeration**: "Too many tools or overlapping tools can also distract agents";
  recommends namespacing and held-out evals. — Anthropic, *Writing effective tools for agents*,
  <https://www.anthropic.com/engineering/writing-tools-for-agents>.

**Precedent**
- **GitHub MCP Server: 92 tools in 24 toolsets, default = 5 toolsets**, allow-lists at group and individual level,
  operations *collapsed* rather than one tool per call. — <https://github.com/github/github-mcp-server> —
  **means:** a comparable surface groups **and turns the filter on by default**, and reduces count by collapsing
  operations.
- The official memory MCP server exposes **9 tools**. —
  <https://github.com/modelcontextprotocol/servers/blob/main/src/memory/index.ts> — **means:** size is a choice.

**Pitfalls**
- **A static or keyword filter narrows the list but does not fix first-pick accuracy.** Vendor benchmark (2,700
  cases / 270 tools): BM25 Top-1 = 14%, hybrid = 21%, embeddings = 38%, reranker 40%+; at Top-5 *every* method
  reaches 85–90% — "the right tool is usually in the results… But agents pick the top result."
  <https://www.stackone.com/blog/mcp-tool-search-bm25-tfidf-hybrid/> *(vendor benchmark)* — **means:** ranking,
  not catalogue size, is the constraint; "group them" is not a fix on its own.
- **Do not conflate the two families of numbers.** Tool-level within one catalogue (Anthropic's 30–50;
  LongFuncEval <https://arxiv.org/abs/2505.10570>) differs from server-level discovery (RAG-MCP varies **N
  servers 1→1100**, <https://arxiv.org/abs/2505.03275>). RAG-MCP's own static pre-filter baseline is **18.20%**,
  so quoting 43.13% as the gain from a group filter is the known error.
- **Grouping pays off only if applied by default and the descriptions are enriched**; the residual failure mode is
  ambiguity, not volume. *(A fourth source cited in the first draft — a PinePaper-ToolBench Recall@5 figure —
  could not be corroborated at the quoted value and is therefore dropped rather than carried.)*

### 5.2 Architecture — keeping a declared surface from drifting

**Canonical**
- The named pattern is a **checked-in golden signature file**: a generator writes the approved surface and a build
  check fails on any difference — **Kotlin `binary-compatibility-validator`** (`apiDump` / `apiCheck`) and
  **Android Metalava** (`frameworks/base/core/api/current.txt`, 63,907 lines). —
  <https://github.com/Kotlin/binary-compatibility-validator> ·
  <https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/api/> — **means:** copy this
  shape. `assert len(TOOL_REGISTRY) == 99` is a degenerate version that records only the *size*.
- **Per-entry approval as a machine-checked field** exists in the wild: Rust's `#[unstable(feature, issue,
  reason)]` plus a defined approval phase (FCP). — <https://rustc-dev-guide.rust-lang.org/stability.html>.
- **Growth recorded as a decision, not a diff:** Go requires API changes be "first discussed… before they can be
  implemented", with an explicit accept/decline and a goal of making past proposals findable. —
  <https://go.googlesource.com/proposal/+/master/README.md> — **means:** the approval must be a *findable* record.
- Python-native: `griffe check` fails CI on surface change between snapshots, with explicit exemption decorators —
  and is candid that "your public API is what you say it is". —
  <https://mkdocstrings.github.io/griffe/guide/users/checking/> — **means:** the surface must be declared.

**Precedent**
- **Android judged plain file ownership insufficient**: its approved-surface `OWNERS` reads in full "# API changes
  are managed via Prolog rules, not OWNERS"; the gate is a rule layer plus a named review body. —
  <https://source.android.com/docs/setup/contribute/api-guidelines> — **means:** "add an owner" is the weaker half.
- **The golden file is one command from being rewritten by its own author** (BCV's `apiDump` overwrites without
  requiring review) — **means:** a baseline check is a *detector*, not an *approver*. This is the crux of §2.3.

**Pitfalls**
- **Approval gets rubber-stamped:** across five large projects **64.7% of PRs had comment-free reviews**, and those
  "exhibit the LGTM smell 3.5× more frequently".
  <https://repository.bilkent.edu.tr/server/api/core/bitstreams/b438e043-7d22-42c3-ae89-37b1d12eaaaf/content> —
  **means:** an approval field will be filled by whoever is already adding the entry unless a **named** approver
  and an explicit thing-to-check are required.
- **The one-line addition is the change least likely to get real review** — 85.8% of tiny (<10-line) PRs had no
  recorded review (vendor dataset, directional). <https://codepulsehq.com/research/rubber-stamp-problem-2025> —
  **means:** the gate must force the substantive question, not accept a signature.

### 5.3 Config — a CI gate that cannot be skipped

**Canonical**
- A skipped job reports **Success** and does not block a required check; a workflow skipped by a path/branch/message
  filter leaves checks **Pending** and does block. GitHub's remedy: "Avoid requiring workflows that can be
  skipped"; for dependency-skips use `always()` with `needs`. —
  <https://docs.github.com/en/pull-requests/reference/status-checks> ·
  <https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks>
  — **means:** the guard must be an **unfiltered** `pull_request` workflow — this repo has already been bitten
  twice (#2055).
- Required checks can be declared instead of hand-typed: rulesets with `required_status_checks` (`context`,
  `strict_required_status_checks_policy`, **`integration_id`**) and a `workflows` rule, with an explicit
  `bypass_actors` list. — <https://docs.github.com/en/rest/orgs/rules> — **means:** `integration_id` is the lever
  that stops a write-capable actor standing in for the check, and a checked-in ruleset makes widening the bypass
  list visible in a diff.

**Precedent**
- **Prow/Kubernetes**: no merge without the `approved` label, which requires an approver from OWNERS; an external
  bot holds merge authority. — <https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/> —
  **means:** "cannot verify → no approval → no merge" is shipped.
- In-repo precedent to copy: `tools/skip-guard.py` fails the run when a live-database test skips ("the run must
  flip RED — the historical silent-green masked the #1382 EP regression class for days"), and
  `.github/workflows/redis-guard.yml` runs with **no path filter**. **Do not** copy skip-guard's
  "log missing/unreadable → exit 0", which is fail-open.

**Pitfalls**
- **Any actor with write permission can set any status check's state**, and a required check can be satisfied by
  the wrong source unless `integration_id` pins it. —
  <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets>
  — **means:** with an agent-held token an unpinned check is forgeable.
- **Bypass is the default for privileged actors** unless "Do not allow bypassing" is enabled — and this repo's
  `.github/settings.yml` declares **`enforce_admins: false`**; the protection live on `main` (measured)
  requires **seven** checks — `pricing-artifact`, `docs`, `test-isolation`, `license-surface`, `legal-e2e`,
  `python-ci-gate`, `ai-review-gate` — and does **not** include the `redis-guard` the tracked file names.
  `python-ci-gate` is an **aggregate** (`python-ci.yml:1865`, `needs: [...]`), so a new gate job can join the
  required set by being added to that `needs` list — the CI half of D2 needs no new required check, only a new
  job. That is a smaller change than first stated, not a larger one.
- Commit-message skip channels (`[skip ci]`, `skip-checks: true`, …) suppress runs entirely. —
  <https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs> — **means:** the guard
  should assert it ran against the PR head commit.

### 5.4 Org infra — ownership of a shared declaration

**Canonical**
- `CODEOWNERS` + "Require review from Code Owners" is the mechanism, and it is **weakest-link** ("an approval from
  any of the owners is sufficient"); the docs warn that "to protect a repository fully… you also need to define an
  owner for the CODEOWNERS file itself", and an unowned path "can be made with the approval of any user who has
  write access". —
  <https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners>
  — **means:** if ownership is used, the declaration, the guard **and** the manifest must all be owned, or the
  constrained population can edit its own gate.

**Precedent**
- **cargo-vet** is the working precedent for an approval record inside the repository: `audits.toml` entries carry
  `criteria`, `version`/`delta` and `who`, and CI runs `cargo vet --locked` so any change without a coverage
  record fails. — <https://mozilla.github.io/cargo-vet/audit-entries.html> — **means:** the pattern works as a
  blocking **completeness** device (see the pitfall for why `who` is not a trust device).

**Pitfalls**
- **An automated actor can satisfy a human-review requirement by default** — GitHub shipped "Allow GitHub Actions
  reviews to count towards required approval", and the 2022 changelog made it **configurable**. Current GitHub docs
  state new **personal** repositories default to **not** allowing Actions to approve PRs — and this repository is
  user-owned (§2.1), so that default applies here. (An earlier draft said the setting ships **enabled** and cited
  the changelog whose own title says the opposite; §8 AC3 carries the corrected premise.) —
  <https://github.blog/changelog/2022-01-13-github-actions-prevent-github-actions-from-approving-pull-requests/> —
  **means:** if a human signature is required, the gate's own logic must enforce it.
- **An approval line written into an artifact is self-asserted prose** — the DCO trailer is plain text filled from
  local git config, and "anyone can use any committer name and email in Git". —
  <https://developercertificate.org/> — **means:** `approved-by: <human>` is checkable for presence and shape
  only. Something the agent cannot write must carry the decision.
- **Ownership rules decay silently** — a malformed or non-resolving CODEOWNERS entry is skipped with no error, and
  the departed-reviewer case is explicitly resolved by an admin merging anyway. — **means:** name a durable
  principal and assert that the owner entry still resolves — **a team where the repository is org-owned, a named
  individual here**, since this repo is user-owned and no `@org/team` can resolve (§2.1, §8 AC12(c)).

**Honest limits.** No retrieved source benchmarks a **human-curated group filter** specifically; the nearest
measured proxies are keyword/BM25 and embedding retrieval, which is why the finding is framed as "ranking is the
constraint". The StackOne/Codepulse figures are vendor datasets of varying rigour; the authoritative sources are
the vendor/platform docs (MCP, Anthropic, GitHub, Kotlin BCV, AOSP, Rust, Go, griffe). One claim (CODEOWNERS
decay) is web-secondary and single-sourced, and one fourth-draft source (PinePaper-ToolBench) was dropped as

### 6.1 The dependency research — how each entry's dependencies are derived

The owner asked: *"very carefully research the dependencies for each of them. Are they used for an eval? Are the
SDK endpoints? Are they using the MCP? So exactly what it does."* This is not knowable from the declaration, so
it is **derived by an executed scan**, not by reading and guessing. The method:

1. **Build the caller index by execution — and treat a bound-method reference as a call.** Parse every tracked
   Python file with the `ast` module and record, per entry: (a) every `ast.Attribute` whose attribute name is the
   entry's method/tool name **wherever it appears — as the callee of a `Call`, as an argument, or as a value**;
   (b) every bare `Name` matching it; (c) every string literal that is a registry tool name **or a public
   `TortoiseSDK` method name** (string dispatch is otherwise invisible); (d) a recorded note of every
   `getattr`/`__getattr__` on an SDK object. **This shape is
   mandatory, not stylistic.** The dominant way an MCP handler reaches the SDK in this repo is a *bound-method
   reference passed as an argument*: `_safe(_quota_gated(_get_org_sdk().create_point, "points", ...), ...)`
   (`mcp_server.py:834`), `_safe(_get_org_sdk().recall_subgraph, ...)` (`:1362`),
   `run_ask_bounded(sdk.ask, ...)` (`:1247`). **One shape dominates, and it is measured.** At `4488de7d9`:
   **88** references to public `TortoiseSDK` methods through `_get_org_sdk()` — **all in argument/value position**
   (bound-method references passed to `_safe`/`_quota_gated`/`run_ask_bounded`), **none** as the callee of a `Call`;
   the **5** call callees are all `_get_org_sdk()._get_proj()`, a **private helper**, not a public endpoint. So
   the call-callee form finds **none** of the public MCP→SDK edges, and a scan that looks only for `obj.name(...)`
   would report agent-reachable methods as unreached. **Two totals, one counting rule each, so neither is
   over-read:** `88` counts references on a `_get_org_sdk()` expression (81 distinct methods); a scan over **every**
   SDK binder in `mcp_server.py` finds **91**, the extra 3 being direct `sdk.<method>` references (`ask` `:1248`,
   `get_session` `:2605`, `mine_corpus` `:2689`) rather than through `_get_org_sdk()`. The **88** is the figure the
   dependency column uses, because it is the form this repo's handlers actually use. (An earlier draft's 85/73 came
   from a narrower rule and is not carried — per item 7.) (Precedent
   in-repo: `tools/ci_selection.py` builds a static import graph and documents this same indirection class as its
   own blind spot — function-local imports and helper/fixture indirection, `tools/ci_selection.py:908-930`
   (`:1032` is the function-local-import case).)
   **One class this scan cannot attribute, named rather than hidden:** `getattr(sdk, "<name>")` dispatch. Checked
   at `4488de7d9`, no `TortoiseSDK` method is currently reached that way (the only public-method `getattr`s are on
   `TortoiseCrMemory` and the protocol adapters), so it is a **latent** limitation — but the string-literal sweep
   in (c) is what keeps it latent, and every unresolved reference is recorded with its location.
2. **Bind each reference to a class, or it is not attributable.** A `<expr>.<name>` reference counts as reaching
   `TortoiseSDK.<name>` only when `<expr>` **yields a `TortoiseSDK`** — the rule is the universal, and the forms
   below are **examples of it that this repo actually uses, not the definition** (an earlier draft stated them as
   a closed list, which two implementers would have read differently — the failure item 2's own tail corrects). The
   forms found here are: a call to `_get_org_sdk()` / `_get_sdk()`
   (including when that call is itself nested or passed as an argument), a local holding their result, or `self`
   inside the `TortoiseSDK` class body. **The REST layer binds its SDKs differently and must be listed or its
   callers are lost:** `hosted_api.py` uses `_make_sdk`, `_data_sdk`, `_registry_anchor`, `_registry_sdk` and
   `_probe_sdk` — never `_get_org_sdk()` — so those five binders are part of the
   attribution vocabulary too, and `_data_sdk`'s own body (`hosted_api.py:3664`) is followed to `_make_sdk`, which
   is what lets the worked example (`:5302 sdk = _data_sdk(org)` → `:5305 sdk.ask`) be attributed at all. **The command line binds its SDK the same way, and must be listed for the same reason:**
   `tortoise/__main__.py` has **no** `_get_org_sdk()`/`_get_sdk()` helper, so its binders are `TortoiseSDK(...)`
   construction expressions — the locals `sdk` and `registry_sdk` — and the vocabulary there is **"any local bound to an
   expression containing a `TortoiseSDK(...)` call"**, not "a local bound to a call" (a special case of the universal
   stated at the end of this item):

### 6.2 The ordering rule — "similar ones are next to each other"

The owner asked: *"reorganize that list so that similar ones are next to each other in the list, just in the order
of the list."* The rule:

1. **Primary order = job family.** The family key is the entry's **applied group** — the `group` value after
   `_apply_groups` (`tool_registry.py:1302-1308`), which reads `GROUP_BY_NAME` (`:1220`) and **defaults to
   `memory`** (`:1306`). Only one entry passes `group=` explicitly (`:198`); every other group is applied, so the
   document labels this field *applied*, not *declared*, and carries a `group-source` marker with **three** values,
   with the precedence **explicit > mapped > defaulted**, because there are three provenances: the single entry that
   passes `group=` (`:198`) → `explicit`; the **90** other names in `GROUP_BY_NAME` → `mapped`; the **8** absent from
   it → `defaulted` (1 + 90 + 8 = 99 — the split is **disjoint**, and an earlier draft's "91 mapped" double-counted
   the one explicit row, which is also in the map). Note that `explicit` is currently **inert**: `_apply_groups`
   overwrites every entry's `group` (`:1306`), so the one `group=` value has no effect — the marker records that the
   declaration exists, not that it survives. The marker is a **required row field** for **tool** rows only (AC13).
   That matters for the **8** names absent from `GROUP_BY_NAME`: they inherit the `memory` default, so
   they are counted into the memory family and sort with it, but they are **unroutable** on a group-scoped server
   (§2.1, #3877) — the marker is what keeps "counted into memory" from being read as "served by memory".
   11 values at `4488de7d9`: memory 32, graph 16, reasoning 14, sessions 9, admin 7, onboarding 7, journal 5,
   sources 4, review 3, ask 1, mining 1 = 99. Families are listed **largest first, then alphabetically for ties**,
   and the sort element is a **stored `family_rank`**, which is the **rank of the row's `order_family` = its
   `recommended_family` where one exists, else its applied `family`**. This is the one place two statements a
   reader could take as contradictory are reconciled, and both halves matter:
   - the **rank table** is fixed once from the declared counts above (memory 1, graph 2, … mining 11) and is **never
     recomputed** — so no recommendation can reorder two families or tie them;
   - a row's **`family_rank` is a lookup in that fixed table using its `order_family`**, so a split cluster whose
     members recommend `graph` all take rank 2 and become contiguous by construction.
   An earlier draft said only "computed once and not recomputed for recommendations", which left it open whether
   `family_rank` ranked the *applied* or the *recommended* family — and those two readings put a split cluster's
   rows in different rank groups, making AC13's adjacency clause unsatisfiable. Ordering on the **recommended**
   family is what §6.2 item 2 intends; the **table** is what the counts above fix — so this is one specific order
   and not "grouped somehow".
2. **Inside a family, order by duplicate cluster first, then by a derived job keyword.** The sort key as SHIPPED is
   **`(family_rank, keyword_rank, cluster or name, canonical-first, own_name)`** — the row's **own** `keyword_rank`,
   and the row's `cluster` falling back to its own name for unclustered rows. An earlier draft of this item described
   the first three elements as the **cluster's** key (`cluster_keyword_rank`, `cluster_name`), which is **not** what
   ships and not what the baseline stores; the two happen to produce the same order today only because no declared
   cluster mixes `keyword_rank` across its members — so any cluster that did would order by the shipped key and not
   by the described one. Stated from the shipped key: because a cluster's members are ordered together and the
   cluster is compared as a unit, the owner's named clusters are **structurally** adjacent rather than incidentally
   so. This ordering was itself a divergence: the alternative considered and rejected was
   *keyword-first per row*, and it fails on the doc's own canonical example — the fetch-by-id cluster
   (`tortoise_get`, `tortoise_get_point`, `tortoise_get_operator`, `tortoise_get_entity`) can be split by any rule
   that treats `get_point` differently from `get`. **Every element is pinned, so two people get the same order:**
   - **`family_rank`** — the stored rank of the family (item 1): 1 = memory, 2 = graph, … .
   - **`cluster_keyword_rank` / `cluster_name`** — taken from the cluster's **canonical** row: the **rank of its
     derived job keyword** in the item-2 table (fetch 1, create 2, update 3, delete 4, list 5, find 6, trace 7,
     check 8, link 9, operate 10 — the **rank**, not the string, exactly as with `family_rank`; a literal string
     comparison would sort `check` before `create` and place the fetch keyword **4th rather than 1st** in
     `memory`, contradicting
     AC13's "job-keyword order inside each family") and its name. A row that is in **no** duplicate cluster is a
     **one-member cluster whose
     canonical row is itself**, so for a singleton these two elements are simply its own keyword rank and name. This is
     the correction of a real defect: with `cluster` = a singleton's own name and the key written
     `(family, cluster, canonical-first, keyword, …)`, **`keyword` was never compared between two unclustered
     rows** — their `cluster` values already differ, so the comparison stopped before reaching it — and the emitted
     order was alphabetical by name while AC13 required "job-keyword order inside each family". Ordering clusters
     **by their canonical row's keyword** delivers both properties at once: clusters stay contiguous, and the
     family still reads in keyword order.
   - **`canonical-first`** — `0` for a cluster's canonical row, `1` for its other members, `0` for a singleton.
     Nothing ahead of it can separate members of one cluster, so the canonical row is always first inside its
     cluster. Under the earlier `(…, cluster, keyword, canonical name, …)` key the canonical **name** was
     **constant across a cluster** and could not separate members at all, while a non-canonical member with an
     earlier keyword sorted **ahead** of the canonical one — contradicting AC13's "canonical entries first inside a
     cluster".
   - **`own_name`** — unique across the surface, so no tie is possible.
   **`canonical` is defined
   operationally, not by taste:** *the entry whose name the other members of the cluster redirect to, or the entry
   carrying the cluster's general name* — for the fetch cluster, `tortoise_get` (the consolidating name designated

and it is **re-derived on every
change rather than trusted** (§8 AC11). **`exemption` and `approval` are two different things and neither substitutes for the other** (they are not
row-level mutual exclusions — the guard accepts a shape-valid `approval` on an exempt row): an
exempt row is outside the gate (its class is `eval-only`, `internal`, `control-plane` or `no-caller-found`, §8

exemption is NOT an approval carve-out.)** Once `approval_status` is `approved`, the guard demands a recorded

from being approved as a whole. An earlier draft said the guard read "exempt" as
*approval-satisfied-and-not-required*, which is the opposite of what ships.
