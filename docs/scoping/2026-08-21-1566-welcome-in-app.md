# Issue #1566 — OAuth should land new users in the app subdomain (provisioning moves into the dashboard welcome mode)

**Level:** task · **complexity:** complex · **base:** origin/main (post-#1559)

## Confirmed Problem
A first-time GitHub/Google signup bounces through `tortoise.premiselabs.co/welcome` (standalone provisioning page) before the dashboard — the user asked for it to land directly in `app.premiselabs.co`. The dashboard already HAS a welcome mode (`app.premiselabs.co/welcome`, #1287) but it does NOT provision — it assumes the key was revealed on the old page and just shows a "Your Tortoise is ready!" card.

## Solution (converged)
1. **OAuth redirect → the app:** `claimRedirectTarget()` (signup.html) returns `https://app.premiselabs.co/welcome` for the non-claim path (the `?claim=1` funnel branch is unchanged). OAuth (PKCE) returns with `#access_token=…` on the app origin; supabase-js `detectSessionInUrl` picks it up, writes the session cookie, and the dashboard welcome mode runs.
2. **Dashboard welcome mode provisions:** port the welcome.html provisioning into main.jsx's welcomeMode path for first-timers (users with a session but NO active team): the same `tenant-provision` edge-function call + membership poll + `reveal_api_key` (reveal-once, A13). The key is revealed on the app origin (its home — #1082 is satisfied: the raw key never crosses origins; it's minted on the app origin now).
3. **Legacy welcome.html:** for signed-in visitors it client-redirects to `https://app.premiselabs.co/welcome` (the app does the provisioning); for signed-out visitors it redirects to /auth. Keep the page (old links + the welcome e2e hit it) — no server 301 needed since it's client-side anyway.
4. **Claim funnel unchanged:** `tt_claim_pending` + `?claim=1` still renders the claim-paste screen (main.jsx claim-intent predicate), never the provisioning welcome. The provisioning double-provision guard (welcome's Phase-2 mint avoids claimable anon teams) is ported: the dashboard's provisioning path checks claim-status / existing membership BEFORE provisioning.

## Key decisions
- **D1 — provisioning runs in the app:** yes. The session JWT (same parent-domain cookie) authorizes the same tenant-provision edge function from the app origin. The key reveal happens there.
- **D2 — legacy welcome redirects:** yes (client-side). It no longer provisions; the app is the single provisioning surface.
- **D3 — first-timer detection:** a valid session + NO active team membership → welcome mode; team exists → dashboard home. (Same signal the current welcome page uses.)
- **D4 — email signup path:** the email flow's post-signup redirect also points at the app welcome (if it has a separate redirect, update it identically).

## Edge cases
- OAuth return on the app origin with `?claim=1` (claim funnel) vs without (new signup): the existing claim-intent predicate decides.
- Anon-team users (tt_claim_pending) arriving at app/welcome: claim-paste screen, never auto-provision (no orphaning).
- Existing users with a team landing on app/welcome (e.g. clicked an old welcome link): skip provisioning, show the ready-card or redirect to home.
- Provisioning failure: the #1559 error-card pattern (actionable error + retry).
- The welcome e2e + dashboard gate + loop e2e must stay green (update the welcome e2e to expect the app redirect).

## Verifier-gate findings (folded in)
- **P0 (CORS):** `tenant-provision`'s ALLOWED_ORIGINS excludes `https://app.premiselabs.co` — the app origin's fetch would 403 on preflight. Add the app origin to ALLOWED_ORIGINS (and the waitlist-subscribe parity test keeps the arrays in sync) + update the CORS harness tests (`test_tenant_provision_cors.mjs`, `test_edge_function_allowlists_*`).
- **P1-1 (mount ordering):** a first-time user has a session + NO team — the dashboard mount must run the ported provisioning pipeline (claim-status guard → tenant-provision → membership re-poll → reveal) BEFORE the bootstrap mint (which 403s "No team membership" for teamless users). Provisioning runs in the mount's no-team branch, not in a render path.
- **P1-2 (reveal-once loss):** `reveal_api_key` is atomic reveal+null (A13) — the in-app welcome card MUST DISPLAY the revealed key (copy block + "copy" button); today it says "Your API key was shown on the welcome page". Every no-team first-timer routes to the `/welcome` welcome mode BEFORE revealing.
- **P1-3 (recovery mode):** welcome.html is the password-reset landing (resetPasswordForEmail redirectTo + reset form + `test_recovery_flow_present`). A recovery landing establishes a session — it must render the reset panel and NEVER redirect to the app. Check `recoveryLanding`/`recoveryMode` FIRST in welcome.html.
- **P1-4 (#1224 OAuth error banner):** with redirectTo = app/welcome, GoTrue `?error=&error_code=bad_oauth_state` lands on the app — the dashboard's no-session `bounceToAuth()` must preserve search params (`bounceToAuth(window.location.search)`) so the sign-in-expired banner still renders (or render an equivalent banner on the app).
- **P1-5 (e2e migration):** the reveal-once (A13) coverage moves to the app — new dashboard welcomeMode e2e (mocked session → no teams → tenant-provision → reveal-once → ready card). The welcome.html provisioning/reveal tests (`test_welcome_success_shows_key_and_artifacts`, `test_reveal_shows_key_once_then_returning_state`, etc.) are re-targeted; `test_welcome_page_no_session_redirects_to_auth` + recovery tests stay.
- **P2:** all FOUR signup.html surfaces pointing at tortoise/welcome update to the app target (head-gate bounce, claimRedirectTarget non-claim branch, email signup success, email login success); the signed-out welcome redirect preserves search+hash into /auth; the app client ingests the implicit-flow `#access_token` fragment (manual-verify step); ready-card copy rewritten.

## Rejected alternatives
- Keep provisioning on tortoise/welcome and only change the redirect hop: still a hop; the user explicitly wants to land in the app.
- Server-side provisioning on OAuth (edge function on auth callback): new infra + the key would need transport to the app anyway.
- Delete welcome.html: breaks old links + the e2e suite.
