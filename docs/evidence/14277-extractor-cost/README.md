# The extractor's measured token spend (#14277)

This directory is the **evidence** for `#14277`: the measurement `#14275` said
must happen before its two numbers are facts rather than a model. Everything
here is generated by `tools/extractor_cost_measure.py` from
`measurements.jsonl` — nothing in `report.md` or `report.json` is hand-written,
and both can be regenerated from the raw rows without spending another token:

```bash
uv run python tools/extractor_cost_measure.py run \
    --out docs/evidence/14277-extractor-cost/measurements.jsonl \
    --docs 50 --sessions 10 --workers 8 --long-split
uv run python tools/extractor_cost_measure.py report \
    --out docs/evidence/14277-extractor-cost/measurements.jsonl \
    --json-out docs/evidence/14277-extractor-cost/report.json \
    --markdown-out docs/evidence/14277-extractor-cost/report.md
```

| file | what it is |
|---|---|
| `measurements.jsonl` | one row per item per arm (122 rows): per-stage input/output/cache-hit, calls, wall clock, errors. Written incrementally by the run — a killed run resumes, it does not restart. |
| `report.md` | the generated human report: per-stage tokens, the fits, modelled vs measured cost, the allowance re-statement, and what the measurement itself cost. |
| `report.json` | the same, machine-readable, for anything that wants to re-derive a figure. |

## What was measured, and how

The **real** pipeline — `extract_session_v2`, the production model
(`build_extractor_model` defaults, thinking disabled, JSON mode, stage caps) —
over

* **50 tracked `docs/**/*.md` files**, stratified into equal-width token bands
  so the sample carries the repo's real length spread (439 → 127,914 tokens;
  median 5,211, p75 9,131), with the median, p75 and the longest document in
  the sample by construction rather than by luck;
* **10 spooled sessions** at the median size from `~/.tortoise/capture-spool`
  (1,534 tokens), because sessions and documents draw on the **same**
  `max_extraction_tokens` budget (owner ruling, 2026-11-21) and so both had to
  be fitted on the same terms;
* each **twice** — a cold arm and a warm arm, which is the cache lever;
* plus the longest document delivered as **40 and 160 turns**, to see what
  chunking does to the constants.

122 measurements, 473 provider calls. Token counts for the corpus were taken
with `cl100k_base` (named because a token count without its tokenizer is not
comparable to anything); that reproduces `#14275`'s size table to within ~3%
on every quantile, which is what makes the two measurements the same
measurement.

## The three findings that change the answer

1. **The per-item input constant is 45.5k tokens, not ~7k** — and the pass
   multiplier is **2.16T, not 1.5T**.
2. **Output is dominated by a constant too.** The model assumed `0.2T`
   (≈1.0k on a median document). Measured: 22.8k fitted, 16.0k on the median
   document. It is the single largest line of the bill, and a cache cannot
   discount it.
3. **S2 and S4 barely move with document length** (R² ≈ 0.00 — the only stage
   that reads the text is S1, at R² ≈ 0.99). A small item is therefore not
   "relatively expensive": it is essentially *all* overhead. That is why a
   1,534-token session costs 36.6k tokens of spend — as much as most documents.

## Limits — stated, because an unstated limit reads as a result

1. **One document is one user turn.** There is no document-ingest lane yet
   (`#14219`). A real ingest that splits a long document into turns changes
   the shape: the 40/160-turn runs in the report show S1's total input stays
   ≈ the document's own text (chunks partition it, and the per-chunk constant
   is small against the text), while **S2/S4 output scales with the turn
   count** and hits the stage cap on a 128k-token document. So the turn count
   is a real cost lever, but it acts on the mapping stages, not the summarizer.
2. **S3 is empty** (`sdk=None`): the graph read degrades to no results, so S4's
   prompt carries no candidate list. That is the first-pack-into-a-new-account
   shape; a pack into a POPULATED graph carries candidates and its S4 input is
   larger. The S4 figure is a floor.
3. **The cache arms are a ladder, not two points.** Within an arm the per-stage
   system prompt is already a cached prefix from the second item onward, so the
   TRUE cold cost is the first item's first call — reported separately — and
   the cold arm's steady state is the realistic production figure. The warm arm
   measures a perfect replay, which is the upper bound of the lever and the
   value content-hash dedup would collect.
4. **Rates are `#14275`'s own quoted figures.** The repo's reprice map
   (`tools/longmem_eval/costing.py`) carries different, lower rates; the report
   states both and picks neither, because picking is a pricing decision this
   lane is not authorised to take.
