# E1 + E2 on one run — the epic's first after-measurement (#9076)

**Measured at:** `c2544f54f14` (the sha `e1-e2.log` names on its `sha=` line) on 2026-10-19, from
`feat/9076-tm`. The branch tip that *commits* the log is necessarily a later commit — the log
cannot name the commit that adds it — so the provenance is this doc's `Measured at` line plus the
log's own `sha=`, and the two agree by construction. `tests/test_e1_e2_measurement.py`
(`test_the_committed_log_is_what_the_probe_prints`) pins the log to what the probe prints at any
head, masking only that one non-reproducible `sha=` line.

> **Status: measured, not scored.** The run reports every number the issue asks
> for, and reports **UNPREREGISTERED** instead of a verdict — because #9075 (the
> pre-registration that must freeze the corpus and the thresholds *before* any
> evidence log exists) has not landed. Measured numbers are evidence; a verdict
> without a frozen threshold is not.
>
> **Verdict so far, in one line:** E1 does not move on the shipped pipeline, and
> the reason is structural rather than a threshold — every discard the gate
> attempts is undone by `apply_vet`'s Layer-1 guard because the Object is
> referenced by the statement it was minted from. E2 loses nothing (90/90 real
> facts, 42/42 value matches), which is only reassuring because nothing was
> removed. (The gate is measured with its flags forced **ON**; the deployed config
> leaves all three OFF, so on the arm production runs today E1 does not move because
> nothing is armed — see the note under the arm table.)

## The measurement

One corpus, one extraction, four arms. The candidate set is held **constant**:
the only variable between `before` and `after` is the gate. The probe **asserts**
that — `assert_one_gate_population` refuses to run when the three gate arms do not
share one `preg_embed_sha` — and the checker requires the two non-counterfactual
arms to share it (V4). The mint-skip arm is excluded from the assertion by
construction (its point is a different candidate set) and is printed apart. The pipeline is the real one — `extractor_v2.extract_session_v2`
(S0→S1→S2.1→S2.2→S2.3→S3→S4→S5/S6) — driven by a scripted model so the run is
hermetic (no provider key, no network).

| arm | scored? | what it is | Objects | `the <X>` | share | real facts | value matches | atomic Points |
|---|---|---|---|---|---|---|---|---|
| `before` | baseline | VET + value gate OFF (all three S2.2 switches default off = the shipped default) | 25 | 15 | **60.0%** | 90 | 42 | 114 |
| `after-vet-shipped` | **YES** | `TORTOISE_VET=1` + `TORTOISE_VALUE_GATE=1`, `arbiter=None` | 25 | 15 | **60.0%** | 90 | 42 | 114 |
| `after-vet-arbiter` | no | + an injected arbiter answering S2.2 with the in-repo definite-description predicate | 25 | 15 | 60.0% | 90 | 42 | 114 |
| `counterfactual-mint-skip` | no | what a **mint-time** rule would produce (entity never minted; the claim keeps its content and loses only the reference) | 16 | 6 | **37.5%** | 90 | 42 | 114 |

> **Which arm is `before`, and which is a what-if?** The `before` arm is what the
> deployed config runs today: `TORTOISE_VET`, `TORTOISE_VALUE_GATE` and — since #5087 —
> `TORTOISE_S2_DECISION_SEAM` are unset in
> `fly.toml`'s `[env]` and absent from `.github/scripts/fly-managed-secrets.txt`, and
> all three default OFF (`tortoise/extractor_v2.py:88`; `TORTOISE_S2_DECISION_SEAM`
> arms the pass even against an explicit `TORTOISE_VET=0`, so leaving it out of this
> count would understate what "off" means). The scored arm is that SAME
> shipped code with `TORTOISE_VET` and `TORTOISE_VALUE_GATE` **forced ON** and the
> seam switch left off — the gate's behaviour once it is switched
> on, which is the decision #7949 still carries (enable the flag and re-measure, or
> change `apply_vet`'s Rule 2 first). Both arms read 60.0%, so no number in this bundle
> moves either way; what changes is the *cause* a reader should infer from the 0.0 pp.
> The arm NAME is unchanged because it is a `REQUIRED_ARMS` contract in
> `tools/e1_e2_census_check.py`, so a rename would force the log to be re-taken.

### Why the shipped arm moves the share by exactly 0.0

This is the finding, and it is a mechanism — an Object referenced by the statement
it was minted from cannot be removed — *on this population*. The discriminating
control below measures which part of that is the gate and which part is the corpus,
and limit 6 states the population the claim holds for.

1. The **mechanical** predicate (`value_gate`, #4899) fires on **3** candidates —
   `tests/test_frontmatter_validator.py` (path), `PR #465` and `issue #3775`
   (references). It is identifier-only by design: it **cannot** fire on a definite
   description, which `value_gate`'s own docstring states ("a definite
   description is left to the arbiter, and is reported, not dropped").
2. All **3** are then **downgraded back to `KEEP`** by `vet_gate.apply_vet`
   Rule 2, the Layer-1 referential guard: *"a referenced entity is never removed"*.
   Removing an Object that a surviving Point names in `about_entities` would fail
   `validate_layer1` and 422 the whole session. Measured: 3 downgrades per VET pass
   (S2 + union) → **6** downgrade warnings, **0** removals.
3. The **semantic** half has no production caller. With the `definite_description`
   predicate injected as an arbiter, 9 more discards are attempted — and **all 9
   are downgraded by the same rule**, for the same reason: each audited Object was
   minted from, and is referenced by, the statement it came from. `vet_gate`'s own
   docstring states the seam is empty in production ("no production caller injects
   an arbiter yet").

⇒ **On this corpus, E1 cannot be reached at S2.2.** Every audited Object is wired
to the statement it was minted from, so Rule 2 downgrades each discard before it
can land. That is NOT the same claim as "the S2.2 gate can never remove a definite
description", and the four arms above cannot tell the two apart on their own — so
the probe measures the difference (below) and limit 6 states the population it
applies to. That is why the only arm above that moves the share is the
**mint-time** one — and even it is a counterfactual: no mint-time
definite-description rule exists (`#4894` owns the semantic half, `#5059` owns the
existing-population question).

### The discriminating control — the gate, or the corpus?

The arbiter arm's "9 discards attempted, all 9 downgraded, 0 removals" is
arithmetic-identical under two different explanations, and the whole conclusion
above depends on which one is true:

* S2.2 cannot remove a definite description at all (a **gate** property), or
* this corpus references every Object, so `apply_vet` Rule 2 fires on every
discard (a **corpus** property).

So the probe measures it instead of choosing: take exactly the 9 Objects the
arbiter tries to discard, strip **only** their `about_entities` references (the
entities and their statements stay — that is what a corpus which never wired the
reference looks like), and run the same arm again.

Measured (`control variant=unreferenced-definite-descriptions` in `e1-e2.log`,
pinned by `tests/test_e1_e2_measurement.py`): **9 references stripped → all 9
Objects removed**, share 60.0% → 37.5% (6 of 16), real facts 90/90, state values
42/42. The 0.0 pp is therefore a **corpus** property — every Object is defended by
a reference — and not a property of S2.2. What this bundle supports is the narrow
claim (*at S2.2, with the references in place, E1 does not move*), not the strong
one (*E1 is unreachable at S2.2 as a rule*).

### The counterfactual arm, and what it is NOT

`counterfactual-mint-skip` is reported as an **estimate of what a mechanism that
does not exist would buy**, never as green. It moves the share 22.5 pp
(60.0% → 37.5%) while preserving every real fact, every state value and every
atomic Point — because it strips the *reference* from the statement rather than
dropping the statement. It is the shape a mint-time rule would have to take, and
it is the reason the E1/E2 tension is not a zero-sum trade: the loss E2 fears is a
property of *how* the Object is removed, not of removing it.

⚠️ The 25-row label set is a **detection specification, never a drop list**
(`tests/test_salience_labels_4917.py` header), and four of its names carry a LATER
`keep-object` ruling (`docs/engineering/1026-calibration-set.jsonl`, owner
2026-09-26). No arm discards any of them; the probe pins that.

## Coverage honesty — the deficit the share cannot show

Scored against the owner-confirmed labels: **25 rows, 15 in scope by shape, 9
positively classified**. Five classes have **no detector at all** under either
shipped predicate: `branch_name`, `code_fragment`, `repo_slug`, `section_marker`,
`symbol_name`. Two more are reached by the *mechanical* gate only — `file_path`
1/1 and `pr_or_issue_number` 2/2 — which is why the two detectors are tabulated
apart on every run: a gate measured only on the class it can detect reads as a
pass.

## Atomicity, and the disclosed omission

§7 requires atomic `Point`s so an operator attaches to one claim. One Point in the
corpus is fused on the sentence-level proxy (2 units, `;`-joined) and it survives
every arm because **`SPLIT` is not implemented** — it is absent from `vet_gate`'s
O4 vocabulary, so no compliant arbiter can even ask for a split. The probe prints
`split-implemented=no` and the checker **fails** if that line is missing, so an
atomicity count that cannot move is never read as an atomicity *pass*.

## Limits, stated

1. **The population is the owner-labelled audit set**, the only owner-labelled
   Object population in the repo — so the *level* (60.0%) is **not** comparable to
   the architecture document's 62.3% production figure (§1:85, reconstructed as
   4,901/7,870 = 62.27% from the G5 census). The **delta** between arms is the
   measurement. #9075 is what should freeze a corpus; this one is a stated
   candidate that a reviewer can reject without touching the probe.
2. **The census reads the Layer-1 commit payload, not a live graph.** The payload
   is what the write path materialises node-for-node (`entities → :Object`,
   `points → :Point`), so a payload census and a graph census agree on NODE
   COMPOSITION by construction — and the payload census needs no server, which
   keeps the run hermetic. **It cannot see an EDGE property, though, and a count
   of derivation anchors is exactly that.** This bundle's earlier wording ("A
   graph census would add a docker dependency and catch no defect this one
   misses") was a measured falsehood, retracted here: `#8501` is a defect this
   census structurally could not see — on the live graph every
   `(Point)-[:extractedFrom]->(:Source)` link was written with a NULL
   `sourceVersion` (**0/113** versioned, against **6/6** for `references`), and
   the payload carries no edge at all, so no payload census could have reported
   it. E1's OBJECT count is answerable from the payload; E3's ANCHOR count is
   not. `tests/eval/write_path/runner.py::graph_census` (`#8444`) is the
   instrument that now carries both off the graph a run wrote, report-only (not
   a `METRIC_VALUES` member, so no baseline re-bless), and
   `tests/test_graph_census_7949.py` pins it.
3. **The extractor is a scripted model.** The candidate set is scripted on
   purpose — it is the control that makes the before/after delta attributable to
   the gate alone — so this run says nothing about extraction quality on live
   traffic, and nothing about recall. It says what the shipped gate does to a fixed
   population.
4. **The structural gate closes inference, not forgery.** A fabricated log whose
   numbers are *consistently* fabricated — every derived figure recomputed from
   the forged operands — would pass. What it does refuse is a log whose printed
   numbers disagree with each other: every criterion line is reconciled against
   the `arm=` lines it summarizes (`e1` V3, `e1-control` V5, `e2-state` V6,
   `e2-atomic` V7), each E2 criterion's verdict is checked against its own
   before/after counts, and the `e1` line's `observed=` conclusion is checked
   against its own `reduction=`. **The mechanism block is checked the same way
   (V13/V14).** The finding above rests on the shipped arm having had the gate
   ENABLED and on `apply_vet` Rule 2 downgrading its 3 discards — so the log's
   `metric=vet` line must show `enabled=yes` on every arm but the baseline,
   `candidates=` must be the sum of its own `by_outcome=` table, `discarded=` must
   be that table's `DISCARD` count, and `vet-downgrades count=` must be the
   `vet-warning=` lines that report each downgrade. Those are the checks that
   stop a log whose scored arm ran with the gate OFF from being called sound: a
   gate that never ran prints the same 0.0 pp. Before them, a log could have
   claimed the *shipped* arm moved E1 by the counterfactual's 22.5 pp, or lost a
   state-value table under a `PASS`, and still pass every other rule (#9110
   reviews).
5. **The value-match detector is a heuristic** (units, percentages, clock times,
   dates, money, spelled-out quantities). It is deliberately generous, and its
   patterns overlap by design — `62 percent` is also the `count` literal `62` — so
   **42 is a count of matches, not of distinct values**; `state_value_points` (34)
   is the distinct-Point count. Every match is printed in the log (one
   `metric=state_value_literals` line per arm, class and literal, overlap visible),
   so a reader audits the literals instead of trusting a number.
6. **All 25 audited Objects are wired to a referencing statement at build time.**
   `build_e1e2_corpus.py` sets `about: [name]` on every row — a corpus-construction
   decision the source supports (every row carries its `statement_excerpt`) but
   which the audit's `reason` field attests on only 15 of the 25. `apply_vet`
   Rule 2 fires on a *referenced* entity, so on this population every discard is
   downgraded, and the 0.0 pp is a statement about a fully-referenced population.
   The discriminating control above is what separates that from a gate property:
   strip the references and the same arm removes all 9 (60.0% → 37.5%). A reader
   should therefore read the finding as *"E1 does not move while every Object is
   defended by a reference"*, not as *"no S2.2 rule could ever remove one"*.

7. **A bar is a threshold AND a population — and this probe now refuses a bar
   whose population is not this run's** (#9076). `--prereg` used to consume
   `e1.min_share_reduction` and never read `corpus.path`, so an artifact that
   pinned `tests/eval/write_path` but happened to carry a parseable number scored
   *this* 25-Object corpus and printed `prereg=<sha>` with a verdict (measured
   pre-fix: `result=RED`, exit 1) — a numerator/denominator mismatch of exactly
   the kind the issue's Research Needed §1.2 refuses. `prereg_binding` compares
   the artifact's pin (`corpus.sha256` when present, else `corpus.path`) and its
   `denominator_floors.e1_objects` against the run, prints the comparison on
   `prereg-binding`, and refuses to score when they disagree — exit 3, not RED,
   because an unsound bar is not a missed bar. A floor the artifact *declares* but
   writes in a form the probe cannot read as an integer (`"30"`, `30.0`, `true`) is
   refused too (`UNREADABLE`), never read as "no floor stated": absent and
   unreadable are different states, and a silently dropped floor is a bar its author
   did not write (#9513 review P2). The same rule covers the floor's KEY: the real
   `capstone-preregistration/v1` record declares five `denominator_floors` and this
   probe can evaluate exactly one (`e1_objects`), so any other key is refused as
   `floor-unconsumed` — printed with the key names on `floor_unconsumed=` — instead
   of being dropped while the bar is stamped `MATCHED`, which would let a run that
   violates the record's own `e1_min_before_share` floor score as if no such floor
   existed (#9513 review P2). `tools/e1_e2_census_check.py` V15
   then requires any SCORED log to carry a `MATCHED` binding whose
   `corpus_sha256` is the corpus that log actually measured, whose named
   `declared_sha256` pin IS those bytes, and whose `floor_unconsumed=` floors (if
   any) are the reason it refused. **Consequence for
   this issue:** #9507's registration freezes the `tests/eval/write_path` corpus
   (30-Object floor) while this probe measures `e1e2_corpus.json` (25 Objects), so
   a re-run here is refused as `MISMATCH` carrying `corpus-path`, `below-floor`
   **and** `floor-unconsumed` for the four floors this probe cannot evaluate
   (`BELOW_FLOOR` is the status only when the floor is the sole reason) until the
   two corpora are reconciled — the refusal names every reason instead of scoring
   a number the bar never saw.

## Re-running

```bash
# measured, not scored (no pre-registration yet → exit 3)
uv run python docs/evidence/7949-capstone/probes/e1_e2_probe.py \
    | tee docs/evidence/7949-capstone/e1-e2.log
uv run python tools/e1_e2_census_check.py docs/evidence/7949-capstone/e1-e2.log

# once #9075 lands a commit whose tree carries preregistration.json
uv run python docs/evidence/7949-capstone/probes/e1_e2_probe.py --prereg <sha>
# exit 0 only when: the share fell by ≥ the pre-registered threshold, the real-fact
# count did not fall, the state-value count did not fall, atomicity holds, and only
# then — the two counterfactual arms are never the scored arm.
uv run python docs/evidence/7949-capstone/corpus/build_e1e2_corpus.py --check
```

`--prereg` reads `docs/evidence/7949-capstone/preregistration.json` out of the
named **commit's tree** (`git show <sha>:<path>`), never from the worktree, so a
threshold edited after the numbers are in cannot be served. The expected artifact
shape is `{"e1": {"min_share_reduction": <float>}, "e2": {...}, "corpus":
{"path": <the corpus this bar was argued over>, "sha256": <optional exact pin>},
"denominator_floors": {"e1_objects": <int>}}` — the corpus pin is required for a
verdict (limit 7): without it the run is `UNPINNED` and exits 3.

The threshold is printed **twice** — once as what the artifact froze
(`prereg_e1_threshold=`), once as what the run scored against (`threshold=`) — and
`tools/e1_e2_census_check.py` fails if they disagree. A log that names a
pre-registration commit and still scores itself against a bar it chose is exactly
the failure the pre-registration exists to prevent.

**E2's criteria consume no number on purpose.** They are no-loss assertions
(`after >= before` on real facts, state values and atomic Points), which satisfies
any preservation floor a pre-registration could state; the log says so
(`prereg_e2_floor=not-consumed`) instead of leaving it to be inferred.
