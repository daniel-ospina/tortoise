Tortoise Documentation

A graph database for agent memory: claims are Points, relationships are edges, and belief scores are computed by propagating evidence through the graph.

What is Tortoise?

Tortoise is a graph database for agent memory. Data is stored as Points (nodes) connected by labeled edges that express how beliefs relate. It keeps the structure of what an agent learned — which claims support which, and which contradict each other — and computes a belief score for every Point by propagating evidence through the graph.

It is used via a REST API or an MCP server (see below). An organization account gets an isolated graph; all writes carry provenance back to the source session.

How it works

The data model

Everything is a Point: an atomic claim with an id, content (text), pointKind, and a status. The kind vocabulary is statement — the asserted belief — plus the write kinds decision, vision, strategy, plan, goal, target, observation, hypothesis, humanApproval, and any domain kinds registered by expansion packs. Canonical vocabulary: docs/ONTOLOGY.md §4.1 and §5. (evidence is an additional kind the SDK registers for decision records. event exists only internally, as the kind on captured episodic turns — it is not a supported write kind: the REST point-create endpoint and the SDK's bundle validator reject it, while create_point only warns.)

The hosted API, the SDK and the graph draw on the same kind vocabulary, plus whatever your expansion packs register.

  • status: draft — created but not yet connected (not counted in confidence)
  • status: live — promoted when its first edge is created; participates in confidence computation
  • status: superseded — replaced by a newer Point, which is linked to it, so the old claim is kept rather than deleted
  • status: retracted — withdrawn with no replacement; kept as a tombstone
  • outdated — a legacy server-managed flag, kept as a back-compat status value, set alongside supersession or an explicit invalidation
  • status: archived — retired

A content hash (SHA-256 of content) is stored on every Point. With dedup enabled — the default over MCP — creating the same content twice returns the existing Point instead of duplicating it; the REST endpoint defaults dedup to false and will create a second Point.

Edges (operators)

Points are connected by operators. The two epistemic edge types are:

  • IMPL — source implies target. If you believe A and A implies B, that supports B.
  • NAND — source contradicts target. Recorded explicitly rather than deleting either belief, so the graph keeps the tension and confidence reflects it.

Part/whole edges (composedOf, decomposesInto, contains, wraps) and provenance edges (wasDerivedFrom, aboutSubject, …) also exist and are transferred on supersede.

Confidence (EP)

Each live Point carries a belief score. Tortoise computes it with expectation propagation (tortoise/ep.py, read back via sdk.get_confidence()): evidence is passed back and forth along the IMPL/NAND edges until the values settle. Support pulls a Point's belief up; a NAND edge pulls it down. Both remain in the graph, so the disagreement stays visible instead of being resolved by deleting one side.

The result is a distribution, not a single number — a mean and a variance. A tight spread means the evidence has settled; a wide spread means the posterior is weakly determined — thin evidence, or evidence pulling in opposite directions — which is how a Point gets flagged as contested. The hosted API exposes the mean as confidence on search and read results.

Confidence is derived, never a stored verdict. Change the evidence — add a claim, supersede one, record a contradiction — and the affected scores recompute.

Sessions & provenance

Agent conversations are captured as Session nodes (with turn counts and metadata). Points created from a session are linked to it, so every insight traces back to the conversation that produced it. Listing sessions and their linked Points is a first-class API operation.

The ontology defines a richer episodic Event model (eventKind, startedAt/endedAt, produces/uses edges). The hosted API produces :Session nodes, and each capture commit also writes an AgentSession Event carrying the capture timestamp and the session summary.

Search

Search fuses three strategies with RRF (Reciprocal Rank Fusion): full-text search (FTS) on content/title/name, vector similarity (embeddings, when available), and structural matches. Results are ranked by fused relevance, not recency.

Quickstart (5 minutes)

1. Create an account

Sign up at tortoise.premiselabs.co/auth. You'll get an API key in the in-app welcome card — copy it (it's shown once), then export it in your shell:

export TORTOISE_API_KEY=YOUR_KEY

2. Write your first Point

curl -X POST https://api.premiselabs.co/v1/points \
  -H "Authorization: Bearer $TORTOISE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"content": "the production port is 16379", "kind": "statement"}'

Response includes the Point's id.

3. Search

curl "https://api.premiselabs.co/v1/search?q=port" \
  -H "Authorization: Bearer $TORTOISE_API_KEY"

Returns ranked results (FTS + vector + structural, RRF-fused).

4. Manage in the dashboard

Open app.premiselabs.co, paste your key, and you can create/revoke API keys and view sessions.

Connect your agent (MCP)

The fastest way to give an agent Tortoise memory is the MCP server — no code required. Your agent (Claude Code, Cursor, Codex, Pi, Claude Desktop, Claude Web, or ChatGPT — or any other MCP client) reads and writes your Tortoise graph automatically. (ChatGPT connects key-less over OAuth through OpenAI's Developer mode — its steps are below.)

Setup — hosted (no install)

The hosted server speaks Streamable HTTP at https://api.premiselabs.co/mcp/ — the slashed form the keyed config-file rows below use. Keep your API key in an environment variable — never paste a literal tt_… key into a file that can be committed. In client JSON config the transport value is "http" (the protocol's spec name is Streamable HTTP): Claude Code accepts "streamable-http" as an alias and Cursor's IDE may tolerate it, but Cursor's CLI can drop the whole config file and Pi ignores type — so "http" is the only universally safe value.

Claude Code

Add to .mcp.json in your project. Claude Code requires "type": "http" — a url entry with no type is read as a stdio server and skipped.

{
  "mcpServers": {
    "tortoise": {
      "type": "http",
      "url": "https://api.premiselabs.co/mcp/",
      "headers": { "Authorization": "Bearer ${TORTOISE_API_KEY}" }
    }
  }
}

Export TORTOISE_API_KEY in your shell profile first. Project-scoped servers need a one-time approval on first use. Equivalent one-liner: claude mcp add --transport http tortoise https://api.premiselabs.co/mcp/ --header "Authorization: Bearer $TORTOISE_API_KEY"

Cursor — .cursor/mcp.json

Cursor expands ${env:…} and infers the transport from url, so the entry carries no type.

{
  "mcpServers": {
    "tortoise": {
      "url": "https://api.premiselabs.co/mcp/",
      "headers": { "Authorization": "Bearer ${env:TORTOISE_API_KEY}" }
    }
  }
}

Pi — .mcp.json

Add to, or merge into, .mcp.json in your project. Pi's mcp-client expands plain ${…} — no env: prefix — and infers the transport from url, so type is not needed (and is ignored if present).

{
  "mcpServers": {
    "tortoise": {
      "url": "https://api.premiselabs.co/mcp/",
      "headers": { "Authorization": "Bearer ${TORTOISE_API_KEY}" }
    }
  }
}

Codex CLI

Codex manages its own config — run this in your terminal:

export TORTOISE_API_KEY=YOUR_KEY
codex mcp add tortoise --url https://api.premiselabs.co/mcp/ --bearer-token-env-var TORTOISE_API_KEY

Codex Desktop (no terminal)

Codex Desktop shares ~/.codex/config.toml with the CLI but does not read shell exports. Add an [mcp_servers.tortoise] block with url = "https://api.premiselabs.co/mcp/" and bearer_token_env_var = "TORTOISE_API_KEY", and put that variable into the app's environment (launchctl setenv on macOS, setx on Windows) — or use the literal http_headers form on a shell-less machine (private file — never commit it).

Claude Desktop

Add the server from Settings → Connectors → Add custom connector: Server URL https://api.premiselabs.co/mcp/, request header Authorization: Bearer YOUR_KEY. Do not use claude_desktop_config.json — it only accepts local stdio servers, so a remote HTTP server placed there is silently ignored.

Claude Web

In claude.ai go to Settings → Connectors → Add custom connector, name it Tortoise, and use the Server URL above. Claude Web has no environment to read a variable from, so its request header holds the key literally: Authorization: Bearer YOUR_KEY. The key is held by Anthropic in your account — keep it private and revoke it from the dashboard if it leaks.

ChatGPT (Developer mode)

Connect it once — ChatGPT is key-less, so there is no config file to edit and no key to store:

  1. Enable Developer mode: chatgpt.com → Settings → Security and login → Developer mode (Plus / Pro / Business / Enterprise / Education).
  2. Open chatgpt.com/plugins → the + button → create a Developer-mode app.
  3. MCP server URL: https://api.premiselabs.co/mcp — no API key. Use the URL exactly as written, with no trailing slash. Choose OAuth; ChatGPT discovers Tortoise's authorization server automatically.
  4. Click Scan Tools, sign in to Tortoise when prompted, and click Authorize. When Tortoise asks which organization to connect, choose the one you want this graph in.
  5. Start a new chat at chatgpt.com (if the Tortoise tools don't appear, re-open chatgpt.com/plugins and re-check the Scan Tools result). Open app.premiselabs.co/skills/tortoise-onboarding/SKILL.md in a browser, copy the whole document, and paste it into that chat — ChatGPT has no local skills, so this document is what onboards it (if the agent can open the link itself, that works too).
  6. Ask it to set up Tortoise: it follows those instructions to verify the connection and file your first memory — that first write is what the dashboard reads as connected. Which tortoise_* tools appear can be plan-dependent — reopen chatgpt.com/plugins and check the Scan Tools result to see which tools were granted. A grant of read tools only can read your graph but cannot finish connecting: write tools may not be granted on your OpenAI plan, so if the Scan Tools result shows no write tools, connect a keyed harness (Claude Code, Cursor, Pi, or Codex) to the same organization to complete onboarding.

If ChatGPT asks for a key (they start tt_… or tk_…) or an Authorization header, you have left the OAuth path — refuse it. The document you pasted also carries keyed recipes for the other harnesses; they do not apply to ChatGPT.

The hosted MCP server runs on our infrastructure — no Python or tortoise install needed — so your client just needs network access to it.

After editing a config file, restart that client (Claude Code, Cursor, Pi, and both Codex surfaces). The Claude Desktop, Claude Web, and ChatGPT connectors are live immediately.

Setup — self-hosted (stdio)

Running Tortoise on your own infrastructure? Point the MCP client at a local process over stdio instead (see the self-hosted guide). A stdio server gets its database from TORTOISE_DB_URI — do not set TORTOISE_API_KEY here: the stdio transport cannot carry auth tokens, and setting it disables every tool:

{
  "mcpServers": {
    "tortoise": {
      "command": "python3",
      "args": ["-m", "tortoise.mcp_server"],
      "env": {
        "TORTOISE_DB_URI": "docker://:falkordb@localhost:6379/tortoise"
      }
    }
  }
}

Cursor requires "type": "stdio" on stdio entries; Claude Code and Pi infer stdio from command. The block above is the durable sidecar path; stdio against an embedded database (with TORTOISE_DB_URI unset) is a single-writer, eval-only fallback — never a durable team setup.

Need python3 and tortoise installed where the client runs? pip install tortoise-graph — the MCP server ships with the package.

What your agent can do

  • Remember: tortoise_create_point — store a decision, observation, or claim
  • Recall: tortoise_search — query the past with hybrid search
  • Reason: tortoise_compute_confidence — see how evidence propagates
  • Structure: tortoise_create_operator, tortoise_traverse, tortoise_entity_profile, and more

For the keyed harnesses (Claude Code, Cursor, Pi, and both Codex surfaces) the in-app welcome flow includes a ready-to-copy setup with your key pre-filled.
