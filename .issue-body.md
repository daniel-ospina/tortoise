Refs #3590 (minted identity), PR #9876 item E / slice C.

## Problem

`tortoise/sdk.py::_update_entity` now journals a rename (`EntityMutated op=rename`, #3590 D3). `tortoise/record_projection.py::RECORD_MUTATIONS["EntityMutated"].refused_ops["rename"]` still REFUSES that record, so on a RECORD-ARMED deployment the first public `update_entity(id, name=…)` raises `RefusedJournalOperation` → `RecordWriteError`: the durable write fails and the caller must roll back. That refusal is correct — the record genuinely cannot represent a rename today — but it means the producer cannot land without this.

Why it is not a one-line change:

* The record's Object/Subject key **is** the name (`public.object` / `public.subject` PK `node_key`, `CONSTRAINT chk_object_node_key_is_contract_key CHECK (name IS NOT NULL AND node_key = name)` and its `public.subject` twin, `supabase/migrations/20261012000002_record_semantic.sql`).
* The composite FKs to `public.node_identity (org_id, graph_id, node_label, node_key)` are `ON DELETE CASCADE` only, so a key move cannot cascade.
* `CHECK` constraints are not `DEFERRABLE` in Postgres, so a cascade that moves `node_key` without moving `name` in the same rewrite violates the pin — the migration has to decide whether the pin survives (trigger? generated `name`? keep both columns and drop the CHECK?).

## Outcome

`EntityMutated op=rename` is accepted by the record projection: the row's canonical key moves, its incident `relation` endpoints follow, and `rebuild_from_record` reproduces the renamed graph.

## Interfaces

* `record_projection.OpDispatch.refused_ops` for `EntityMutated.rename` → a key-move statement builder.
* New `supabase/migrations/…_record_rename_key_move.sql`.
* `tests/test_record_projection.py::test_entity_mutated_dispatches_on_op_and_refuses_undeclared_ops` (currently asserts the refusal citing `#3377`) is rewritten to assert the key move.

## Tests

* Statement-shape test: a rename yields the key-move statements and no refusal.
* Postgres integration (record lane): rename an Object with an incident relation; the relation's `src_key`/`tgt_key` follow and `rebuild_from_record` agrees with `rebuild_from_journal`.

## Complexity: standard (separate subsystem)

Record schema + projection, no graph change. Split out of PR #9876 so the graph producer is not blocked on it, and so the schema decision gets its own review.
